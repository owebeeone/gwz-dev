# Python caller guide — Surface review

**Verdict: NO-GO.** The review found three P2 interface defects and two P3 documentation defects. I reviewed only the committed candidate guide and `gwz-py/README.md`. The permitted root and `gwz-py` HEAD checks matched the required SHAs at both the start and end: `ee11f44efa5a0796a71d874ffaa4bc570a611a4e` and `45bcd7b3ea102ca927935cee1b41b43934d68140`.

The first-day path is partly clear: the README shows how to install `gwz`, and the guide shows how to start two fetches, cancel one, read events and a result from the other, release both handles, and leave the client context. The following gaps arise when that path meets retention, failure, or an optional placement.

### Findings

**P2-1 — A late event reader can silently miss the beginning of an operation.** In the guide’s `handle.events()` paragraph, iteration starts at “the oldest event still retained when iteration begins.” The stated `EventCursorGap` protection applies to a *slow reader*, with no corresponding signal for a reader that starts after eviction. Start two operations, let the second produce more than its 1 MiB event budget while cancelling the first, then begin `second.events()`. The documented behavior yields a retained suffix without reporting that earlier events are gone. This violates the invariant that lost event history is detectable. Require an initial cursor tied to operation acceptance, or report a gap on the first iteration when earlier events have expired; document the recovery call. A regression test should delay first iteration until eviction and assert an explicit gap with a usable retained cursor.

**P2-2 — The published `start_fetch` signature omits the fetch metadata arguments it promises to preserve.** The opening signature lists only `request_id`, `concurrency`, `max_connections_per_host`, and `placement`, then says “Other existing fetch metadata arguments keep their current meanings.” Neither that signature nor the README names those arguments or their defaults. A caller migrating a metadata-bearing `fetch()` call cannot construct the documented `start_fetch()` call; taken literally, the displayed signature accepts no such arguments. Publish the complete signature, including every supported metadata argument and default, or correct the parity claim. A documentation regression check should translate each supported `fetch()` argument into a shown `start_fetch()` call.

**P2-3 — Cancellation and terminal outcomes lack public discriminants.** The `result()` paragraph promises a stable error `code` and says a cancelled result raises “an error with cancellation code,” but does not give that code. The `terminal()` paragraph names a status and typed error without defining their values or shapes. After `await first.cancel()`, a caller cannot write a documented branch that distinguishes cancellation from Git failure using `first.result()` or `first.terminal()`. Define the cancellation code and terminal status/error variants, and show a branch over them. A regression example should cancel one operation, inspect its result or terminal record, and identify cancellation by a documented value.

**P3-1 — The `cli` placement has no documented binding path.** The opening paragraph offers `placement="cli"` when an endpoint “was bound in the same process,” but neither allowed document identifies how a Python caller binds one. Following the installation and API examples, a caller can request `cli` placement but cannot reach its stated prerequisite or recover from `PlacementUnavailable`. Document the binding API and its lifecycle, or state that this placement is reserved for an internally bound CLI endpoint. An example should start and close a client using the documented binding path.

**P3-2 — The cancellation cleanup report does not tell callers what action its fields require.** The `cancel()` paragraph returns `TransportCleanup(pending_local_work, peer_cleanup_confirmed)` while also saying cancellation joins worker and transport cleanup. The guide defines neither field’s type nor what to do if local work remains pending or peer cleanup is unconfirmed. In the guide’s own two-operation example, a nonempty `first_cleanup.pending_local_work` leaves the caller unable to decide whether to retry, close, wait, or safely release. Define the fields and the recovery sequence for each noncomplete report, with an example or test that exercises that case.

I pre-commit to **GO** on a revision that resolves P2-1 through P2-3 as specified, provided the revision introduces no new blocking surface defect.
