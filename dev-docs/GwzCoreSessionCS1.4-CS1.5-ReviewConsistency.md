## 1. Findings (severity-ordered)

### C-P2-1 — `EnvironmentSnapshot::capture()` is an environment read inside gwz-core, inventoried `permanent`; no disposition the controlling documents define admits it, and it opens a blind spot in the O9 check

- **Root cause (one):** the capture point lives in core. `src/session_host/environment.rs:60` `pub fn capture()`, reading `std::env::vars_os()` at `:63`; inventoried at `scripts/checks/process_globals_allowlist.json:54–55` as kind `env`, disposition `permanent`; documented as public API at `docs/RustApi.md:136` (example) and `:148–149`.
- **Violated invariants:**
  - Contract §5.6: "The driver captures the process environment once, at its edge, and passes it to `open` in `options`… Core and the extension never read the environment themselves." Plan CS1.5: "captured by the driver as byte-string pairs". A public function in core whose body reads the environment is core reading the environment; the rustdoc at `:56–59` and the allowlist reason restate the driver rule as a calling convention, which nothing enforces.
  - O9, §5.7, the allowlist's own rule text (line 2 of the JSON), GWZDesign and GWZRequirements all define `permanent` entries as those that "carry no session-relevant state or are imposed by a dependency". This read carries the whole session-relevant state and is imposed by no dependency. It is not `debt` either ("scheduled for removal"; the entry itself says "no step removes the capture point"). The inventory's two dispositions model "the session path may read it" versus "must not, and it is being removed"; a read the session path must never make and that is never removed has no representation, so the classification is unrepresentable, not merely mislabelled.
  - Plan §3.0 standing rule: "A step that adds state lists it as `debt` and names the step that removes it. A spawn entry flips from `debt` to `permanent` only with a test that proves `env_clear()`…". The step adds an environment read as `permanent` with no removing step. Plan §5.4 lists, exhaustively, what "stay[s] `permanent`" at the end state (`TIMEOUT_STATE`, libgit2's timeout options, the `gh` spawn, the ID counters); the end state has no environment read in gwz-core.
- **Reproduction / interleaving (checker source, not run):** the checker recognises an environment read only as the token pair `env` `::` `<func>` (`check_process_globals.py:369–376`). A call `EnvironmentSnapshot::capture()` from any production file — a session-path fallback in core ("no snapshot given, capture one"), the socket or stdio host core will provide, or gwz-py's extension, which §9 says "reads neither the environment nor the process's working directory" — contains no such pair and is invisible to gwz-core's and gwz-py's checks. Today's only environment wrapper of session state, `with_local_transport`'s read (`local_command.rs`), is `debt` and scheduled out; this would be the first permanent, public one.
- **Impact:** O9's mechanical guarantee ("a check keeps new state out") no longer covers the environment read that matters most; the inventory's printed summary ("N debt, M permanent; nothing new") and the "no `debt` on the session path" criterion become false statements about one entry; the step contradicts the contract sentence it cites, and breaks the plan's ratchet rule that every step's gate relies on.
- **Required correction (bounded to this step's files):** remove `capture()` and its allowlist entry, so core contains no environment read and §5.6 holds literally; give Rust drivers a read-free constructor that takes what they already hold, e.g. `pub fn from_os_pairs(pairs: impl IntoIterator<Item = (OsString, OsString)>) -> Self` (infallible: the platform yields nothing `from_byte_pairs` refuses, as the removed comment at `:62` says), and let gwz-cli, the CS5.1 example host binary (outside the checker's `src/` roots) and any stdio host call `std::env::vars_os()` in their own crate at their edge; gwz-py already captures in Python (§5.6). Update `docs/RustApi.md:136, 148–149` and the rustdoc rows at `environment.rs:7, 56–59` accordingly. If the operator instead wants the helper in core, that is a contract change (§5.6's sentence, O9/§5.7's disposition definitions, GWZDesign, GWZRequirements) plus a plan change (§3.0, §5.4) and a checker change for a third disposition, through the plan's §7 trigger — not something this step can decide by an allowlist reason.
- **Regression test:** (a) the allowlist holds no entry for `src/session_host/environment.rs`, and `rg -n 'env::(var|var_os|vars|vars_os)' gwz-core/src/session_host` matches only inside `cfg(test)` code; the checker's run over gwz-core then passes at the pre-step entry count (30, plan §5.4) with no `STALE`; (b) the existing `capture_takes_each_process_variable_once` becomes a test that `from_os_pairs(std::env::vars_os())` yields the same entries, first occurrence winning, as `from_byte_pairs` of the same pairs' `into_encoded_bytes()`.

## 2. Invariant analysis (attacks that held, with evidence)

- **§1 limits and `open`'s validation.** `Limits` (limits.rs:27–51) carries exactly the ten non-fixed rows with the contract's defaults (test `the_defaults_are_the_contract_table_and_are_valid`); the two fixed rows are `MAX_READ_WAIT` and `MAX_FRAME_BYTES` (limits.rs:16, 19). The contract's one stated rule, table ≥ running + queued, is enforced with overflow handling (limits.rs:103–108; test at :158–174, including a table of exactly running + queued accepted). The added lower bounds and the frame/queue overflow guards (:86–122) refuse only configurations under which a stated rule could never hold; "`open` validates the limits it is given" names no exhaustive list, and the server design (line 211) expects "`open`'s own validation" after its own maxima, which is consistent with "no upper bounds in process". Refusals are `invalid_request` before any effect: `open` validates before constructing anything (context.rs:222; test `open_refuses_invalid_limits_with_invalid_request`). `docs/RustApi.md:170–177` states these rules accurately.
- **O8's three states and what each refuses or ignores.** `GateState::{Live, Cancelled, Revoked}` (gate.rs:167–176). Cancelled: `effect` and `append` refused with `Cancelled` without running the closure, `report` lands (tests at :321–336) — §5.6's "refuses new effectful requests… also refuses further log appends", and §5.3's "a handler that has succeeded keeps its `Completed` terminal". Revoked: `report` returns `None` without running (:339–356), and `revoke` returns only when no crossing is in flight (:422–449), which is §8 step 5's "cannot touch session state". Contract §5.6 lists "log appends" among the reports ignored after revocation; the code refuses them with `Cancelled` instead of silently dropping them (revocation implies cancellation, `revoke` cancels first at :159). Nothing lands and the producer stops, which is the clause's purpose; the plan's own CS1.4 test row lists only "events and terminals" as ignored. Held.
- **"Nothing but the token cancels" (§5.3).** The only path to `TokenInner::cancel` is `CallControls::cancel` (:149) and `CallControls::revoke` (:159, close's step 5, after close's step 3). Crossings, a failed effect, dropped clones of the gate, the handler context and the token, and dropping `CallControls` itself cancel nothing (test `nothing_but_the_token_cancels`, :359–389). `CancellationToken` exposes no cancel (:60–91). Held.
- **O7.** `CallControls::new` creates token and gate together (:127–141), documented for the reading thread at frame receipt; the worker later receives clones. Held; the ordering against admission is CS2.x's to prove.
- **Registration semantics (§5.2).** `on_cancel` is refused with `Cancelled` once the token is cancelled and never runs then (:75–90; test :392–419); a kept callback runs exactly once across repeated cancels; a panicking callback is caught (:51). Held.
- **§5.6 host context.** `HostContext::new`, `Clone` as a shared handle, `Default`, no static (context.rs:40–47, 124–158); the supervisor starts with its first job (:141–147) and ends once the last handle is gone and no job remains (:95–121; tests :383–437, including a session holding its host context and a job that panics). ## 3. Risks and next action

- **Next action:** apply C-P2-1's correction (drop `capture()` and its entry; add a read-free `from_os_pairs`; fix the two docs), re-run `cargo test --lib session_host` and the gwz-core checker; I pre-commit to GO on that revision.

- **gate.rs at 479 lines.** CS2.4/CS2.5 add the call's record to `GateScope` (gate.rs:192–193); the file will cross the 500-line new-file ceiling and should be split (rust-split) when that lands.
