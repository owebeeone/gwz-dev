## 3. Frozen replacement architecture

### 3.1 Checked paths use an explicit, component-wise capability

Checked-artifact paths are protocol paths generated by GWZ, not arbitrary user
paths. The internal API accepts only nonempty, root-relative, normal **ASCII**
components. A non-ASCII component returns typed `UnsupportedOperation` before
private hierarchy creation, authority publication, or managed mutation. This
restriction is intentional: it permits exact ASCII filesystem equivalence
without pretending that Rust Unicode lowercasing is NTFS, APFS, ext4, F2FS, or
another filesystem's collation algorithm.

Acquisition walks the complete managed parent path with retained no-follow
directory handles. For each component it asks the opened parent for one of:

```text
PathComponentMode = Sensitive | AsciiCaseFold

CanonicalComponent {
    original_ascii,
    parent_mode,
    canonical_ascii,  // unchanged or ASCII-folded according to parent_mode
}
```

There is no root-wide default and no unknown-as-sensitive fallback.

- Linux queries the effective directory mode. Filesystems with
  `FS_CASEFOLD_FL` use that flag per opened parent. A filesystem that can have
  another lookup equivalence and cannot expose it through the supported
  capability table is rejected. The table is explicit and exhaustive; adding
  a filesystem requires an implementation and tests, not a default arm.
- macOS requires the existing volume capability result and applies it to the
  ASCII-only components. The existing persistent-object-ID capability remains
  mandatory.
- Windows queries `FileCaseSensitiveInfo` on every opened parent and checks
  `FILE_CS_FLAG_CASE_SENSITIVE_DIR`. Unsupported queries reject before
  publication. There is no `to_lowercase` path.

The parent of the managed leaf must exist for a checked mutation. Acquisition
may report an observational missing parent, but it cannot issue mutation
authority for it. Creation of an operation-owned parent is a separate durable
preflight action; checked-artifact code never silently creates a user-managed
parent to make path identity possible.

The persisted path fact contains original components, mode tags, and canonical
components. A retry must reacquire the same mode vector. Mode change or parent
replacement is ambiguity, never a new family.

For a workspace artifact, the pre-mutation order is frozen:

1. acquire the capability-neutral live workspace lease;
2. perform read-only durable-provider/path-mode checks and a lossless Git
   index/tracked-path collision scan for the complete private control namespace;
3. on unsupported capability or any tracked/index-visible collision, return
   without creating the private root or any managed path;
4. bootstrap or recover the private catalog;
5. perform a full bounded catalog enumeration, reject global ambiguity,
   recover infrastructure intent, and select any existing action family;
6. admit capacity and recover or run the complete declared managed-parent plan;
   and
7. freshly re-enumerate the catalog before issuing checked-action authority.

For a workspace artifact the collision domain is the union of:

- the complete `.gwz/checked-artifacts` prefix; and
- the exceptional first-catalog names
  `.gwz/checked-artifacts-catalog-bootstrap-v1.scratch`,
  `.gwz/checked-artifacts-catalog-bootstrap-v1.active`, and
  `.gwz/checked-artifacts-catalog-bootstrap-v1.staging`.

The lossless scan checks exact, parent-prefix, and platform-equivalent forms for
every union member. Index-only, higher-stage conflict, skip-worktree, tracked
worktree, case-equivalent, and prefix collisions all reject before any of these
paths is created. An absent worktree path with a present index entry therefore
still collides. A Git-directory policy uses its separately proved non-worktree
root and has no worktree collision scan, but it still completes capability and
path-mode checks before catalog creation. Unsupported and collision rows
preserve the absent private root and all managed bytes exactly.

### 3.2 The private namespace is a catalog, not a current-key-only lookup

Deriving a filename only from today's canonical family key can hide an older
authority after a directory mode change. Acquisition therefore scans one
bounded checked-protocol catalog before choosing an action family.

The catalog enumerates every directory entry in the selected private root, not
only the prefix calculated for the current request, and every entry in each
recognized active action directory. The retired root is enumerated only to its
bounded child-directory/name/metadata shape; retired action contents are not
decoded as active state. Every inspected entry consumes the applicable entry-
count, filename-byte, and metadata budget before classification. The closed
grammar is:

While the persistent admission record is `Preparing`, its fixed staging
directory is a **prospective action directory**. Before any child lookup,
decoding, adoption, or publication it is enumerated under the same
`MAX_ACTION_SLOTS`, aggregate-name, aggregate-metadata, no-follow kind, and
closed-child grammar as its final active name. Its only legal populated child
at that stage is the matching missing/partial/exact resident reservation; an
additional child, wrong kind, limit-plus-one entry, or aggregate limit overflow
is `other` and global ambiguity. Staging and final are two names for the same
reserved directory credit and are never charged as two action directories.

| Category | Forms | Recovery meaning |
| --- | --- | --- |
| Active family | one bounded action directory containing the resident reservation, authority, physical payload, action-local intent, scratch, marker-retirement, alias-retirement, and cleanup slots | the only checked-action authority; payload files are streamed and never catalog-decoded |
| Infrastructure | fixed format record, catalog-anchor pair, roaming-anchor home, retirement root/descriptor, retained catalog-bootstrap record, and persistent action-admission active/scratch/staging slots | identity-pinned catalog machinery, never interpreted as checked-action authority |
| Active internal intent | one indexed action-local `BarrierIntentV1` or `ManagedParentBootstrapIntentV1` generation in its owning action directory | recover this namespace action before advancing the owning checked action |
| Unpublished scratch | one deterministic infrastructure or action-bound slot per declared kind and ordinal | inert and never authority; exact partial content is rewritten in place on retry |
| Retired | one pre-reserved per-action directory containing indexed write-through-retired intent/marker/roaming-anchor-alias generations and fixed source/goal/authority alias slots | inactive; bounded/enumerable for privacy and GC, never required for correctness |
| Malformed/foreign | unknown version, invalid recognized name, duplicate active owner, type substitution, or an unrecognized entry | global ambiguity with a category-specific reason; never auto-deleted |

Only the fixed infrastructure grammar and active action directories live at the
private root. Action-bound intents, their successor/retirement generations,
payload files, and marker-retirement slots live inside the owning action
directory. Retired action directories live in one retained child named by the
infrastructure record; its children consume separate fixed count/name/metadata
budgets and are never read as active state. Externally staged bootstrap
directories are reachable only through one active indexed bootstrap intent and
its bounded component list.

A syntactically valid action scratch name contains its action digest, kind, and
ordinal where the kind is indexed. It is the **only** slot for that binding: a
retry never chooses a new nonce or creates another entry. It is inert only when
the active capacity
reservation or authority binds it and its no-follow kind/metadata fit that
scratch category. Its content may be empty or partial because the create/write/
flush boundaries are intentional crash rows; under the same binding the slot
is safely truncated and rewritten. Scratch is never decoded as authority. A
published record name with an invalid payload, unbound scratch, wrong kind, or
different binding is malformed/foreign. Correctness never depends on scratch
or retired-object GC.

Before publishing an authority, action-local intent, or making a managed
mutation, the catalog completes a durable `ActionDirectoryAdmissionV1`
handoff. Admission computes the worst-case physical schedule for the complete
action. The schedule includes its authority and payloads, every scratch kind,
every logical barrier invocation, every managed-component intent successor and
marker retirement, external aliases, cleanup, and final directory retirement.
It succeeds only when current entries plus every outstanding reservation fit
the fixed root, action, name, metadata, and retired-subtree budgets.

Admission is catalog infrastructure rather than a child of the directory it
creates. The catalog always has one fixed active admission record, one fixed
record scratch, and one fixed staging-directory name. The active record is
`Idle` or:

```text
Preparing {
    action_digest,
    request_and_owner_binding,
    capacity_schedule_sha256,
    staging_name,
    final_action_name,
    resident_reservation_sha256,
}
```

The catalog anchor provides one reviewed fixed-slot replacement primitive for
infrastructure records. It encodes and flushes the new value into the fixed
scratch, atomically replaces the fixed active record (`renameat` plus directory
barrier on Unix; `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` plus exact
reobservation on Windows), and then reobserves the exact active bytes and
identity. A partial scratch is inert and reusable. Recovery accepts old active
plus missing/partial/exact bound scratch, or new active plus missing scratch,
only according to the closed replacement table. A duplicate name, substitution,
two different complete values, or an active value not matching its retained
catalog identity is ambiguity. This primitive is used only for the admission
record; action authority and intent publication remain no-replace.

The admission sequence is:

1. prove capacity and durably replace `Idle` with `Preparing` before creating a
   directory;
2. create only the fixed global staging directory, populate its resident
   `ActionCapacityReservationV1`, and flush the file and directory;
3. publish that populated directory no-replace to the deterministic active
   action name and reobserve its resident reservation;
4. durably replace `Preparing` with `Idle` only after the resident record owns
   the exact final directory; and
5. issue authority or run a managed action only after the `Idle` handoff is
   observed.

A crash before step 1 owns no directory. At every later boundary the durable
`Preparing` record owns the fixed staging/final alternatives and either resumes
publication or proves the matching resident handoff. A final directory is
adopted only through that matching record. An orphan staging/final directory is
ambiguity. Reusing the persistent admission record is bounded compaction, not
GC: no prior admission history is needed after the resident reservation owns
the directory. The active action reservation remains until terminal catalog
closure. Failed retired-action GC may prevent a **new** admission, but cannot
consume capacity required by an admitted action.

The v1 schedule and bounds are literal and versioned:

```text
MAX_ACTIVE_ACTION_DIRS               = 64
MAX_RETIRED_ACTION_DIRS              = 64
MAX_MANAGED_PARENT_BOOTSTRAPS         = 8
MAX_MANAGED_PARENT_COMPONENTS        = 8  // total across all bootstraps
MAX_BARRIER_INVOCATIONS_PER_ACTION   = 64
MAX_CLEANUP_ROWS                     = 3  // source, goal, authority aliases
MAX_BOOTSTRAP_INTENT_GENERATIONS     =
    MAX_MANAGED_PARENT_BOOTSTRAPS +
    (2 * MAX_MANAGED_PARENT_COMPONENTS) = 24

BASE_ACTION_SLOTS                    = 13
BARRIER_ACTION_SLOTS                 = 3 * 64 = 192
BOOTSTRAP_INTENT_ACTION_SLOTS        = 2 * 24 = 48
BOOTSTRAP_MARKER_RETIREMENT_SLOTS    = 8
MAX_ACTION_SLOTS                     = 13 + 192 + 48 + 8 = 261

MAX_INFRASTRUCTURE_ENTRIES           = 10
MAX_ROOT_ENTRIES                     = 64 + 10 = 74
MAX_NAME_BYTES                       = 255 per component
MAX_ROOT_NAME_BYTES                  = 74 * 255 = 18,870
MAX_ACTION_NAME_BYTES                = 261 * 255 = 66,555
MAX_RETIRED_NAME_BYTES               = 64 * 255 = 16,320
METADATA_ACCOUNTING_BYTES_PER_ENTRY  = 256
MAX_ROOT_METADATA_BYTES              = 74 * 256 = 18,944
MAX_ACTION_METADATA_BYTES            = 261 * 256 = 66,816
MAX_RETIRED_METADATA_BYTES           = 64 * 256 = 16,384
```

The ten infrastructure entries are exactly: catalog format; catalog anchor A;
catalog anchor B; roaming-anchor home; retired-action root; retirement-root
descriptor; retained catalog-bootstrap record; action-admission active;
action-admission scratch; and action-admission staging. The last item is a
directory only during admission. Capacity conservatively counts it even though
its no-replace rename to an active action directory does not increase root
cardinality.

The thirteen base action slots are exactly:

```text
Reservation | Authority | SourcePayload | GoalPayload |
AuthorityScratch | GoalScratch | RecordScratch |
BarrierIntentScratch | BootstrapIntentScratch |
RetiredSourceAlias | RetiredGoalAlias | RetiredAuthorityAlias |
CleanupWorklist
```

The indexed families are:

```text
BarrierIntentActive(i)  | BarrierIntentRetired(i) |
RetiredRoamingAnchorAlias(i),                       0 <= i < 64
BootstrapIntentActive(g)| BootstrapIntentRetired(g),0 <= g < 24
RetiredBootstrapMarker(c),                        0 <= c < 8
```

Each logical barrier uses its precomputed ordinal and the same active/retired/
anchor-alias triple on every retry. The pre-admission planner orders every
managed-parent spec, assigns a stable bootstrap ordinal, and assigns contiguous
global intent-generation and marker ordinals. Each bootstrap contributes one
initial generation, one successor per installed component, and one successor
per retired marker. For `K` plans and `N` total missing components the exact
generation count is `K + 2N`; every admitted plan has at least one missing
component, so `K <= N <= 8` and the maximum is 24. Each prior generation is
write-through retired to its paired global slot before the next becomes
authoritative. Each marker is write-through retired into its assigned global
component slot. Records bind the global ordinal to their bootstrap/local
component ordinals and schedule digest. The planner rejects more than eight
plans, more than eight total missing components, or more than 64 barriers before
admission or managed mutation.

`CleanupWorklist` is immutable. It has at most three rows: the bound source,
goal, and authority aliases whose destinations are the three base retirement
slots. Roaming-anchor aliases and managed-parent markers are completed by their
indexed intent protocols and never enter this worklist. Before the first
cleanup edge, `RecordScratch` is encoded/flushed with the complete ordered list
of bound source identities, reserved destination slots, and ordinals from the
resident schedule, then published no-replace as `CleanupWorklist`. Its bytes
never record progress.
Progress is derived from exact physical facts for the current ordinal:

| Source | Reserved destination | Resolution |
| --- | --- | --- |
| exact | missing | perform checked retirement |
| missing | exact expected identity/bytes | ordinal complete; advance |
| any other combination | any other combination | ambiguity; retain worklist and facts |

The worklist is published before any listed source is retired. Missing/partial
scratch before publication is rewritten; an exact worklist is adopted only when
its hash equals the resident schedule. A cleanup source changed before
worklist publication is ambiguity, not evidence that cleanup started. Retry
rescans from ordinal zero and skips only exact completed rows, so no cursor
update, successor slot, deletion, or GC is required. Terminal directory
retirement is permitted only after every row is physically complete.

After terminal closure the complete action directory is moved no-replace into
its deterministic child name below the retired root. The retired root therefore
consumes one bounded entry per prior action rather than one per fault or intent.
Adding an infrastructure form, base/indexed slot kind, transition generation,
or limit is a protocol-version and review event. Generated equality tests pin
the enum families, limits, arithmetic, decoder grammar, and complete caller-
derived schedule.

Within that grammar the catalog:

1. bounds directory-entry count and filename bytes before opening a file;
2. reads every authority with its independent 16 KiB decoder bound;
3. treats an unknown version, malformed or foreign entry, orphan active
   residue, or duplicate active owner as globally visible ambiguity;
4. compares decoded original/canonical path facts and current component modes;
5. selects exactly one authority only when artifact-root, path profile,
   action, expected value, goal value, retained parent, and source identity all
   match; and
6. leaves unrelated valid families available for independent actions.

The catalog permits distinct `A` and `a` families in a proven sensitive
directory. Because it sees both authorities, a later switch of that parent to
case-insensitive mode makes the overlap ambiguous rather than hiding one
family. The reverse mode change is also ambiguous until old state is resolved.

Generated restart tables enumerate every category at every admission replace,
directory create/flush/publish/handoff, intent create/flush/publish/successor,
marker retirement, alias retirement, cleanup, and final-directory retirement
boundary. Each row either resumes from its named owner or rejects with its exact
foreign-state reason. GWZ's own valid scratch or retired residue never becomes
ambiguous merely because a crash exposed it.

The admission table crosses `Idle`/`Preparing`, partial/exact scratch,
missing/exact/other staging, missing/exact/other final directory, and
missing/exact/other resident reservation. It repeats every crash more times
than nominal catalog capacity and proves constant cardinality. Staging tests
cover exact limits and limit-plus-one for entry count, aggregate name bytes, and
aggregate metadata, plus wrong kind and an exact reservation with one foreign
child; every invalid form rejects before publication.

The maximum-schedule table covers both extremal managed layouts: one
eight-component bootstrap (deepest successor chain) and eight one-component
bootstraps (all 24 intent generations), each with all 64 logical barrier
ordinals. It crashes after every successor and marker/intent retirement, fills
all non-reserved retired-action capacity, disables deletion/GC, and still
reaches terminal catalog closure without allocating another name. Malformed
protocol state may conservatively block the private catalog, but it is never
read without bounds and is never deleted automatically.

### 3.3 Durable object identity is a capability, not a successful syscall

`DurableObjectIdentity` is issued only by a platform provider that supports
the promised restart/reboot model:

```text
Linux  { filesystem_uuid, handle_type, persistent_file_handle }
Mac    { volume_uuid, persistent_object_id }
Windows{ volume_guid, file_id_128 }
```

Linux replaces raw `f_fsid` with an external filesystem UUID. The first frozen
provider is the ext4-only `FS_IOC_GETFSUUID` tuple in
`GwzM5-8R4bLinuxCapabilitySpike.md`: runtime support for that ioctl (upstream
Linux 6.9 or a proven backport), `fsuuid2.len == 16`, a nonzero 16-byte UUID,
and a positive 1..=128-byte handle from
`name_to_handle_at(retained_fd, "", ..., AT_EMPTY_PATH)`. The provider forbids
`AT_SYMLINK_FOLLOW`, `AT_HANDLE_FID`, and pathname relookup fallbacks. Syscall
success alone does not admit a filesystem. No
pre-6.9 heuristic, `f_fsid`, mount ID, overlay/network/unknown filesystem, UUID
failure, or unqualified fallback is accepted. All such rows return typed
`UnsupportedOperation` before residue publication. A compatibility provider
is a future reviewed provider, not a fallback arm in this implementation.

Windows limits durable authority to filesystem profiles for which full
`FILE_ID_INFO` identity stability is part of the supported contract. The first
profile is local NTFS. ReFS or remote filesystems are added only with explicit
identity and behavioral evidence. The volume GUID is retained in full.

Every platform has an injected identity/equivalence provider used by unit and
restart tests. Real-host tests remain mandatory; the seam does not substitute
for Windows or Linux behavior.

Both Linux release architectures must pass the spike's fail-not-skip ext4
unmount/remount probe and publish the exact provider tuple before R1. If they
cannot, implementation stops at R0-L and the affected Linux merge capability
remains unsupported. It does not restore `f_fsid`, weaken the reboot claim, or
silently turn supported recovery into permanent ambiguity.

### 3.4 Protocol budgets and artifact payloads are separate

The one-MiB family sum is removed. It mixed small recovery records with source
and goal payloads and could strand GWZ's own action after authority publication
or detach.

The replacement decoder limits are literal:

```text
MAX_AUTHORITY_RECORD_BYTES          = 16 KiB
MAX_CAPACITY_RECORD_BYTES           = 16 KiB
MAX_ADMISSION_RECORD_BYTES          = 16 KiB
MAX_BARRIER_INTENT_BYTES            = 16 KiB
MAX_BOOTSTRAP_INTENT_BYTES          = 16 KiB
MAX_CATALOG_BOOTSTRAP_RECORD_BYTES  = 16 KiB
MAX_INFRASTRUCTURE_RECORD_BYTES     = 8 KiB
MAX_MARKER_RECORD_BYTES             = 4 KiB
MAX_CLEANUP_WORKLIST_BYTES          = 16 KiB
MAX_CANONICAL_PATH_IDENTITY_BYTES   = 4 KiB
```

Catalog entry/name/metadata bounds are the literal derived values in section
3.2. Every decoder rejects `limit + 1` before allocation or semantic parsing.
Generated maximum-encoding tests prove that all three maximally sized cleanup
rows fit `MAX_CLEANUP_WORKLIST_BYTES`. No protocol-size cap is applied to a
legitimate artifact payload.

Catalog inspection stats a no-follow entry before allocation. Unknown or
unrecognized entries are marked foreign from name/metadata and are not read.
Authority and other protocol records use `take(limit + 1)` or an equivalent
bounded reader and revalidate length and identity afterwards.

Recognized source and goal payload files physically occupy their reserved slots
inside the action directory. They are not copied into or materialized by the
in-memory catalog model. The observer validates the exact expected length
already supplied by the request, then streams through SHA-256 and an exact chunk
comparison. A legitimate payload larger than one MiB therefore remains
restart-closed. Any future product payload ceiling must be checked before
private or managed mutation.

The ordinary public `observe()` path may still return bytes because callers
consume manifest/lock/bundle contents. It first rejects a statted length above
`isize::MAX` or the container's exact capacity with typed
`UnsupportedOperation`, then uses `try_reserve_exact`; allocation failure maps
to typed `IoError` before reading. It reads exactly the statted length plus an
EOF check and revalidates the same file identity and length. Simulated-length
and sparse-file tests prove there is no panic, abort, or read of another path.
"No protocol-size cap" applies to the streamed checked-action payload proof; it
does not promise that this byte-returning convenience API can materialize an
arbitrary-size value. Catalog recovery never uses it.

### 3.5 One durable-leaf observer owns file and namespace proof

The former `observe_durable` read/sync-parent/read sequence is replaced by one
primitive:

```text
observe_durable_leaf(parent, leaf, expected)
    -> MissingDurable | ExactDurable { identity, length, sha256 } | Other
```

For an existing file it:

1. opens once with no-follow semantics and retains that handle;
2. proves kind, identity, length, and exact bytes/hash;
3. flushes that exact handle;
4. establishes the platform namespace barrier for the retained parent;
5. revalidates parent mapping, name-to-handle identity, opened-handle identity,
   length, and exact bytes/hash; and
6. only then issues `ExactDurable`.

On Windows the single no-follow handle is opened with `CreateFileW` using
`OPEN_EXISTING`, `GENERIC_READ | GENERIC_WRITE`,
`FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, and
`FILE_FLAG_OPEN_REPARSE_POINT`; `FILE_FLAG_BACKUP_SEMANTICS` is added only for
a directory handle. The same handle supplies kind, full `FILE_ID_INFO`, exact
read, and `FlushFileBuffers`. Access denial, a read-only/ACL restriction, or a
flush failure is a typed pre-barrier error. It never falls back to a read-only
handle, ordinary observation, `FILE_FLAG_WRITE_THROUGH` alone, or a successful
namespace-only proof, and it does not move an anchor after such a failure.

For durable absence it proves missing, performs the namespace barrier, and
proves missing again against the same retained parent. Operational errors stay
operational errors; substitution or third forms are not collapsed to missing.

All proof-only, authority-free `After`, duplicate recovery, destination
publication, and cleanup paths use this primitive. No caller can combine
ordinary bytes with a separate barrier and call the result durable.

### 3.6 Namespace durability is a typed platform protocol

The platform seam becomes:

```text
NamespaceProtocol {
    publish_no_replace(source, destination) -> PublishedIdentity,
    retire_exact(source, retirement_slot)   -> RetiredIdentity,
    barrier(parent)                         -> DurableNamespace,
}
```

Unix retains handle-relative rename and ordered directory `sync_all`: durable
destination before durable source retirement for cross-directory moves.
Unlink is permitted only after exact identity revalidation and is followed by
the owning directory barrier.

Windows no longer exposes `sync_parent -> Ok(())`. Its protocol uses retained
handles for pre/post identity and obtains extended absolute names from those
handles while the workspace mutation lease is held. The actual same-volume
namespace edge is `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)` with no replace
unless replacement is explicitly part of the row. Each call is followed by
no-follow identity/name reobservation. Raw uncooperative mutation remains
outside the lease contract; path lookup is never treated as authority without
those handle checks.

Windows retirement is a write-through rename into an operation-owned retired
namespace, not `remove_file` followed by a no-op. Source aliases, staged-goal
aliases, authority records, and anchor aliases follow this rule. Retired names
are outside every active catalog prefix and are never required for correctness
after their retirement edge. Physical deletion is best-effort GC performed
only after terminal proof; failure cannot reopen an active action.

Windows has two distinct anchors:

- the fixed **catalog anchor** moves only between two reserved names inside the
  retained private root and makes catalog record publication/retirement
  durable; both names are always globally discoverable; and
- the **roaming barrier anchor** may enter a managed parent only while one
  durable `BarrierIntentV1` names its destination.

The catalog anchor is established while bootstrapping the private root: create
and flush its one fixed infrastructure scratch slot, publish it no-replace with
`MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`, reobserve its full identity, then
exercise the two fixed home-local names. It never leaves the catalog root.

Before the roaming anchor moves outbound, the catalog publishes and barriers:

```text
BarrierIntentV1 {
    intent_id,
    caller_and_action_binding,
    anchor_identity,
    private_home_identity_and_name,
    target_parent_durable_identity,
    target_parent_path_profile,
    reserved_target_leaf,
}
```

At most one active barrier intent exists under the workspace mutation lease.
The complete action schedule assigns each logical barrier call a stable ordinal
before admission; retry reuses that ordinal rather than consuming the next one.
After durable publication into `BarrierIntentActive(i)`, the protocol
write-through moves the exact anchor to the reserved target leaf and reobserves
it, write-through returns it home and reobserves it, then write-through moves
the intent no-replace to `BarrierIntentRetired(i)` and barriers the catalog. No
later barrier invocation begins until any active intent is recovered.

The closed restart table is:

| Durable intent | Home | Named target | Resolution before caller resumes |
| --- | --- | --- | --- |
| absent | exact anchor | absent | idle |
| active | exact anchor | absent | replay outbound and return, then retire intent |
| active | absent | same exact identity | return home, reobserve, then retire intent |
| active | same exact identity | same exact identity | retain home, write-through-retire the target alias, then retire intent |
| active | missing/other | missing/other | ambiguity; retain intent and both facts |

The home/target duplicate row is permitted only for the same full object
identity; different identities are ambiguity. A crash after outbound during a
proof-only or authority-free `After` row is therefore discoverable without an
outer checked-action authority. A second action recovers it rather than
creating another anchor.

New GWZ-owned private directory components are bootstrapped before authority.
The first private catalog root is the one non-catalog-backed case. A bounded
`CatalogBootstrapV1` record uses exactly the fixed `.scratch`, `.active`, and
`.staging` forms named in section 3.1 in the already retained GWZ parent
(`.gwz` for a workspace artifact or the retained Git directory for a
Git-directory artifact). It is flushed and published directly with the
platform durable no-replace edge, creates only the fixed staging directory,
populates and flushes its infrastructure, and publishes the directory to the
final private-root name.

The three exceptional forms and final prefix are collision-scanned before the
workspace variant creates any of them. Their restart table is resolved before
catalog access. Once the catalog root and catalog anchor are durable, the active
bootstrap record is write-through moved no-replace to the fixed permanent
infrastructure destination `catalog-bootstrap-retired-v1` inside that catalog.
That one-time retained record consumes the infrastructure count and is never an
action-local retirement or a prerequisite for GC. Scratch must be absent or an
exact bound partial; staging must be absent or the exact active-owned directory.
Any index/tracked collision, wrong kind, substitution, or unmatched active/
staging/final combination rejects with zero bootstrap, private, or managed
mutation.

`WorkspaceRuntimeBootstrapV1` is an earlier, capability-neutral live-process
coordination protocol. It deliberately makes **no power-loss/reboot durability
claim** and never calls `DurableIdentityProvider`, `NamespaceProtocol`, a
catalog anchor, or `BarrierIntentV1`. An OS advisory lock cannot survive its
process or a power loss; if its directory entry also disappears, the next
invocation recreates it before any checked authority exists. This is sufficient
for the lease's only promise: cooperative mutual exclusion among live GWZ
processes.

Its complete fixed grammar is:

```text
<workspace-git-dir>/gwz-runtime-bootstrap-v1.lock   // bootstrap guard
.gwz                                                 // final directory
.gwz/locks                                           // final directory
.gwz/locks/workspace-mutator.lock                    // final lease file
```

There are no random, staging, active-intent, or retirement names. The root Git
directory and workspace root are opened and retained first. A process opens or
creates the bootstrap-guard file no-follow and takes its advisory lock. While
holding that guard it creates each missing final directory with no-replace
`mkdir`, accepts `AlreadyExists` only after a no-follow directory revalidation,
then opens or creates the final lease file no-follow without truncation. It
acquires and retains the final OS advisory lock **before** releasing the
bootstrap guard. Every contender therefore converges on the same final lock
object; a contender that loses a create race reopens the winner rather than
inventing another name.

The closed live/crash rows are: missing; exact final; create won; concurrent
create lost to exact final; final lock opened but not acquired; final lock
acquired; and process exit at each point. Exit releases whichever advisory
locks were held, and retry begins from missing or exact finals. Symlink,
reparse, wrong-kind, parent substitution, or a changed final identity between
open and lock acquisition rejects. Invocation-local no-follow identities bind
the live handles only and are not persisted.

Because this protocol performs only additive reserved-name creation and issues
no checked authority, it needs no Windows namespace barrier. Windows uses
`CreateDirectoryW`/`CreateFileW(OPEN_ALWAYS)` plus retained-handle kind and file
ID revalidation; Unix uses `mkdirat`/`openat` equivalents. Non-checked commit,
stage, tag, materialize, and other ordinary mutators stop at this lease and are
never gated by the ext4 checked provider. Only after the lease exists may a
checked merge request run durable capability/collision preflight and bootstrap
the private catalog.

All other new GWZ-owned directory components use the catalog-backed bootstrap
below. Existing user-managed parent directories are never renamed.

### 3.6.1 Managed parent creation is its own restart-closed preflight

`ManagedParentBootstrap` is the only interface allowed to create missing
managed parents used by checked consumers after the runtime/private-root
bootstrap above. Its input is a declared ASCII `ManagedParentSpec`; the initial
table contains only the GWZ-owned merge-store and preservation parent sequences
actually inventoried from callers. One admitted action may bind an ordered plan
of at most eight specs and at most eight missing components **in total**. Every
admitted spec has at least one missing component. The complete caller inventory
and generated plan table prove those bounds. A ninth plan/component, an empty
invocation, a longer aggregate missing suffix, or a user-managed missing
component is typed unsupported before capacity admission or private/managed
mutation.

Each bootstrap begins at the deepest retained existing no-follow parent. It
publishes the plan's assigned initial global generation of one bounded
`ManagedParentBootstrapIntentV1` in the corresponding
`BootstrapIntentActive(g)` slot, binding the root, caller, capacity reservation,
bootstrap/local/global ordinals, full component list, retained parent identity/
mode, component cursor, deterministic action-bound staging/final names, and a
random ownership token stored as record content rather than used as a filename.
For each component it:

1. creates only the reservation-bound fixed staging directory with no-replace
   semantics;
2. writes and flushes an ownership marker bound to the intent/component;
3. makes the staging contents durable;
4. publishes staging to the missing final name with the platform's durable
   no-replace directory edge;
5. reopens final no-follow, encodes and flushes the next immutable successor in
   `BootstrapIntentScratch`, retires the prior active generation to its paired
   slot, publishes the scratch no-replace to the next active generation, and
   only then descends; and
6. after all components are installed, moves each marker to
   `RetiredBootstrapMarker(component_index)`, publishing and retiring one
   immutable cleanup successor per marker; then proves every final identity/
   mode again and retires the last intent generation.

The before-staging, staged, marker-flushed, published, reopened, successor, and
marker-retirement forms are closed physical rows. A plan with `n` components
consumes `1 + 2n` contiguous global generations; the capacity planner assigns
non-overlapping ranges whose total is `K + 2N <= 24`. During a successor
handoff, prior-active owns successor scratch until retirement; after retirement,
the exact prior-retired record plus that same scratch owns successor publication.
There is never an unowned gap or more than one active managed-bootstrap intent
across the ordered plan. A missing scratch is recreated; a valid exact scratch
resumes; an exact installed component is adopted only through its active intent
and recorded ownership marker; and a pre-existing final name, nonempty foreign
partial, collision, substitution, mode change, exhausted/overlapping/out-of-
order ordinal, or different identity is ambiguity. The bootstrap publishes no
checked-action authority, adds no merge lifecycle phase, and remains idempotent
across restart without deletion or retired-object GC.

Unix uses `mkdirat`/no-follow reopen and parent `sync_all` at the corresponding
edges. Windows uses staging-directory publication with
`MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`; publishing its catalog successor
uses only the fixed home-local catalog anchor, never an unrecorded roaming
anchor.

All former ad hoc `create_dir_all` or equivalent paths that can prepare the
runtime root, merge-store, checked-artifact, or preservation parents are
inventoried. They either call the named runtime/private/catalog-backed
bootstrap before checked acquisition or prove that their parent is user-managed
and already retained. No legacy parent-preparation path may remain.

The fault enum is iterable and includes every runtime-root/catalog bootstrap,
file flush, publish, retirement, catalog-intent publication/retirement,
roaming-anchor outbound/return, managed-parent bootstrap step, reobservation,
and successor boundary. Adding an enum variant changes an independently pinned
test key set.

### 3.7 Complete checkout has no reserved-prefix eraser

`raw_excluded_paths` no longer prepends `.gwz/checked-artifacts`. A checkout
overlay contains only exact path/domain facts proved by a named alternate
aggregate owner. Paths use the backend's lossless Git path bytes; this
interface does not convert arbitrary repository paths to UTF-8.

Ordinary ignored and untracked private residue is absent from Git's
non-ignored checkout image. Tracked or index-visible content below the private
prefix remains in both the expected and live image and any drift rejects.
Before private-catalog bootstrap, the section 3.1 private-namespace guard
rejects a tracked/index collision with any GWZ control prefix; it never makes
that collision disappear from terminal comparison. R3 consumes the same
preflight facts but does not introduce or postpone the guard.

The comparator consumes a path-keyed observation rather than global dirty
booleans:

```text
CheckoutPathFact {
    path_bytes,
    index: {
        entries: Absent | Stages { stage0, base, ours, theirs },
        semantic_flags,
        staged_conflict_type_and_rename_facts,
    },
    worktree: {
        value: Absent | Regular | Symlink | Directory | Gitlink,
        unstaged_untracked_unreadable_type_and_rename_facts,
        nested_gitlink: None | { live_head, attached_state, exact_status },
    },
}

CheckoutOverlayFact {
    owner,
    domain: Worktree(path) | Index(path),
    exact_fact,
}
```

An overlay applies only after that owner has independently proved the exact
fact. A worktree overlay replaces the exact worktree value **and its
worktree-side status**, but retains every index stage, semantic flag, conflict,
and index-side type/rename fact. An index overlay replaces only those index-side
facts and never erases worktree facts. Rename relationships retain their
lossless source/destination paths inside the side that observed them. Display
dirty summaries are derived after exact comparison and never authorize
recovery.

For a gitlink the observer opens the nested repository without following a
substituted path, reads its live HEAD and attached/detached state, and proves
its exact staged, unstaged, untracked, conflict, and nested-repository status.
A missing, unreadable, detached-at-another-commit, dirty, or recursively
unprovable nested checkout rejects conservatively.

Tests cover tracked/staged/type/semantic/rename/conflict drift below the
private prefix; exact, moved, dirty, missing, and unreadable submodules; a valid
lock/marker worktree overlay whose paths have non-clean worktree status; and
that same overlay plus independent index drift or unrelated staged, unstaged,
untracked, rename, or gitlink drift. Every unrelated drift rejects.

### 3.8 Rollback aggregate owns every durable terminal row and every handoff

Lifecycle validation makes rollback order explicit. For stored
`selected_targets = [a, b, c]`, rollback traversal is `[c, b, a]`; after one
completed owner the only legal terminal set is `{c}`, and after two it is
`{c, b}`. Terminal rows are therefore a suffix of the stored forward list and
a prefix of the reverse traversal. The pending/current cursor sits immediately
before that suffix in forward order and immediately after that prefix in reverse
order. Any other terminal placement is an unreadable model.
The live aggregate nevertheless iterates every stored `Aborted`/`RolledBack`
row, not only a cursor-derived slice, so a future validator regression cannot
silently drop a terminal checkout.

The selected-root physical reset has one frozen `After` postcondition: exact
terminal target ref, attached HEAD, native state, and **every index entry**;
the terminal commit's worktree at every path except the exact lock and managed
marker worktree paths still owned by publication evidence. It has no index
overlay. If the safe physical reset leaves another index fact, it is not
`After` and its journal is retained.

The aggregate uses this domain ownership table. "Participant" means the named
selected-root before/terminal projection, not merely its durable row state.

| Window | Publication evidence owns | Selected-root participant owns | Root-metadata rollback owns |
| --- | --- | --- | --- |
| evidence complete; participant not pending or pending `Before` | boundary; exact lock/marker worktree and index facts | exact before ref/HEAD/native; every other index/worktree fact | nothing |
| participant pending and physically `After` | boundary; exact lock/marker **worktree only** | terminal ref/HEAD/native; every index fact including lock/marker; manifest and every other non-overlaid worktree fact | nothing |
| `FinishParticipant` durable; before root-metadata mutation | boundary; exact marker worktree | terminal ref/HEAD/native; every index fact and all other checkout worktree facts | exact manifest and lock worktree facts |
| root-metadata pending or complete | boundary; exact marker worktree | terminal ref/HEAD/native; every index fact and all non-manifest/non-lock/non-marker worktree facts | step-specific exact manifest and lock worktree facts |

The marker worktree fact may be `Missing`; absence is still an exact owned
fact. Worktree overlays for the two evidence paths are applied only after the
evidence observer succeeds. No index overlay is admitted in the pending
`After` window. The durable participant successor atomically activates the
root-metadata owner for manifest/lock worktree facts; it does not transfer or
erase unrelated checkout facts.

This projection is checked before consuming the pending participant action.
No boolean such as `selected_root_checkout_supersedes_evidence` may reduce an
owner before the complete replacement projection is proved. Tests include a
valid pending-`After` row whose evidence-owned lock and marker worktree bytes
differ from the terminal commit, plus independent drift in every listed
worktree/index/ref/HEAD/native domain.

Directly seeded service tests cross both terminal states, out-of-order stored
rows, every shared-root fact, and every admitted request. Drift retains the
record/pending journal byte-for-byte and causes zero later-owner calls.

### 3.9 Fresh ambiguity always outranks executor diagnostics

`PreservationAmbiguous` uses the common reconciliation relation after its
record, request, action, prefix, and attempt bindings are validated. Matching
`Success` and matching `Failed` both apply the representable ambiguity rule.
Stale, mismatched, and consumed attempts still reject.

There is no preservation-only diagnostic-precedence helper. Tests assert the
exact recovery overlay, retained pending action, record bytes, and zero second
execution for both matching diagnostic forms.

### 3.10 C7 executes keys; it does not count tuples

The declarative source remains independent of production traversal. Keys are a
stage-typed sum because an honest production `service::run` can create only no
attempt, matching success, or matching failure; stale/mismatched attempts are
rejected at binding and consumed-second execution is rejected still earlier at
the invocation guard.

```text
CaseKey =
    ServiceObservationCase {
        durable_row, request,
        attempt: None | MatchingSuccess | MatchingFailed,
        fresh_form, restart_boundary, platform_form,
        expected_owning_stage,
    }
  | BindingRejectionCase {
        durable_row, request,
        rejection: StaleRecord | MismatchedRequest | MismatchedAction,
        fresh_form, expected_rejection_stage,
    }
  | InvocationRejectionCase {
        durable_row, request,
        rejection: ConsumedSecondExecution,
        first_diagnostic, expected_rejection_stage,
    }
  | ProofOnlyCase
  | ActionFreeCase
  | PlatformBoundaryCase
```

Each row owns a constructor that directly seeds its exact durable record and
physical state. A named `ProductionStageHarness` may stop after production
observer issuance, physical-action issuance, attempt recording, binding, or
the invocation guard. Every request, observation, action, prefix, and attempt
comes from its production constructor; the harness may interpose at a stage
but cannot forge a sealed token.

Service-observation rows invoke production `service::run` and the restart loop
to terminal exhaustion or the specified retained-owner result. Binding rows
obtain a real sealed attempt from a first production invocation, then either
advance the record through a production transition or pair it with a different
production-issued request/action to make the named stale/mismatched form. They
assert rejection at binding. Invocation rows call the production invocation
guard again on the same action after its first success or failure diagnostic
and assert second-execution rejection. Both rejection classes assert exact
unchanged record/artifact bytes and zero additional physical execution. A key
is recorded only after its own stage-specific assertions pass.

There is no inherited 20-cell or five-by-four executable cardinality. Expected
domains are independently declared per production stage:

- service reconciliation crosses `None | MatchingSuccess | MatchingFailed`
  only with fresh facts that the row's production observer can represent;
- binding crosses stale record, mismatched request, and mismatched action only
  with observations production can issue for the retained/new binding;
- invocation covers repeat-after-first-success and repeat-after-first-failure,
  independent of any fresh-fact Cartesian product; and
- proof-only, action-free, checked-platform, runtime bootstrap, catalog
  bootstrap, capacity, barrier, and managed-bootstrap rows use their own closed
  alphabets.

If a pure relation retains stale/mismatched or consumed-second labels for
documentation, they are pre-relation stage sentinels and are not counted as
service cells. Prefer deleting an unreachable relation variant. Expected-key
cardinalities are exact per stage and change when a production stage's legal
alphabet changes.

The independently declared expected-key set is compared with the executed-key
set. Duplicate and missing keys fail. Expected keys and row constructors live
in separate modules and are not derived from the same iterator.

Coverage includes:

- both absent handoffs, all candidate shapes, both root owners, all five
  admitted requests, all root phases, non-root preservation/rollback,
  no-mutation, evidence, root-metadata, recovery, and exhaustion rows;
- every independently declared legal service, binding, invocation, proof-only,
  action-free, and platform key in the stage-specific domains above;
- real `Before`, `After`/`AfterNeedsDurability`, representable ambiguity, and
  operational-error observer forms;
- source-equals-goal proof-only, all action-free positions, both terminal
  participant states, every checked-artifact transition/fault boundary,
  unsupported/tracked-collision no-mutation rows, runtime/catalog/managed-parent
  bootstrap, persistent admission-record replacement and directory handoff,
  capacity admission/exhaustion, both extremal eight-component managed-plan
  layouts with all 24 intent generations and 64 barrier ordinals, immutable
  cleanup-worklist recovery, repeated deterministic scratch, and Windows
  catalog-anchor, barrier-intent, roaming-anchor, and retirement boundaries; and
- exact record/artifact bytes, identities, calls, journal retention or
  consumption, recovery disposition, and terminal state.

Large cross-products use deterministic in-memory `GitBackend` and `MergeStore`
implementations but call the production stage named by each key. Real Git,
real filesystem, and real platform fault suites independently pin each adapter
boundary. A tuple collector, forged authority, or direct call only to
`reconcile` cannot satisfy a key. The independently declared expected-key set
includes the owning/rejection stage, so moving a rejection across a security
boundary changes the expected contract rather than silently preserving a
count.

### 3.11 Rollback-prefix authority is observer-private and request-bound

The prefix payload binds:

```text
RollbackPrefixBinding {
    request,
    aggregate_position,
    current_owner,
    current_action,
    current_phase,
    record/location/operation binding,
    aggregate_projection_sha256,
}
```

The token type and a prefix-specific private `RollbackPrefixIssuer` move into
the reverse-observer module. The resolver may consume the sealed result returned
by that observer but cannot construct it; executors receive only
`require_rollback_aggregate(...) -> ()` and never receive a prefix. The generic
`AuthorityIssuer` remains available to its other legitimate transition owners;
the privacy rule does not ban that generic type. Test-only constructors seed
physical/model state and call the observer rather than issuing a token.

Rust visibility and a compile-fail gate reject imports or calls to
`RollbackPrefixIssuer`/the prefix constructor outside the reverse observer. A
separate semantic call-graph assertion proves executors receive only the
non-authoritative `require -> ()` seam and verifies that request/owner/action/
phase fields participate in the binding hash.
