## 1. Findings

### [P3-32] The `git credential fill` recipe leaves `core.askPass` as a prompt path on gits before 2.40, and the text names neither the path nor its one-token closure
- **Location:** §5.8 line 360 ("without `GIT_ASKPASS` and `SSH_ASKPASS`, plus `GIT_TERMINAL_PROMPT=0` and `-c credential.interactive=false` (older gits ignore the key)"); change 5 (the "never prompting" claim dropped rather than restored); §15.8 line 614 (the recorder test names only `GIT_ASKPASS`).
- **Violated invariant:** the replacement for a `debt` spawn must not be worse than what it replaces; libgit2's helper lookup (git2 `CredentialHelper::execute`) never prompts on any git version; the recipe's remaining prompt path is undisclosed, so an operator reading §5.8 cannot tell what the "older gits" caveat permits.
- **Sequence:** an ordinary-build session on a host with git 2.34 (Ubuntu 22.04 LTS) or 2.39 (Debian 12), whose global or system git configuration sets `core.askPass` (some IDE and distribution setups do). An HTTPS fetch to a host with no helper result: core spawns `git credential fill` per the recipe; git ignores `credential.interactive`; `GIT_ASKPASS` is absent; git reads `core.askPass` from the snapshot's `HOME` and runs that program with the snapshot; a GUI prompt appears or the program blocks; the worker blocks until the stated bound kills the child; the fetch then fails. Bounded, but a prompt that libgit2's lookup never produced, and the text does not say it can happen.
- **Impact:** a user-visible prompt or a bounded stall on widely deployed gits, undisclosed; `credential.interactive=false` alone does not restore the status quo there.
- **Required correction:** add `-c core.askPass=` to the recipe in §5.8 (an explicit empty override that git's prompt code treats as no program, on every version), state that with it the spawn never prompts on any git version, and extend §15.8's test to a configuration that sets `core.askPass` to the recorder.
- **Regression test:** with `core.askPass` set in the snapshot's global configuration to a recorder, `GIT_ASKPASS` unset, and no helper configured, an HTTPS fetch fails with an authentication error and the recorder never runs, on a git older than 2.40 (or with `credential.interactive` removed from the recipe to simulate one).
- **Classification:** bounded correction; not architectural.

## 2. Invariant analysis

Attacks that failed, with the evidence:

- **A gate that can be skipped or silently pass.** Local: fail-closed on neither checkout; a named checkout that is missing fails rather than falling back; a directory that is not a gwz-transport checkout fails in the checker ("no crate roots match"); `check=True` propagates the checker's exit; the skip flag prints `SKIPPED GATE` with the reason and cannot be abbreviated. CI: the boundary job cannot skip (no flag in the job; `TransportPin` asserts it); the pin is read from the allowlist by the checker, which validates its shape; the checkout is double-guarded (HEAD equality, then ancestry on `origin/main`); a broken or absent `reconciled_commit` fails the reader step and, failing that, the equality check. The release and matrix jobs skip visibly and say where the check runs. gwz-py's leg is unchanged and fail-closed. gwz-transport's CI carries no gate, and every governing text now says so.
- **A pin that cannot move.** A pin-only bump is an allowlist change and is allowed. A substantive allowlist change without a bump fails the boundary job (STALE or NEW against the old pin), so the bump rule is self-enforcing where it matters. A rewritten gwz-transport `main` that drops the pinned commit turns the job red until a bump to a commit on the new `main`; bounded. The pin can move backwards to an older commit on `main` that still matches the list without failing; a reviewer sees it in the diff (residual).
- **A release that can no longer run.** From the gwz-dev workspace the release's gate runs over the sibling. From a standalone clone it stops with a message naming both remedies (`GWZ_TRANSPORT_CHECKOUT=<path>` or a sibling checkout). Unpushed sibling changes that add state block the release until the operator names a clean checkout; self-diagnosing. The release verify job in `release.yml` skips the leg; in the normal flow the tag's commit was checked by the boundary job on its push to `main` and by `release.py` locally before tagging.
- **Degraded and mixed versions.** The boundary job checks an older gwz-transport than the sibling until gwz-transport is pushed (disclosed, RemPlan-2 §4 item 3); the local gate checks the newer one; both pass today. A stale sibling behind a bumped pin fails locally with a named item. The transport build stays candidate-only and links the sibling, which the local gate covers.
- **Retention.** The 30-second condition ties the make-room release to the only read wait the contract has; a parked read is an open stream, so a reader that has asked is never released from under it; a running producer's log is never eligible. `operation_expired` for every release way is consistent with the operation table.
- **Bridge view.** A non-release `operation_expired` no longer discards a held result; the size bound still holds; the closed-loop keep rule and §15.1 now agree.
- **Credentials.** The recipe removes the environment prompt paths, disables the terminal, bounds and kills the child, and puts helper output under the secrecy rule; the configuration path on older gits is P3-32.
- **Disclosure.** Nothing new carries the snapshot or helper output into a frame, event, error or log; the `SKIPPED GATE` line names no secret.
- **Status quo.** Revision 4 is stronger than revision 2 for the gwz-transport gate (a pinned, non-skippable CI run on the consumer's side plus a fail-closed local run, against revision 2's unpinned run) and stronger than revision 3 everywhere revision 3 was weaker. The only remaining regression from today's behaviour is the older-git prompt path of P3-32, which is bounded and cheap to close.
