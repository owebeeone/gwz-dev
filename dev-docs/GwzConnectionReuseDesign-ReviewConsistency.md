## 1. Findings

### [P2-1] §14 T1 and T3 contradict each other on whether an idle pool entry has an owner, and the reading T3 invites makes the existing `cancel_session` path close idle connections

**Location.** §14 T1: "Idle entries have no owner." §14 T3: "An idle entry keeps its last owner, and a lease reports whether its previous owner differs from its current one." §5: "Idle entries belong to no operation." §8: "`cancel_session` on the binding's session ID is the backstop when a binding is abandoned (POOL/lifecycle.rs:80-107). Idle connections and other bindings are untouched." §4, first paragraph: the cross-operation check runs when "a connection that a different binding leased last is leased again (the pool reports it, §14 T3)".

**Violated invariant.** TR1.2 question 8 ("Cancelling or failing one operation never closes another operation's lease or a healthy shared connection") and the object's own §8. The pool's documented model at gwz-transport `src/pool/lifecycle.rs:84` ("Idle resources have no session owner and survive"), which `cancel_matching` (`lifecycle.rs:88-107`) relies on: it starts closing every entry whose `entry.owner` matches the cancelled owner (`:101`).

**Reproduction (state sequence).** Implement T3 as its words say: leave `entry.owner` set to the last lessee when the entry returns to idle, so the next lease can compare it. Binding A (session S1) leases connection c, finishes its exchange and releases c to idle; c now carries owner A. A is abandoned; the host calls `cancel_session(A.session)` as §8 prescribes. `cancel_matching` matches c at `lifecycle.rs:101` and starts closing it. §15 item 6's assertion "A's lease closes, idle connections survive, and B's next request reuses one" fails: c is gone and B opens a new connection. `cancel_operation` (`lifecycle.rs:80-82`) produces the same loss.

**Impact.** The one gwz-transport change that §4's cross-operation revalidation depends on is specified two incompatible ways, on the pool's ownership model — the state whose sharing §17 names as "the area where four Python designs failed". One reading is a correctness defect in the gwz-transport that Phase 10 releases and defeats §8's isolation; the other is what §5 and §8 need. The T-steps are the interface Phase 6 implements and TR2.6 reviews; a self-contradiction there cannot be left to the implementer's choice.

**Remedy (text; not architectural).** Rewrite T3 so that ownership is unchanged: an idle entry's `Owner` is `None`, as today; the pool records the *last lessee* in a separate field that `cancel_operation`, `cancel_session`, eviction and per-owner accounting never consult; the lease (or checkout result) reports whether that last lessee differs from the new owner. Strike "keeps its last owner"; make T1's "Idle entries have no owner" the governing sentence. In §4, say that the checked-out connection is held as the requesting binding's lease during the proof, is released back to idle when the proof is cancelled or times out, and is closed through the lease's release path when the proof fails; T4's `retire_idle` covers the *other* idle same-key or same-host-key entries the outcome table's second row names.

**Closure test.** §15 item 6 as written, plus a gwz-transport unit test: after a release, `entry.owner` is `None` and the last-lessee field is set; `cancel_session` and `cancel_operation` naming the last lessee leave the idle entry untouched; a subsequent lease by a different owner reports "previous lessee differs" and one by the same owner reports "same".

### [P3-7] "One supervisor per instance" names a thread the design never defines, and the name collides with the host context's setup supervisor and with A3's no-per-endpoint-thread rule

**Location.** §2 "Threads. The SSH worker, the HTTPS thread and one supervisor are per instance. A binding keeps today's driver-session and link threads (TH/session.rs:314-333, 955-1007)". §7 "three per instance: the SSH worker, the HTTPS thread and the supervisor". §17 "48 threads". §2's diagram puts "setup supervisor · 64 setup jobs" in the host context.

**Violated invariant.** One name, one meaning (interface shape). A3:37-40: "One existing supervisor thread polls jobs and retained pools; no extra reaper thread per endpoint … No endpoint/helper thread may be detached and forgotten." CS §5.6/§14: the setup supervisor is one per host context.

**Evidence.** Today's four threads per runtime are `gwz-placement` (`session.rs:314-333`, the endpoint `Session`'s drive loop, which steps `state.engine` and `state.https` through `session/driver.rs:242`), `gwz-placement-local` (`session.rs:955-1007`, the link), the SSH worker and `gwz-https`. The object assigns the first two to the binding and the last two to the instance, then adds "one supervisor" per instance with no duty stated.
