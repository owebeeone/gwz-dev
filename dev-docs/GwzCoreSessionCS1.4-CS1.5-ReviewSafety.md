## 1. Findings (severity-ordered)

### S-P2-1 — A test dumps the whole live process environment, hex-encoded, into its failure output

- **Location:** `src/session_host/environment/tests.rs:107-118` (`capture_takes_each_process_variable_once`), the `assert_eq!(seen, wanted)` at line 118 on two `BTreeSet<String>` built by `line()` (`:25-31`), which hex-encodes every name and value.
- **Violated invariant:** contract §5.6 "The snapshot is secret-bearing. It is never serialized into a frame, event, result, error message or log"; §15.8 "An error raised … contains no environment value"; plan §2.4 "Evidence handling … redact agent-socket paths … `gh` tokens … A secret in filed evidence fails its step". The review brief names test output as a disclosure path.
- **Reproduction:** make `seen != wanted` with equal lengths (any one value differing, which is exactly the regression this test exists to catch) and run `cargo test --lib capture_takes_each_process_variable_once`. `assert_eq!` on failure prints `left:` and `right:` with `Debug`, i.e. every entry of the live environment as `hex(name)=hex(value)`. On a developer machine that is the shell's API keys and tokens; on dabeest and CI runners it is `SSH_AUTH_SOCK`, home paths and any token in the runner environment. Hex encoding defeats GitHub Actions' secret masking. Because the run is captured with `tee platform-matrix.log` and filed as evidence, the plan's own rule would then fail the step.
- **Impact:** credential and path disclosure into test logs and filed evidence, gated only on this test's failure, in a test whose retry loop (five attempts for environment churn) shows failure is anticipated.
- **Required correction:** never print entries. Compare and, on mismatch, report only counts and the number of entries present in one set and absent from the other (or a per-entry SHA-256 digest); keep the existing `assert_eq!(snapshot.len(), expected.len())` first. The same applies to `a_child_spawned_by_the_helper_sees_exactly_the_snapshot` if its pairs ever come from the live environment (today they are synthetic plus `SystemRoot`, which is acceptable).
- **Regression test:** factor the comparison into `fn mismatch_report(seen: &BTreeSet<String>, wanted: &BTreeSet<String>) -> String` and unit-test that, for two sets that differ in one planted entry `474854=s3cr3t`-style, the report contains neither the planted name nor value nor their hex.

### S-P3-1 — `EnvironmentSnapshot::capture()` is a public library entry point that the process-globals ratchet cannot see

- **Location:** `src/session_host/environment.rs:60-67`; allowlist entry `scripts/checks/process_globals_allowlist.json` (+54) with disposition `permanent`.
- **Violated invariant:** O9 "Code on the session path reads no environment variable … other than the inventoried `permanent` entries. Those carry no session-relevant state or are imposed by a dependency"; §5.6 "Core and the extension never read the environment themselves"; §5.7 "a check keeps new state out"; server design §5.7 amendment: releasing `server start` requires the checker's no-`env`-debt mode to pass.
- **Reproduction:** add `let live = EnvironmentSnapshot::capture();` anywhere on the session path (for example as a fallback in CS3.2's configuration derivation) and run the checker: it stays green, because it matches the `env::vars_os` spelling at `environment.rs:63` only, and that occurrence is `permanent`. Contrast `Cred::credential_helper`, where the checker deliberately tracks the wrapper spelling (`check_process_globals.py:399-404`).
- **Impact:** the release gate that the server design depends on (no `env` debt) can no longer prove O9 for core: a whole-environment read is reachable from any session-path code through a one-token call, and the entry's `permanent` label contradicts O9's definition of permanent (it carries all session-relevant state).
- **Required correction:** either (a) teach the checker `EnvironmentSnapshot::capture` as an `env` spelling requiring an allowlist entry per call site, with the drivers' call sites (gwz-cli startup, CS5.1's host binary, the stdio host) listed and nothing else; or (b) move `capture` out of the library into the driver binaries (the plan's CS1.5 wording is "captured by the driver"), keeping only `from_byte_pairs` in core. Either way the entry's reason should say why it is not `permanent` in O9's sense.
- **Regression test:** a checker test (beside `test_check_process_globals.py`) that a file containing `EnvironmentSnapshot::capture()` without an entry fails; or, under (b), a `cargo test` assertion that `gwz_core::session_host` exports no `capture`.

### S-P3-2 — A supervised job that panics on every poll is re-polled at 50 Hz forever, keeping the thread alive and emitting a panic report each time

- **Location:** `src/session_host/context.rs:100` (`retain_mut(|job| !catch_unwind(AssertUnwindSafe(|| job.poll())).unwrap_or(false))`) with the exit condition at `:103-108` and the 20 ms `wait_timeout` at `:114-118`.
- **Violated invariant:** §5.6 "Dropping it stops its supervisor thread once its jobs have finished"; reuse design §7 (bounded disposal, "unfinished work stays under the supervisor with its permit"); the brief's question "a job that panicked is kept and re-polled, which keeps the thread alive — unbounded?".
- **Reproduction:** a `SupervisedJob` whose `poll` always panics (the existing `PanicsOnce` with the flag never set). `supervise` it, drop the host context, observe: `wait_ended(10 s)` never returns true; `stderr` receives "thread 'gwz-host-supervisor' panicked at …" from the default panic hook every 20 ms (`catch_unwind` does not suppress the hook); the thread and everything the job owns live for the process lifetime. In gwz-py that is a permanent 50 Hz stream into the user's terminal; in the server, forever.
- **Impact:** unbounded thread and resource lifetime and unbounded diagnostic spam from one deterministic bug in any future job (CS3.5's SSH setup jobs, the reuse design's disposals).
- **Required correction:** quarantine a job whose poll panicked: keep it (so its finish is never assumed and its permit stays held, the fail-closed direction the implementer chose) but stop polling it, and do not let quarantined jobs keep a released supervisor alive (drop them on exit so their `Drop` runs, or count them in a report for TR1.4b's `shutdown`). Alternatively cap re-polls after a panic.
- **Regression test:** an always-panicking job is polled at most N times (N ≤ 2) and `wait_ended` returns true within the poll interval after the host context drops.

### S-P3-3 — A nested crossing or `state()` on the same gate from inside a closure deadlocks the worker and then `revoke`, so the close bound becomes unmeetable

- **Location:** `src/session_host/gate.rs:246-255` (`refusable` holds the lock across `f`), `:240-244` (`report`), `:209-221` (`state()` also takes the lock), `:158-162` (`revoke` waits on it).
- **Violated invariant:** §8 step 5 / O5 "The close bound ends the session"; §16 "A handler that never returns is detached at the close bound"; §5.2's panic rule (a worker panic yields `Failed` and "The session carries on"). The doc comment (`gate.rs:17-20`) states the constraint but nothing detects a breach.
- **Reproduction:** `gate.effect(|_| handler.gate().state())` or `gate.report(|_| gate.append(|_| ()))` on one thread. `std::sync::Mutex::lock` from the holding thread "will not return on the second call" (documented; futex-based deadlock on macOS and Linux). The worker hangs inside the closure; `controls.revoke()` then blocks forever (the existing test `revocation_waits_for_a_crossing_in_flight…` demonstrates that revoke waits for the closure), so CS2.12's close can never pass step 5, and gwz-py's exit join hangs.
- **Impact:** one accidental re-entry in later-step worker or handler code converts a bug the contract promises to survive (a handler that never returns) into a permanent session-close hang. `state()` is the likely accidental call, since it looks like a read.
- **Required correction:** record the crossing thread in `GateInner` (for example `Mutex<Option<ThreadId>>` or an atomic set under the lock) and, on re-entry from the same thread, panic with a clear message instead of deadlocking (the worker's `catch_unwind` then reports `Failed`, the guard drops during unwinding, and `revoke` proceeds). Make `state()` not take the crossing lock: read the token lock-free and use `try_lock` for the session slot, since a held lock implies not yet revoked. Name the gate lock explicitly in the callback constraint at `gate.rs:69-74` ("take no session lock" should include "and do not cross a gate").
- **Regression test:** a nested `effect` inside `effect` panics rather than hangs (run under a test-thread timeout), and `revoke` returns afterwards; `state()` called inside a closure returns without blocking.

### S-P3-4 — `Limits::validate` accepts a `read_bytes` that cannot be honoured inside a frame

- **Location:** `src/session_host/limits.rs:109-113` (`read_bytes >= MAX_FRAME_BYTES` refused; `MAX_FRAME_BYTES - 1` accepted), with the claim at `:82-83` "a read's byte limit is below the frame size, which bounds its reply (§3)".
- **Violated invariant:** §3 "No frame may exceed 64 MiB" and a frame over the limit "ends the session"; §1's `read_bytes` meaning "bytes returned by one read".
- **Reproduction:** `Limits { read_bytes: MAX_FRAME_BYTES - 1, ..Default::default() }.validate()` is `Ok`. A CS2.10 read that returns that many record bytes must encode them in a `LogReadResponse` with cursor, state and per-record CBOR framing, which exceeds 64 MiB, so either the host emits a frame that ends its own session or it silently returns fewer bytes than the limit promises.
- **Impact:** an accepted limit under which the read path must break one of two contract promises; the validation comment asserts a bound that does not hold at the margin.
- **Required correction:** reserve documented headroom in `validate` (for example `read_bytes + READ_REPLY_HEADROOM <= MAX_FRAME_BYTES`, or `read_bytes <= MAX_FRAME_BYTES / 2`), and state in `Limits` that the reply frame, not the record bytes, is what the frame limit bounds.
- **Regression test:** `read_bytes = MAX_FRAME_BYTES - 1` is refused with `invalid_request` naming `read_bytes`; the largest accepted value plus the documented headroom equals `MAX_FRAME_BYTES`.

### S-P3-5 — `close_wait` has no upper bound, so an accepted value makes the natural deadline arithmetic panic

- **Location:** `src/session_host/limits.rs:50` (`close_wait: Duration`), `:85-124` (no check on it); RustApi.md documents no bound and no meaning for zero.
- **Violated invariant:** §1 "`open` validates the limits it is given"; §8 step 4 "up to `close_wait`"; the brief's question on overflow and on what 0 means.
- **Reproduction:** `open` with `close_wait: Duration::MAX` succeeds. `Instant::now() + limits.close_wait`, the natural form for CS2.12's close deadline, panics with "overflow when adding duration to instant" (std `time.rs:421-429`); the closing thread unwinds mid-shutdown. (`Condvar::wait_timeout` would saturate, `Instant + Duration` does not.) `close_wait: Duration::ZERO` is accepted and means "detach every running worker at once", which is safe but undocumented.
- **Impact:** a limit the contract makes configurable at `open` admits a value under which close cannot be implemented with ordinary arithmetic, and a value whose meaning later steps must guess.
- **Required correction:** either cap `close_wait` in `validate` (a stated maximum, refused with `invalid_request` naming it) or provide the deadline through a saturating helper on `Limits` (`close_deadline(now) -> Option<Instant>`), and document that zero detaches immediately. The same guidance applies to the count limits: document that consumers must never pre-allocate by a limit, since `usize::MAX - 1` is accepted for `outstanding_calls`.
- **Regression test:** `Duration::MAX` is refused, or `close_deadline` returns `None`/saturates for it; a doc test states zero's meaning.

### S-P3-6 — On Windows the snapshot's name folding differs from the comparison `Command::env` itself uses, so `get` and the child can disagree

- **Location:** `src/session_host/environment.rs:226-231` (`same_name` via `wide::fold`), `:283-292` (`fold` = Unicode simple uppercase of one UTF-16 unit), `:140-146` (`apply_to`); std's `EnvKey` uses `CompareStringOrdinal(ignoreCase)` in a `BTreeMap` (`sys/process/windows.rs:74-107`).
- **Violated invariant:** the module's own contract (`environment.rs:9-10, 14`): "one value per name, the first occurrence winning, as a lookup of the live environment finds it" and "A child gets `env_clear()` plus the snapshot"; plan C7 "lookups follow the platform's name rules". RustApi.md states "case-insensitively on Windows" with no caveat.
- **Reproduction (Windows CI):** two driver-supplied names that differ only in a character the two tables treat differently. Where Rust's table folds them equal and the OS does not (the likely direction for mappings newer than Windows' frozen NLS uppercase table, for example Georgian Mkhedruli/Mtavruli, U+10D0 vs U+1C90), `insert` drops the second entry: `apply_to` never gives the child a variable the OS treats as distinct, and `get(second)` returns the first's value. Where the OS folds them equal and Rust does not, `apply_to` inserts both and the `BTreeMap` keeps the last, so the child sees the second value while `get` reports two entries with the first. A test can observe the second case directly: after `apply_to`, `command.get_envs().count() != snapshot.len()`.
- **Impact:** narrow (non-ASCII names on Windows only; `HTTPS_PROXY`, `GIT_SSL_CAINFO`, `GIT_ASKPASS` are unaffected), but it is a silent drop or a first/last-wins inversion in the primitive later steps use to remove prompt hooks and derive configuration, and the approximation is undocumented in the public API text.
- **Required correction:** on Windows compare names with `CompareStringOrdinal(..., TRUE)` through `windows-sys` (feature `Win32_Globalization`; the crate is already a dependency), exactly as std's `Command` does, so `get`, `insert` and the child agree; or, if the approximation is kept, document it in RustApi.md and `same_name`.
- **Regression test:** on Windows, for every snapshot `apply_to` produces `command.get_envs().count() == snapshot.len()`; plus a pair from the divergence class above asserting both `get` answers match the child's environment via the probe.

## 2. Invariant analysis (attacks that held, with evidence)

- **Cancel racing a crossing.** `cancel` never waits; a crossing that passed `is_cancelled()` under the gate lock runs with a cancelled token. §5.3 permits exactly this ("observes cancellation only at gate crossings"). Held.
- **Revoke racing a crossing and a report.** All three crossing kinds and `state()` take `GateInner::session`; `revoke` takes it after cancelling, so it returns only when no closure is in flight and `session` is `None` thereafter; a report that then upgrades finds nothing. Verified by `revocation_waits_for_a_crossing_in_flight…` (report blocked, revoke blocked 100 ms, then `report` returns `None`). The claim "once `revoke` returns no crossing is in flight" holds. Residual: std's mutex is not fair, so a worker issuing back-to-back reports can delay `revoke` under contention; bounded in practice, noted under risks for CS2.12.
- **Session-state escape from a closure.** `f: impl FnOnce(GateScope<'_>) -> R` is higher-ranked over the scope lifetime, so `R` cannot carry `&SessionContext`; `SessionContext` has no `Clone`, `EnvironmentSnapshot` has no `Clone`; only `HostContext` (shared by design) and `Limits` (plain data) can be cloned out. Held.
- **Poisoning.** A closure panic unwinds through `refusable`, dropping the guard; the guarded state (`Option<Weak<_>>`) is never half-written by a closure, so `into_inner` recovery is sound. Token callbacks (`Callbacks`) and supervisor state are likewise never left half-written under a panic. Held.
- **Weak session reference.** An ended session's gate reports `Revoked`, refuses effects with `Cancelled` and ignores reports (fail-closed) while its token reads not cancelled (`a_gate_does_not_keep_its_session_alive`). In this step no worker exists, so no waiter can depend on the token. The state "revoked but not cancelled" contradicts §8's ordering only if a later host drops the context without closure; carried as a risk.
- **Token callbacks.** Every interleaving of `on_cancel` and `cancel` either runs the callback exactly once or refuses the registration: the flag is set before the pending list is taken, and `on_cancel` checks the flag under the same lock. A panicking callback is caught, the remaining callbacks still run, and the flag is already set. A registration dropped mid-cancel may run once; the callback owns its captures, so this is harmless for any callback that tolerates a late wake, which the doc requires. A callback that re-registers gets `Cancelled`; one that drops another registration does not deadlock (callbacks run outside the lock). Held. Callbacks run on the cancelling thread (the reading thread for `operation.cancel`) and can block every control frame if they block: a discipline constraint, documented at `gate.rs:69-74`, with the gate lock omitted (S-P3-3).
- **Supervisor start and stop.** Thread creation happens under the supervisor lock with `running` set only on success; a failed `spawn` returns `Err` and drops the job, and the next `supervise` retries. `released` can only be set once no `HostContext` handle exists, so no `supervise` races the thread's exit. Condvar use is correct (all state changes under the lock, waits in loops). `dropping_a_host_context_ends_its_supervisor_thread_once_its_jobs_finish` and `an_open_session_keeps_its_host_context` confirm the lifetime. Held, except S-P3-2.
- **Snapshot secrecy in production code.** `Wiped`, `EnvValue`, `SessionContext`, `GateScope` derive no `Debug`; `EnvironmentSnapshot`, `HostContext`, `ClientChannel` have count-only or empty `Debug`; no `Display`, no `Serialize`; `from_byte_pairs` errors carry a static reason and the index only (`formatted_output_carries_no_value_and_no_name`, `an_unrepresentable_entry_is_refused_without_its_contents`); `EnvValue` and `get` are crate-private so the type is opaque outside gwz-core. Held.
- **Zeroization.** `Wiped::drop` overwrites the full allocation (spare capacity included) with volatile writes and a compiler fence; the `Vec<(Wiped, Wiped)>` reallocates only the tuples, not the byte buffers; on Windows both the input `Vec<u8>` and the UTF-16 scratch are wiped; refused inputs and the remaining iterator are wiped on the error path. Copies core does not own: std `Command`'s env map (documented at `environment.rs:132-135`), the spawn-time `CStringArray`/UTF-16 block std frees unwiped, and on Windows `EnvKey`'s extra UTF-16 copy. Those reach only the child by design, so "best effort" is accurate for core's buffers; RustApi.md's unqualified "its bytes are overwritten" should say "its own buffers" (documentation note, not a finding).
- **`capture()` correctness.** std's unix `parse` yields exactly the names `entry()` accepts (non-empty, no `=` after byte 0, no NUL), so the comment at `environment.rs:62` holds; duplicates from a duplicated `environ` are dropped through `Wiped` and first-wins matches glibc `getenv`. Held.
- **WTF-8.** Overlong forms, values above U+10FFFF, bad leads and truncation are refused; lone surrogates and split pairs are accepted, and `OsString::from_wide` canonicalizes a split pair, so two byte strings can decode to one `OsString` but no two `OsString`s share bytes. A byte-for-byte must-match comparison in the server can therefore only refuse (fail closed), never falsely accept. Held.
- **Spawn helper on POSIX.** `env_clear()` plus the snapshot, verified against `/usr/bin/env -0`, including a non-UTF-8 name and value. Windows relies on the driver's snapshot carrying `SystemRoot`, which a live capture always does; the contract's "nothing else from the live environment" is implemented literally. Held.
- **Limits.** `running + queued` and `outstanding + reserve` use `checked_add`; `event_log ≥ 2` matches §5.4's reset-plus-later rule; defaults equal §1's table. Held, except S-P3-4 and S-P3-5.
- **`open` before any effect.** Validation precedes construction; construction allocates only. A refused `open` consumes and wipes the snapshot, so a driver must re-capture (a Rust-API property, not a contract breach). Held.
- **Thread safety of the public types.** `HostContext`, `SessionOptions`, `EnvironmentSnapshot`, `ClientChannel` are `Send + Sync` (test `the_public_types_cross_threads`); `CallControls` is not `Clone`, so exactly one authority exists per record. Held.
- **Conditional compilation and braces.** Every platform arm is a `cfg_if!` block or an enclosing `platform`/`wide` module; the test module is declared through `cfg_if!`; every control-flow body is braced. Held.

## 3. Risks and next action

- **Revoked-but-not-cancelled.** If a later host ever drops `SessionContext` without running §8 steps 2–5 (a panic on the reading thread, for example), a lock wait that wakes only on the token never wakes and a producer looping on `report` while `!is_cancelled()` spins. CS2.2/CS2.12 must guarantee cancel-before-drop; the `Weak` fallback is defence in depth, not a substitute. Consider cancelling every token in the operation table from `SessionContext::drop` once CS2.6 places the table there.
- **Revoke under contention.** A non-fair mutex lets a busy reporter delay `revoke`; CS2.12 should measure close latency with a worker emitting events in a loop and, if needed, add a "revoking" flag that crossings check before taking the lock.
- **Callbacks on the reading thread.** Every `on_cancel` callback in CS3.7 and CS3.9 must be non-blocking or the control lane stalls; a test with a deliberately slow callback and a concurrent `session.close` belongs in CS3.7.
- **Pre-allocation by limit.** `outstanding_calls + control_reserve` up to `usize::MAX` is accepted; CS1.2's bounded queues must be counter-bounded, never `with_capacity(limit)`.
- **Quadratic insert.** `insert` scans existing entries, so a driver-supplied snapshot of n entries costs O(n²); harmless for real environments, but a socket host taking `SessionOpen` from a same-user peer should keep the server design's entry bound in mind.
- **Documentation.** RustApi.md should qualify zeroization as the snapshot's own buffers, state what `close_wait = 0` means, and (unless S-P3-6 is fixed) say that Windows name comparison approximates the OS table.

**Next action:** resolve S-P2-1 (a small change confined to `environment/tests.rs`), then re-review single-axis; S-P3-1 through S-P3-6 have bounded fixes and can land in the same revision or be recorded against CS1.7's checker (S-P3-1), CS3.5 (S-P3-2), CS2.4/CS2.12 (S-P3-3, S-P3-5) and CS2.10 (S-P3-4) with the tests named above.
