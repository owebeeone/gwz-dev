The [Consistency](GwzCoreSessionDesign-ReviewConsistency.md) and [Safety](GwzCoreSessionDesign-ReviewSafety.md) reports are filed verbatim.

This plan is one consolidated correction across the contract, the paired core paragraphs and the gwz-py pointers. It is not a series of per-finding patches. It also specifies:
- the GWZ Taut schema addition the contract needs;
- the `convert.rs` mapping change the contract needs.

Both are implemented later, with the contract's implementation. No implementation starts before the corrected tuple reaches GO.

No disposition changes the contract's architecture: frames over one channel, core owning calls and operations, one worker and one transport runtime per operation. The dispositions make stated rules implementable, move two process-global inputs into session state, and bound two things the contract left unbounded.

| **B2** — Consistency P2-2 | This is an API-shape defect, not a missing plumbing step. The fix passes the cancellation mechanism in before the action starts, instead of returning a handle after it has started. The session host creates a cancellation token for each operation when it admits it, before any worker exists, and passes the token to the worker. The shared dispatch's transport entry, a session variant of `with_local_transport`, takes that token as an input. Core's transport API gains a request constructor that takes the caller's token: when the request registers, it attaches its cancellation to the token. If the token is already cancelled, registration fails with `Cancelled` and the handler never runs. Otherwise, cancelling the token cancels the request. The token is the only cancellation authority. Nothing on the session path returns a handle upward, and no rule is needed to apply a cancel recorded before a handle arrives. The existing `TransportRequest::cancellation_handle()` stays for the legacy path only. The worker also passes the token to the handler's context, so handlers can check it at safe points later without another API change. On the protocol side, `operation.cancel` accepts the `call_id` of any call, unary or submit, because the client chooses that handle before sending. `operation_id` remains accepted as well. List the core transport-API change in §5.2 and §16. | Core test 1: an operation blocked opening a stream to a latch-held endpoint is cancelled through its token. The cancel returns within the admission deadline with a cleanup report, and the handler's I/O fails with `Cancelled`. Core test 2: the token is cancelled while the runtime is being built. | **B4** — Consistency P2-4 | Adopt the proposals' close bound, and make detached workers harmless by construction rather than by rule. **The gate:** each worker reaches its session's state and resources only through an operation gate, a proxy the session host creates at admission together with the operation's cancellation token (B2). Events, the terminal report, member locks, transport runtimes and log registrations are all reachable only through the gate. **Cancellation:** once the token is cancelled, the gate refuses new effectful requests (a member lock, a transport open, a log registration) with `Cancelled`. ## Principles applied throughout

**Handles are created before the action.** B2's defect is a shape, and the revision applies the same rule wherever the contract hands out something the caller needs for control. The party that will use a handle creates it before the action starts and passes it in. Downstream work attaches to it; no API on the session path returns a control handle after the action has begun. The revision states this as ownership rule O7 and applies it in these places:

- **Cancellation:** the session host creates the token at admission (B2).
- **Call identity:** the client chooses each `call_id` before sending, and every control message (`operation.cancel`) may use it, so a client never waits for a returned `operation_id` before it can cancel.
- **Reply delivery:** the bridge creates and registers each call's waiter under its `call_id` before calling `send`, so a fast reply can never arrive for a waiter that does not exist yet.
- **Workers:** the session host creates the operation record, including its token, before it replies `accepted` and before it starts the worker. The worker receives everything it needs as arguments.

**Resources are reached through a gate.** A worker never holds session state or session resources directly. Its gate knows the operation's cancellation token and the session's lifetime. After cancellation, effectful requests through it fail with `Cancelled`. After revocation, reports through it are ignored as well (B4). The revision states this as ownership rule O8.

**Context, not globals.** Everything session-relevant travels in the session context created at `open` and reached through the gate (B5). No module on the session path reads the environment or process-global mutable state, and `check_process_globals.py` keeps it that way: a new static, thread-local or ambient read fails the gwz-core and gwz-py test runs. The revision states this as ownership rule O9.

## Nonblocking findings folded into the same patch

| Finding | Disposition |
| --- | --- |
| Consistency P3-9, Safety P3-1 — queue capacities and control calls | **Queue capacities:** each in-process queue holds the outstanding-call limit plus a 64-frame control reserve. `operation.cancel` and `session.close` use the reserve and are never refused for the outstanding-call limit. **Full queue:** `send` on a full queue raises `transport_session_full`; it never blocks or drops. **Bridge bound:** the bridge bounds outstanding calls per session with a thread-safe counter, and a call that must wait does so on its own event loop. **Sizes:** every read has a byte limit, 1 MiB by default, and no frame may exceed 64 MiB. |
| Consistency P3-11, Safety P3-4 — `diff.output` and `log.output` logs | The logs a session's direct calls create belong to that session and live in its context (B5). At most 64 are open at once; the next open is refused before any effect. They are released, and their spools deleted, when the session ends. Other sessions cannot read them and get `operation_not_found`. |
| Consistency P3-1 — the supersession list | Rewrite §14 so it names each superseded clause exactly and lists what survives. **Superseded:** the Python transport design's single long-lived runtime and its ban on calling `with_local_transport` per operation; the single-active-operation refusal and the Python network lock; §4's same-generation capability clause, since capability checks become ordinary calls; §4's cancel error codes; §5's physical-session-reuse test. **Surviving:** environment stability (kept by B5), the file-identity preflight, the `TransportCleanup` shape, `max_retries`, gh-only HTTPS and sanitisation. Name the gwz-py design's native bridge ABI statements too. |
| Consistency P3-2 — the event-log rule | Adopt GWZDesign's rule unchanged. Each operation keeps a ring of at most 4096 events, set in §1. On overflow, older incremental events are dropped and a reset event is kept, followed by later events. The final `OperationResult` is kept separately. Remove the byte limit and the "terminal event never dropped" wording. Note that the current `OperationRuntime`'s clear-all overflow must meet this rule when it is reused. |
| Consistency P3-3 — close step 1 and repeated close | Step 1 refuses every later call other than `session.close`. After the channel has closed, the bridge's `close()` returns its retained report. |
| Consistency P3-4 — how terminals appear in `OperationResult` | A `Cancelled` terminal has `aggregate_status = failed` and `errors[0] = GwzError{code: cancelled}`. If the handler failed for its own reason after the cancel was signalled, that error follows as the second entry. This also covers Safety's residual risk that a real cause could be masked. Member rows are the planned rows, marked skipped; a record that never planned has none. A `Failed (InternalError)` terminal has `aggregate_status = failed` and `errors[0] = GwzError{code: internal_error}`. |
| Consistency P3-5 — log-read call bodies | Read calls carry taut-shape's `LogReadRequest` and `LogReadResponse`. The log handle is the method's scalar parameter (an operation ID or log ID); `diff.output` also keeps its stream ID, as today. Ending a stream uses taut-shape's end-stream message. GWZ-specific messages are added only where taut-shape has none: `operation.result`, `operation.response`, `operation.cancel`, `operation.release` and `session.close`. |
| Consistency P3-7 — CLI progress | The CLI uses submit plus event reads whenever its renderer consumes events, which includes JSONL and the progress line in human mode on a terminal. Otherwise it uses a unary call. |
| Consistency P3-8 — scope of the requirements MUST | Rewrite it: "gwz-cli and gwz-py MUST reach core's operations only through the session protocol's frames; direct in-process embedding of the library remains supported (REQ-010, REQ-011)." |
| Consistency P3-10 — the two-bridge run | Scope the twice-run suite to Client-level and native-integration tests. Bridge-internal tests are rewritten against a fake channel. The plan lists the assertions that change, such as a foreign cancel now reporting `operation_not_found`. |
| Consistency P3-12 — `request_id` uniqueness | Keep the proposals' rule. A second live operation with the same `request_id` in one session is refused with `invalid_request` before any effect. |
| Consistency P3-13 — 1.1.0 plan S6.3 | Add S6.3 to §14. Its test becomes "two overlapping Python operations complete independently on one Client, each on its own runtime". The plan text is amended when the contract is accepted. |
| Safety P3-2 — a panic in finish during unwinding | The worker catches the handler's panic first. It then runs finish and shutdown under their own `catch_unwind`, as today's extension does, and reports `Failed (InternalError)` with unconfirmed cleanup. The session's transport entry never finishes from `Drop` while unwinding. |
| Safety P3-3 — ordinary builds | State the degraded behaviour. Without the transport, cancelling a running network operation waits for it to finish, because libgit2's own transfers cannot be cancelled. Close waits up to the close bound. `transport_capabilities` reports whether cancellation is supported, so the bridge promises no promptness it cannot deliver. |
| Safety P3-5 — the pump at interpreter exit | The bridge registers a finalizer that closes the channel and joins the pump before interpreter finalization, waiting at most the close bound. `close()` joins the pump too. Exiting with an open session therefore waits up to the close bound for running operations, which keeps most of today's behaviour of joining worker threads at exit. |
| Residual risks adopted from both axes | **Direct calls:** they run on their own pool of 8 workers, which does not count against the running limit. `status` and the capability check then never wait behind eight long operations; both axes raised this. **Member lock:** it uses a blocking lock manager that recovers from poisoning, so one panic cannot fail later operations. **Root resolution:** workspace roots are resolved on the host's admission thread, never on the channel thread. **Shared dispatch:** it also absorbs gwz-cli's diff, log and hook paths. **Test host binary:** it is a development-only target, not a published binary. **Document updates:** MessageCatalog, ErrorCatalog, Protocol, Reference, the CLI's MachineOutput and gwz-py's release notes are updated at implementation. |
