The [Consistency](GwzCoreSessionDesign-ReviewConsistency.md) and [Safety](GwzCoreSessionDesign-ReviewSafety.md) reports are filed verbatim.

This plan is one consolidated correction across the contract, the paired core paragraphs and the gwz-py pointers. It is not a series of per-finding patches. It also specifies:
- the GWZ Taut schema addition the contract needs;
- the `convert.rs` mapping change the contract needs.

Both are implemented later, with the contract's implementation. No implementation starts before the corrected tuple reaches GO.

No disposition changes the contract's architecture: frames over one channel, core owning calls and operations, one worker and one transport runtime per operation. The dispositions make stated rules implementable, move two process-global inputs into session state, and bound two things the contract left unbounded.

## Blocking findings

| Finding | Disposition | Closure evidence required |
| --- | --- | --- |
| **B1** — Consistency P2-1, Safety P2-1 | Append `transport_session_full` (75) and `operation_expired` (76) to `GwzErrorCode`, after `transport_record_limit` (74). Change `protocol/convert.rs` so the model's `Cancelled`, `TransportSessionFull` and `OperationExpired` map to `cancelled` (73) and the two new members instead of `io_error`. The session host never produces `TransportCapacityConflict`, since each operation has its own runtime, so its mapping stays. Rewrite §4.2 and §13 to say "two codes appended, none redefined". State that the bridge's "already finished" rule for a cancel that races its unary reply keys on `operation_expired`. | A `SessionError` carrying each code the contract names survives a round trip through the Rust and Python projections as the same member. A queue-full refusal reads `transport_session_full` on both bridges. A queued operation cancelled by close reads `errors[0].code == cancelled`. A cancel racing its unary reply raises nothing. |
| **B2** — Consistency P2-2 | The shared dispatch's transport entry becomes a session variant of `with_local_transport`. It builds the operation's runtime from the session's captured configuration (B5) and registers the request. Before running the handler, it hands the request's `cancellation_handle()` to the session host, which stores it on the operation. A cancel recorded before that point is applied as soon as the handle arrives. After construction and before the handler starts, the worker checks for a recorded cancel and settles `Cancelled`, with no Git work run. List this core change in §5.2 and §16, beside the member-lock change. | Core test 1: an operation blocked opening a stream to a latch-held endpoint is cancelled. The cancel returns within the admission deadline with a cleanup report, and the handler's I/O fails with `Cancelled`. Core test 2: a cancel that arrives while the runtime is being built is applied when the handle registers, and no handler runs. |
| **B3** — Consistency P2-3 | Define the error frame as `SessionError { call_id, error: GwzError, response_meta: ResponseMeta (optional) }`. `GwzError` is the existing Taut message: code, message, member ID, member path, detail, target kind and record context. Map it onto `GwzBridgeError` exactly as today's native error does, with `machine_message` taken from `GwzError.message` and `response_meta` from `ResponseMeta`. | A member-scoped model error and a merge-record error, raised through `NativeCoreBridge` and through `StreamCoreBridge`, carry `member_id`, `target_kind`, `record_context` and `response_meta.request_id` equal to today's in-process values. |
| **B4** — Consistency P2-4 | Adopt the proposals' bound. Add `close_wait` to §1's limits: default 60 seconds, set at `open`. After signalling cancellation, close waits for workers up to `close_wait`. It then answers every outstanding call and replies to the close. The report's `pending_local_work` counts unfinished workers, and `peer_cleanup_confirmed` is false when any remain. Unfinished workers are detached: they cannot be stopped in-process, their later terminals are discarded, and a report with `pending_local_work` above zero tells the client that work may still be running. Align the GWZRequirements amendment: "MUST cancel its operations and wait for their workers up to the close bound, reporting any that remain". | A handler blocked on a test latch: `session.close()` answers within the bound, with `pending_local_work == 1` and unconfirmed cleanup. Releasing the latch later does not change session state. Repeated close returns the same report. The byte-stream host closes its channel. |
| **B5** — Safety P2-2 and P2-6; Consistency P3-6 and P3-1(b) | `open(options)` captures the endpoint configuration once, on the calling thread: `SshEndpointConfig` and `HttpsEndpointConfig` from the environment at that moment. The session keeps it and builds every per-operation runtime from clones, so no core thread reads the environment. `configure_transport_runtime` changes the session's captured timeouts for operations admitted after its reply, and never touches another session. In ordinary builds without the transport, the timeout remains libgit2's process-wide setting, exactly as today, and §4.2 says so. The Python transport design's environment-stability clause is therefore kept, not superseded. | Two sessions in one process: A sets a zero timeout, and B's next operation still uses B's own deadline. A later call by A is not refused. After `open`, changing `HOME`, `SSH_AUTH_SOCK` or `GIT_SSL_CAINFO` leaves a later operation's endpoint configuration equal to the one captured at open. |
| **B6** — Safety P2-3 | Refine class N: at most one push per workspace runs at a time within a session, because push takes the cross-process workspace mutator lock. Fetches, and one push, run together. Push and fetch member steps both take the session's member lock. A later push on the same workspace waits in the queue. Document the mutator lock as a try-lock, so "already held" can come only from another process or another session. | Two pushes on one workspace in one session complete one after the other, with no `UnsupportedOperation`. Fetch and push run concurrently, and so do two fetches. |
| **B7** — Safety P2-4 | Make retention coherent with admission. One operation table per session holds live operations and terminal submitted records, with 128 entries by default: at least 8 running plus 64 queued. When a new admission needs an entry, the host may evict only a terminal record whose result has already been delivered once, oldest first. If none can be evicted, the request is refused with `transport_session_full` before any effect. Live and unread records are never evicted. | 72 submitted operations run and complete, and every result is still readable. With the table full of unread terminal records, a new request is refused before any effect. After results are read or released, admission resumes. |
| **B8** — Safety P2-5 | A frame that reuses an outstanding `call_id` is a protocol error and ends the session (§3). No reply is attributed to the reused ID. | A stream-bridge test sends a duplicate outstanding ID. The session ends, and the original call fails with the closed-session error, never `InvalidRequest`. |
| **B9** — Safety P2-7 | The pump never exits silently. Any exception in its loop closes the channel, marks the bridge closed and fails every outstanding call with the typed closed-session error, after which `send` fails. A frame whose tag or CBOR does not decode is treated the same way. A reply payload that does not decode as its call's expected response fails only that call, with a protocol error. A reply for a call whose event loop has closed is dropped, and the pump continues. | A test host injects an undecodable frame: every outstanding call fails with the closed-session error, and later sends fail. A test host injects one undecodable response payload: only that call fails. |

## Nonblocking findings folded into the same patch

| Finding | Disposition |
| --- | --- |
| Consistency P3-9, Safety P3-1 — queue capacities and control calls | **Queue capacities:** each in-process queue holds the outstanding-call limit plus a 64-frame control reserve. `operation.cancel` and `session.close` use the reserve and are never refused for the outstanding-call limit. **Full queue:** `send` on a full queue raises `transport_session_full`; it never blocks or drops. **Bridge bound:** the bridge bounds outstanding calls per session with a thread-safe counter, and a call that must wait does so on its own event loop. **Sizes:** every read has a byte limit, 1 MiB by default, and no frame may exceed 64 MiB. |
| Consistency P3-11, Safety P3-4 — `diff.output` and `log.output` logs | The logs a session's direct calls create belong to that session. At most 64 are open at once; the next open is refused before any effect. They are released, and their spools deleted, when the session ends. Other sessions cannot read them and get `operation_not_found`. |
| Consistency P3-1 — the supersession list | Rewrite §14 so it names each superseded clause exactly and lists what survives. **Superseded:** the Python transport design's single long-lived runtime and its ban on calling `with_local_transport` per operation; the single-active-operation refusal and the Python network lock; §4's same-generation capability clause, since capability checks become ordinary calls; §4's cancel error codes; §5's physical-session-reuse test. **Surviving:** environment stability (kept by B5), the file-identity preflight, the `TransportCleanup` shape, `max_retries`, gh-only HTTPS and sanitisation. Name the gwz-py design's native bridge ABI statements too. |
| Consistency P3-2 — the event-log rule | Adopt GWZDesign's rule unchanged. Each operation keeps a ring of at most 4096 events, set in §1. On overflow, older incremental events are dropped and a reset event is kept, followed by later events. The final `OperationResult` is kept separately. Remove the byte limit and the "terminal event never dropped" wording. Note that the current `OperationRuntime`'s clear-all overflow must meet this rule when it is reused. |
| Consistency P3-3 — close step 1 and repeated close | Step 1 refuses every later call other than `session.close`. After the channel has closed, the bridge's `close()` returns its retained report. |
| Consistency P3-4 — how terminals appear in `OperationResult` | A `Cancelled` terminal has `aggregate_status = failed` and `errors[0] = GwzError{code: cancelled}`. If the handler failed for its own reason after the cancel was signalled, that error follows as the second entry. This also covers Safety's residual risk that a real cause could be masked. Member rows are the planned rows, marked skipped; a record that never planned has none. A `Failed (InternalError)` terminal has `aggregate_status = failed` and `errors[0] = GwzError{code: internal_error}`. |
| Consistency P3-5 — log-read call bodies | Read calls carry taut-shape's `LogReadRequest` and `LogReadResponse`. The log handle is the method's scalar parameter (an operation ID or log ID); `diff.output` also keeps its stream ID, as today. Ending a stream uses taut-shape's end-stream message. GWZ-specific messages are added only where taut-shape has none: `operation.result`, `operation.response`, `operation.cancel`, `operation.release` and `session.close`. |
| Consistency P3-7 — CLI progress | The CLI uses submit plus event reads whenever its renderer consumes events, which includes JSONL and the progress line in human mode on a terminal. Otherwise it uses a unary call. |
| Consistency P3-8 — scope of the requirements MUST | Rewrite it: "gwz-cli and gwz-py MUST reach core's operations only through the session protocol's frames; direct in-process embedding of the library remains supported (REQ-010, REQ-011)." |
| Consistency P3-10 — the two-bridge run | Scope the twice-run suite to Client-level and native-integration tests. Bridge-internal tests are rewritten against a fake channel. The plan lists the assertions that change, such as a foreign cancel now reporting `operation_not_found`. |
| Consistency P3-12 — `request_id` uniqueness | Keep the proposals' rule. A second live operation with the same `request_id` in one session is refused with `invalid_request` before any effect. |
| Consistency P3-13 — 1.1.0 plan S6.3 | Add S6.3 to §14. Its test becomes "two overlapping Python operations complete independently on one Client, each on its own runtime". The plan text is amended when the contract is accepted. |
| Safety P3-2 — a panic in finish during unwinding | The worker catches the handler's panic first. It then runs finish and shutdown under their own `catch_unwind`, as today's extension does, and reports `Failed (InternalError)` with unconfirmed cleanup. The session's transport entry never finishes from `Drop` while unwinding. |
| Safety P3-3 — ordinary builds | State the degraded behaviour. Without the transport, cancelling a running network operation waits for it to finish, because libgit2's own transfers cannot be cancelled. Close waits up to the close bound. `transport_capabilities` reports whether cancellation is supported, so the bridge promises no promptness it cannot deliver. |
| Safety P3-5 — the pump at interpreter exit | The bridge registers a finalizer that closes the channel and joins the pump before interpreter finalization, waiting at most the close bound. `close()` joins the pump too. Exiting with an open session therefore waits up to the close bound for running operations, which keeps most of today's behaviour of joining worker threads at exit. |
| Residual risks adopted from both axes | **Direct calls:** they run on their own pool of 8 workers, which does not count against the running limit. `status` and the capability check then never wait behind eight long operations; both axes raised this. **Member lock:** it uses a blocking lock manager that recovers from poisoning, so one panic cannot fail later operations. **Root resolution:** workspace roots are resolved on the host's admission thread, never on the channel thread. **Shared dispatch:** it also absorbs gwz-cli's diff, log and hook paths. **Test host binary:** it is a development-only target, not a published binary. **Document updates:** MessageCatalog, ErrorCatalog, Protocol, Reference, the CLI's MachineOutput and gwz-py's release notes are updated at implementation. |
