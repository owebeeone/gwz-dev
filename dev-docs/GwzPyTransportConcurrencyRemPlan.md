# Python transport concurrency — remediation plan and draft design amendment

Date: 2026-09-23. Status: **REJECTED at the first design review; implementation and gwz-py Phase 6/7 remain NO-GO**. This is the preserved first draft addressing [P2-1](GwzPyTransportConcurrencyNoGo.md), not implementation authority. The independent [Consistency](GwzPyTransportConcurrency-ReviewConsistency.md) and [Safety](GwzPyTransportConcurrency-ReviewSafety.md) NO-GO reports and the [merged remediation](GwzPyTransportConcurrency-RemPlan-1.md) require a broader correction before re-review. The [Surface report](GwzPyTransportConcurrency-ReviewSurface.md) also says NO-GO but disclosed a docs-only method deviation.

## 1. Outcome and authority

One Python `Client` may have multiple top-level network operations in flight through its one long-lived native `TransportSession` and one core `TransportRuntime`. Each operation owns a distinct `TransportRequest`, backend, cancellation handle, result and cleanup completion. Fetch A need not finish before fetch B or push B starts. A network operation may itself process member repositories concurrently under its own `jobs` and per-host limits. The same physical SSH connection still has only one active exchange; concurrency uses separate pool leases.

Keep the existing Python `Client` and bridge call/submit/stream APIs, existing Taut request and response shapes, core host ownership, local-only isolation, endpoint credential locality, gh-only HTTPS, idle reaping and retry clocks. There is no Python pool, second transport host, new wire message or physical carrier. Distinct Python clients/processes have distinct hosts and physical pools.

This draft supersedes only `gwz-py/dev-docs/GwzPyTransportDesign.md` §2's requirement to finish before admitting the next network operation, its singular `ReadyActive`/active-request wording and singular close wording, and §3's blanket overlap refusal and Python network-lock serialization. It also replaces §4's "latest completed cancellation" rule only where that rule assumes there can be just one live operation. Its other accepted requirements remain. It adds explicit overlap evidence to `gwz-core/dev-docs/GwzV110Plan.md` Phase 6 S6.3. It preserves `gwz-core/dev-docs/GwzRemoteTransportRetryPlan.md` §3 item 7: a request cannot *raise or change* physical capacity under a non-idle lease. Identical-capacity admission is not a capacity change.

## 2. Admission and capacity contract

The native session has one monotonic host lifecycle and a bounded map of live operations keyed by unique operation/request ID, rather than singular `admitting` and `active` slots. The installed capacity's `max_requests` bounds the number of reserved plus admitted live IDs; reaching it refuses the new ID with `Capacity`. Before the first capacity is installed, one construction/admission leader establishes it while later admissions wait for that transition or close, not for the leader's Git work. A short lock reserves each ID and orders construction, admission and close; it is not held through blocking Git work, network I/O, `finish()` or Python callbacks. An ID cannot be admitted twice, even via another Python thread. The session refuses new work after Closing begins. Existing local-only calls retain their close behavior and never construct or depend on the endpoint.

At admission, core resolves the operation's physical `pool::Capacity` from `jobs` and `max_connections_per_host` as the accepted retry plan specifies. The first request installs it before remote Open. Another request on the **same endpoint placement** may start while leases are non-idle if its resolved physical capacity is exactly the installed capacity: core must validate and reuse the installed value atomically, without resetting the pool or the idle timer. `max_retries` and other operation-local options need not match; they remain scoped to their own request. Per-operation `jobs`/per-host fan-out still applies independently, while the shared physical caps bound their combined leases and queue allocation fairly.

If a live request needs a different physical capacity, refuse that *new request* with a typed non-retriable `Capacity` error before its handler, remote Open, credential/helper access or pool mutation. The existing requests continue unchanged. The caller may retry after the conflicting work finishes; this draft does not add an implicit potentially unbounded wait or silently clamp the caller's explicit value. When all requests and their physical cleanup have retired, a later request may install new capacity under the existing bounded cleanup rule. Different placements use their respective endpoint/session capacity owner; an unbound explicit `cli` still refuses before mutation. No code may mistake a successful registration or an accepted `submit` for completed capacity admission.

The current `gwz-core/src/transport_host/session.rs::install_capacity` rejects a live peer even when the installed capacity matches and a lease is non-idle. The implementation must change that specific guard, preserve the no-resize-under-load rule, and remove the new request's registration on any failed admission. A focused core test must start two same-capacity requests with a held live lease and show both admitted, then show a differing-capacity third refused without changing pool counts/capacity or either existing request. It must also cover retirement followed by a successful capacity change.

## 3. Per-operation lifecycle and Python bridge

Remove the cross-operation `asyncio` network lock. Python may submit or call multiple network operations on one bridge, including from different tasks and threads. Reserve and bind each request ID to its native operation before publishing `Accepted`; its worker retains the session and scoped backend until Git work, `TransportRequest.finish()` and result recording complete. A queued task that has not reserved an ID can be cancelled without touching any admitted operation. Event consumers and result readers for different operation IDs remain independent. Dropping one async generator does not close another operation or the host. The GIL stays detached around blocking native work.

`cancel_operation(id)` targets exactly the matching live operation, waits for its `finish()` and returns that operation's `TransportCleanup`. A second cancellation of that same live operation joins its completion. An unknown, foreign, expired or different operation ID refuses without cancelling any peer. Retain only a bounded completed-cancellation record for idempotent repeat (at most the existing latest completed ID); all other completed IDs expire. No result/event registry is replaced with an unbounded cancellation map.

`close()` atomically enters Closing, refuses later calls, cancels **all** admitting and active network operations, joins their bounded completion, then shuts the single runtime down once. Concurrent close calls join the same completion and return the same retained report. A constructor that loses to close never publishes a runtime. The final report must include genuinely pending local work once per physical owner; it must not sum duplicate per-request and host snapshots. Closing one client does not affect another client's host. Last-owner drop still initiates cleanup, while awaited close remains the inspectable path.

## 4. Implementation and closure gates

1. Obtain Consistency, Safety and Python Surface GO on this document as the bounded design amendment. Then annotate the accepted Python design with the supersession and NO-GO status before implementation acceptance. The plan review does not self-close P2-1.
2. Change core's compatible-capacity admission guard and the native Python session/bridge together. Preserve the candidate switch until Phase 7 activation. No new Python-visible pool API. Use explicit `cfg_if` boundaries for modified conditional Rust sections.
3. Make the existing actual-extension fixture run two same-client network operations whose Git work overlaps against disposable SSH and HTTPS endpoints. Assert request IDs, simultaneous liveness, physical pool caps/reuse, no cross-cancellation and successful results. Cover `call` and early-returning `submit`/stream APIs, different Python tasks and threads, two independent clients, and any installed in-process `cli` placement claimed by S6.3. A fixture that merely launches tasks sequentially does not close this finding.
4. Fault cases: incompatible capacity refuses without touching active peers or credentials; the same request succeeds after retirement; cancellation of A leaves B running; close during two admissions and two active requests drains each exactly once; repeated close returns the retained snapshot; wrong/expired IDs refuse; local-only commands remain independent; no secret reaches Python-visible errors. Include deterministic barriers so a missed overlap cannot pass by scheduling accident.
5. Run focused core/native Python checks, then the normal supported-platform and selected-source gates already required by v1.1.0. A settled Code/State review must verify the implementation and original P2-1 counterexample before the NO-GO can be lifted. Phase 7 activation, registry wheel proof, tags and publication remain separate later gates.

No new public switch or wire field is planned. If implementation needs to change an accepted transport capacity rule, add a bounded amendment and re-review before doing so rather than treating this plan as blanket authority.
