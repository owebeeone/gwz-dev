## 1. Findings (one subsection per finding, severity-ordered)

### [P1-1] The lock and log files the host creates in a directory a sandboxed same-user process can write have no no-follow, file-type or append rule, so a planted symbolic link turns the unsandboxed server into a writer of any user-writable file

- **Location:** §6 "Defaults" table, `--log` row (line 473) and "`--log PATH` is parsed and walked as an address is (§3), without the length limit" (line 476); §6 "Starting in the background", "with standard streams redirected to the log" (line 484); §4 "One server per address" (lines 252–256); §11 rows "Per-user directory", "`--log PATH`" and "One server per address" (lines 669–670, 676); §17 "Files" (line 1103).
- **Violated invariant:** §4, "A process inside a sandbox must not gain its user's full authority through the server", on the design's own premise (amendment §2 item 4, restated in §14 line 855) that a same-user sandboxed process can write the per-user directory. Also §4's stale-socket sentence's spirit, "a mistyped address can never delete a file".
- **Why it fails:** The walk of §3 reads links along the path but nothing states how the final entry is opened. The socket gets a rule (lstat-style "is a socket the user owns, not a link"; `bind` refuses an existing entry). The lock file and the log file get none: no `O_NOFOLLOW`, no regular-file check, no owner or mode check, no statement that the log is appended rather than truncated. `open(2)` of a path whose last component is a symbolic link follows it.
- **Sequence:** (1) The user runs with `GWZ_SERVER=auto`; a server starts and, after 10 idle minutes, exits (§6 default). The lock file stays by design (line 255) and nothing removes the log. (2) A same-user sandboxed process (macOS `sandbox-exec` with `$TMPDIR` writable, or a Linux seccomp-only sandbox) lists the 0700 directory (same uid), removes `server-<key>.log` and plants a symbolic link of that name to `~/.ssh/config`, `~/.gitconfig` or `~/.ssh/authorized_keys`. (3) The user's next command auto-starts a server; the starting CLI or its copy opens `server-<key>.log` for the redirected streams and writes `gwz server: listening at …`. With truncation the target is destroyed; with append the target is corrupted (`ssh` refuses a config with a bad line; `git` refuses a bad config line). The same holds for `server-<key>.lock` if the lock is ever written, and for a FIFO planted at either name (an `O_RDONLY` open blocks the start forever). The attacker never passes the peer check; it needs only the write access the design already assumes it has.
- **Impact:** Data loss or corruption of user-owned files outside the sandbox, or a wedged auto-start, from inside a sandbox — the class §4 exists to exclude. Windows is not affected in the default layout (`%LOCALAPPDATA%` is medium-integrity; low-integrity and AppContainer tokens cannot write it), but an explicit `--log PATH` on Windows has the same gap for reparse points.
- **Required correction:** State, in §4 or §6 and in §11's rows, that every file the host creates in the per-user directory or at `--log PATH` — the lock, the log, and the socket's stale check and removal — is opened relative to the walked directory descriptor with `O_NOFOLLOW | O_CLOEXEC` (`O_NONBLOCK` during the open, cleared after), that an existing entry is accepted only if it is a regular file owned by the user with no group or other bits, that the file is created 0600, that the log is only ever appended (`O_APPEND`, never `O_TRUNC`), and that an entry failing these checks is reported and never followed, truncated or written; on Windows, open with `FILE_FLAG_OPEN_REPARSE_POINT` and refuse a reparse point, and apply the owner check. The stale-socket check and removal use `fstatat(AT_SYMLINK_NOFOLLOW)`/`unlinkat` on the same descriptor. Add the rows to §12's socket-host list.
- **Closure/regression test:** In gwz-core's socket-host tests on Linux and macOS: with a symbolic link, and separately a FIFO, planted at `server-<key>.log` and at `server-<key>.lock` before `server --start`, the start refuses (or replaces the entry it owns with a fresh 0600 regular file) within a bound, and the link's target has the same size and hash afterwards; the same with `--log PATH` naming a link. On Windows: a junction and a symbolic link at the log path are refused.

### [P2-1] On Linux the relative sandbox rule makes two sibling sandboxes of one user indistinguishable, so a sandboxed caller's snapshot can reach, and a sandboxed server can serve, another sandbox

- **Location:** §4 "The sandbox rule", Linux bullet (line 228) and "A server that a sandboxed caller starts inherits the caller's namespaces and filters, so it serves callers inside that sandbox only" (line 238); §4 "Sandboxed callers", "On Linux the rule is relative, so it needs a peer" (line 249); §7 "On Linux, the server it starts would inherit the sandbox and serve only that sandbox" (line 537); §14 "A sandboxed process can hold an `auto` address … Clients refuse it and send nothing" (line 855) and "The Linux rule compares seccomp filter counts, not the filters" (line 853).
- **Violated invariant:** §4's headline rule ("only the same user, on the same machine, from outside any sandbox, may open a session; and a client sends nothing until it has verified the same of the listener") as the design itself narrows it for Linux to "the same sandbox"; and the explicit claims quoted above.
- **Why it fails:** The rule's only inputs are the mount namespace, the user namespace and the count of seccomp filters. Two sandboxes that differ only in their seccomp policy, or only in Landlock rules, and share the user's mount and user namespaces (the shape of a seccomp-only tool sandbox, of a systemd service with `SystemCallFilter=`, and of any harness that filters syscalls without unsharing) present equal counts and equal namespaces to each other. Nothing else distinguishes them.
- **Sequence:** (1) Sandbox A (one filter, shared namespaces) runs a `gwz` client with `GWZ_SERVER=auto` and `GH_TOKEN` in its environment. (2) A same-user process in sandbox B (one filter, same namespaces, writable `$TMPDIR`/`$XDG_RUNTIME_DIR`) binds `server-<key>` after an idle exit. (3) A's client walks, connects, verifies: same uid, B's process has one filter, not more than A's, same namespaces — verification passes. A sends `SessionOpen` with its snapshot into B. (4) The reverse: A's auto-started server accepts B's client (one filter, same namespaces) and runs B's commands with A's file authority, which Landlock or a path policy may have made wider than B's. The client-side claim "Clients refuse it and send nothing" and the server-side claim "serves callers inside that sandbox only" are both false in this interleaving.
- **Impact:** Secret disclosure and authority crossing between two sandboxes of one user, exactly the exposure amendment §2 item 4 rated worth listener verification, now for sandboxed callers on the platform the design deliberately opened to them. Not P0: it needs a hostile same-user sandbox, a caller that opted in, and a shared per-user directory.
- **Required correction:** Either (a) a rule that is sound for this case (for example: a process under one or more seccomp filters that is not in a mount namespace of its own refuses every socket server, so that only containers and namespace sandboxes keep the relative rule), or (b) withdraw the three claims, state in §4 and §14 that on Linux "the same sandbox" means the same mount and user namespaces and an equal filter count, that sibling sandboxes differing only in seccomp or Landlock policy are one sandbox to this rule, and that a harness running several such sandboxes for one user must give each its own `XDG_RUNTIME_DIR` or `TMPDIR` or set `--no-server`; S7.2's migration notes carry the same sentence. Either way, §12 gains a row with two seccomp-only sandboxes of equal count in one namespace and states the outcome the rule gives.
- **Closure/regression test:** In gwz-core's socket-host and listener-verification tests on Linux: a listener under one added filter in the caller's namespaces, and a caller under one added filter of a different policy; the row asserts the chosen outcome (refusal under (a); documented acceptance under (b), with the migration note present) and, under (a), that a client in a container with a filter still reaches a server in the same container.

### [P2-2] No bound on the socket handshake: a wedged server hangs every client, including `server --stop` and `server --status`, with no diagnostic

- **Location:** §3 "The socket channel parses, walks, connects, verifies the listener (§4), sends `SessionOpen` and waits for `SessionOpened`" (line 189); §6 `server --stop` and `server --status` rows (lines 459–460), which open a session; §17 `server_unavailable` (line 1125), whose only handshake bound is the SSH form's 30 seconds; §16 question 7 (lines 1030, 1044), where the bound is stated for `ssh` only; §6 "Crash" (line 521), which covers a closed channel but not a silent one.
- **Violated invariant:** §6 "A stuck client stalls no other client" has no counterpart for a stuck server; §10 "Failure scope" discloses that a crash affects every client but not that a hang does; a hang is a defect on this axis.
- **Why it fails:** Listener verification is answered entirely by the kernel (credentials, process descriptor, `/proc`), so a live but wedged gwz server — accept thread alive, sessions blocked in `open` (for example on a hung file read during the files-read-once check, or any deadlock) — passes verification. The client then waits for `SessionOpened` with no timer. Under `auto` that is every gwz command for the user; `server --stop` and `--status` open a session too, so the documented remedy hangs as well. Ctrl-C ends the command but names nothing; the pid is recoverable only from the log file.
- **Impact:** A stuck state reachable under the text's own rules, in which the one recovery path the design offers (`server --stop`) is itself stuck, and the user has no message naming the process to kill.
- **Required correction:** State a bound on the wait for `SessionOpened` over a socket (the SSH form's 30 seconds is a reasonable default; `--status` and `--stop` may use a shorter one), after which the client disconnects and fails with `server_unavailable` naming the listener's process ID, which it already holds from `SO_PEERCRED`/`GetNamedPipeServerProcessId`, and the lock and log file paths. Since `SessionOpen` has by then crossed only to a verified same-user unsandboxed process, the bound adds no disclosure. Add the message form to §17 and the rows to §12.
- **Closure/regression test:** A socket-host double that accepts, passes the peer check and never answers: a client command, `server --status` and `server --stop` each fail within the bound with `server_unavailable` naming the double's pid; the client sends no second frame.

### [P2-3] The stale-socket rule deletes a live socket of another program at an explicit address, contradicting "a mistyped address can never delete a file"

- **Location:** §4 "One server per address", "if it gets the lock and a socket file already exists at the address, that file is stale. The host removes it before binding, but only when it is a socket the user owns. Any other file refuses the start, so a mistyped address can never delete a file" (line 254); §11 "Stale listener" row (line 677).
- **Violated invariant:** The quoted claim; and the irreversible step's precondition ("stale") is decided without evidence that can establish it for a socket gwz did not create.
- **Why it fails:** "The lock is free" proves only that no gwz server holds `<socket path>.lock`. A socket file at an explicit address that a different daemon of the same user is listening on (a keyring or gpg agent socket, a D-Bus session socket, another tool's control socket) has a free `.lock`, is a socket, and is owned by the user, so it is "stale" by the text and is unlinked. The daemon keeps running but is unreachable by that path until it is restarted.
- **Sequence:** `gwz server --start --server /run/user/1000/keyring/ssh` (or `GWZ_SERVER` set to such a path by a script, since `server --start` defaults its address to `GWZ_SERVER`, §6 line 463): the directory is user-owned 0700, the host takes `…/ssh.lock`, sees a user-owned socket, removes it, binds gwz there. New SSH clients of the user now fail to reach the agent. Under `auto` the directory holds only gwz sockets, so the case is confined to explicit addresses; the consequence is destructive and irreversible.
- **Impact:** Loss of another daemon's socket from a mistyped or scripted explicit address; a false safety claim.
- **Required correction:** Before removing an existing socket file the host connects to it: `ECONNREFUSED` (no listener) establishes that it is stale and it is removed; a connection that succeeds, or any other error, refuses the start with `server_unavailable` naming the address and, from the peer credentials, the listening process ID. The host sends no frame on that probe connection. Reword the sentence to "a mistyped address never deletes a file, and never a socket something still answers on". Also state that the `.lock` file is created only after the walk and directory checks pass, so a refused start leaves nothing beside a foreign socket, or accept and state the leftover.
- **Closure/regression test:** In gwz-core's socket-host tests: a test daemon listening on a user-owned socket at the explicit address: `server --start` refuses, the daemon's socket file survives and still answers; a socket file with no listener is removed and the start proceeds.

### [P3-1] The client's first frame carries the snapshot to any listener that passes OS identity checks, including a same-user foreign daemon at a mistyped explicit address, before anything shows it is a gwz server

- **Location:** §3 "Opening a session" and "The socket channel … sends `SessionOpen` and waits" (lines 148–189); §4 "Secrets … It crosses the socket once, in `SessionOpen`, and only after listener verification has passed" (line 262); §17 `server_unavailable`, "`<address> did not answer as a gwz server`" (line 1125).
- **Violated invariant:** Disclosure scale: the design's own error text presumes the client can tell a non-gwz listener apart, but that determination is made only after the secret-bearing frame has left.
- **Why it fails:** Listener verification establishes user, machine and sandbox, not program. A same-user unsandboxed daemon (a session bus, a notification or logging socket) at an explicit address the user or a script mistyped passes verification and receives the environment snapshot; whether it persists any of those bytes is that daemon's business.
- **Impact:** Bounded (same-user process, explicit addresses only, and the design's model already trusts such processes), but the secret leaves the process on a path the design believes it guards, and a version mismatch is likewise detected only after the snapshot crossed.
- **Required correction:** Add a secret-free step before `SessionOpen`: either the server sends its identity first on accept after its peer check (product, core, protocol range), or the client sends a `SessionHello` (tag appended, no environment) and waits for a `SessionWelcome`; `SessionOpen` follows only after a well-formed reply. This also gives P2-2's bound something to time and moves `server_version_mismatch` before the snapshot crosses. The schema change is append-only.
- **Closure/regression test:** A same-user listener that never speaks the protocol (an echo double and a silent one) at an explicit address receives zero environment bytes; a version-mismatched double receives none either.

### [P3-2] "It exits and says which process holds it" is not implementable with `flock`, and the lock-holder's identity is the recovery datum for a wedged server

- **Location:** §4 "One server per address", "If the lock is held, it exits and says which process holds it" (line 253); §11 "One server per address", "`flock` on the lock file" and "`LockFileEx`" (line 676).
- **Violated invariant:** Diagnosability of the stuck state in P2-2 and of a starter racing a running server: neither `flock(2)` nor `LockFileEx` reports the holder.
- **Required correction:** Either the holder writes its process ID into the lock file after taking the lock (truncating its own regular file, under P1-1's open rule), and a starter reads it, or the POSIX lock is an `fcntl` write lock whose `F_GETLK` returns the holder's pid; state the same for Windows (pid in the file). The message names the pid and the log path.
- **Closure/regression test:** A second `server --start` while a server runs exits 1 and prints the running server's pid; with a stale pid (holder gone, file present, lock free) the start proceeds.

### [P3-3] Shutdown releases the address last, so a client arriving during a drain is failed with "effect unknown" and, under `auto`, no replacement can start for up to 185 seconds

- **Location:** §6 "Shutdown" steps 1–5 (lines 498–505); `server --stop`'s bound "three close bounds plus 5 seconds" (line 459); §6 "Crash" and §17 `server_session_closed`, "the command's effect is unknown, and it was not retried" (lines 521, 1131); "The starting CLI waits up to 5 seconds" (line 486).
- **Violated invariant:** Degraded-path behaviour: a command that never reached `SessionOpened` has a known effect (none) and a safe retry, yet is reported as unknown; and "one server per address" holds the lock through a drain of up to 180 seconds that serves no one.
- **Sequence:** A server begins shutdown (idle exit or `--stop`) with a latched worker: step 1 stops accepting; a client's connect still lands in the backlog or is reset; the client either hangs (P2-2) or gets `server_session_closed` after sending `SessionOpen`; under `auto` its auto-start copy finds the lock held and exits, and the 5-second wait expires with `server_unavailable`. Every `auto` command fails until the drain ends.
- **Required correction:** State that a channel closure before `SessionOpened` is reported as `server_unavailable` (nothing was sent to core) and that under `auto` the client may then start a server once; and reorder shutdown so that the server closes its listening socket, removes the socket file and releases the lock (steps 1 and 5) before it drains sessions and instances, so a fresh server can bind while the old one drains. `server --stop`'s wait on the process handle is unchanged.
- **Closure/regression test:** gwz-cli lifecycle row: a client arriving during a drain with a latched worker gets a fresh server under `auto`, and `server_unavailable` (never `server_session_closed`) at an explicit address; the old process exits within its bound.

### [P3-4] The background copy inherits every descriptor above 2, so a caller's locks and pipes outlive the command for the server's life

- **Location:** §6 "Starting in the background", "with standard streams redirected to the log" (lines 483–487); §11 "Background start" row (line 678).
- **Violated invariant:** "Never worse than the status quo": today a gwz command releases everything at exit; an auto-started server holds inherited descriptors for 10 idle minutes by default, or indefinitely with `--start`.
- **Sequence:** A cron or CI script holds `exec 9>lock; flock 9` and runs `gwz --server auto fetch`; the copy inherits fd 9; the script ends but the lock stays held by the server until idle exit, so the next run blocks. A harness waiting for EOF on a pipe the script left open waits the same way.
- **Required correction:** State that the copy closes every descriptor above 2 before it serves (or the starter marks them close-on-exec, for example `close_range(3, ~0U, CLOSE_RANGE_CLOEXEC)`), and on Windows passes only the log handle through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`; the stdio child of §15 gets the same rule.
- **Closure/regression test:** A starter holding an `flock`ed descriptor and a pipe's write end: after `--start` returns, the lock is acquirable by another process and the pipe's reader sees EOF.

### [P3-5] At an explicit address the must-match rule is only as long as the server's list, so a newer client's values the older server never compares are silently the server's

- **Location:** §3 "Versions and identity" (lines 181–185); §14 "Mixed versions at an explicit address" (line 872), which considers only missing methods; §5 "The must-match set" (line 293).
- **Violated invariant:** §5, "The server's value must never silently replace the client's", on the mixed-version path the design itself names.
- **Sequence:** A 1.1.x server without a later release's added row (the design has grown the list twice within this revision) serves a newer client at an explicit address; the client cannot check, because the server's values are never sent and the list lives in the server. The newer client's `DYLD_INSERT_LIBRARIES` or `SSLKEYLOGFILE` difference is not refused; under `auto` the core version in the key prevents it.
- **Required correction:** At an explicit address, refuse a `SessionOpened.core` version and build different from the client's with `server_version_mismatch` (the design already treats the core version as identity under `auto`); or carry a digest of the must-match list's names in `SessionOpen` and refuse on difference.
- **Closure/regression test:** A client whose list is longer than a server double's is refused at open.

### [P3-6] Windows: the client accepts a listener of lower integrity than itself, so an elevated client's commands run with a medium-integrity token and a different device namespace

- **Location:** §4 "Listener verification", Windows: "must not be an AppContainer token or below medium integrity" (line 244); §4 sandbox rule, "when a host checks a client, below the host's own integrity" (line 230); §11 rows (lines 674–675).
- **Violated invariant:** §5's "behave as the same command run in the client's own process, or be refused": the token's integrity and elevation are process attributes the server cannot hand over, and the comparison is one-directional.
- **Sequence:** An elevated prompt runs `gwz --server \\.\pipe\x …` against a medium-integrity server of the same user: writes that succeed in-process fail in the server with a bare permission error, and drive letters mapped in the non-elevated logon session resolve where the client's would not. `auto` separates the two through the logon session in the key; explicit addresses do not.
- **Required correction:** The client-side rule requires the listener's integrity level to equal the client's, as the host-side rule already refuses a lower client; message under `server_listener_refused`.
- **Closure/regression test:** dabeest row: an elevated client against a medium server is refused before any frame; a medium client against an elevated server is refused by the server.

### [P3-7] Windows: the `auto` pipe name is predictable by other users, so any local user can hold it and deny `auto` to the victim indefinitely

- **Location:** §4 "The default address", `\\.\pipe\gwz-<user SID>-<key>` and "The Windows pipe name is visible to other users" (lines 205, 211); §11 "No other process claims the address first: `FILE_FLAG_FIRST_PIPE_INSTANCE`, and the lock" (line 671); §14 covers only a same-user sandboxed holder (line 855).
- **Violated invariant:** Degraded path on shared machines: the POSIX `auto` address lives in a 0700 directory no other user can name into; the Windows pipe namespace is flat, the SID is public and the key is a digest of values another user may share.
- **Sequence:** Another user creates the pipe first with a permissive DACL; the victim's `server --start` fails at `CreateNamedPipe` and every `--server auto` refuses the foreign SID. Nothing expires it.
- **Required correction:** Add a per-user secret component to the `auto` pipe name, generated once and kept in the per-user directory under its user-only ACL (both CLIs read it), or state the residual in §14 with the explicit-address workaround and the message the start gives.
- **Closure/regression test:** Windows CI: a pipe pre-created by another user under the predicted name does not prevent the victim's `auto` server from starting and being found.

### [P3-8] The agent pipe's local-only refusal has no code and no message form, and the address-refusal format it would naturally reuse prints the value the plan's redaction rule protects

- **Location:** §5 "Local pipes only" (lines 432–434); §12 rows "a remote agent pipe is refused before any open" (lines 725, 813); §17 `server_address_refused` message "`… <reason>: <address>`" (line 1129) and the error table, which lists no agent-pipe refusal.
- **Violated invariant:** Plan §2 (as amended): agent-socket paths are redacted from server logs and Python-visible errors.
- **Required correction:** Name the refusal's code and state that its message and any log line name `SSH_AUTH_SOCK` and the rule that refused it, never the pipe name; add a §12 assertion.
- **Closure/regression test:** The refusal's message, the server log and the Python-visible error contain no substring of the refused pipe name.

### [P3-9] The client's own OpenSSL configuration scan has no failure rule, so a client may key `auto` on a partial scan

- **Location:** §5 "OpenSSL's configuration fails closed", "The key. A client that computes the `auto` key runs the same scan over its own effective configuration" (line 385); "Failing closed" states the host's outcome only (line 381).
- **Violated invariant:** The key must partition by the same values the host checks; a client whose scan stops early (an unreadable include, the depth or file bound) would compute a key over fewer names and either miss its server or start a second one that then refuses it.
- **Required correction:** A client whose scan cannot finish refuses `auto` with `server_unavailable` naming the file and the reason, and starts nothing; explicit addresses are unaffected.
- **Closure/regression test:** With an include the client cannot read, `--server auto` refuses before any connect and no server is started.

### [P3-10] Must-match path values that are relative resolve against the working directory, which a server or stdio child cannot reproduce, so equal values give different behaviour

- **Location:** §5 Linux table, `XDG_CONFIG_HOME` "Set but empty, it gives the relative path `git` (inferred)" (line 311); §5 "Comparison" (lines 371–373), which keeps unset and empty distinct but admits any value; §6 "the copy's working directory is not the caller's: the file-system root" (line 481), which also governs the stdio child.
- **Violated invariant:** §5, "A command run through a server must behave as the same command run in the client's own process, or be refused."
- **Sequence:** `export XDG_CONFIG_HOME=` in a profile: in-process libgit2 looks for `<cwd>/git/config`; through a server or the stdio local form it looks for `/git/config`; both sides hold the equal value "empty", so nothing refuses. The same for a relative `HOME`, `OPENSSL_CONF` or `SSH_AUTH_SOCK`.
- **Required correction:** A socket or stdio host refuses at `SessionOpen`, with `server_environment_mismatch` naming the variable, any must-match value that is a relative path, including a set-but-empty `XDG_CONFIG_HOME`.
- **Closure/regression test:** An empty `XDG_CONFIG_HOME` and a relative `OPENSSL_CONF` are refused at open over a socket and in the stdio local form; absolute values pass.

### [P3-11] The claim that no must-match refusal can arise under `auto` fails for library clients that configure a timeout after opening

- **Location:** §5 "The `auto` key and native routes", "Under `auto`, no must-match refusal of either kind can then arise" (line 411); §4 "a library client uses the default" in the key (line 207); §5 timeout row (line 301); §7 `SocketCoreBridge("auto")` "with the default timeout in its key" (line 572).
- **Why it fails:** `Client.configure_transport_runtime` sets a session timeout after `open`; the key carried the default, so the server's libgit2 timeout is 9 seconds and every `git://`, `http://` or routed operation of that session is refused at routing.
- **Required correction:** Narrow the claim to the native row; either let `SocketCoreBridge` take the timeouts at construction so the key carries them, or state in §7 and §17 that a library session under `auto` that configures a non-default timeout has its native-path operations refused, with the message §17 already gives.
- **Closure/regression test:** gwz-py Client-level: under `auto`, a session configuring 30 seconds gets the documented refusal on a `git://` remote, or a second server if keyed.

### [P3-12] The stdio mode's address resolution is unspecified, so an inherited or remote `GWZ_SERVER` can refuse `server --stdio` at start

- **Location:** §6 "The address is `--server`, else `GWZ_SERVER`, else `auto`" for the `server` command (line 463); §15 "Options", which refuses `--server` as an option but says nothing of `GWZ_SERVER` (line 905); §16 question 2, where the remote command is `gwz server --stdio` under the remote account's profile (line 981).
- **Sequence:** The stdio local form's child inherits `GWZ_SERVER=stdio`; a remote account's profile sets `GWZ_SERVER` to `auto` or to a form the parser refuses. If `server --stdio` parses the variable, the child either refuses at start (`server_address_refused`, surfacing as `server_unavailable` at the client with a misleading cause) or resolves an address it must not use.
- **Required correction:** State that `server --stdio` neither reads nor parses `GWZ_SERVER`, and that `--no-server` semantics do not apply to it.
- **Closure/regression test:** The stdio rows run once with `GWZ_SERVER` set to a refused form in the child's environment; the session opens.

### [P3-13] [SSH form] Bytes a remote login shell prints before the first frame are parsed as a length prefix, and the resulting failure names neither the cause nor a code the table lists

- **Location:** §16 question 2 "The remote command" (line 981) and question 7 "Errors" table (lines 1040–1047); §3 "Frames" (line 146).
- **Sequence:** The remote account's `~/.bashrc` echoes text (bash sources it for non-interactive `sshd` commands); the first four bytes reach the client as a `u32` length, usually over 64 MiB or short of the real frame, so the client sees a protocol error after `ssh` connected successfully. The table's rows cover `ssh` exiting, no handshake within 30 seconds, and a refusal, not a corrupt first frame; the user sees no hint that their remote shell start-up output is the cause.
- **Required correction:** Add a row: a first frame that is not a well-formed `SessionOpened` (length over the limit or a tag other than 5) fails with `server_unavailable`, with a message that names remote shell start-up output as the likely cause and shows the first bytes with control characters escaped; the client then kills `ssh` as at the bound.
- **Closure/regression test:** Disposable `sshd` with a login shell that prints a banner: the command fails within the bound with that message, and no `ssh` process is left.

## 2. Invariant analysis (attacks that held, with evidence)

- **Disclosure order, socket form.** Parse → walk → connect → kernel-answered listener checks → `SessionOpen`. Verification uses only kernel-supplied facts (`SO_PEERCRED`/`SO_PEERPIDFD`, `getpeereid`/`LOCAL_PEERTOKEN`, `GetNamedPipeServerProcessId` and the token), so a listener cannot influence it; no client byte precedes it. On the host, "before reading a byte" is sound: a refused peer's `SessionOpen` sits in the kernel buffer and is discarded on close, never read into user space. Held, subject to P2-1 (sibling sandboxes) and P3-1 (a same-user foreign program).
- **Walk-versus-connect race.** Linux: connecting through `/proc/self/fd/<n>` of an `O_PATH` descriptor and binding through `/proc/self/fd/<n>/<name>` pin the inode and directory; without `/proc`, and on macOS inside `SocketCoreBridge`, the residual is a mount or automounter contact. I could not turn it into disclosure: a swapped component reaching a socket on a network file system still yields a local peer whose credentials and sandbox are checked after connect, and a directory swapped by another user in a non-sticky parent yields another user's socket, refused by peer credentials. The design's claim (line 142) holds; parent-directory ownership is therefore not needed for safety.
- **PID reuse.** A `SO_PEERPIDFD` descriptor holds a reference to the pid, so `/proc/<pid>` cannot name another process while it is open; the audit token's pid version and Windows creation time cover the other platforms; "cannot be made → refuse" is stated on both sides. The residual "a listening socket handed to another process" needs an unsandboxed same-user accomplice, which the design's model already trusts. Held.
- **Completeness of the enumerated list against the vendored sources.** `grep` over libgit2 1.9.7 `src/` found exactly the reads the object's per-platform tables and exclusion table name (`sysdir.c` 347/357/402/405, `fs_path.c` 1984/2081, `path_w32.c` 193/207, `remote.c` 1147–1160, `signature.c` 230–261, `repository.c` sites, `ssh_exec.c` 156/160, `sysdir.c` 29) and no other name; libssh2 1.11.1 reads only `SSH_AUTH_SOCK` (`agent.c:180`, `agent_win.c:136`); openssl-probe 0.1.6 writes at lines 134–136 and filters by existence at 156, as stated; native-tls 0.2.18 probes once per process (`LazyLock<ProbeResult>`, line 19) and loads the file and directory per connector (lines 291–296), consistent with the "every session" row and with §12's "not a transport one" row. The one non-`getenv` process-wide read, `mktime` in `git_signature_now` (signature.c:172, reading `TZ`), does not reach the session path: every `Signature::now` and `env::temp_dir()` hit in gwz-core is inside a `#[cfg(test)]`/`mod tests` block, and production commits and tags go through the spawned `git`, an allowlisted `process` entry that will carry the snapshot. Held. The `debt` count matches the object's "10 entries" (10 of kind `env` or `process`; the other 8 are statics and a thread-local).
- **Capture timing of `SSL_CERT_FILE`/`SSL_CERT_DIR`.** The comparison "as openssl-probe resolves them" gives the same answer whether a side captured before or after git2's start, because resolving a resolved value is idempotent and the probe writes only what it resolved; the host resolving once after its own start matches what its libgit2 loaded. Held.
- **`auto` under an unread environment.** A refused `XDG_RUNTIME_DIR`, `TMPDIR` or `GWZ_SERVER` value is refused, not skipped, and the refusal names `--no-server`; `--no-server` never parses `GWZ_SERVER`. Fail-closed and recoverable. Held.
- **Stdio mode descriptors and signals.** Moving the channel off descriptors 0 and 1 before anything runs, null devices on 0 and 1, close-on-exec pipe ends on the client, `setsid`/`CREATE_NEW_PROCESS_GROUP` with `CTRL_BREAK_EVENT` ignored: children cannot touch the stream and the terminal's interrupt reaches only the client. The client's 10-second kill after `session.close` bites only after a cancel reply has returned or on a second interrupt, which is today's Ctrl-C exposure. Held (P3-4 adds the inherited-descriptor rule for the child as well).
- **SSH remote form.** The character allowlist with no leading `-`, `--` before the destination, `-T`, a fixed remote command with nothing from the address, `PATH`-only resolution of `ssh`, refusal of every local file input and of `forall`, `BatchMode=yes` without a terminal with a 30-second bound, and interruptible prompts with one: option injection, planted binaries and no-terminal hangs are closed. Closing the client's end propagates to the remote through EOF, and a dead client closes the pipe. Agent forwarding and `SendEnv` are the user's SSH configuration and are disclosed. Held, with P3-13.
- **Redaction.** Every must-match refusal names a variable, the mask, the library or the logon session, never a value; the log's four line kinds carry no environment value, URL or repository name; `--verbose` prints addresses the user chose or derived from their own `TMPDIR`. Held, with P3-8 for the unspecified agent-pipe refusal.
- **Reuse restated.** §4 "What a server grants" and §6 "Idle" restate the reuse design's §4, §7, §11 and §12 without weakening them: a pooled connection is leased only after the requesting session's own agent, key file and known_hosts re-prove it; an instance's configuration holds no secret and may outlive the session; pooled connections neither count as activity nor keep a server alive. Held.
- **Idle exit versus detached workers; crash.** A detached worker killed by an idle exit is what a second Ctrl-C does today; a crash's blast radius is disclosed. Held (P3-3 covers the arriving client).
- **OpenSSL configuration scan.** Fails closed on the host; the residual (a patched OpenSSL reading another variable) is disclosed; the files-read-once rule refuses rather than serving stale roots. Held, with P3-9 for the client side.
- **Elevation and logon sessions.** Under `auto` the logon session in the key separates an elevated and a filtered token's servers; only explicit addresses meet P3-6.

## 3. Risks and next action

- **Files-read-once at an explicit address under a service manager.** After an OpenSSL package update changes `openssl.cnf`, a `--foreground` server with `--idle-exit off` refuses every session until an operator restarts it; the message says so. A cheaper recovery would let the server exit at its next idle point after detecting the change, so a service manager restarts it. Not filed as a finding; the drafter may take it with P3-3.
- **The scan's file handling.** The scan bounds file count and include depth but not file size or type; state that only regular files are read, with `O_NONBLOCK` and a size bound, so a FIFO or a huge file cannot wedge a start. Low likelihood (system or Homebrew paths); fold into P1-1's open rule if convenient.
- **Kernels before 5.9 and Landlock.** Disclosed in §14; P2-1's correction should restate them beside the sibling-sandbox residual so the Linux rule's limits are in one place.
- **Windows claims marked inferred** (`GetFullPathNameW` identity, `GetNamedPipeServerProcessId` on a client handle, whether a non-administrator can redefine `PIPE`) are pinned to dabeest rows; if `GetNamedPipeServerProcessId` fails on client handles, listener verification on Windows fails closed and the server is unusable there until an alternative (for example `GetNamedPipeServerSessionId` plus the token via impersonation at identification level) is designed. Worth a named fallback in §14.
- **`server --stop`'s 185-second bound** in scripts; and P2-2's bound choice for `--status` should be short.
- **Next action:** a remediation plan for P1-1, P2-1, P2-2 and P2-3 as specified; the P3 corrections are each a few sentences and can land in the same revision.
