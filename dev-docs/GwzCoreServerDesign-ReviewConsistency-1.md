## 1. Findings (one subsection per finding, severity-ordered)

### P3-1. The core-version refusal is written for "the client over a socket", which includes the `server` subcommands' `ServerControl` exchange, so `server list` and `server stop` cannot reach the other-core servers §6 says they do

- **Location.** §3 line 180: "Over a socket and in the stdio local form, the client refuses a `core` whose version or build differs from its own, with `server_version_mismatch`, before the snapshot crosses." Against §3 line 195 (`ServerControl` "needs no session, so no must-match check applies to it … so `server stop` and `server status` reach a server of any environment, such as one `server list` shows"), §6 line 594 ("The others belong to another core version or another environment: `auto` never chooses them, and each ends at its idle exit, or when stopped with `gwz server stop --server <address>`"), §17 line 1362 (the `list` footer promising the same), and §17 line 1387 (the core-mismatch template). Departures record R2.2 items 5 and 6.
- **Root cause.** Item 6 widened S-P3-5's refusal from "at an explicit address" to every socket client without excluding the pre-session `ServerControl` path that item 5 introduced. The rationale given for the check (a shorter must-match list on an older core) does not apply to `ServerControl`, which compares nothing.
- **Invariant violated.** One rule per clause; the lifecycle pair §17 line 1432 gives a server of another key (`list` shows it; `server stop --server <address>` ends it).
- **Reproduction.** Start a server with `--idle-exit off`; upgrade gwz; run `gwz server list`. Each probe is a socket client that reads the old server's `SessionHello`; by line 180 it refuses before sending, so the old server is neither "answering" nor "not answering" as §6 line 593 defines them. `gwz server stop --server <old address>` then fails with `server_version_mismatch`, contradicting line 594 and the `list` footer, and the leaked process Su-P3-5 was about cannot be stopped by the tool.
- **Impact.** An unstoppable old-version server, and an unspecified `list` rendering for it. Text-level, not architectural.
- **Required correction.** Scope line 180 to the session path: the socket channel opening a session, and the stdio local form's client, refuse a differing core before `SessionOpen`; the `server` subcommands' `ServerControl` exchange checks only the protocol range. Say how `list` renders a server whose protocol range does not intersect (refused, with its recorded process ID).
- **Closure test.** §12's lifecycle rows gain: a server double whose `SessionHello` names another core version and build is listed by `server list` and stopped by `server stop --server <address>`, while a command through it is refused with `server_version_mismatch` and no environment byte is sent.

### P3-2. The relative-path rule counts an empty `SSH_AUTH_SOCK` as relative, which §5 defines elsewhere as a legitimate "no agent" selection; under `auto` such a server can never start

- **Location.** §5 line 419 (`SSH_AUTH_SOCK` in the relative-path list, Linux and macOS), line 422 ("On Linux and macOS an empty value counts as relative … A socket host whose own values hold such a path refuses to start, naming the variable"), against line 475 ("when it is unset or empty: … on Linux and macOS, no agent, and agent authentication fails as it does today"), line 410 ("Unset and empty stay distinct on every platform"), §17 line 1309 and line 1390 (the message: "set it to an absolute path"). Departures record R2.2 item 15.
- **Root cause.** The empty-means-relative rule was stated for `XDG_CONFIG_HOME`, where libgit2 forms a relative path from the empty value, and then applied to every listed variable, including one whose empty value the design gives a different meaning and which resolves against no directory: libssh2's `connect` to an empty `sun_path` fails identically in-process and in a server.
- **Invariant violated.** One meaning per value; §5's own "behave as the same command run in the client's own process, or be refused" — in-process the command runs with no agent.
- **Reproduction.** `SSH_AUTH_SOCK= gwz --server auto status` on macOS (a common way to disable the agent). The client's snapshot holds the empty value; the auto-started copy inherits it; by line 422 the copy "refuses to start, naming the variable", so `--server auto` fails for as long as the variable is empty, with a message telling the user to set an absolute path they do not want. At an explicit address the session is refused at `SessionOpen` while the same command runs in-process.
- **Impact.** `auto` unusable, and a refusal with contrary advice, for an environment the design elsewhere treats as valid. Text-level, not architectural.
- **Required correction.** Exempt `SSH_AUTH_SOCK` from the empty-means-relative clause (a non-empty relative value stays refused): an empty value compares as a value, distinct from unset, and selects no agent, as line 475 says. Consider the same exemption for `SSLKEYLOGFILE`, whose empty value OpenSSL ignores. Update §17 line 1390's template list accordingly.
- **Closure test.** §12's `serve_session` rows: a client and a socket host with `SSH_AUTH_SOCK` set but empty open a session, the transport reports no agent, and under `auto` a server starts.

### P3-3. On Windows, `server start` refuses where an `auto` client recovers: a stale lock record naming a pipe another user has re-created

- **Location.** §4 lines 229–231 ("When no name is recorded, or the recorded pipe does not answer or fails listener verification, an `auto` client starts a server once … The copy either takes the lock and draws a new name, or finds a live server holding the lock"), §11 line 778 ("A lock record whose pipe does not answer is stale, and an `auto` client starts a server once"), against §6 lines 531–535 ("`server start` first probes its address as a client would … something else answers, or a check refuses: `start` fails with that refusal, having created nothing") and §12 line 877 (a pipe another user creates under a name it saw "is never used, since the next server draws a new name"). Departures record R2.2 item 7.
- **Root cause.** Item 7's recovery (draw a new name after a failed record) was written into the `auto` client's path and not into `server start`'s probe, which was written for the POSIX stale-socket case where nothing can recover.
- **Invariant violated.** Internal consistency between §4 and §6 for one input; §12 line 877's test names `auto` only, so the gap is untested.
- **Reproduction.** Windows; a server exits uncleanly (its record stays); another user, who saw the name in the pipe listing, creates a pipe under it. `gwz --server auto status` reads the record, fails listener verification (foreign SID), starts a server once, and the copy takes the lock and draws a new name: it succeeds. `gwz server start` reads the same record, probes, meets "a check refuses", and fails with `server_listener_refused` naming another user's pipe, having created nothing — although §4 and §11 call the record stale.
- **Impact.** The explicit start fails where the implicit one succeeds, on the platform the plan calls least tested; the message blames a listener the design already knows is not the user's. Text-level, not architectural, and Windows-only.
- **Required correction.** In §6 "Probing first", treat a recorded `auto` pipe that does not answer or fails listener verification as "nothing answers" for `server start` on Windows, as §4 does for the `auto` client, so the start takes the lock and draws a new name; keep the refusal for an explicit pipe or socket address. Extend §12 line 877's row to `server start`.
- **Closure test.** Windows CI: with a stale record naming a pipe another user holds, `gwz server start` starts a server under a new name and exits 0, and `server status` finds it.
