# GWZ operation session — start-ticket redesign

Date: 2026-09-23. Status: **DRAFT replacement; design review required**.

This is a new, complete proposed application contract for concurrent operations on one Python Client and a later CLI/core route. The rejected [operation-session v1 draft](GwzOperationSessionV1Design.md), its guide and the [final NO-GO verdict](GwzOperationSessionV1-Verdict-3.md) are historical evidence, not normative dependencies. This document, its [full caller guide](GwzOperationStartTicketCallerGuideDraft.md), the paired [core capacity amendment](../gwz-core/dev-docs/GwzRemoteTransportCapacityAmendment.md), and the [independent transport delivery amendment](../gwz-core/dev-docs/GwzIndependentTransportDeliveryAmendment.md) are one design-review tuple. The accepted placement design controls unless its exact host-delivery clauses are replaced by the paired amendment. Design GO accepts a contract only; it does not authorize implementation, release, a physical wire carrier or iroh work. The Python Phase 6/7 [NO-GO](GwzPyTransportConcurrencyNoGo.md) remains.

## 1. Ownership and compatibility boundary

The current Python path can derive an operation ID from caller `request_id` and expose process-global event/result lookup. Version 1 binds every read and control to the originating Client or authenticated route. A `session_id` and `operation_id` are identifiers, not bearer credentials. The receiver checks both identifiers **and** the route binding on every event, result, cleanup, cancel, ticket prepare/commit/status, release and close action. Two Clients may choose the same caller ID without sharing records. A route that reconnects is a new owner; it cannot reattach to, read or cancel the old route's operations under this version.

The hierarchy is route/Client → logical session → operation execution scope → optional request-local transport scope. One session also owns its endpoint constructor, shared endpoint and capacity epoch. A process-local cleanup supervisor can inherit a closing session's unfinished committed admission, constructor, handlers, request cleanup and endpoint cleanup when its route or last owner disappears. Uncommitted permits are cancelled/expired without Git effects. It is not a socket, new wire carrier or thread per orphan. Physical stream data remains discrete `gwz-transport` messages. The paired delivery amendment gives them a Taut delivery-only lane whose pumps never wait for application requests, responses or Python action coroutines. Operation-session messages are application messages. The in-process host boundary is in scope; a later physical wire route needs separate framing and qualification.

The current service is version 0. A receiver advertises `operation_sessions=1` only through the cheap `operation_session.open` negotiation. An absent/unknown method yields `UnsupportedOperation` before version-1 work; no silent downgrade after partial acceptance. Version-0 calls continue under their old call semantics but a version-1-capable build **must** bind their writes and event/result/merge reads to the originating Client/route. Unowned module-level legacy lookup fails closed. Legacy and v1 records are isolated; neither lookup falls through to the other store. This legacy owner hardening is an activation precondition, not a claim it exists today.

## 2. Proposed Taut service and message shapes

Names and field allocations below are the candidate schema contract, not generated code already present. Add them through Taut codegen and fingerprint checks; do not hand-edit generated files. Existing version-0 field numbers and meanings remain unchanged.

| Method | Request and outcome |
| --- | --- |
| `operation_session.open` | Negotiate the proposed schema and placement (`local` default; `cli` internal only), bind the originating route and return the session ID and finite limits without constructing an endpoint or reading credential/helper environment. An unbound `cli` placement refuses before setup. |
| `operation.prepare_v1` | **No Git, endpoint construction, request registration or helper I/O.** Validate the session, action/request schema, metadata and policy that can be checked without effects; reserve one bounded status/terminal record for the caller's monotonically increasing `start_seq`. Return a fresh opaque `permit_id` and 60-second prepared TTL. The same owner/sequence with the same request bytes returns the same live permit; differing bytes refuse. If no record slot exists, return a stateless `RetainedCapacityFull` refusal and create no permit. |
| `operation.commit_v1` | Take the session ID, `start_seq` and matching live `permit_id`. Only this method may begin endpoint construction, registration or Git work. Under the already reserved status record, admission moves through `committing` to `Accepted` with a fresh operation ID, or stores one typed refusal/setup/cancel outcome. Duplicate commit of the same permit returns the original state and never runs Git twice. |
| `operation.start_status_v1` | Owner-checked lookup by session and sequence: `prepared`, `committing`, `accepted` with operation ID, or original stored refusal/cancel outcome. A missing/expired record is `UnknownOrExpired`, never evidence of no effect and never authority to replay a commit. No-slot prepare is deliberately not retained; a Client that has **never received a permit and never sent commit** may retry prepare safely. |
| `operation.cancel_start_v1` | Owner-checked cancellation by session and sequence, valid before and after acceptance. It atomically either prevents commit/acceptance and seals/drains any pre-accept owner, or signals cancellation of exactly the accepted operation. It returns bounded progress and optional accepted operation ID; a five-second wait is not completion proof. |
| `operation.events_v1` | Owner-checked Taut shape-log read by session and operation IDs, with sequence cursor, tail, end and bounded retention. A late read behind eviction gets `EventCursorGap` with oldest retained cursor. |
| `operation.result_v1` | Owner-checked terminal read by both IDs. It waits/reports pending while the handler or mutation-capable children run, then returns one immutable `OperationTerminalV1`. |
| `operation.cancel_v1` | Idempotently signal only the named accepted operation and wait at most five seconds for local drain, returning truthful progress. |
| `operation.cleanup_v1` | Read/wait for the same operation's cleanup without signalling cancellation; `wait_ms` is capped at 5000. It remains available after terminal release while its cleanup record is retained. |
| `operation.release_v1` | Release a completed terminal and event log, not a live handler or pending physical owner. |
| `operation_session.close` | Stop new prepares/commits, cancel all prepared/committing/accepted starts, join admission and handlers, then drain request-local and endpoint work. Each call waits at most five seconds and returns final progress or `ClosePending` with current progress. |

The accepted transport placement design reserves `RequestMeta.transport_message?` at field **10** and `ResponseMeta.transport_message?` at field **9** as shared transport Envelopes. These fields are not the independent delivery schedule; the paired delivery amendment supplies that lane. `RequestMeta.session_id?` uses field **11**. The session-open placement and the request's `TransportOptions.placement` use the same accepted enum (`local=1`, `cli=2`, omitted=local); mismatch refuses before endpoint work. `ResponseMeta.operation_id?` remains field 5. `OperationSessionOpenRequest` fields 1/2 are version/optional placement; response fields 1–4 are session ID/version/limits/placements.

`OperationPrepareV1` fields 1–5 are session ID, positive `start_seq`, action method name, generated request-message name and canonical Taut CBOR request bytes. The method/name pair must be in the closed generated service table; the decoded `RequestMeta.session_id` must match field 1. The receiver checks the owner-bound session's highest successfully reserved sequence: an existing live record for the same sequence is checked first; a new reservation requires a sequence greater than that high-water value. This constant-size watermark prevents reuse of an expired committed token from creating new Git work. The Client serializes **prepare sends**, not Git operations, in sequence order and does not send a higher sequence while the preceding prepare reply is unresolved. This allows overlap after permits arrive while keeping the high-water rejection unambiguous. A no-slot prepare does not advance the watermark; after a later reservation advances it, that old sequence is expired and its caller must create a new ticket. A prepared record expires after 60 seconds **only if no commit has begun**. Its expiry releases its slot and makes any old `permit_id` unusable. A late duplicate prepare for that sequence returns `UnknownOrExpired`, not a fresh permit. A duplicate live prepare with different bytes is `InvalidRequest`.

`OperationPreparedV1` fields 1–2 are opaque permit ID and remaining TTL in milliseconds. `OperationCommitV1` fields 1–3 are session ID, sequence and permit ID. At the commit linearization point, the prepared record becomes a charged `AdmissionScope`; its status slot remains reserved through admission, acceptance, terminal and cleanup retention. A commit with a missing, expired or mismatched permit refuses with no work. If its reply is lost, `start_status_v1` or a repeated commit of the same still-retained permit reveals the original state. Never retry an unknown/expired commit: the Git effect may have occurred. `OperationStartStatusV1` fields 1–4 are phase, optional `OperationPreparedV1`, optional `OperationAcceptedV1` and optional original typed error; exactly the matching payload is present after settlement. Its request and `cancel_start_v1` take session ID field 1 and sequence field 2. `OperationStartCancelProgressV1` fields 1–3 are phase, optional accepted operation ID and cleanup progress. A cancelled prepared ticket produces a stored cancelled outcome without Git work. A cancellation racing commit/acceptance observes one atomic order and never cancels a peer. Accepted operations use the existing `OperationAcceptedV1` fields 1–2, operation ID and initial cursor zero. Event, result, cancel, cleanup and release requests take session ID field 1 and operation ID field 2; cleanup additionally takes `wait_ms` field 3. Close takes session ID field 1.

`OperationCleanupProgressV1` fields 1–6 are phase, handler-running, pending-local-work, peer-cleanup-confirmed, structured effects and local-completion-confirmed. Phase enum values are `running=0`, `cancelling=1`, `draining=2`, `local_complete=3`. `SessionCloseProgressV1` fields 1–5 are closing/final phase, running-handler count, pending-local-work count, peer-cleanup-confirmed and local-completion-confirmed. A final report requires handler-running false, pending-local-work zero and local-completion-confirmed true, but peer-cleanup-confirmed may be false.

`OperationTerminalV1` fields 1–11 are opaque operation ID, caller request ID, action, status, optional existing `OperationResult`, optional validated response message name, optional canonical Taut CBOR response bytes, optional **nonfinal** cleanup snapshot, optional typed error, structured effects and kind. Kind is `succeeded=0`, `failed=1`, `cancelled=2`, `output_limited=3`. Cleanup field 8 is a snapshot at terminal publication, **not** the source of cleanup finality; call `operation.cleanup_v1` for the latter. The action-specific response name must occur in the closed service method/response table; decoded `ResponseMeta` IDs, action and schema must match the terminal header. This is a generated typed response, never arbitrary JSON. Fetch retains `FetchResponse.repos`; merge retains state, record and recovery fields. Successful `handle.result()` returns the generated action response. On failure, cancellation, partial/dirty/conflicted outcome, the same generated response, when present, is in `GwzOperationError.response` for handle, unary and stream forms. `ResultLimitExceeded` has `response=None` and a bounded terminal instead of partial or false success.

`OperationEffectsV1` has `local` field 1 and `remote` field 2. Each is `none=0`, `may_have_applied=1`, `applied=2`. The domains mean mutation of local Git/workspace state and mutation of remote Git state, respectively; an SSH connection, remote advertisement or object read is not a remote effect. `none` requires proof that this operation caused no effect in that domain (for example cancellation before an effectful request was sent or any local mutation began); mere absence of acknowledgement is not proof. `may_have_applied` starts when an effectful request or local mutation could have occurred without proof of the final state. `applied` requires domain-specific confirmation of the effect, not merely a successful cleanup or peer teardown. A request capable of remote Git mutation moves `remote` to at least `may_have_applied` **before** terminal publication, so later remote application cannot invalidate a terminal's `none`. Ordinary fetch reads do not mutate the remote: its `remote` effect remains `none` even if a read or peer cleanup is uncertain. A fetch cancelled after remote response but before any local object/ref mutation proved untouched has both effects `none`; once local object or ref updates may have begun, `local` becomes at least `may_have_applied`, and a confirmed update makes it `applied`. The terminal freezes the conservative knowledge at handler join; cleanup progress may later refine `may_have_applied` to `applied` if specific proof arrives, but cannot retract an `applied` claim or turn a terminal's proved `none` into a possible effect. For retry decisions use the latest owned cleanup progress when available; an older terminal's `may_have_applied` remains safe by requiring inspection. `peer_cleanup_confirmed` is independent and neither upgrades nor downgrades either effect. Retrying is automatically safe on effect grounds only if **both** domains are proven `none` and the action's other preconditions still hold. Either `may_have_applied` requires inspection; `applied` requires inspecting whether the desired state is already present before deciding on another action. A caller cannot infer rollback from cancellation or local drain.

`GwzErrorCode` extends current value 72 with `session_capacity_full=73`, `capacity_busy=74`, `retained_capacity_full=75`, `capacity_conflict=76`, `placement_unavailable=77`, `operation_expired=78`, `result_limit_exceeded=79`, `close_pending=80`, `event_cursor_gap=81`, `operation_cancelled=82`, `start_unknown_or_expired=83`. Existing values are unchanged. The existing `GwzError` fields 1–7 keep their meanings; add optional `capacity_context?` field 8 of type `CapacityRefusalV1` and optional `close_progress?` field 9 of type `SessionCloseProgressV1`. `CapacityRefusalV1` fields 1–7 are resource enum, scope enum, positive limit, nonnegative in-use count, retry-condition enum, `retry_after_ms` and optional list of caller-owned blocking operation IDs. Resource variants are logical-session, start-ticket, endpoint-owner, operation-scope, operation-worker, member-worker, terminal-record, **cleanup-marker**, terminal-bytes, physical-epoch and draining-generation. Scope is session, route or receiver. Retry condition is `owned_cleanup`, `external_cleanup`, `record_release_or_expiry`, **`marker_expiry`**, `session_close_or_expiry` or `epoch_quiescence`. The four capacity codes 73–76 **require** field 8 and forbid field 9. `close_pending=80` **requires** field 9 and forbids field 8. All other codes omit both unless a separately versioned contract later adds a context. A malformed/missing required context is a version-1 protocol error, never parsed from prose or silently treated as a generic retry. Python maps field 8 to `GwzOperationError.capacity` and field 9 to `GwzOperationError.progress`, preserving numeric code identity. `operation_session.close` returns final `SessionCloseProgressV1` on success and `GwzError(code=close_pending, close_progress=...)` on a timed wait; prepare/commit/open return `GwzError(code=capacity_*, capacity_context=...)` on the corresponding refusal. A no-slot prepare returns a typed but stateless capacity error: it has no retained start-status entry, and no commit can have been sent. After a permit exists, commit refusals use its reserved record and `operation.start_status_v1` returns the original typed error until expiry. `start_unknown_or_expired=83` carries no claim of zero Git effect.

Capacity context may include **only caller-owned** blocking operation IDs; foreign IDs and endpoint/credential details are never disclosed. `retry_after_ms` is at least 1000 and is a minimum backoff, not a promise of capacity recovery. Repeated external-capacity refusals use exponential backoff with jitter capped at 30 seconds; a caller's own identified cleanup may instead be awaited. `CapacityBusy` for physical/worker/scope saturation is not repaired by releasing a terminal. `RetainedCapacityFull(resource=terminal-record)` at prepare is a stateless, no-permit refusal repaired by owned terminal release or expiry; `RetainedCapacityFull(resource=cleanup-marker, retry_condition=marker_expiry)` left after early terminal release is **not** repaired by calling that cached `release()` again and expires after its published 60-second TTL. `CapacityConflict` requires all scopes and physical cleanup to quiesce before a higher epoch can install. `SessionCapacityFull` requires a logical session to close/expire. A caller may give up; pending resource ownership continues independently.

`OperationSessionLimitsV1` publishes fixed initial fields 1–24: receiver sessions 32; route sessions 4; session executing operations 8; session queued operations 16; receiver active-plus-orphan operation scopes 128; session operation workers 8; receiver workers 64; session member workers 128; receiver member workers 256; session retained records 64; receiver retained records 256; per full terminal 16 MiB; session terminal bytes 64 MiB; receiver terminal bytes 256 MiB; per-operation events 1 MiB; session events 8 MiB; receiver events 64 MiB; completed-record sliding TTL 10 minutes; completed-record hard TTL 30 minutes; idle-session TTL 10 minutes; closed-report TTL 60 seconds; cleanup/close wait 5000 ms; receiver active-plus-orphan endpoint owners 32; receiver active-plus-orphan cleanup scopes 128. Field 25 is cleanup-final marker TTL 60 seconds; field 26 is maximum four live/draining transport generations **total** per session; field 27 is post-commit refusal-status TTL 60 seconds; field 28 is uncommitted prepared-permit TTL 60 seconds; field 29 is maximum 64 live-or-retained Python tickets per Client. A fifth generation while an old one still drains refuses `CapacityBusy(resource=draining-generation, scope=session)` until one drains; generation age alone does not free a live owner. All counts/bytes are positive; times are milliseconds. Limits are not user-configurable in version 1 or enlarged by `jobs`; changing them requires a newly negotiated version. A retained terminal keeps its associated final cleanup marker readable until terminal release/expiry. The 256 receiver retained-record slots include prepared permits, post-commit refusals, terminal-plus-cleanup or cleanup-only markers; one slot and its fixed byte charge are reserved at successful prepare, before any effectful commit. Active cleanup records use a fixed 1 KiB charge included in the terminal-byte budgets; at prepare the 4 KiB terminal fallback reservation includes that 1 KiB and at least 3 KiB for the result fallback. Releasing a terminal frees its portion but not a still-active cleanup charge. The generated-schema test must prove the encoded fallback including a 256-byte caller ID stays below 2 KiB; otherwise raise the admission charge before activating version 1.

## 3. Admission and execution

`operation_session.open` checks the bound route, selected version, requested placement and logical-session budgets before it allocates a logical session. It does **not** call the older endpoint-constructing `transport_capabilities` path. The ordinary Python Client exposes local endpoint placement; internal `cli` placement has no public Python binding API until separately reviewed. An unbound `cli` request fails cheaply, even with poisoned credential/proxy/CA environment. Local-only operations never construct an endpoint.

For `operation.prepare_v1`, validate the owner-bound session, caller `request_id` UTF-8 length ≤256 bytes, duplicate **live** caller ID, action and generated request type, selected transport placement, and requested policy that can be checked without endpoint/helper access. Reserve one of the 64/session and 256/receiver retained-record slots plus its fixed byte charge **before** returning a permit. No worker, endpoint, Git handler or transport request starts at prepare. Any validation or capacity refusal before a permit is stateless and provably no-work; exhaustion returns `RetainedCapacityFull(resource=terminal-record)` without a permit or retained refusal. That reply may be lost, but a Client that has not received a permit cannot send a valid commit, so no Git effect is possible; retrying prepare is safe. This is the deliberate no-record boundary, not an unconditional 60-second refusal-recovery promise. The Client's own ticket remains an inspectable pending/no-permit owner. A successful prepare reserves one result/cleanup slot throughout its lifecycle; post-prepare refusal, cancellation and setup failure use that slot for their original typed outcome. If the Client drops or cancels the ticket before commit, it sends `cancel_start_v1` if a permit arrives; a never-committed prepared record otherwise expires after 60 seconds. Neither case can run Git work.

On `operation.commit_v1`, the receiver atomically checks the live permit and session state, transfers the already-reserved status slot into one charged `AdmissionScope`, and records `committing` before endpoint construction or helper access. It validates worker/queue/member permits, endpoint-owner capacity if network work, and physical-capacity policy before effects. A policy/capacity refusal is stored under the reserved status slot. Endpoint setup then reserves its owner and current physical epoch, publishes the constructor under the admission owner, and may access required environment/helper state. Setup failure stores a typed failure after joining/draining any constructed resource. The whole pre-accept transition is one charged task through request registration and atomic acceptance; it counts in the same 24/session and 128/receiver operation-scope limits. A late duplicate commit reads the same record instead of creating another admission. A late `prepare_v1` for an expired old sequence cannot revive the permit, because the session high-water mark remains.

The `AdmissionScope` installs a request-local cleanup ticket before any registration side effect, then registers and waits for mux/endpoint readiness. Close, `cancel_start_v1` or route loss atomically seal admission and join/transfer its task, registration and ticket; failure or cancellation seals and drains any partially installed request before charges release. No final close or epoch resize is permitted while it remains. At the `Accepted` linearization point the owner-bound operation record is installed under that same start sequence, the execution scope takes the exact existing reservations and request ticket without a gap, and only then is `OperationAcceptedV1` emitted. If cancellation wins first, there is no Accepted and no handler start. If acceptance wins, cancellation targets exactly that operation. A lost Accepted delivery cannot create a second operation: status and repeated commit return its original ID while the record is retained. No Git handler starts before Accepted. Queued accepted operations already have a handle and can be cancelled before worker start. After record hard expiry, status is explicitly unknown; it never licenses automatic replay.

Python `Client.start_fetch(...) -> StartTicket[FetchResponse]` is a **synchronous** method. It requires the Client's bound running event loop, allocates a unique positive `start_seq` and one of 64 Client-owned live/retained ticket entries, and returns that ticket before any cancellable await. If no local ticket entry is available, it raises typed `CapacityBusy(resource=start-ticket, scope=session)` synchronously without sending anything. The Client-owned admission task serializes prepare sends by sequence, waits for a permit, then sends commit; different tickets' Git operations may overlap. `await ticket.accepted()` returns an `OperationHandle` or raises the stored typed refusal; `await ticket.result()` awaits that handle's result. The ticket exposes `start_seq` and `request_id`; `Client.tickets()` returns a bounded owner-only snapshot and `Client.ticket(start_seq)` returns that exact retained ticket. Caller request IDs remain correlation only and need not be unique across Clients; a duplicate **live** ID in one session refuses after a prepared slot is reserved. Cancelling the Python task awaiting `accepted()` or `result()` cancels only that wait, not the Client-owned ticket or the delivery pumps. `await ticket.cancel()` works before prepare response, during commit/admission, and after acceptance: before a permit it prevents any commit and discards a late permit; after a permit it calls `cancel_start_v1` and returns bounded progress. A later `accepted()` may report a typed cancelled outcome. A dropped ticket remains in the Client registry while live; final release/TTL remove it. Closing/dropping the Client cancels/transfers ticket tasks under the same charged owner rules. No other Client or replacement route can enumerate or recover them.

Every accepted operation gets a distinct internal transport request ID, unique in its mux generation, separate from caller `request_id`, start token and opaque operation ID. A duplicate live caller ID refuses; a retired caller ID may be reused, but the start, transport and operation IDs remain distinct. Late old-generation messages cannot attach to the new operation. Rotate the current mux generation before its 256 lifetime-ID ceiling; at most four generations including the current one may be live/draining per session. A full generation budget refuses with the published `CapacityBusy` resource before registration. Generation rollover is internal to the host, not a Taut wire carrier; its algorithm still requires implementation proof.

An operation scope owns the worker, all mutation-capable children and request cleanup ticket. A handler panic or fallible worker launch becomes a typed terminal after the scope joins; never an orphaned accepted ID. Cancelling a waiter does not cancel its worker ownership. Terminal publication requires the handler and every mutation-capable child to have joined; a still-running handler stays pending and charged, even if cancellation was requested. If cancellation races actual handler success, preserve success. If cancellation actually terminates the handler before an action result, publish the cancelled terminal with effect uncertainty. A finished terminal may precede physical drain. Event retention cannot erase it; an oversized response uses the reserved `ResultLimitExceeded` terminal with accurate effects and no action response. The result serializer writes into a charged bounded buffer. Completion, explicit release and TTL obey the stated record/byte caps; no second process-global merge result store exists.

The endpoint constructor and subsequent request registration are stages of the charged `AdmissionScope`, starting when the first slot is reserved even before an endpoint object exists. Close and route loss atomically mark the session Closing, forbid new admission/acceptance/publication and transfer or join the admission task plus any constructor or registration ticket. A constructor that finishes after Closing cannot publish: its result is shut down under the retained owner. A registration that loses Closing cannot return `Accepted` and must seal/drain any partially registered request. Only after local drain do their charges release. Failure releases each charge exactly once. Explicit close returns `ClosePending` if either stage cannot join within five seconds; it cannot report final close or release their reservations. Route-loss supervision retains the task and charges. This preserves the accepted Python construction/close race protection and extends it through request registration and orphan transfer.

The current `TransportRequest.finish()` and `Session::cleanup()` return `CleanupReport` snapshots that can have nonzero `pending_local_work`; a five-second return is not completion proof. Version 1 requires an owned request/endpoint cleanup ticket or equivalent retained join handle and a **monotonic sealed-and-drained transition**. After cancellation, no new child may register; join all producers, then prove all local streams, checkouts, helpers and endpoint cleanup tasks retired. A zero snapshot before sealing is insufficient. Handler join (no further local workspace mutation), local physical drain, and remote peer confirmation are separate facts. Peer unconfirmed may persist in a final local report and does not pin local capacity by itself. If a background child can still mutate the workspace, it belongs to the execution scope and delays terminal/final close. A version-1 network handler that cannot isolate its cleanup from peer requests fails the concurrency activation gate; the product must not expose overlapping `start_*` under a silently shared cancellation path.

## 4. Close, route loss, retention and capacity

`cancel_start_v1` signals only its one prepared, committing or accepted start; `cancel_v1` signals only its named accepted execution/request scopes. A five-second call may return progress with handler running or physical cleanup pending. `cleanup_v1` waits on the same owner without cancelling; it can later return `local_complete` even when `peer_cleanup_confirmed=false`. Neither method tears down healthy peer operations. `result_v1` may remain pending if a synchronous native Git handler cannot be interrupted. This design promises **bounded resource counts and honest pending states**, not a time bound for native termination. If work never ends, its worker, operation scope and physical charges remain; future admissions can receive typed refusal. A future hard deadline requires a separately reviewed terminable process or proved cooperative library path.

Explicit close stops new prepare/commit, cancels prepared permits and every committing or accepted start, seals all constructor, registration and operation publication, joins **every pre-accept `AdmissionScope`**, accepted handler and request ticket, then drains shared endpoint work. Each caller wait is five seconds. `ClosePending` includes current charged progress and preserves the single close task; another call joins it. Final close requires all handlers and all local physical work retired, so no handler can still mutate the workspace, but may retain peer uncertainty. **Per-operation results/cleanup and retained ticket outcomes remain owner-readable after close begins and after final close** through the original Client/route until release/TTL; the closed session keeps only bounded read-only binding metadata while records exist. An empty closed session report expires after 60 seconds; retained records still obey the 64/session and 256/receiver caps and their 10-minute sliding/30-minute hard TTL. `__aexit__` starts the same close and propagates `ClosePending` if incomplete, preserving any body exception as context; the Client can be used for read-only result/cleanup, ticket recovery and repeated close while reachable. A cancelled close waiter never cancels the close task. Last-owner drop has no inspectable handle but transfers ownership to the supervisor.

On route loss, the receiver cancels uncommitted prepared permits (which have no effects) and atomically moves all pre-accept `AdmissionScope` tasks (including constructor and partially registered request), accepted operation workers, request cleanup tickets and endpoint owner to its process-local supervisor **with their existing reservations** before releasing the route/session owner. It stops new work and signals cancellation. Transfer needs no newly available slot, so it cannot fail because the supervisor is full. The old route cannot be reattached or queried from a replacement route. The logical live-session slot may retire, while active/orphan endpoint-owner, worker, operation/cleanup-scope, terminal-byte and physical-epoch charges stay until their respective true completion/release rules. Orphan result/event bytes stay under the ordinary caps; no unbounded audit store is introduced. No TTL drops live physical work. Process crash is outside this volatile ownership guarantee; no restart may claim a lost operation succeeded or rolled back without separate durable evidence.

The physical-capacity owner applies the paired core amendment: first permitted commit entering charged admission or a later truly quiescent boundary installs exact resolved caps; componentwise equal/lower requests may overlap under the installed epoch while obeying their own `jobs` and per-host work limit; a required raise refuses with `CapacityConflict` before Open. Quiescence requires no admitted or orphaned scope, non-idle lease, pre-accept constructor/registration task or unfinished physical cleanup. Atomic install has one leader/target and wakes all waiters on cancellation/failure/close. An orphaned endpoint or request pins the epoch; releasing a logical session record cannot permit resize. The tuple remains `per_user_host=per_host=max_per_host`, `total=max(256,jobs)`, `max_requests=max(1024,jobs)`; these are pool checkout caps, not operation worker quotas. For internal `cli` placement the bound physical owner must check capacity pre-Open or placement refuses early. The core amendment's exact retry §3(7), §6, S1.4 and transport Phase-2 replacements are part of this review object; until they receive GO, their accepted predecessors remain authority.

Receiver admission counts active **plus orphaned** endpoint owners (32), operation/cleanup scopes (128), operation workers (64), member workers (256), and charged result/event bytes. A live session has at most 8 executing and 16 queued operations, 128 member workers and 64 retained records. There are at most 32 live logical sessions and 4 per route; read-only closed bindings are accounted through retained records, not free unbounded session objects. A local-only session may open while all endpoint slots are occupied, but its first network use then refuses `CapacityBusy` before construction/helper access. A transferred orphan keeps the same charge; no release is caused by terminal publication, caller result release, a five-second timeout, route loss or a `pending_local_work == 0` snapshot taken before sealing. Completion releases exactly once and wakes admission waiters. If physical work never finishes, bounded saturation and typed refusal are the stated availability outcome; no fixed 35-second retirement promise remains.

## 5. Review and activation gates

The exact design-review object is this new standalone spec, its standalone caller guide, the paired core capacity amendment and the independent-delivery amendment. A GO accepts their proposed contract only.
