## 3. (a) What crosses the carrier

### 3.1 Frames and the handshake

- **Framing:** `session-channel`'s byte-stream framing unchanged (its writer changes, §3.3): little-endian `u32` length, tag byte, deterministic-CBOR body, at most 64 MiB, the length checked before allocation. The tag registry gains tags 16 and 17 on both adapters (`frame.rs:14, :96, :154` change; 18–31 remain a protocol error).
- **Handshake:** the server design's §3 order and bounds (host `SessionHello` first after its peer check; client sends nothing until it holds a well-formed `SessionHello` within 30 s; one `SessionOpen`, or `ServerControl` to a socket host; `SessionOpened`). The client checks only the protocol range, as the server design's SSH form does, then `transport_capabilities` (§4.8): no must-match value exists any more.
- **`SessionOpen` for the `cli` placement carries no environment** (amending `GWZRequirements.md:108`, `GWZDesign.md:104, :106`, server design §3 :193–202): `environment` absent, `host_environment` true, `attributes` with `umask` and `openssl` absent and `transport_off` absent or false. Every host in this release, socket and stdio alike, accepts exactly that combination and refuses any other with `invalid_request` before `SessionOpened`. The session then uses the core process's own environment for Git (§3.5). `session-contract`'s `frame.rs:25` comment ("a body can carry the environment snapshot") becomes historical for this placement; the byte-stream reader keeps wiping bodies.
- **Calls:** `SessionCall`/`SessionReply`/`SessionError` (tags 1–3) carry the existing taut requests with their `RequestMeta`/`ResponseMeta` (session design §4.1). In this placement the request's `TransportOptions` carry `placement = cli` and the client's `endpoint_path_base`; `RequestMeta.transport_message` and `ResponseMeta.transport_message` are absent in both directions (a present value is `invalid_request`), because every envelope travels on the transport lane (§3.3).
- **Events and spools:** progress events and notes are read with `events.subscribe`; diff and log output with `diff.output` and `log.output` reads (session design §4.2, §6), each reply at most 1 MiB. Nothing else is pushed by the host on tags 1–3.
- **Cancel and close:** `operation.cancel` and `session.close` on the control lane (session design §3, §4.2). On a byte stream the priority writer of §3.3 writes them ahead of ordinary frames, except where the rule's exceptions apply (a `SessionCall` and ordinary frames of their own target are never overtaken), so neither waits behind spool replies written before it. The close report, `session.close`'s reply, is exempt from priority (§3.3 "Close report").


**Amended 2026-10-31 at step 2.3d (clerical; the frozen shapes stand).** The server design's §3 says a first frame other than `SessionHello` is `server_unavailable`; its §4 and §17 say a refused peer receives one `SessionError(call_id 0, server_peer_refused)` naming the cause, then the close, and is told "the server at <address> refused this process: <cause>". Step 2.3d's handshake states the two together:

- **The host's first frame** is `SessionHello`, or, for a peer its listener refused, exactly one `SessionError` for `call_id` 0 and then the carrier's close; this release's hosts send `server_peer_refused` (a later host may refuse before the hello with another code, such as a shutdown). The client takes a `call_id`-0 `SessionError` first frame as the refusal and shows its code and cause, escaped; it writes nothing. Any other first frame, a `SessionError` with another `call_id` included, is `server_unavailable` with its first bytes escaped. The 4 KiB first-frame cap applies to both forms.
- **Later handshake replies** (`SessionOpened`, `SessionError`, `ServerState`) are read up to 128 KiB, the largest legal `ServerState` (a log path of up to 32 767 UTF-16 units on Windows, up to 98 301 UTF-8 bytes, with its other fields); a longer reply is `server_unavailable`. Every frame after `SessionOpened` keeps the carrier's own limit.
- **A refusal** is one `SessionError(call_id 0)` and then the carrier's close (its close announcement, §3.3 as amended 2026-10-27). Its message never repeats text the peer sent; it may name a number the peer sent, such as a refused protocol version.

### 3.3 The transport lane

- **Body:** a GWZ taut message appended to the schema, `TransportLaneFrame { request_id: str (1), envelope: Envelope (2) }`, where `Envelope` is gwz-transport's, imported through the existing `transport_consumer` route (placement design §3; no second definition, no change to gwz-transport's schema).
- **Tag by kind:** tag 17 carries `bind`, `bound`, `bind_rejected`, `opened`, `open_failed`, `window`, `flush`, `flushed`, `end_write`, `close`, `closed`, `cancel`, `failed`, `identity_checked` and `identity_check_failed`, every kind gwz-transport charges to its control reserve (`gwz-transport/src/mux/mod.rs:638–641`); tag 16 carries `data`, `open` and `check_identity`. A kind under the other tag faults its binding (contract §6). Terminal kinds are therefore control, as plan 2.0(a) and 2.1 require; revision 1's placement of `closed`, `close` and `end_write` on tag 16 is withdrawn (C-P3-2), and the writer's own-target exception keeps every orderly kind behind data of its own stream.
- **When:** only after `SessionOpened`; a lane frame before it is a protocol error ending the carrier. Both directions.
- **Scope:** `request_id` must name a live call this client sent on this carrier; `Envelope.session_id` is the binding, valid only on the carrier connection and request that bound it (plan 1.2). A frame for a binding of another carrier, or a retired one, is discarded with no state created; an invalid frame for a live binding faults that binding only (contract §6).
- **Bounds:** each end's sending side is bounded by gwz-transport's own outbound queue under the binding's negotiated `Limits` (`queued_frames`, `queued_bytes`, `control_reserve_*`; `gwz-transport/src/mux/mod.rs:627–650`), separately from the call lanes, and it sends `data` only within `Window` credit. Each end's receiving side keeps per-stream state bounded in quantities the sender controls ("Transport-class bound" below), never a frame count the sender cannot observe.
- **Timeliness:** the core's handler never sends an envelope in a reply and never waits for its call's reply to deliver one; the lane is pumped by the carrier's reader and writer independently of operation workers (placement design §4).
- **Byte-stream writer (D-N).** Each end's writer, at each frame boundary, writes the oldest control frame (tag 17, and tags 1–3 on the control lane) ahead of ordinary frames, except ordinary frames of its own target (same `call_id`, or same `(request_id, session_id, stream_id)`) and any `SessionCall` (tag 1), which are never overtaken, so per-target order and the increasing call-ID rule survive.
- **Writer interface.** The adapter decodes no body. Core keys each frame when it encodes it and sends it with `FrameSink::send(frame, lane, key)`, where `key` is a `FrameKey { class, target }`, a `gwz-session-contract` type that holds no GWZ or Taut type: `class` is control or ordinary, and `target` is an opaque value that the adapter compares for equality only and that core derives from the frame's `call_id` (tags 1–3) or its `(request_id, session_id, stream_id)` (tags 16–17). The adapter orders by `key` and the tag byte only. `lane` keeps its in-process meaning and a byte stream does not use it.
- **Close report.** Core keys the close report (`GwzCoreSessionDesign.md` §8 step 8) as an ordinary frame although it travels on the control lane, so it is exempt from priority: the writer writes it only after every frame the host queued before it, and step 9 closes the channel only after the writer has drained. A client that has sent `session.close` keeps its reader running until the close report, end of stream or the close bound, and delivers every reply that arrives to its waiter before it fails the calls that remain.
- **Byte-stream reader (D-N).** Each end's reader never blocks on a consumer: it routes every frame to a per-class queue whose bound the peer must respect (the call limit, the control reserve and the binding's transport `Limits`), and an overrun is a protocol error of that class.
- **Reader interface.** The adapter's reader checks each frame's length, tag and size as today and hands it, as `(tag, body)`, to a core-supplied router port, `FrameRouter::route(frame) -> Result<(), Closed>`, a `gwz-session-contract` trait given to `byte_stream(read, write, router)`; `route` never blocks. Core decodes the body there and owns every per-class and per-binding state: the call limit, the control reserve and each binding's transport state. An error `route` returns ends the session; core settles everything else itself. A byte-stream end implements `FrameSink` only, not `FrameSource`: it delivers every frame it receives through its `FrameRouter`. The shared conformance suite drives a byte-stream end through a test router that queues the frames it is given and exposes `recv()` to `run_all`.
- **Transport-class bound.** The transport class's queue is per-stream state, not a frame queue, and is bounded by quantities the sender controls: `window` coalesces to the highest `max_offset` (gwz-transport already ignores a lower one); `data` appends to a buffer bounded by the binding's `receive_window`; every other kind holds at most one slot per stream. A sender that sends `data` only within `Window` credit cannot overrun it, whatever the size of its frames. Core hands this state to the binding's consumer as the consumer drains, and a consumer that is not ready holds back that binding only, never the reader.
- **Fault scope.** A transport-class overrun, or any other frame that breaks a live binding's rules, faults that binding only (`GwzConnectionApiContract.md` §6); the carrier's other bindings and calls continue. Only call-class and session-class overruns (the outstanding-call limit, the control reserve) and the protocol errors of `GwzCoreSessionDesign.md` §3 end the session.
- **Tag alignment.** Tag 17 carries exactly the kinds gwz-transport charges to its control reserve (`gwz-transport/src/mux/mod.rs:638–641`: every kind but `data`, `open` and `check_identity`), and tag 16 carries `data`, `open` and `check_identity`. The own-target exception keeps per-stream order, so no terminal or orderly kind overtakes data of its own stream.
- **Where it applies (D-N).** To every byte-stream carrier: socket, named pipe, stdio and `ssh`, which are every carrier of a served core. The in-process adapter keeps its call and control lanes and its one order, takes `key` without using it, and is otherwise unchanged. This replaces the byte-stream FIFO that `GwzCoreSessionDesign.md` §3 stated before 2026-10-25; step 2.1 implements it and step 2.2b's control-progress rows depend on it.
- **Reply order.** Under the writer rule, `operation.cancel`'s reply (control lane) can reach the client before the final reply of the call it cancels (call lane) when spool replies are queued ahead of that reply. The bridge waits on each `call_id` and accepts either order (session design §10), and 2.1's bridge rows test both orders.

**Amended 2026-10-27 at step 2.1 (clerical; the frozen shapes stand).** Step 2.1's carrier, accepted after its round-2 re-verdicts, states these points more exactly than revision 3 did:

- **Reader interface, completion:** `FrameRouter` has a second method, `ended(reason: Closed)`, called once after the last `route` when the session has ended at that end (`gwz-session-contract::channel::FrameRouter`).
- **Writer rule, exactness:** the writer picks the oldest **unblocked** control frame: a control frame is blocked while an ordinary frame of its own target, or any `SessionCall` (tag 1), is queued ahead of it, and same-target control frames block each other, so per-target order and the increasing call-ID rule survive.
- **Per-kind bound:** "every other kind holds at most one slot per stream" is, in the carrier, at most **4** queued frames of each such kind on a stream (`BindingLimits::per_kind`), and a binding holds queued state for at most 4096 streams (`max_streams`; step 2.2c owns deriving it from the binding's stream limit). Both are quantities the sender controls, so the "Transport-class bound" stands.
- **Binding end:** a consumer taking from a binding that is faulted, retired or was never opened gets that binding's own terminal (faulted, with its fault, or not open), distinct from the carrier's end; a scoped link ends only the join of that binding and keeps serving the others.
- **Byte-stream errors:** `byte_stream(read, write, router)` and its reader and writer report transport failures as `io::Result`; a peer-side failure seen by either half (EPIPE, ECONNRESET, `ERROR_NO_DATA`, EOF) stops writing, drains what was received, and ends with one deterministic reason: the peer's close announcement if one arrived, else `PeerGone`; only a local close or abort, or a failure of this end's own (`Stream`), discards inbound frames.
- **Close announcement (defined here):** the one frame an end owes its peer when it ends the session: tag 17 with a zero-length request name (which no transport message can have), body `[0, code]`, `code` one of the carrier's four close codes: 0 normal, 1 dropped, 2 cancelled, 3 protocol fault. It is queued past the lane's capacity (the one exception), the closing end then waits up to 2 s for the peer to close its end in answer, so the announcement is read before the handle goes, and after a peer's announcement further frames are discarded and counted, not delivered.
- **Stall bounds:** the carrier carries `StallBounds { no_progress: 60 s, close: <session close bound> }` as a parameter step 2.3 sets from policy; a writer with queued frames and no byte moved for `no_progress` ends with `Stalled` and aborts.
- **Handshake (the frozen form as the code accepts it):** `SessionOpen` keys 1 and 2; optional 4; key 5 a map with at most `transport_off = false`; key 6 = `true`; anything else is refused with exactly one `SessionError(call_id 0, invalid_request)` then close; a refused peer gets one `SessionError(server_peer_refused)` then EOF, and the refusal holds the accept thread for at most 1 s overall on every platform.
- **Routing by request (deferred):** "`request_id` must name a live call … valid only on the carrier connection and request that bound it" is enforced by steps 2.2b and 2.2c's routers, not by the carrier, which routes by `session_id` only after a shallow decode (key 2) and faults only the named live binding on a bad body.

### 3.4 The served-core composition (D-L)

- **Construction:** for each session the core builds `gwz_connection::remote::handle(binding)`, where `binding` is a constructor argument (the session's lane port and its live-call registry), not a fifth `HostPort`. It is a `HostHandle` with a carrier backing; `Operation` and `Exchange` keep no public constructor.
- **`admit(op_ref)`:** carries only an operation reference, the call's `request_id`. Core-side it reserves a local record with no carrier I/O. **`acquire().await`** waits for core-side bounds only. **`register()`** stays synchronous and infallible and is a **deferred commit**: it enqueues one `bind` (fresh `session_id`, `stream_id` 0, `role = driver`) into a preallocated lane slot and returns an `Operation` whose registration is pending. On receipt the client's receiver resolves `request_id` to the call it sent, builds the `PreparedOperation` itself from that call's captured invocation (route, profile, `AuthContext`, `OperationPolicy`, allowed sets, service class), and runs its own owner's `admit → acquire → register`; it answers `bound` (the client binding is registered) or `bind_rejected` (`capacity`, `invalid_request`, `cancelled`; `Effect::None`). The core's registration becomes `Registered(binding)` on `bound`; on `bind_rejected` it ends terminal `NeverRegistered(ClientRefused(code))`; on carrier loss before `bound` it ends terminal `NeverRegistered(CarrierLost)` with zero effects (the third revocation outcome, amending contract §5). An `open` on a pending operation waits for the outcome first.
- **What the core cannot supply:** a profile, authentication context, policy, retry budget or capacity field. The lane carries none; a `bind` for an unknown, finished or already-bound `request_id`, or whose request's class (§4.5) admits no `bind`, is `bind_rejected(invalid_request)`; §5.6 states what the core reports for it.
- **One operation per call (decided 2026-10-31, plan §10 D-P):** a call has one operation and one `bind` for its `request_id`, so a second route is a second call, and the client's `admission_bound_ms` defaults to 4 s, below the core's 5 s bootstrap bound.
- **`open(spec)`:** the core-side handle maps gwz-git's `ExchangeSpec` to the typed `Open` through this closed table and refuses anything else core-side (`invalid_request`, `Effect::None`, nothing sent):

  | `ExchangeSpec` | `Open.service` |
  | --- | --- |
  | `SshExec`, command `git-upload-pack '<path>'` in gwz-git's own quoting | `upload_pack_exchange` |
  | `SshExec`, command `git-receive-pack '<path>'` | `receive_pack_exchange` |
  | `Http`, `GET <path>/info/refs?service=git-upload-pack` | `upload_pack_advertisement` |
  | `Http`, `GET <path>/info/refs?service=git-receive-pack` | `receive_pack_advertisement` |
  | `Http`, `POST <path>/git-upload-pack`, `application/x-git-upload-pack-request` | `upload_pack_exchange` |
  | `Http`, `POST <path>/git-receive-pack`, `application/x-git-receive-pack-request` | `receive_pack_exchange` |

  Refused: any other method, path suffix, query, command or content type; any header beyond those the endpoint itself sets for the service; a non-empty `auth`; an `http://` origin. The client independently refuses any `Open` that is not one of these `GitService` values (generic HTTP never crosses). The `Open` carries `destination`, `service`, `identity`, `policy`, `deadlines` and `receive_limits`; §5 says what the client accepts of each.
- **Admission** (§5) runs only at the client's receiver, on `bind` and on every `open` and `check_identity`; the core's handle enforces nothing a hostile core could skip.
- **`snapshot()`** on the carrier-backed handle returns a refusal-only value with no counts: the client's pools (which hosts it is connected to) are not the core's to see.
- **Live bindings on carrier loss:** revoked; open exchanges fail `carrier_lost`; a `receive_pack_exchange` that had started reports `Effect::possible`; their connections are discarded, never pooled. Client close or `session.close` cancels the session's bindings; the client's `HostOwner` and its idle connections survive for its next session.
- **Walkthrough, served form** (contract §12 gains this beside the in-process one):

  ```rust,ignore
  // client process: gwz-cli's command, or gwz-py's module composition (plan 3.1, 3.2)
  let (owner, host) = build(config, ports)?;                    // the only HostOwner
  let carrier = connect_verified(&address)?;                    // 2.1: walk, listener check, SessionHello
  let session = open_session(carrier, SessionOpen::no_environment())?;
  let receiver = serve_bindings(&host, &session);               // 2.2c: builds PreparedOperation, admits
  let reply = session.call(fetch_request_with(capture_on_original_entry()?)).await?;
  // core process (gwz server), per session
  let handle = gwz_connection::remote::handle(binding);         // carrier-backed HostHandle
  let op = handle.admit(OperationRef::from(&meta))?.acquire().await?.register(); // deferred commit
  run_git_via_gwz_git(&op).await?;                              // opens become typed Opens on the lane
  let end = op.finish().await;                                  // the client's connections survive
  ```

### 3.5 Whose environment each thing uses

| Core (the serving process's own environment and filesystem) | Client (its captured invocation) |
| --- | --- |
| repositories, worktrees, `.git/config`, global Git configuration for Git behaviour, `url.<base>.insteadOf`, hooks, filters, `core.*`, commit and tag identity, file-creation mask or ACL, locks | known_hosts, the agent (`SSH_AUTH_SOCK`, Pageant, the OpenSSH agent pipe), key files, `--identity`/`--remote-identity` paths and `endpoint_path_base`, the HTTPS helper and its environment, `gh` and its tokens, CA and trust, proxy and no-proxy, the WinHTTP machine proxy, the SSPI logon session, `--max-per-host`, `--ssh-timeout` ceilings, the D43/D51 `http.proxy` reader when it resumes |
| `--root`, `--target`, member paths and `InvocationContext.caller_cwd` describe the core's filesystem | `GWZ_URL_SCHEME`/`--url-scheme`, `--transport`, pager and terminal are the client's, sent as the request fields they fill |

A destination rewritten by the core's `insteadOf` is still only an `Open` the client must admit (§5).

### 3.6 Sensitive metadata that crosses, and why it is acceptable

Nothing listed in contract §7 as secret crosses: no environment, key bytes, agent signature, token, helper input or output, password or OS handle. A core URL carrying a password is refused core-side before any effect. What does cross:

| Item | Direction | Class | Why acceptable |
| --- | --- | --- | --- |
| `Open.destination` (scheme, host, port, path, usernames) | core → client | location | the core holds its workspace's URLs anyway; the client never sends its allowed set back |
| `Identity.key_path`, `path_base` (= `endpoint_path_base`) | both | sensitive metadata (contract §7) | the client sent them in its own request; admission refuses any other path, so the core can only echo them; the server never logs them (server design §6 log rule) |
| `CheckIdentity` result | client → core | one bit, `Effect::None`, no facts | asked only for client-named paths, so it is no file-existence oracle on the client |
| `Opened.facts` (method, `credential_offered`, `authenticated`, `key_fingerprint`, HTTP status, SSH exit status, native facts) | client → core | sensitive metadata (public key fingerprint, mechanism) | needed for `TransportObservation`; public values; never logged by the server |
| `Bound.schemes`, `Bound.policies`, `Bound.receive_limits` | client → core | sensitive metadata (client configuration) | they say which schemes and authentication policies the client's configuration permits for this binding (for example `gh`, or a Windows native policy) and how much it accepts; the core needs them to name a permitted `Open.policy` (§5.4) and to size what it sends (§3.3); they carry no credential, account, key path or allowed tuple, admission still decides every `Open`, and the server never logs them |
| `endpoint_id`, `connection_id`, `trust_owner` | client → core | opaque identifiers | no authority (placement design §2) |
| `Failure` code, effect, cause, detail | client → core | diagnostics | no raw stderr or helper output (placement design §6) |
| `SetupFailureCause` (`connection_refused`, `not_found`, `address_not_available`) | client → core | reachability | only for admitted tuples, so it answers no port scan beyond the grant |
| `data` payloads | both | repository content | the content of the core's own repositories |

### 3.7 Diagnostics

Endpoint notes (agent source, proxy, helper, Pageant, retry lines) are produced in the client and rendered by the client from its own sink, to standard error in the CLI and through the sink the `local` placement uses in gwz-py; under `--json`/`--jsonl` they are standard-error lines, not record fields. Driver-side notes and observations reach the client in events and `ResponseMeta` as today. Nothing is lost; the relative order of a client note and a core event is not preserved.

### 3.8 Credential variables never leave the client

- **Scrub list** (closed): `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, every `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, every `GCM_*`. The helper's own variables are covered by the `GIT_CONFIG_*` and `GCM_*` families.
- **Children:** the client starts `ssh` with an allow-listed environment only: `PATH`, `HOME`, `USER`, `LOGNAME`, `SSH_AUTH_SOCK`, the POSIX locale names `LANG`, `LC_ALL`, `LC_COLLATE`, `LC_CTYPE`, `LC_MESSAGES`, `LC_MONETARY`, `LC_NUMERIC` and `LC_TIME` (no other `LC_` name, so a user-defined one is never forwarded), `TERM` and, on Windows, `SystemRoot` and `USERPROFILE` (the Windows entries are provisional until probe (1) from a Windows client, §7, fixes them before 2.3 lands). It adds `-o SetEnv=GWZ_NONE=1`, so a `SetEnv` from the user's configuration cannot apply (the first value obtained wins), and `SendEnv` can then send only allow-listed names. It removes the list from every `sudo` and local stdio child it starts, and for the local stdio child and the test-only separate-user launch it also removes `SSH_AUTH_SOCK`. `ssh` keeps `SSH_AUTH_SOCK` for its own login and is started with `-a` (§4.4).
- **`gwz server stdio`** refuses to serve, with a usage error naming the variable, when its environment holds `SSH_AUTH_SOCK` or any listed variable. This also catches a variable set on the core's side, such as by the remote account's shell start-up, which no client-side scrub reaches; 2.3's message and 6.4 name that start-up file as the likely cause. It is the only command that refuses (plan 2.3).
- **`gwz server start` scrubs and does not refuse:** it launches its background server with the list and `SSH_AUTH_SOCK` removed, and a `--foreground` server removes them from its own environment before any thread starts. So no served core holds one, and a default login session, where launchd or the desktop sets `SSH_AUTH_SOCK`, starts a server unchanged (§4.3, §4.9). `gwz help server start` says that the server runs without the caller's agent or credential variables.
- **Residual (6.4 states it):** an agent the user forwards to the core machine by other means, such as their own `ssh -A` sessions, is the user's own exposure; gwz neither creates it nor can close it. On the same-user forms the core has the user's authority anyway (§5.1).

## 4. (b) The surface

### 4.1 Commands and selectors

- `gwz server start | stop | status | list | stdio` (server design §6, §17 synopses). Bare `gwz server` prints the subcommands. The root help's "Other" line gains `server`, and its common options gain `--server ADDRESS`.
- `--server <address>` is global, like every selector; `GWZ_SERVER` sets its default; `--no-server` runs in-process even with `GWZ_SERVER` set and cannot be combined with `--server` (server design §7). An empty `GWZ_SERVER` is unset; an empty `--server` is refused. Without any of them gwz runs in-process exactly as today; nothing ever starts or selects a server.
- **There is no `auto` address and no auto-start** in this release: `--server auto` and `GWZ_SERVER=auto` are refused with `server_address_refused`, naming the reason.
- `gwz --server X server start` is a usage error ("server start chooses its address and prints it"); `server start` and `server stdio` neither read nor parse `GWZ_SERVER`. `stop` and `status` take `--server`, else `GWZ_SERVER`, else, when run inside a workspace, that workspace's own server (`<per-user directory>/ws-<key>` on Linux and macOS, the pipe that `ws-<key>.lock` records on Windows; §4.2); outside a workspace with neither given they are a usage error. `list` and `stdio` take no address, and `--server` given to either is a usage error. The `hook` family and `init --update` refuse `--server` and never read `GWZ_SERVER`.
- New client options, accepted only with a server selected: `--allow-destination`, `--allow-push`, `--allow-native-auth` (§5.6).
- **gwz-py has no `server` family (D-O).** The server design's `gwz-py server start|stop|status|list|stdio` is replaced: gwz-py is a client only in this release, through its in-process host (plan step 3.2) and `SocketCoreBridge` (§4.7). No step builds or schedules a Python-hosted server; it is Phase 7 at the earliest.

### 4.2 Addresses and the per-user directory

- **Forms accepted by `--server`:** an absolute socket path (Linux, macOS), a pipe name `\\.\pipe\<name>` (Windows), `stdio`, and `ssh://[user@]host[:port]/absolute/path` (§4.4). `GWZ_SERVER` accepts the first three; `SocketCoreBridge` the first two. The server design's §3 grammar, refusals and walk apply unchanged except for `auto`.
- **Per-user directory:** §1's locations on Linux and macOS (mode 0700, owned by the user, checked under server design §4), `%LOCALAPPDATA%\gwz\` from `SHGetKnownFolderPath` on Windows (server design §11). A running server checks every 30 seconds that its entries there are still linked (§4.3).
- **Address chosen by `server start`:** `<per-user directory>/ws-<key>` on Linux and macOS (socket mode 0600); on Windows `\\.\pipe\gwz-<32 hex>` drawn at each start from the system's cryptographic generator, created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS` and a DACL granting only the user's SID, then recorded. The lock file `ws-<key>.lock` (server design §4 file rule and lock) records the process ID, the address, the workspace root and the log path. `start` prints the address, and with `--json` a record `{address, pid, root, log}`.
- `server list` reads every `ws-*.lock` record in the per-user directory and probes each address as `status` does (server design §6 "Listing", without the `auto` mark).

### 4.3 Server lifecycle

- **Start:** `gwz --root <workspace> server start [--foreground] [--max-sessions N] [--idle-exit D] [--log PATH]`, defaults 64 sessions, idle exit off, log `ws-<key>.log` beside the lock (standard error with `--foreground`). It resolves the workspace from `--root` or the current directory and refuses outside one. It runs the plan's 1.7 driver-only builder: no endpoint, no agent, `native` transport refused. **It scrubs and does not refuse:** the background server is launched with the §3.8 list and `SSH_AUTH_SOCK` removed from its environment, and a `--foreground` server removes them from its own environment before any thread starts (§3.8). It probes first and is idempotent for the same workspace and options (server design §6 "Probing first"); background start, descriptor and session rules as server design §6, §11.
- **Peers:** the server design's §4 peer check, sandbox rule and listener verification apply in both directions, unchanged; no test-only override exists in production code (2.1 source check).
- **Concurrent clients:** each connection is its own session; §1's CLI-equivalent locking; `--max-sessions` refuses the next `SessionOpen` with `transport_session_full`.
- **Stuck peers, in both directions:** the handshake bounds of server design §3. The host closes a session as carrier loss when its carrier accepts no byte for 60 seconds while the host has frames queued for it. The client closes the carrier as lost when it has frames queued and the core accepts no byte for the same 60 seconds, failing its outstanding calls with `server_session_closed` and revoking its bindings (§3.4). So a dead or stopped peer without EOF wedges neither side; the `ssh` form adds a keepalive below that bound on its own connection, never a shared master (`-o ControlMaster=no -o ControlPath=none`, §4.4). Residual: a core that hangs while the client is idle, with nothing queued in either direction, is not detected without an application heartbeat; the client waits until Ctrl-C (CLI) or `close()`, which the close bound bounds (gwz-py).
- **Carrier loss** runs the session design's §8 channel-closure path (steps 2–5 and 7): every live operation of that session is cancelled, local phases included (its gate refuses at the next crossing), bindings are revoked (§3.4), and each operation's method, ID, outcome and duration are logged core-side. Nothing is replayed; the client reports a push interrupted after its receive-pack exchange began as a possible remote effect.
- **SIGINT/SIGTERM** (Ctrl-C, Ctrl-Break or `server stop` on Windows) run the server design's §6 shutdown: stop opening sessions (keeping the listener to say why), close sessions through channel closure, wait one more bound for detached workers (a second signal or `stop --force` ends that wait), then remove the socket, clear the record, release the lock and exit. Step 4 (endpoint disposal) has nothing to dispose.
- **Stale socket and crash:** the server design's §4 rule unchanged: under the lock, a leftover socket is removed only when it is the user's, a non-blocking connect is refused, and the lock record names exactly that address; otherwise the start refuses and deletes nothing. After a crash clients see `server_unavailable` before `SessionOpened` and `server_session_closed` after it; the next `start` recovers through the stale-socket rule.
- **Directory removed under a running server:** every 30 seconds the server checks that its socket path (Linux, macOS) and its lock file are still linked and are the inodes it created. If either is not (a system cleaner, Linux's logind removing `/run/user/<uid>` at the user's last logout unless lingering is enabled, or a user's `rm`), it stops accepting new sessions, logs the cause, drains the open sessions for at most the close bound, and then shuts down as on `stop`, so no unreachable server keeps a lock on an unlinked inode while a second `start` takes a new one.
- **Client interrupts:** first Ctrl-C sends `operation.cancel` and waits up to the close bound; the second disconnects (server design §7).

### 4.4 The `stdio` and `ssh://` client forms

- **`--server stdio`:** the client starts its own executable as `gwz server stdio` through core's launcher (server design §15: new session, only the stream pipes and standard error cross, interrupt kept from the child), with the §3.8 list and `SSH_AUTH_SOCK` removed; same user, same machine.
- **`--server ssh://[user@]host[:port]/path`** (`--server` only, never `GWZ_SERVER` or configuration; server design §16 grammar, `ssh` resolution on `PATH`, prompts, bounds and error table). It is the evidence form in this release, not a supported feature (plan 6.3); 6.4's help says so. **Amended argument vector:** resolved `ssh`, `-a`, `-x`, `-T`, `-o ForwardAgent=no`, `-o ClearAllForwardings=yes`, `-o ControlMaster=no`, `-o ControlPath=none` (so gwz's session uses its own connection with its own keepalive and never becomes or rides a shared master), `-o SetEnv=GWZ_NONE=1`, `-o ServerAliveInterval=15`, `-o ServerAliveCountMax=3` (45 seconds, below §4.3's 60-second bound), `-o BatchMode=yes` when no terminal, `-p <port>` when given, `--`, the destination, `gwz server stdio`. The child's environment is §3.8's allow-list only. The path is the remote `caller_cwd`. Server design §16 question 4 ("gwz neither turns forwarding on nor turns it off"; `SendEnv` of `GH_TOKEN`) is replaced: the remote core holds no credential and every Git-host connection is made by the client.
- **Test-only launch hook:** the test harness alone may start `sudo -n -H -u <core-user> env -i PATH=… HOME=<core home> gwz server stdio` and, on Windows, `CreateProcessWithLogonW` with redirected standard streams and a generated password. It lives in test code only; the 2.1 source check proves no production binary carries it.

### 4.5 The service-class table (closed, by request type)

The client classifies each request it sends; its class fixes what admission can grant during that call (§5.3). A request type not in this table, including one added later, is refused under `--server` before connecting.

| Request type | Class under `--server` |
| --- | --- |
| `FetchRequest`, `PullHeadRequest`, `PullSnapshotRequest`; `TagRequest` with `op` Fetch, or List with a remote | **fetch**: upload-pack only |
| `PushRequest` (with its preflight and post-push reads); `TagRequest` with `op` Push, or Delete with a remote; each with `meta.dry_run` absent or false | **push**: receive-pack for push-allowed tuples, upload-pack for allowed tuples |

| `status`, `ls`, `resolve_forall_targets`, `list_snapshots`, `diff`, `diff.output`, `log`, `log.output`, `snapshot`, `capture`, `commit`, `stage`, `stash`, `branch`, `merge` without a family, other `TagRequest`s, `repo_sync`, `add_existing_repo`, `create_repo`, `detach_repo_member`, `attach_repo_member`, `local_family`, `transport_capabilities`, `configure_transport_runtime`, `events.subscribe`, `operation.*`, `session.close` | **local**: no `bind` or `open` is admitted |
| `materialize` | **local**; the core refuses it before any effect when its plan clones |
| `clone_workspace`, `init_from_sources`, `create_workspace`, `clone_repo_member`, `clone_local_workspace`, `remote_identity` (`gwz auth identity`), `merge --remote <family>`, `pull`/`push` whose `--remote` names a local clone family | **refused** (clone-family and local routes; workspaces other than the served one; repository-configured identities) |

**Plan-only fields narrow the class.** The class is a function of the request type and of every field that turns the operation into a plan without mutation; today that is only `RequestMeta.dry_run` ("Plan without mutation", `gwz-core/protocol/gwz.taut.py:1150–1151`). Such a field only ever narrows the class: a request with `dry_run = true` admits no `receive_pack_exchange`, ever, and a dry-run fetch-class request is fetch class at most. The plan class admits no `open` because gwz-core's dry runs make no remote exchange today (read at gwz-core `0ed48168`):

- a dry-run push returns its plan before any preflight or transfer (`src/workspace_ops/push_member.rs:111–131`), and its member and root plans read local state only (`:478–501`, `:567–595`; `push_state.rs:75–108`, whose last-known ref is the local remote-tracking ref, `git/gitbackend/push_plan.rs:125–133`);
- a dry-run tag push or tag delete skips `prepare_push` and every `ls_remote_url` and `preflight_remote` (`src/workspace_ops/handle_tag.rs:118`, `:161`) and stops before any remote traffic (`:236–238`, `:301–303`);
- both still check the selected identity (`push_member.rs:475`, `:564`; `handle_tag.rs:152–159`), which under `cli` crosses as `check_identity` (`git/gitbackend/transport_support/identity.rs:230–233`), so the plan class admits `bind` and `check_identity`.

### 4.6 Other dispositions

- **`forall`:** the client gets targets with `resolve_forall_targets` and runs the commands itself on the paths the core reports, holding the workspace guard as today, over a socket or `stdio`; refused over `ssh://` and the test-only separate-user launch, where those paths are another account's or machine's (server design §16 question 5).
- **Repository-configured identities:** the core does not consult them under `cli`; a planned remote that has one fails before any effect with a message naming `--remote-identity`.
- **`--max-retries`:** refused under `--server` with today's text ("not carried to the Cli placement's endpoint", `cli_placement.rs:56–71`): the endpoint runs the retries and the lane carries no budget. `--transport native`, `GWZ_TRANSPORT=native` and `gwz.transport native` are refused too (plan 1.7).
- **Routes:** `file`, local clone families, `http://` and `git://` are refused before any effect (placement design §2); `init --update` and the `hook` family stay in-process, refuse `--server` and never read `GWZ_SERVER` (§4.1).
- **Paths:** `--root`, `--target`, member paths and `caller_cwd` describe the core's filesystem; the CLI resolves `--root` and operands against its captured directory as text (server design §7). `--identity`, `--remote-identity` and `endpoint_path_base` describe the client's: the client sets `endpoint_path_base` to its own captured absolute directory whenever a selected key path is relative.

### 4.7 Python

- gwz-py is a client only (D-O): this bridge is how it reaches a served core, and it has no `server` command family. Its console script gains no `--server`, `--no-server` or `GWZ_SERVER` in this release (server design :38 and §7 :631 are replaced for gwz-py, §8): `SocketCoreBridge` is Python's only route to a served core, and a Python command-line route is Phase 7 at the earliest.
- `Client(root, bridge=SocketCoreBridge(address, *, allow=[…], allow_push=[…], allow_native_auth=[…]))`. `Client` gains no `core=` parameter. `root` is a core-filesystem path.
- **Construction** parses the address (socket path or pipe name only; `stdio`, `ssh://` and `auto` raise `server_address_refused`) and every grant (the §5.2 grammar; a malformed one raises `ValueError`); it does no I/O. The bridge takes its `HostHandle` from the module composition object of plan 3.2.
- **Carrier lifetime:** one carrier and one session per bridge, opened on the first call; its pump, call table and errors follow session design §10, and its stall rule is §4.3's: the bridge closes the carrier as lost when it has frames queued and the core accepts no byte for 60 seconds. Carrier loss closes the bridge for good: outstanding calls fail `server_session_closed`, there is no reconnect, a new bridge is needed. The bridge attaches its revoked bindings' effect to the failed call: when a `receive_pack_exchange` of that call had begun, the `server_session_closed` error carries `possible_remote_effect`, as the CLI reports a possible remote effect (§4.3).
- **`close()`** sends `session.close` and keeps its reader running until the close report, end of stream or the close bound; it delivers every reply that arrives first to its waiter, so an `operation_result` waiting on a push returns the push's terminal, then fails what remains with `server_session_closed`, disconnects and returns the close report (§3.3 "Close report"). It revokes this bridge's bindings but never closes the module's `HostOwner`, whose idle connections serve the next bridge.
- The library never prompts, never reads `GWZ_SERVER` and never reads `gwz.server.*` (§1).

### 4.8 Capabilities

`transport_capabilities` (placement design §3 fields 3–7): a served core advertises `placements = [cli]` only, schemes `ssh` and `https`, the auth policies its driver may request, its message versions and limits; an in-process core advertises `local` and `cli`. A client refuses a served core that does not advertise `cli` with a common version, before any `bind`. The answer is pinned to the carrier connection; a new carrier asks again.

## 5. (c) The trust model (D-H (b))

### 5.1 Where and when

Admission lives in the client's receiver of the carrier-backed binding (§3.4), shared by gwz-cli and `SocketCoreBridge`. It runs on every `bind`, `open` and `check_identity`, and again at every HTTPS redirect hop, before `CheckIdentity` work, agent, key file, helper, `gh`, native authentication or connect. A refused envelope gets `open_failed`/`identity_check_failed`/`bind_rejected` with `invalid_request`, `Effect::None` and no facts; the core learns only that it was refused, never the allowed set. The client prints the refusal itself (§5.6). Admission is a security boundary only where the core runs as another account or on another machine (`ssh://` and the test-only separate-user launch); on the same-user forms (a socket, `--server stdio`) the core already has the user's authority, as server design §4's "A server acts with its user's full authority" still says there, and admission prevents misdirected requests only. 6.4's help and the R7 README state this per form.

### 5.2 The tuple and its canonical form

An allowance is `scheme://[user@]host[:port]/path` (exact) or `…/path/` (prefix), or the SCP form `[user@]host:path[/]`; an `Open` is canonicalized by the same function before matching:

- **Scheme:** `ssh` for SCP-like, `ssh://`, `git+ssh://` and `ssh+git://`; `https`. Anything else is refused.
- **Host:** IDNA ToASCII (UTS-46, nontransitional), lowercased, no trailing dot; IPv4 only in canonical dotted decimal; IPv6 bracketed in RFC 5952 form; zone identifiers, empty labels and non-LDH labels refused.
- **Port:** the explicit one, else 22 or 443; compared as a number.
- **Path:** the operand actually sent (libgit2's grammar, never decoded for SSH); a `.` or `..` segment, an empty segment, `\`, NUL, a control character, or a percent-encoded `/`, `\`, `.` or NUL is refused; other escapes compare in uppercase hex, never decoded; one trailing `.git` on the last segment and one trailing `/` on an `Open` path are removed; case is preserved and compared exactly on both schemes.
- **`~` and SCP:** for SSH, `~/` marks a home-relative path and `~user` is refused. An SCP-relative operand (`host:owner/repo`) is home-relative (`~/owner/repo`) and matches only a home-relative allowance, except on gwz's known hosts (`github.com`, `gitlab.com`, `bitbucket.org`, `git/url_scheme.rs:372`), where gwz already treats `git@HOST:o/r` and `ssh://git@HOST/o/r` as one repository and the SCP operand canonicalizes to `/owner/repo`. For HTTPS `~` is an ordinary character.
- **Match:** exact when the allowance ends without `/`; prefix when it ends with `/`, requiring at least one further segment. `ssh://host/` or `https://host/` is a host-only grant: every path on that host and port, a full grant for the host (6.4 says so).

### 5.3 Service class and the push allowance

- The class is the client's own, from its request (§4.5), never the core's. Fetch class admits `upload_pack_advertisement` and `upload_pack_exchange` only.
- `receive_pack_*` is admitted only for a tuple in the separate **push allowance** (`--allow-push`, `gwz.server.allow-push`, `allow_push=`) and only under a push-class request. A push allowance does not imply the fetch allowance; a push needs both for its preflight and post-push reads.
- The core must open every planned member's receive-pack advertisement before its first `receive_pack_exchange`, so a refused push tuple fails the push before any member is pushed (2.3 red row).
- A plan-class request (§4.5: a push-class request type with `meta.dry_run = true`) admits `bind` and `check_identity` only. Every `open` is refused with `open_failed(invalid_request)` and `Effect::None`, even for a push-allowed tuple (2.3 red row: a `--dry-run push` with a push allowance in configuration; a core-sent `receive_pack_exchange` is refused that way and the fixture remote is unchanged; the same for a dry-run tag push and tag delete).

### 5.4 Identity, username, policy and limits

- **Identity:** an `Open` or `CheckIdentity` naming `explicit_key` is admitted only when its `key_path` is one the client's invocation named (`--identity`, or a `--remote-identity` value) and its `path_base` equals the `endpoint_path_base` the client sent; `ambient` only when the invocation named none for that request; `credentials_disabled` always. A core-named key path is refused.
- **Username:** SSH: `user@` in the matching allowance, else the client's SSH configuration for that host, else `git`; HTTPS: `user@` in the allowance, else none. A core-supplied `ssh_username` or `https_username` is admitted only when absent or equal to the client's choice.
- **Policy:** `Open.policy` must be one the client's own configuration permits for that destination; the client advertises that set per binding in `bound.policies` (this keeps the anonymous-then-helper HTTPS transition). Windows native policies also need §5.5.
- **Limits:** `deadlines` and `receive_limits` are clamped to the client's own ceilings; `--max-per-host`, its default of 32 (D-M) and pool policy are the client owner's.
- **Ports:** refused unless they match the allowance (§5.2); no prompt grants a non-default port.

### 5.5 Windows native authentication and redirects

- Under either native policy (`windows_configured` or `windows_default`), the logon session answers an NTLM or Negotiate challenge only for an `https` host named by `--allow-native-auth` (or `allow_native_auth=`) that is also allowed; otherwise the client answers no challenge and the exchange fails with `authentication`, `Effect::None`. Every host in a served `Open` is core-named, so this flag is required for native authentication under `--server`.
- Every redirect hop is canonicalized and admitted again, with the same service class and native-auth rule, before any credential, helper or native exchange; a hop from an allowed to a refused tuple ends the exchange. The existing HTTPS-to-HTTP refusal stands.

### 5.6 Supplying the allowed set; prompt; refusal

- **Sources**, unioned per invocation: `--allow-destination` and `--allow-push` (repeatable); `gwz.server.allow` and `gwz.server.allow-push` in the client's global Git configuration, read from the files and with the rules of `gwz.transport` (workspace and member configuration ignored with a note), each value `<server address> <allowance>` (the allowance is the last space-separated token) and applied only when the address equals the one in use, byte for byte after parsing; and the bridge parameters (§4.7). On Windows the pipe name changes at every start, so a configuration grant lasts one server lifetime (6.4 notes it).
- **Default under `--server`:** empty; admission fails closed.
- **Refusal text** (standard error, before the core's own result): `gwz: refused: the core asked to <fetch from|push to> <canonical tuple> (<service>, port <n>), which this command does not allow`, followed by the flag that would allow it. The tuple is canonical, control characters removed, hosts in punycode only. The client's receiver sends `open_failed` with `invalid_request`, `Effect::None` and no facts only for an admission refusal (any other invalid `Open` is a protocol fault of its binding, contract §6), and the core maps exactly that, under `cli`, to `server_destination_refused` (86) for the member, so `--json` records carry the code too. A `bind_rejected(invalid_request)` (an unknown, finished or already-bound `request_id`, or a request whose class admits no `bind`, §3.4) names no destination: the core treats it as a protocol fault of that binding and reports it through the binding's fault path, `NeverRegistered(ClientRefused(invalid_request))`, as `invalid_request` (1) with today's text "invalid transport session message" (gwz-core `src/transport_host/session.rs:105–108`); the client prints nothing for it. An `identity_check_failed(invalid_request)` (a core-named key path, §5.4) keeps today's mapping, `invalid_request` (1) with "invalid endpoint identity path" (`src/transport_host/session/driver/opening.rs:394–396`), and the client prints `gwz: refused: the core asked for an identity this command did not name`.
- **Prompt:** only when the client has a controlling terminal (`/dev/tty` opens, or a console is attached), never in gwz-py: the same canonical text, `Allow this repository for this command only? [y/N]`, and §1's limits on what it adds.

## 6. Amendment: HTTPS at the `cli` placement (plan 2.4)
