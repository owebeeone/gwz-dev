## 2. Invariant analysis (attacks that held, with evidence)

**CS1.9's bullets, each with its test-first row (plan :234–242).**

1. *Bounded `shutdown` disposing what the members hold within one cleanup bound and reporting what remains* (reuse §7:174; §13:251 amending CS:308, contract :313). `HostContext::shutdown` (`context.rs:262-264`) → `HostShared::shutdown(CLEANUP_BOUND)` (`:292-308`) → `Supervisor::dispose(Instant::now() + bound)` (`:164-177`). `CLEANUP_BOUND` is 5 s (`:74`), pinned by the first assertion of `context/tests.rs:280` against "reuse design §7". `dispose` closes the supervisor to new jobs (`:166`), waits with `wait_timeout_while` while `active() > 0` (`:168-171`, `active` = waiting + being polled, `:139-141`), counts `active() + quarantined.len()` (`:172`) and only then releases (`:173`). Attack on missed wakeups: the thread changes `polling`/`jobs`/`quarantined` and notifies while holding the mutex (`:196-204`), and `dispose` tests the predicate under the same mutex, so no finish can slip between test and wait. Attack on a job blocked inside `poll`: `polling` stays ≥ 1, the wait ends at the deadline, the job is reported and then polled to its end (`:205-210`); test `context/tests.rs:278-298` shows `took >= BOUND && took < BOUND + SLACK`, `ONE_PENDING`, the job dropped once it finishes, and the supervisor stopping while the host context lives. Row "returns within its bound": held.
2. *A second call returns the same report* (plan :241; the analogy is contract §8:420, repeated close). The report mutex stores the first report (`:306`) and any later call returns its clone before touching the supervisor (`:294-296`); test `:294-297` calls from a cloned handle after the job finished and still gets `ONE_PENDING` with `drops() == 1`. A concurrent call blocks on the report mutex, which the first call holds for at most its deadline, so it returns within a bound from its own start; test `:326-338` runs six barrier-released callers, each `< BOUND + SLACK`. Held.
3. *A quarantined job appears in the pending report* (Verdict-1 :68, carried; plan :238). `remaining` adds `quarantined.len()` (`:172`), and a quarantined job does not delay the wait, since it is not in `active()`; test `:340-361` shows `ONE_PENDING` in under 10 s with a 60 s bound, then the supervisor stopping and dropping it. Held.
4. *A drop after `shutdown` disposes nothing more* (plan :241). After `dispose` sets `released`, `HostShared::drop` (`:64-70`) calls `release()` (`:152-158`), which re-sets two already-true flags and notifies a stopped condvar; test `:363-385` asserts the finished job's drop count stays 1, no second poll, the drop under 1 s and `wait_ended(ZERO) && !running()`. Held.
   *The reading the code takes on quarantined jobs.* The question posed: is "a drop after `shutdown` disposes nothing more" consistent with quarantined jobs "which hold their resources for the host context's lifetime" and "dropped when the supervisor stops"? The code makes `shutdown` the host context's end: it closes and releases the supervisor, so the thread stops once the running jobs finish and drops the quarantined ones then (`:218-226`), and a later drop finds nothing to release. The alternative reading, quarantined jobs kept until the drop, would make the drop release the supervisor and dispose them, which is exactly "more", so the plan's own test row forces the code's reading. The documents allow it: reuse §7:156 puts unfinished work "under the supervisor" after a disposal and §7:174 makes a drop dispose "the same way"; neither fixes when a quarantined job drops; the plan's "for the host context's lifetime" (:238) is the rationale for counting them, and the host context's life ends at `shutdown`, after which `open` and `supervise` refuse. Every planned caller exits after `shutdown` (CS6.6 :645, CS8.10 :904 step 4, server §15:1081) or drops without it (CS4.5 :523, reuse §7:177), so no caller can observe the difference. The doc comments say the reading plainly (`context.rs:100-103`, `:85-88`, module row :10) and `RustApi.md:155-158` matches.
5. *Dropping without `shutdown` disposes the same way and reports nothing* (reuse §7:174, §13:251). `HostShared::drop` → `release()`: no wait, no report, the thread polls the rest to their end and drops the quarantined ones (`:149-151`); CS1.4's tests `:192-254` pass unchanged. Held.
6. *`open(options)` takes `transport_off` into the session context; the snapshot never carries it; nothing derives it* (server §5:489-490; §8:704; plan :239). `SessionOptions.transport_off: bool`, public, documented, `false` from `new` (`context.rs:374-378`, `:388`); `open` destructures it into `SessionContext.transport_off` (`:405-416`) and touches the snapshot only to move it; the crate-private accessor `:352-356` is what CS3.10 (plan :457) reads through the gate. Structural evidence that nothing derives it: `open` contains no `environment.get` and no environment read, and the process-globals checker reports nothing new. Test `:405-440` opens, on one host context, one session with `true` and one with `false` for each of 10 switch-like names × 9 values, asserting `new` gives `false`, the snapshot holds the name, and `transport_off()` equals the option. Held.
7. *The snapshot is zeroized when its session ends, shown through the zeroizing type's own test* (server §4:326, §8:702; plan :240-241). The chain: `ClientChannel` drop → `Arc<SessionContext>` drop → `EnvironmentSnapshot` drop → each `Wiped` drop → `overwritten()` overwrites the allocation that held the value, spare capacity included, and returns it still allocated, which the drop then frees (`environment.rs:43-54`, `overwrite` `:210-219` with `write_volatile` and a `compiler_fence`). `into_encoded_bytes` keeps the allocation on both platforms, so the test's pointer-equality assertion (`environment/tests.rs:60`) is meaningful. Tests: `:51-64` inspects the live allocation after `overwritten()` (pointer unchanged, capacity ≥ 64, all zero over the whole capacity via `whole`, whose `set_len(capacity)` is sound because `overwrite` initialized every element); `:40-49` covers `u8` and `u16` buffers with poisoned spare capacity; `:66-71`'s `NotClone` trick compiles only while neither `EnvironmentSnapshot` nor `Wiped` is `Clone` (two blanket impls become ambiguous otherwise), so the session context's drop is the snapshot's only one; `context/tests.rs:442-464` shows the session context no longer upgrades once the client end drops.
