## 2. Invariant analysis (attacks that held, with evidence)

**S-P3-3's thread-local rule (the plan's first flagged choice).**
- *Across threads.* The mark is per thread, so a crossing on thread A never marks thread B; a closure on A cannot make an unrelated worker on B panic. Conversely the rule cannot see a closure that hands work to another thread and waits for it (a spawned thread crossing the same gate blocks on `crossing`, and the closure blocks on the join): that is a blocking closure, which the module doc already forbids, and the consequence is unchanged from round 1. Not a regression; recorded in §3.
- *Unwinding.* `CrossingMark::drop` restores the previous value, so a panic inside `f` (its own, or the nesting panic from an inner `cross`) leaves the thread unmarked and the gate unlocked once the outer `cross` frame unwinds: `_mark` drops before `_held`. The three nesting tests then call `revoke` on a spawned thread with a 5 s bound and it returns. A thread reused across operations (a worker pool) therefore never carries a stale mark. `Cell<bool>` has no destructor, so `CROSSING.with` cannot fail during thread teardown.
- *A panic caught inside a closure.* `catch_unwind` around an inner `cross` inside `f` catches the nesting panic before any lock was taken; `CROSSING` stays true, which is correct because the thread is still inside the outer closure, and the outer mark restores it later. `cancel()` called inside a closure enters a nested mark whose `previous` is `true`, so it restores `true`, not `false`: no window opens for a nested crossing after an in-closure cancel.
- *Cancel callbacks (implementer's choice 1).* `TokenInner::cancel` takes `pending` under the callbacks lock, releases it, then marks the thread and runs each callback under `catch_unwind` (`gate.rs:97-101`). A callback that crosses or revokes panics in `forbid_nesting` before taking any gate lock, and the panic is caught, so the reading thread can no longer be blocked on a gate's `crossing` lock by a callback, which is stronger than round 1 (there a callback could block behind an in-flight closure). `revoke` forbids nesting before it cancels, so a revoke attempted from a callback or closure has no half-effect: the token stays as it was. Test `a_cancel_callback_that_crosses_a_gate_is_stopped_and_the_canceller_goes_on`: the callback stops at its crossing and the canceller returns with the gate `Cancelled`.
- *Lock ordering.* The callbacks lock is never held while `crossing` is taken (callbacks run after it is released; a callback that would cross panics first), and `crossing` is never held while the callbacks lock is needed for anything but a brief `on_cancel` or registration drop inside a closure. No inversion.
- *Lock-free `state()` (choice 2).* `revoke` stores `revoked = true` while holding `crossing`, so at the instant the store becomes visible no closure is in flight and any later `cross` sees the flag after acquiring the lock (the mutex orders it; the Acquire/Release pair covers the lock-free reader). A `state()` that reads `Revoked` therefore reads it only when revocation is final; one that reads `Live`/`Cancelled` while `revoke` waits on an in-flight closure is correct, since the gate is not yet revoked. Inside a crossing's closure `state()` cannot see `Revoked` (the closure holds the lock `revoke` needs and an upgraded `Arc`), which `state_inside_a_crossing_returns_the_gates_state` confirms. The dead-session arm (`strong_count() == 0`) agrees with `cross`'s failed upgrade. Held.

**S-P3-2's quarantine (the plan's second flagged choice).**
- *Owed resources.* A quarantined job is neither polled nor dropped while the host context lives, so nothing it owes (a permit, a child) is released early; its finish is never assumed, the fail-closed direction the reuse design §7 wants for stuck disposals. Once released, the quarantined jobs are dropped outside the lock, so their `Drop` releases what they own, and a `Drop` panic is contained by `discard`. Nothing is released "never": the host context's end is the last owner's end. The cost is that a quarantined job's resources persist for the host context's lifetime (in gwz-py, the interpreter's), recorded in §3 for TR1.4b's `shutdown` report.
- *`wait_ended`'s meaning (choice 3).* `ended = released && !running`; `running` is cleared only after the quarantined jobs have been discarded (`context.rs:136-139`), and finished jobs are discarded inline before the relock (`:112`), so `wait_ended == true` means every job the supervisor ever held has been dropped. A never-started supervisor is ended as soon as it is released. Held.
- *Wakeups and races.* Every state change happens under the lock followed by `notify_all`; the quarantine-only wait re-checks in the loop, so no wakeup is lost. `released` can only be set once no `HostContext` handle exists, so no `supervise` can race the exit branch or push while the quarantined jobs drop. Held.

- *`from_os_pairs`' refusal path (choice 5).* Analysed in §0: the rest of the input is drained and, through `Wiped`, overwritten; for byte pairs the decode's scratch buffers are wiped inside `from_bytes`. A refusal leaves nothing unwiped that core touched. Held.
- *Windows `CompareStringOrdinal` arm (choice 7).* Length inequality implies inequality under a per-unit case mapping, as std relies on; `i32::try_from` failure or an API failure (return 0, only for invalid parameters, which non-empty names of equal length never are) yields "not equal", so the worst case is a duplicate kept rather than a value hidden, and the Windows test's `get_envs().count()` assertion would surface it. The `TRUE` and `CSTR_EQUAL` constants and the five-argument signature match `windows-sys` 0.61 as std uses them; the implementer reports the arm clippy-clean for `x86_64-pc-windows-msvc`. The two temporary `Vec<u16>` copies hold names, not values, and are freed unwiped; the zeroization claim covers the snapshot's own buffers, as the docs now say. Held.
- *Windows probe into a pipe (choice 12).* The probe's environment is the synthetic snapshot; the parent prints none of it, and `String::from_utf8(...).unwrap()` on the pipe could only ever print synthetic ASCII. The probe prints the live environment only if a developer both sets the marker variable in their own shell and runs the ignored test with `--nocapture`. Held.
- *New limits.* 32 MiB leaves 32 MiB for the reply envelope, more than any `LogReadResponse` envelope needs provided CS2.10 counts each record's encoded size (a CBOR array adds no per-element framing beyond the record's own encoding); one hour bounds every close, so a driver cannot request an unbounded close bound, which is the direction O5 and §8 want. Neither cap can overflow `Instant` arithmetic. Held.
- *Fail-closed direction, braces, cfg boundaries, file sizes.* An ended session's gate still refuses effects and ignores reports; `open` still validates before construction; every new arm is inside `cfg_if!` or an enclosing module; every control-flow body braced; every file under 500 lines (largest `environment/tests.rs`, 416). Held.

## 3. Risks and next action

- **Nesting from `Drop` during unwinding.** The rule now panics instead of deadlocking. If a later step places, inside a closure's frame, a guard whose `Drop` crosses a gate, and that closure panics for any reason, the nesting panic escapes a destructor during unwinding and the process aborts. Round 1's code deadlocked in the same double-violation, so this is not a regression, but the module doc should say the rule includes crossings made from `Drop` impls of values that live inside a closure. CS2.4, CS2.5 and CS2.9 (whose registration guard "drops on thread exit or unwind") should keep such guards in the worker's frame, outside any closure.
- **Cross-thread hand-off inside a closure** is undetectable by a thread-local mark; a closure that blocks on another thread's crossing still hangs `revoke`. The "must not block" rule carries the load; CS2.11's spool writes and CS3.7's transport open should be reviewed for it.
- **Callbacks may no longer report.** A cancel callback that wants to record anything through the gate now panics (caught). CS3.7's registration must signal its runtime without a gate crossing, and any observation of the cancel must be reported by the worker at its next crossing.
- **Quarantined jobs hold their resources for the host context's lifetime.** TR1.4b's bounded `shutdown` should count quarantined jobs in its pending report, and CS3.5's jobs should release a permit in `Drop`, not only in `poll`, so the release at supervisor end is real.
- **Carried unchanged from round 1:** a session context must never drop with a live, uncancelled token (CS2.2, CS2.12); `revoke` under a busy reporter (CS2.12); bounded queues by counter, never `with_capacity(limit)` (CS1.2); CS2.10 counts encoded record sizes; the Windows-only tests are first observed in Windows CI at the Phase 1 exit.
