## 2. Ruling on the ten applied choices

Judged against the RemPlan @ bab5a81 dispositions. None goes beyond them; no fresh round.

1. **B5 — driver-captured environment (§5.6).** Within. The disposition's substance is "captured once; no core thread reads the environment; environment stability kept". The B5 inventory row for `with_local_transport`'s snapshot already says "Captured by the driver and passed in", and O9 plus the checker would flag an environment read inside the extension's `open`, so driver capture is the only placement consistent with the plan's own principles. Deriving `SshEndpointConfig`/`HttpsEndpointConfig` per network operation from the raw snapshot keeps B5's closure evidence (changing `HOME`, `SSH_AUTH_SOCK`, `GIT_SSL_CAINFO` after `open` changes nothing) and honours the surviving GwzPyTransportDesign §2 clause (lines 51–54) that local-only operations never parse proxy/CA settings.

## 3. Findings (new material)

### [P3-14] The thread that handles cancel frames is unspecified across the new reader/admission split, so §7's in-order claim is unsupported
- **Location:** §5.1 line 181 ("Roots are resolved on the host's admission thread, never on the thread that reads the channel"); §5.1 line 184 (record, token and gate created "at admission", which follows resolution); §4.2 line 159 ("A target that the session never admitted gets `operation_not_found`"); §7 line 348 ("The host handles frames in order, so the cancel finds the admitted operation and its token"); §15.5 line 526.
- **Violated invariant:** O7 — the handle the client will cancel through exists before the action; O2 — a defined single reply.
- **Sequence:** reader thread takes `SessionCall(submit, call_id 7)` and hands it to the admission thread, which is resolving the workspace root (filesystem I/O); the reader takes `SessionCall(operation.cancel, target call_id 7)`. Nothing says cancel frames are handled on the admission thread after the calls they name; an implementation that handles cancels on the reader thread (the natural choice, since cancels of running work must not wait behind resolution) finds no record or token, answers `operation_not_found`, and the operation is admitted and runs uncancelled. Read strictly, §7's sentence forbids this but then makes every later frame — reads and cancels for other operations — wait behind each request's resolution, a latency consequence the text does not state.
- **Impact:** a conforming implementation can lose a cancel in the resolution window and fail §15.5's protocol test; the alternative reading serialises all frame handling behind filesystem resolution.
- **Required correction:** either create the record, token and gate when the call frame is taken off the channel (before resolution; a resolution failure settles the record), so a cancel always finds a token; or state that call frames are handled sequentially on the admission thread and that a cancel naming an outstanding call is held until that call is admitted or refused — and say which thread handles which frames.
- **Regression test:** §15.5's protocol test with a resolution latch: the cancel is sent while the submit's resolution is blocked; the operation settles `Cancelled` and its handler never runs.
- **Classification:** bounded correction.

### [P3-15] `diff.output` logs have no release short of session end, so the new 64-log cap has no per-log release for them
- **Location:** §4.2 line 148 (end-stream "ends a `diff.output` reader stream. On `log.output` it also releases the log"); §5.4 lines 249–252 ("At most 64 are open at once … They are released, and their spools deleted, when the session ends"); §1 line 43 ("open `diff.output` and `log.output` logs | 64").
- **Violated invariant:** a lifecycle pair needs both halves; "open" is undefined.
- **Evidence:** taut-shape's contract (TautShapeArchitecture.md 106–107): a log has an "Operation-scoped, finite lifetime: created by the producing call, released on close / EOF-drain / TTL / last-stream-end / disconnect"; gwz-core's `DiffLogRegistry::release(log_id)` exists (`log_service.rs` 389) and its doc (333–334) says release "on the last reader frees the operation's retained render state". The contract adopts none of this for `diff.output`.
- **Reproduction:** a long-lived `Client` runs 65 `diff` calls with byte output, each read to EOF and end-streamed; per the text only session end releases `diff.output` logs, so the 65th `diff` is refused `transport_session_full`. Today's registry has a release path the contract does not name.
- **Impact:** an implementer following the text either caps diffs per session at 64 or invents the meaning of "open".
- **Required correction:** define "open" and adopt taut-shape's release rule for both log kinds: a log is released when its producer has sealed or closed and its last stream has ended (the existing `DiffLogRegistry::release`), with session end as the backstop; keep `log.output`'s end-stream-releases rule as the stated special case.
- **Regression test:** 65 sequential diffs read to EOF on one session succeed; 65 diffs whose streams are left open refuse the 65th; ending those streams admits it.
- **Classification:** bounded correction.

### [P3-16] Log appends are not a gated resource, so revocation cannot stop a detached producer while close step 7 deletes its spool
- **Location:** §5.6 lines 285–293 (gate covers the event log and terminal, locks, transport runtime construction, "log registrations"); §8 step 7 line 361 ("releases the session's `diff.output` and `log.output` logs and deletes their spools"); §5.6 line 293 ("A detached worker therefore cannot touch session state"); §15.9 line 547 ("session state is unchanged").
- **Violated invariant:** O8 — a worker reaches session resources only through its gate; revocation makes a detached worker harmless "by construction" (RemPlan B4).
- **Sequence:** a `log` direct call's producer is blocked inside libgit2 walking a large repository; close reaches the bound; the gate is revoked; step 7 releases the log and deletes its spool; the producer resumes and appends records to the released log and its spool file — appends are not in the gated list, so nothing drops them. On Windows the deletion of an open spool fails and step 7's guarantee is false; on POSIX the writes go to an unlinked file.
- **Impact:** §15.9's "session state is unchanged" cannot be met for the log registries; spool deletion at close is unsafe under a detached producer.
- **Required correction:** list log appends, seal and close among the gated reports that a revoked gate drops (and a cancelled gate refuses); step 7 then releases logs safely.
- **Regression test:** detach a `log` producer at the close bound, release it afterwards; assert no write reaches the spool path and the registry holds no entry.
- **Classification:** bounded correction.

### [P3-17] The reply kind for a unary or direct call whose record does not end `Completed` is unspecified
- **Location:** §4.2 line 141 (unary: "the reply is the method's final response, sent when the operation ends"); §5.2 lines 221–224; §6 lines 326–329 (maps terminals onto `OperationResult` only); §5.3 line 230 (queued operation "settled `Cancelled` … and the cancel is answered" — the unary call's own reply is not mentioned); §8 step 2 (direct calls "settled `Cancelled`"); §8 step 5 (detached operations).
- **Violated invariant:** O2 — one reply, of a defined kind; §15's "typed fields and codes".
- **Reproduction:** a unary `fetch` is cancelled while queued. Its terminal is `Cancelled`; its reply is either `SessionError{cancelled}` or `SessionReply{FetchResponse with failed status}`; the text gives no rule. The same holds for a direct `status` settled at close, a detached unary operation, and a handler that returns a model error. Today's native `call` raises for a refused or cancelled operation (`transport_session.rs` 222–227 via `refuse`), so the bridge's cancel-and-join (§10) expects an error from the call and `operation_expired` from the cancel.
- **Impact:** two implementations or bridges can diverge; §15.12's cancel-and-join test has no defined expectation for the call's own reply.
- **Required correction:** state that a unary or direct call whose record ends `Cancelled`, or `Failed` without a response, receives `SessionError` carrying the terminal's first `GwzError` and the `ResponseMeta`; a handler that produced a response, even with a failed aggregate status, gets `SessionReply`. Say what `operation.cancel` on a waiting direct call does (settle `Cancelled` before it runs).
- **Regression test:** cancel a queued unary call and a waiting direct call; assert `SessionError{cancelled}` for both on both bridges.
- **Classification:** bounded correction.

### [P3-18] `call_id` monotonicity is a client obligation with no host rule, and the cancel disambiguation rests on it
- **Location:** §4.1 line 129 ("unique and increasing within the session"); §3 lines 93–97 (protocol errors: only reuse of a *still outstanding* id); §4.2 line 159 ("Because call IDs increase, the host can tell an unseen `call_id` from a spent one").
- **Violated invariant:** a stated protocol invariant must have a host-side consequence; the not-found/expired distinction the bridge relies on must be sound.
- **Reproduction:** a stream bridge or third-party client sends call 5 after call 9 has been answered. §3 does not make it a protocol error, so the host accepts it as a new call. Now `operation.cancel(4)` (an id never used) returns `operation_expired` ("spent") rather than `operation_not_found`, and a call reusing an answered id (3) is accepted as a new call, so "spent" no longer means "answered".
- **Impact:** §4.2's inference is exact only for clients that never violate an unenforced rule; the bridge's "already finished" rule inherits the ambiguity.
- **Required correction:** add to §3 that a `SessionCall` whose `call_id` is not greater than the highest `call_id` received is a protocol error (or, if the lane prefers a softer rule, is refused `invalid_request` without ending the session) — one of the two, stated.
- **Regression test:** stream-bridge test sends a lower id and asserts the chosen behaviour.
- **Classification:** bounded correction.

### [P3-19] O9's absolute wording contradicts the contract's own permanent exceptions on the session path, and both paired paragraphs copy the absolute
- **Location:** O9 line 79 ("Code on the session path reads no environment variable and no process-global mutable state"); §5.7 line 297 ("The contract's O9 is met when neither allowlist holds a `debt` entry on the session path"); §5.7 table row 1 and §5.8 line 318 (ordinary builds keep `TIMEOUT_STATE` and libgit2's process-wide options); GWZDesign paragraph line 13 (same absolute sentence); GWZRequirements bullet 6 ("Code on the session path MUST NOT read the environment or process-global mutable state").
- **Violated invariant:** the paired paragraphs make the same claims as the contract, and the contract's acceptance criterion is single-valued.
- **Evidence:** `transport_support.rs` 11–25: `TIMEOUT_STATE` is a static consulted by `ensure_server_timeout()` at backend creation; the allowlist marks it and the two libgit2 options `permanent`. §5.2 line 219: in ordinary builds "the handler runs with the default backend", i.e. on the session path.
- **Reproduction:** in an ordinary build the session path creates a `Git2Backend`, which reads and freezes `TIMEOUT_STATE`; O9 and the REQ bullet say MUST NOT; §5.7 says this is acceptable.
- **Impact:** read literally, O9 can never be met (libgit2's option is process-wide by dependency); read per §5.7, permanent entries are fine. A reviewer of the implementation cannot tell which criterion applies.
- **Required correction:** reword O9, the GWZDesign paragraph and the REQ bullet: "… no process-global mutable state other than the inventoried `permanent` entries, which carry no session-relevant state or are imposed by a dependency (libgit2's server timeout in ordinary builds)".
- **Regression test:** documentary; each permanent allowlist entry states its reason (already true for all 11).
- **Classification:** bounded correction.

### [P3-20] O7 is narrowed to "the session path" while the operator's O7 covers any threaded or async API, and the after-launch handle is kept without a sunset
- **Location:** O7 line 74 ("Nothing on the session path returns a control handle after the action has begun"); §5.2 line 218 and §14 line 483 ("The existing `TransportRequest::cancellation_handle()` stays for the legacy path only"); §9 line 389 (keeping the legacy entry points "is an implementation choice"); GWZRequirements bullet 4 ("No API on the session path may return a control handle after the action has begun"). Operator direction O7: "in any threaded or async API … returning a handle after launch is a defect".
- **Violated invariant:** the contract states the operator's fixed rule as given.
