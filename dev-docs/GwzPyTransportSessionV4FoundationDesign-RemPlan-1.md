# Python transport session v4 foundation — second design remediation

Date: 2026-09-24. The first remediation tuple is **NO-GO** at root `11358352a237a673ecf0fd82347b45ca4aca8950`, gwz-core `d43b1474566eb607e2fb6d9d2da1b7419149f1dd`, gwz-py `0ffc4cb7bbdeff8244ee4c5c78c4b3d1f91f6753` ([verdict](GwzPyTransportSessionV4FoundationDesign-Verdict-1.md)). The [Consistency](GwzPyTransportSessionV4FoundationDesign-ReviewConsistency-1.md), [Safety](GwzPyTransportSessionV4FoundationDesign-ReviewSafety-1.md) and [Surface](GwzPyTransportSessionV4FoundationDesign-ReviewSurface-1.md) re-reviews are filed verbatim. This plan is one consolidated correction across the V4 design, the paired core paragraphs and the caller guide. It is remediation round 2 of at most 2. No implementation starts before the corrected tuple reaches GO.

No disposition changes an ownership rule, a transfer or the single-arbiter rule. B8 removes a special case rather than adding one: local submitted operations stop being minted natively and use the reviewed issuance and transfer path (reserve, T1, T2) that network operations already use. The rest renames one code, makes one reported field provable, states when owner clocks fault the Client, replaces a shared Python future with the native record the other waiters already use, declares one synchronous core call that the design already relied on, and corrects text.

## Blocking findings

| Finding | Disposition | Closure evidence required |
| --- | --- | --- |
| **B8** — Consistency R2-C-P2-1; Safety P3-7 and §3 residuals | Withdraw native minting and give local submitted operations every v2 guarantee. (1) `merge` and `clone_local_workspace` submissions are issued before their first await, as v2 §2 requires of unary and stream forms: `reserve(request_id, Local)` with a generated request ID when none is given, T1 `begin_attempt`, then T2 `claim` inside native `submit`, all through `_admit`. A cancellation while the native call is queued settles `Attempting → Cancelled(NotRegistered)`; the late claim reads that terminal, so the handler never starts, and the helper detaches the refusal onto the raised exception and releases its record (§11 item 8). Rows L1 and L2 (native mint) are deleted. (2) A local claim takes one of the eight top-level slots and the 8 MiB ledger upgrade (S5, S6), as v2 §5 and §6 require of every top-level operation; it does no construction, capacity admission or registration. `faulted` refuses no local step. (3) A local handler has no cancellation checkpoint. Before acceptance, checkpoint 1 settles `Cancelled(NotRegistered)`. After acceptance, cancel and close record the intent and join, and the handler's own outcome settles the record (`Completed` or `Failed`, never `Cancelled`), which is v2 §6's outcome when normal completion wins the race. Cancel never returns `UnsupportedOperation`. (4) Close marks live local records close-owed with network ones (the eight slots bound the total), and its wait on `slots == 0` joins them, so close returns only after every submitted local operation has settled, and the report summarizes them. That join is bounded by the handler's local Git and filesystem work, not by an owner clock (§9, §14). (5) A local record's guard drop, handler panic or failed gate send settles it (`Refused/NotRegistered` before acceptance, `Failed`/possible after) and never sets `faulted`; only a network owner or the `Construction` guard does. (6) Because a local join can be long, native `cancel(id)` applies its intent and returns once the owner will decide; Python `cancel()` and `cancel_operation()` then join by awaiting the terminal with the off-loop wait `result()` uses, shielded, and read the retained cleanup. No join holds the bridge's two-thread control executor. (7) `MergeOperationHandle` follows the handle contract: its record is kept until its new `release()` or expiry, and `result()` and `events()` can be repeated until then. The round-1 rule that merge helpers release the record after reading the final response is withdrawn. (8) §11 item 10 states this as the clarification it now is, and the guide's limits, close and merge-handle text say it. | Submit a merge that blocks, then call close: close returns only after the merge settles, and its report summarizes the merge. `cancel_operation` on the running merge joins it and returns its cleanup; the merge's own outcome is reported, and a second `result()`, and `events()` after `result()`, return the same retained data until release. Saturate the default executor, submit a merge, cancel before native entry, then free the executor: the raised exception carries the operation ID, `Cancelled`/`NotRegistered` and effect `none`, the merge never starts, and 65 repetitions never refuse `TransportSessionFull`. Eight live top-level operations of any mix refuse a ninth with `TransportSessionFull` before effects. A local handler panic settles `Failed`/possible, and the next network admission succeeds with `faulted` clear. With two cancels joining long merges, `close()` can still start. |
| **B9** — Surface P2-1 | Name the faulted refusal for the permanent condition it reports: **`TransportGenerationFailed`**. It replaces `TransportGenerationBusy` for the faulted state everywhere in V4 (§3.6, I8, S2, S4, S7, A6, A8, §7.6, §11 item 7, §12, §13, §14) and in the guide's refusal table and limits paragraph. The guide's table row and limits paragraph use the new name, and no V4, core or guide text uses `TransportGenerationBusy` for the faulted state. |

## Nonblocking findings folded into the same patch

| Finding | Disposition |
| --- | --- |
| Safety P3-9, Consistency R2-C-P3-3 — the owner-clock premise | §3.5, §12 and §14 name the state: an owner clock wins only against a **stalled** supervisor, one that is neither driving nor holding core's session mutex. An exited supervisor is covered by the §6.3 final retirement pass, so owners' futures return first. Every owner-clock win against the installed generation sets `faulted`: A8 settles `Refused/NotRegistered` with `TransportGenerationFailed`, and the clocks on A10's registered cleanup and the A12, A13 and C1 finishes join C6. Construction clocks act on a runtime that is not yet installed and keep §3.6's construction rule. §14 records that a clock win under scheduling delay beyond the one-second margin also faults the Client, the conservative direction. Test 4 adds the three setup steps: stall after construction; hold an admission or capacity gate so that phase 1 is pending; let the handler return without core I/O (after a cancel that completes its reply waiters) so that finish is reached. Closure: with no live operation, stall the supervisor; the first phase-1 clock win faults the Client and the next network attempt refuses `TransportGenerationFailed`. Run as written, test 4 reaches both owner-clock branches. |
| Consistency R2-C-P3-1 — the capability wrapper re-types preflight refusals | §7.6 rule 1 states that preflight refusals reach the caller unchanged: `TransportGenerationFailed` from a faulted session, the closed-session `InvalidRequest`, and typed construction errors. The Client's capability check re-types to `UnsupportedOperation` only a genuine absence: a bridge without `transport_capabilities`, an `UnsupportedOperation` from it, or a response without the requested identity support. §1 lists `gwz-py/src/gwz/client.py` among the changed files. Closure: on a faulted Client an identity-option fetch refuses `TransportGenerationFailed`; an injected preflight bootstrap failure surfaces as `IoError`, and a later call is admitted. |
| Safety P3-8, Consistency R2-C-P3-2(b) — `request_id_consumed=false` is not established before core's duplicate check | Keep the field's meaning (the ID's registration state in this generation) and make every `false` established by the reporting path. The session keeps a per-generation set of consumed request IDs: under the session mutex it gains a network record's ID when that record's owner learns `Registered`, `MayHaveRegistered` or `AlreadyRegistered` provenance. It holds at most 256 IDs of at most 128 bytes and only feeds the reported field; core alone decides admission (I5). A refusal reports `true` if the ID is in the set, or if the live network record holding the ID is `Admitting` or later, and `false` otherwise. This rule covers S2's synchronous live-claim refusal, which now has a defined value. The guide says the table shows values for an ID that no earlier operation used, and splits the duplicate row into "held by another live handle" and "already registered". Closure: register and release `r`; new handles on `r` refused at S6 and at the leadership timeout report `true`; a fresh ID refused the same way reports `false`; a live-claim refusal reports `false` while the holder is `Issued` and `true` once it is `Admitting`. |
| Consistency R2-C-P3-2(a), Surface P3-9, and the Surface and Safety residuals on the same row — `TransportSessionFull` | The table row and the limits paragraph cover all three limits. When eight operation slots are busy, the refusal clears after one of the caller's live operations finishes. When 64 records or the result ledger are full, it clears after the caller releases finished records that its own code owns and no longer needs, or after they expire. The refusal's message names the limit. The guide states that releasing a record removes it for every holder of its handle or ID. |
| Safety P3-6, Consistency residual — the shared `accepted()` future | Replace it. A `threading.Lock` guards each handle's attempt flag; the first `accepted()` caller runs `_admit`. Every other concurrent caller waits for the native record to reach `Accepted` or `Terminal` with a native condvar wait run off the loop like `result()`'s wait, awaited shielded, then projects its own outcome. A caller whose own task is cancelled applies v2 §2: it cancels and joins the operation and raises `GwzOperationCancelled`. The other callers observe that terminal as the typed pre-acceptance cancellation, never as a `CancelledError`. No Python future is shared, so no caller's cancellation reaches another's wait, and callers on other loops complete from the native record if the first caller's loop stops after native entry. Safety's closure test has the first and third callers observe the admitted handle after the second is cancelled. Under v2 §2, a cancellation that lands before acceptance cancels the operation for every caller, so this plan keeps v2 §2 and tests both timings. Closure: three threads with three loops await `accepted()` while admission is held. Cancelling the second before acceptance gives it `GwzOperationCancelled` and the others the typed cancellation refusal. Cancelling it after acceptance gives all three the handle, and the second's cancel then joins the accepted operation. Stopping the first loop after native entry lets the others complete from the native terminal. |
| Surface P3-7 — `cancel()` on a refused handle | The guide's handle contract and V4 §8 state `cancel()` for every state. On an unstarted handle it records `Cancelled` with effect `none`. On a refused, cancelled or finished handle it returns the retained `TransportCleanup` at once without raising (row E1). On a running operation it joins. The example's comment says so. Closure: on the consumed-ID and second-refusal paths the refusal itself propagates. |
| Surface P3-8 — `release()` under task cancellation | V4 §8, §11 item 9 and the guide's handle contract state that `release()` completes its native removal and the bridge's own bookkeeping even if the awaiting task is cancelled, then lets the cancellation propagate, as `cancel()` and `close()` do. The guide also states `release()`'s return contract: it returns `None`, a live operation refuses `OpenOperation`, and a repeat reports `OperationExpired`. Closure: in both of Surface's reproductions no record is retained. |
| Consistency R2-C-P3-4 — mechanical defects | The §5.2 terminal and release rows T1–T3 become E1–E3, so T1–T4 name only transfers, and §12 cites E2 and E3. A3 types construction failures as a typed construction error: `InvalidRequest` (for example `HOME` unset), `IoError` (a bootstrap failure or clock win) or `InternalError` (an unwind). Test 7 closes a Client holding 56 issued handles and 8 live operations. §3.6's "four ways" becomes "exactly three ways" (Consistency residual). |
| Safety and Consistency residuals — no declared synchronous generation close | §6.1 declares `TransportRuntime::close_generation()`: synchronous, it marks the runtime closed and closes its endpoint and driver sessions, the synchronous prefix of today's `shutdown()`; waiters wake with `Closed`, and physical cleanup still runs in `shutdown()`. A11, A14 and the `Construction` drop use it. The core design and requirements paragraphs list it. |
