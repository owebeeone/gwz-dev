# Operation cleanup ownership — replacement design boundary

Date: 2026-09-23. Status: **DRAFT, new design object; review required**.

This is the redesign called for by the [operation-session NO-GO](GwzOperationSessionProtocol-Verdict-3.md), not a third correction to that stopped object. It selects an owner for work that outlives a cancellation wait. If accepted, its lifecycle rules replace the cancellation, close, orphan-retirement and cleanup-report claims in the rejected [operation-session draft](GwzOperationSessionProtocolDesign.md) and [caller guide](GwzOperationSessionCallerGuideDraft.md). Its [caller-facing companion](GwzOperationCleanupCallerGuideDraft.md) is part of this design review. No schema, implementation, Python activation or release is authorized by this draft. The existing `gwz-transport` discrete stream messages and their Taut envelope are unchanged.

## Decision and invariant

Choose a **receiver-owned cleanup supervisor with charged, transferable scopes**, rather than a guaranteed time to physical termination. An operation's execution and physical cleanup are distinct states. The five-second wait is a reporting interval, never proof of completion. There is no unconditional 35-second orphan-retirement guarantee. If a native handler or physical disposal never finishes, its owner and capacity charge remain until process termination; new work receives a typed capacity refusal at the published limit. This is an explicit availability limit, not a claim that cancellation can kill a synchronous Git thread. A future hard deadline requires a separately reviewed, genuinely terminable execution boundary.

Three facts have different meanings:

1. **Handler joined:** the Git/local handler and every child capable of mutating the workspace have stopped. No local workspace mutation from that operation may occur afterward. A cancellation signal or timed wait is not a join.
2. **Local physical drain:** after registration is sealed against new child work and all producers have joined, every request stream, connection checkout, helper and endpoint cleanup task owned by that scope has retired. A transient `pending_local_work == 0` before sealing is not proof. Completion requires a monotonic sealed-and-drained transition from the owner, not inference from one report snapshot.
3. **Peer confirmation:** whether the remote peer acknowledged cleanup. `peer_cleanup_confirmed == false` may remain false after local drain; it records uncertainty about remote effects, not locally pending work. It never alone forces client close or holds a local capacity charge forever. The operation's effect classification remains `none`, `may_have_applied` or `applied` and is not upgraded by local drain.

An immutable operation terminal is published when the handler and all mutation-capable children join. It records the actual action response or failure, including cancellation/effect uncertainty, but does **not** claim local physical drain. Cancellation racing successful handler completion preserves the observed handler outcome; requesting cancellation cannot rewrite success into `cancelled`. A pending handler has no terminal yet. The independent cleanup record begins at admission, remains queryable while charged, and becomes final only on sealed local drain. Its final report may still have `peer_cleanup_confirmed == false`. An accepted operation that never joins remains pending and charged; no terminal or successful close is fabricated.

## Ownership and state transitions

```text
admitted -> running -> cancellation requested -> handler joined -> draining
                    \-----------------------> handler joined -> draining
draining -> sealed + locally drained -> cleanup final

session open -> closing -> all handlers joined + all local cleanup final
                           + endpoint locally drained -> closed
route/owner loss -> closing -> atomic ownership transfer to supervisor
                                      -> same joins and drains, no reattach
```

Each admitted operation has one execution owner, one per-operation cleanup owner and one receiver charge. A network operation also has a request-local physical owner; a local-only operation has no endpoint. The session owns its shared endpoint and its shutdown scope. The supervisor is a process-local logical owner, not a new network connection or one new thread per cleanup. On route loss or last-owner drop, it atomically takes the operation workers, request cleanup tickets and endpoint owner under the receiver's lock before the route/session owner is released. The transfer carries the existing budget reservations; it cannot fail for lack of a newly allocated slot. It stops admissions and seals new child creation first, signals cancellation, then waits for actual joins and drains. A cancelled asyncio waiter does not cancel these owned tasks.

The physical host and its capacity epoch remain charged while any transferred request or endpoint cleanup is pending. A logical route/session record may retire after atomic transfer, but that does not free physical permits or permit a capacity-epoch resize. The receiver retains a bounded orphan record and any worker handle needed to join it. A later route cannot read, cancel or reattach to the old operation. When the final local drain occurs, the supervisor releases the physical charges exactly once; the remaining audit record expires on the ordinary bounded retention schedule. No live owner is discarded by TTL. Process crash is outside this in-memory ownership guarantee: a restart must not present lost volatile work as a successful operation or confirmed rollback.

The terminal/action record and the cleanup record have different release rules. `operation.release_v1` releases a completed terminal and event log only. A pending cleanup record and its charges survive release, including when no caller can still read it. A local caller's handle can continue to wait for its own cleanup after terminal release until cleanup becomes final; then the Python handle may cache the final report. Protocol reads after both release and cleanup retirement report `OperationExpired`. These records share the existing receiver byte budgets; cleanup records are fixed-size and charged at admission. The supervisor never retains unbounded events or action responses after route loss.

## Caller and message contract

This is a **replacement shape for the unpublished proposed version-1 methods**, not a wire compatibility change to a released API. Keep session and operation IDs bound to the originating Client/route; no global ID lookup. The existing action terminal/result schema remains typed and immutable, but its optional cleanup field is a snapshot only and cannot be interpreted as final local drain. Add a separately addressable `OperationCleanupProgressV1` with `phase` (`running`, `cancelling`, `draining`, `local_complete`), `handler_running: bool`, `pending_local_work: uint`, `peer_cleanup_confirmed: bool`, `effect`, and `local_completion_confirmed: bool`. `local_completion_confirmed` is true only on the monotonic sealed-and-drained transition; `pending_local_work == 0` alone does not set it. A final report has `handler_running=false`, `pending_local_work=0`, `local_completion_confirmed=true`, while peer confirmation may be false. The schema patch allocates additive field numbers and error codes and runs the normal Taut fingerprint/codegen gate; it must not hand-edit generated files.

`operation.cancel_v1(session_id, operation_id)` signals only that operation, then waits at most five seconds for **its** local completion. It returns progress, including `phase != local_complete` when the wait expires; it does not close the shared client or claim a final cleanup report. Repeating cancel is idempotent and observes the same scope. `operation.cleanup_v1(session_id, operation_id, wait_ms)` waits at most `min(wait_ms, 5000)` for the operation's local completion and returns current progress; Python exposes it as `await handle.wait_cleanup()` with a five-second wait per call. Calling it does not request cancellation. The owner checks apply to both calls. A caller may repeat `wait_cleanup()` until `local_completion_confirmed`, or proceed with other operations while the scope remains charged. If the scope cannot be observed because its route is gone, the supervisor still owns it. A completed operation whose cleanup already drained returns final progress without changing its terminal.

`operation_session.close` stops admissions and requests cancellation of all of **that session's** operations, then starts shared endpoint shutdown. It waits at most five seconds per call. If any handler, operation cleanup or endpoint cleanup is pending, it returns typed `ClosePending` with charged progress; a repeat call joins the same close task. A final close report requires all handlers and local physical cleanup to have actually finished. It may report peer cleanup unconfirmed. A successful final close means no handler from that session can still mutate the workspace. Context-manager exit propagates `ClosePending` rather than pretending cleanup finished; the Client object remains usable for repeated `close()` while reachable. If the caller drops it instead, the supervisor retains the unfinished work. Per-operation `cancel_v1` and `cleanup_v1` never escalate to session close merely because a peer did not confirm cleanup.

No successful terminal, cleanup or close report implies rollback of a remote operation whose effect is uncertain. The current `TransportRequest.finish()` and `Session::cleanup()` returning `CleanupReport` with nonzero `pending_local_work` cannot themselves satisfy the new finality predicate. Implementation must provide an owned cleanup ticket or equivalent retained join/poll handle for both request and endpoint cleanup, with a monotonic sealed-and-drained notification. If any background child can still mutate the workspace after the synchronous handler returns, it belongs to the execution scope and delays terminal publication. If request-local cleanup cannot be isolated from healthy peer requests on the same endpoint, version-1 overlapping admission is refused before `Accepted` until it can; operation-local cancellation may not silently tear down peers.

## Finite accounting and admission

The existing draft limits remain starting ceilings: 32 live logical sessions, at most 4 per route, 128 receiver accepted/unfinished operation scopes, 64 operation workers, 256 member workers, 256 MiB receiver terminal records and 64 MiB receiver events. This redesign additionally caps **active plus orphaned endpoint owners at 32** and **active plus orphaned operation/cleanup scopes at 128**. An endpoint owner reservation is taken before the first network admission, before endpoint construction or helper/environment access; each operation reserves its cleanup record and scope at `Accepted`. Transfer to the supervisor moves rather than duplicates those reservations. Orphaned handler workers remain in the 64/256 worker caps until joined. Terminal byte charges and bounded event retention obey the prior draft; retained cleanup records use a fixed small charge from the same receiver terminal-byte budget. No retention TTL frees a live physical charge.

Session open remains the cheap placement/capability path and may admit a local-only logical session even if all endpoint-owner slots are held by orphans; its first network operation then receives typed `CapacityBusy` before side effects. A new logical session above the 32/4 limits receives `SessionCapacityFull`. An operation above an active-or-orphan worker/scope/cleanup limit receives `CapacityBusy` before `Accepted`. A request needing a higher physical capacity while an orphan or live operation pins the installed epoch receives `CapacityConflict` before Open. Equal/lower capacity remains eligible if other slots exist. Refusals preserve the unchanged operator-supplied policy and do not evict a pending owner. Cleanup completion releases charges and wakes waiters. If physical work never completes, bounded saturation and typed refusal are the truthful outcome; the API must not advertise eventual capacity recovery on a fixed deadline.

## Review and implementation gates

1. Reproduce the old five-second case: block physical disposal, obtain `pending_local_work > 0`, lose the route, and prove the supervisor still owns and charges the exact request and endpoint. A zero snapshot before producer join must not complete cleanup. No incompatible capacity epoch may install; completion must release once.
2. Block a synchronous network handler outside a transport wait, cancel it and lose the route. Verify pending result/close, retained worker and scope charges, and typed saturation at receiver limits. If it later joins, publish exactly one terminal and complete local cleanup; never publish success or a 35-second retirement claim early.
3. Overlap A and B on one Client. Cancel A; delay A's physical cleanup and make peer confirmation false. `cancel()` reports pending, `wait_cleanup()` can later finish A locally, and B stays live throughout. `client.close()` is the only operation that cancels B. A final A report with peer confirmation false does not force close.
4. Race handler success with cancellation, terminal release with pending cleanup, owner drop with explicit close, route loss with result publication, and repeated cleanup/close waits. Assert one terminal, one physical-charge release, no cross-route read, no unowned worker and no workspace mutation after a final close.
5. Fill the 32 endpoint-owner and 128 operation-scope limits with orphans. Assert no extra physical admission, bounded receiver memory and truthful typed refusal. Local-only session open remains cheap; its first network attempt refuses before constructing an endpoint. Test process shutdown/crash reporting separately without claiming in-memory cleanup survives restart.
6. Before version-1 activation, settle the Taut shapes and codegen/fingerprint checks, qualify the actual Git/local handlers and core cleanup ticket, run the concurrent Python and route-loss tests, and obtain implementation/release reviews. Until then the rejected operation-session draft and Python Phase 6/7 remain NO-GO.
