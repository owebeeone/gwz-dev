# Python concurrent transport session — correction 1

Date: 2026-09-24. Status: **DRAFT for a new Consistency, Safety and docs-only Python Surface review. No implementation or Phase 6/7 activation authority.** This is the one corrected design object required by [the merged round-1 verdict](GwzPyTransportConcurrency-RemPlan-1.md). The rejected [first draft](GwzPyTransportConcurrencyRemPlan.md) remains historical. This design addresses the operator's [P2-1 finding](GwzPyTransportConcurrencyNoGo.md) and every blocking finding in the three first-round reports. Review GO accepts this contract only; a separate settled Code/State gate must accept implementation.

## 1. Scope and precedence

One Python `Client` keeps one `NativeCoreBridge`, one native `TransportSession`, and one long-lived core `TransportRuntime`. Network operations may overlap on that session. Each has its own request, cancellation, result, event cursor and cleanup completion; all share the same endpoint pools and physical capacity. A leased SSH or HTTPS connection still serves only one exchange at a time. Local-only methods neither construct nor depend on the transport host.

This document supersedes the singular `ReadyActive`, finish-before-next-operation, Python network-lock and one-completed-cancellation rules in `gwz-py/dev-docs/GwzPyTransportDesign.md` §§2–4. It also narrows that design's post-Closing refusal: new work is refused, while `close()` and the retained close report remain readable; operation handles and result/event/cancel/release lookups become invalid when Closing starts, so callers inspect them before close. It replaces `gwz-core/dev-docs/GwzRemoteTransportRetryPlan.md` §3 item 7, §6 and S1.4's no-non-idle-lease installation condition **for a shared Python endpoint** with §3 below. A differing physical capacity is refused before Git or credential effects while another operation or non-idle lease owns the endpoint, even between leases. It replaces `gwz-core/dev-docs/GwzRemoteTransportPlan.md` Phase 2's different-limit overlap exit row as specified in §3 below. It narrows `gwz-core/dev-docs/GwzV110Plan.md` S6.3's Python placement claim as specified in §7. The existing request/response Taut schema and public Git operation semantics do not change. These replacements become authoritative only on design-review GO and the corresponding core design/baseline update.

The accepted profile-3 [sequenced stream design](../gwz-core/dev-docs/GwzTransportSequencedStreamDesign.md) is independent of this session ownership correction. Python does not inspect transport Envelopes. Concurrent Python activation must use a core host with truthful delivery tickets, generation pinning and the profile-3 proof gate; a successful review here does not enable that host schedule or replace its proof. Profiles 1/2 remain subject to their ordered-carrier contract while retained.

## 2. Identities and owned results

At native session creation, generate an unpredictable 128-bit session nonce. Every **accepted** operation gets the next contiguous session-local serial, with public `operation_id` formed from nonce and serial. Pre-admission attempts use a separate internal token and consume no public serial. Core registration still receives the caller's `RequestMeta.request_id`, which is also the caller-visible result/event correlation key; it may be identical in two different clients because they own different core generations. In one Client, a request ID already used by the current core generation is refused with typed `InvalidRequest` before `Accepted`, including after the earlier operation completed; no same-generation reuse is promised. The core lifetime-used set enforces this rule. A later generation may accept that caller ID again, but the public operation serial remains distinct and the old generation's frames cannot attach. Successful registration consumes one of that generation's 256 IDs even if a later worker launch fails. A serial never wraps or reattaches to a later host generation. The bridge may not derive an operation ID by concatenating `op_` and a caller-supplied request ID.

Event, result, retained merge-response and completed-cancellation records belong to the native session, not the process-global `operations::STORE`. All session calls (`subscribe_events`, `wait_events`, `operation_result`, `try_operation_result`, merge lookup, cancel and release) first verify the nonce and an issued serial, then look up that session's record. A foreign or not-issued ID is a typed `InvalidRequest` before any record is read. The existing module-level compatibility functions keep an isolated legacy store; they cannot read or create a session-owned record. A two-client collision on caller `request_id` therefore yields distinct operation IDs and records, even if completion order is reversed.

An accepted operation owns its record through terminal result and cleanup. Each accepted ID publishes exactly one terminal outcome; publication occurs only after its `TransportRequest.finish()` completes. Event readers can observe events before terminal, but never a final result before cleanup. Dropping one event iterator does not discard another operation's result or release its host. A worker panic, failed worker launch after reservation, transport loss or close cancellation terminalizes the owned record and wakes every waiter. No error path may leave an accepted ID with no terminal result.

## 3. Physical capacity admission

Resolve the four `pool::Capacity` fields for each request exactly as the accepted retry plan does: both per-host fields from `max_connections_per_host`, `total=max(256,jobs)`, and pool `max_requests=max(1024,jobs)`. `jobs`, retry policy, member selection and per-operation fan-out stay local to that operation. Pool `max_requests` counts checkout requests; it is **not** the top-level operation, worker, event or result budget.

The native session serializes every initial or later physical-capacity transition with a leader, target capacity and cancellable waiters. Equal-target waiters wait for that transition for at most five seconds, without holding the state mutex or blocking independent host message pumps. On success they compare the completed installed value and may admit; on failure, cancellation or close they wake with that typed failure, without silently becoming another leader. A different-target request is refused `TransportCapacityConflict` before `Accepted` while the transition or any live operation/non-idle lease exists. It can be retried after all operations and their physical cleanup retire. If the host is quiescent, a later request may become leader for a different capacity; excess idle connections close under the existing bounded cleanup rule before its admission. Closing never starts a replacement transition.

If the installed value is already exactly equal, admission reads it atomically and does not call `install_capacity_pair`, reset idle timers or resize either pool, even when another request holds a lease. Installing **different** capacity requires zero live operations, zero non-idle leases and completed physical cleanup, not merely a gap between leases. A failed transition leaves no partially published installed value; the pair of pools, shared reservation authority and the published capacity either all represent the old value or all represent the new value. If physical installation has already changed one component and cannot roll back, the endpoint generation fails closed and drains before another request is admitted. A new request's registration and reserved worker slot are released on any failed admission. Core must use a typed host admission result that lets the Python bridge distinguish capacity conflict from full session admission; a display string is not an error discriminator.

The revised Phase 2 exit case is: overlapping operations with different **per-operation fan-out** may run when their resolved four-field physical capacity is identical, and their combined leases obey that capacity; reducing one operation's fan-out cannot evict another's connection. Operations requiring different physical capacities do **not** overlap: the second is refused before endpoint effects and can install its limits after the first and its cleanup retire. The old row's unconditional different-physical-limit overlap claim is not retained.

## 4. Bounded top-level work and admission truth

A session admits at most **8** top-level network operations (reserved, admitting, running or finishing). It runs at most **8** top-level native workers and **128** member workers across them, with at most **256** queued member work items in a bounded scheduler shared by that session. These are fixed session limits, independent of caller-controlled `jobs` and of pool `max_requests`. Each operation's `jobs` is its own upper bound; an explicit value above 128 remains represented in the request but cannot raise the session's physical worker ceiling. A queue producer waits for capacity without allocating another unbounded queue or holding the host pump/operation lock. Exhausting a top-level slot refuses `TransportSessionFull` before `Accepted`; it does not queue unbounded Python tasks. A failed thread spawn is fallible and releases every reservation; a spawned worker's unwind runs a completion guard and publishes a typed terminal failure. Close and cancellation cannot wait on a worker that never started.

`Accepted` means all of the following have happened: the session owns a unique ID and reserved result capacity, the request has passed placement and physical-capacity admission, a bounded top-level worker slot is reserved, core has registered the request, and a fallible native worker spawn succeeded. That worker waits at an admission gate while the session atomically allocates the next **public** serial, attaches the owned record and releases the gate; failed placement, registration or spawn consumes no public serial. It does **not** mean Git succeeded. `call()` performs the same preflight and then waits for its terminal response. `submit()` returns `Accepted` only after preflight; a high-level stream helper performs that submit on first iteration, then yields events. Both capacity refusals therefore surface *before* `Accepted` for all three forms. A failure after acceptance is a retained, request-attributed terminal result, never a second admission refusal. An incompatible policy raises Python `GwzBridgeError(code="TransportCapacityConflict")`; top-level or result-budget exhaustion raises `code="TransportSessionFull"`. Both are non-retriable while their stated owner remains; the former may succeed after all conflicting operations and cleanup retire, the latter when a slot/retention budget is released. The Python-only codes are stable bridge errors, not additions to GWZ's outer Taut enum.

The native bridge removes its `asyncio` network lock only after this admission contract is implemented. Separate Python event loops and threads call the same Rust admission state. Python task cancellation while pre-admission waiting removes that request's waiter; after `Accepted`, it cancels only that operation, joins its cleanup, then propagates `CancelledError`.

## 5. Core generation rollover and stale messages

The current mux/session retains at most 256 lifetime request IDs in one generation; pool checkout `max_requests` does not change that. Core counts caller request IDs actually consumed by successful registration, including a later worker failure, and refuses a 257th in that generation. The native session anticipates the limit before admission. At a quiescent boundary it stops new admissions, waits for all registered requests, transport tickets, endpoint work and physical cleanup to retire, then shuts down the old runtime and constructs a new runtime generation from the **captured first-construction endpoint configuration**, not a fresh process-environment read. The old generation's healthy idle connections close and are not promised to survive rollover. The new generation has a fresh transport session/Port identity and request namespace; public operation serials and retained result records remain native-session scoped and never reset. In-flight old-generation frames cannot attach to the new Port. A rollover has the existing finite cleanup deadline; failure refuses new operations with `TransportGenerationBusy` and leaves the old generation closing, never accepting an ambiguous request. Close racing rollover wins admission and joins cleanup. Failed pre-registration attempts do not consume a mux ID; an ID consumed by a successful registration is never reused in that generation. Public serials are contiguous because only successful acceptances issue them; a same-nonce serial at or below the high-water mark whose record expired yields `OperationExpired`, while a serial above it, malformed ID or foreign nonce yields `InvalidRequest`. The high-water mark is one fixed-size integer, with no lifetime tombstone table.

## 6. Bounded results, cancellation and close

The session stores at most **64** completed records and **64 MiB** of charged event/result/cancellation data, including active records and readers' retained snapshots. Before `Accepted`, each operation reserves its **full 8 MiB** lossless record allowance from the aggregate, including mandatory events, result and a small terminal-failure slot. Up to eight active operations can therefore reserve the entire 64 MiB; retained records and reader snapshots use the same ledger and may make new admissions refuse `TransportSessionFull` before Git or credential effects. On completion, the operation exchanges its reservation for its actual retained charge and releases unused capacity. An in-flight operation never loses its reservation to another record or reader. Events are sequenced per operation and occupy at most **2 MiB** of that operation's charge. Progress events may be coalesced only when their published schema permits it; required start, error and terminal records are never silently dropped. If an operation's own event or result exceeds its 2/8 MiB budget, the session cancels it if still running, completes transport cleanup, and retains an attributed `TransportRecordLimit` terminal under the reserved failure slot. It must not report a successful Git result or imply that effects were rolled back. This terminal carries `operation_id`, caller `request_id` and available transport facts in the existing `OperationResult`; unary callers receive it as `GwzOperationError.response` even without a handle. The Python-only `GwzOperationError.effect` is `"possible"` and the caller guide gives a reconciliation action; no Taut result field is added. Completed records expire after **15 minutes** or explicit `Client.release_operation(operation_id)`, whichever comes first, but an active reader retains its charged snapshot until it closes. A slow reader can reduce new admissions, not make storage unbounded. Expiry/release wakes capacity waiters. A terminal result is inspectable until that advertised expiry **while the Client remains open**; no successful result is silently evicted earlier.

`cancel_operation(operation_id)` targets a record from the same native session. For a live operation, repeated cancellation joins the same completion and receives the same `TransportCleanup`, including after A and B cancel in either order, while their records remain retained. The returned cleanup means transport finish and terminal publication have completed. `result()` then either returns an already completed successful `OperationResult` (if completion won the race) or raises `GwzOperationError` whose `response` is a retained failed `OperationResult` with a `Cancelled` error and whose Python-only `effect` is conservatively `"possible"` for an admitted operation; no unknown push effect is presented as safely retryable. The terminal event is observable before `events()` ends. For an already completed operation that was never cancelled, cancel returns the retained cleanup facts without retroactively changing the result. An expired same-session serial returns `OperationExpired`, distinct from a foreign or never-issued ID. `release_operation(id)` removes a completed record; a second release of that same issued ID reports `OperationExpired` rather than pretending that an unknown ID was released. Cancellation of one operation never cancels its overlapping peer. Close atomically enters Closing, refuses new work and result/event/cancel/release lookups, cancels every admission waiter and live operation, joins all request finish paths, then shuts the one current or rolling-over runtime down once. Close reports physical pending work once per owner. A shared native close completion survives any Python waiter cancellation; `Client.close()` and `__aexit__` shield and join it, propagate `CancelledError` only after cleanup, and a later close returns the retained identical report. Last-owner drop starts the same close, with awaited close the inspectable path.

## 7. Placement and Python caller surface

The Python 1.1 `TransportSession` has only its local endpoint configuration; it has no bound CLI endpoint or capacity owner. It therefore refuses explicit `transport.placement=cli` with typed `UnsupportedOperation` **before** runtime construction, credential access, handler work or mutation. Its capabilities advertise only `local`. This narrows the Python claim in the accepted Python design §4 and v1.1.0 S6.3; it does not remove Rust CLI/core placement or the later ability to design a Python CLI placement handshake. Omitted placement uses local. SSH agent/known-host, explicit key and gh HTTPS secrets remain endpoint-local and are absent from Python errors and events.

Existing `Client.fetch`, `fetch_stream`, `push`, `push_stream` and analogous network verbs retain their signatures and accept the existing `request_id=` metadata keyword. For a first-class pre-event ID, add `Client.start_fetch(**meta)` and `Client.start_push(..., **meta)` returning an `OperationHandle` only after `Accepted`; the same `start_<verb>` pattern applies to every network verb that offers a streaming form. The handle exposes immutable `operation_id` and `request_id`, `events()`, `result() -> OperationResult`, `cancel() -> TransportCleanup` and `release()`. The existing stream helpers remain convenience iterators; callers needing cross-task by-ID cancellation use a start method and share the returned handle. `Client.cancel_operation(id)` and `Client.release_operation(id)` also accept a handle's operation ID. A handle is tied to its creating Client and cannot read another client's record. If cancellation reaches a `start_*` task before acceptance, admission withdraws its reservation and publishes no operation. If acceptance already happened but the handle has not returned to the caller, the task cancels that owned operation, joins cleanup and then propagates `CancelledError`; it does not leave an undiscoverable live operation. A returned handle remains usable through the stated retention period until `Client.close()` starts. Handle methods may be awaited on different Python event loops/threads; the native session owns synchronization, while each awaited Python future stays on its creating loop.

The user-facing [draft concurrent-operations guide](../gwz-py/dev-docs/GwzPyConcurrentOperations.md) is the Surface review object. It states defaults, the two pre-acceptance refusal codes, retry conditions, start/cancel/close ordering and an executable first-day example. On review GO it becomes part of the package guide before activation. No raw transport Envelope, physical carrier or new core request/response method is exposed to Python.
