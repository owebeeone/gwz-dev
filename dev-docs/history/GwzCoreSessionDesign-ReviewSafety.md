## 1. Findings

### [P2-1] `TransportSessionFull` and `OperationExpired` have no wire code; both serialize as `io_error`, so "refused before any effect" and "already finished" are indistinguishable from I/O failure
- **Location:** contract §4.2 line 131 ("Error codes: all reused, none added: … `OperationExpired`, … `TransportSessionFull` …"); §4.2 line 127 (bridge treats `OperationExpired` as "already finished"); §5.1 lines 160–161 (`TransportSessionFull` refusals "before any effect"); §4.1 line 94 (`SessionError.code: GwzErrorCode`). Source: `gwz.taut.py` `GwzErrorCode` (669–838) contains neither; `src/model/mod.rs` 143/146 defines them Rust-side only; `src/protocol/convert.rs` 86–87 maps both to `Self::IoError`. Today's extension never crosses the wire enum (`native/src/error.rs` 19: `format!("{:?}", error.code)`), which is why the distinction works today.
- **Violated invariant:** a refusal that had no effect must be distinguishable from a failure after possible effect (proposals §5 closure paragraph; contract §5.1 "before any effect"); the bridge's "already finished" branch requires a distinct code.
- **Sequence:** (1) 64 operations queued; client sends `fetch` (unary) → host refuses `TransportSessionFull` → frame carries `io_error` (28). (2) Client sees the same code as a fetch that failed mid-exchange after refs may have moved; a retry policy keyed on "no effect" cannot be written. (3) Task awaiting a unary is cancelled; its reply lands first; the bridge's `operation.cancel(call_id)` gets `OperationExpired` → wire `io_error`; the bridge cannot apply §4.2's rule and (as today's `bridge.py` 372–374 does for anything but `InvalidRequest`) raises a spurious cancellation error for an operation that completed.
- **Impact:** both adapters are affected (frames are Taut on the in-process path too). Refusals-before-effect and benign expiries are reported as I/O failures; cancel-and-join surfaces false errors.
- **Remedy:** append `transport_session_full` and `operation_expired` to `GwzErrorCode` (append-only, G8-compliant), fix `convert.rs`, correct the "none added" claim, and state that the bridge keys the already-finished rule on `operation_expired`.
- **Closure test:** schema round-trip for both codes; §15.2 refusal test asserts `transport_session_full` through both bridges; §15.8 cancelled-unary test with the reply landing before the cancel asserts no error raised.
- **Classification:** bounded correction.

### [P2-2] `configure_transport_runtime` is a process-global, frozen-after-first-backend setting, not the session-wide setting the contract describes; one session can remove another's transport deadlines
- **Location:** contract §4.2 line 106 ("changes session-wide transport settings for operations admitted after its reply and leaves running operations unaffected"); §5.5 line 191; O5. Source: `transport_capabilities.rs` 34 → `configure_server_timeout_ms` → `transport_support.rs` 11–14 (static `TIMEOUT_STATE`), 43–47 (refused with `UnsupportedOperation` "transport timeout is process-wide and already in use" once frozen), 56–63 (libgit2 process-global `git2::opts::set_server_*_timeout`); per-operation runtimes read it through `gitbackend.rs` 59 → `transport_support.rs` 279–281 → `mod.rs` 55; `mod.rs` 34–38 sets `connect_timeout_ms = 0` when it is 0; `driver.rs` 174–175 sets no open deadline when `io_timeout_ms == 0`.
- **Violated invariant:** O5 — a session's deadlines are its own; the stated session scope.
- **Sequence A:** one process hosts two sessions (two `Client`s, or the CLI's in-process session beside an embedded one). Session A calls `configure_transport_runtime(0)` before any backend exists. Session B's later operations build runtimes with `io_timeout_ms = 0`, `connect_timeout_ms = 0`; a stuck host holds B's worker in `reply.get()` with no deadline until B cancels or closes. B never chose that. **Sequence B:** any operation has already run in the process (backend constructed, `frozen = true`); a session's `configure_transport_runtime(3000)` is refused `UnsupportedOperation` — the direct method the contract lists cannot do what it says after the first operation.
- **Impact:** cross-session control of deadlines (unbounded network waits inducible from another session); a documented method that is one-shot per process; in ordinary builds the libgit2 globals change running operations' next connections, contradicting "leaves running operations unaffected".
- **Remedy:** carry the timeout in session state (`open(options)`), pass it into `SshEndpointConfig.io_timeout_ms`/`pool.connect_timeout_ms` and `TransportRuntime::with_https` per operation; state that the libgit2 global remains process-wide for the default backend and is not session-configurable (or refuse the method in ordinary builds); withdraw "session-wide" until so.
- **Closure test:** two sessions in one process; A sets 0; B's open deadline is B's own (stuck-host fixture times out at B's value); a later A call with a different value is not refused.
- **Classification:** bounded correction.

### [P2-3] Push takes the workspace-wide cross-process mutator lock with a try-acquire, so the N∥N admission promise cannot hold for two pushes on one workspace
- **Location:** contract §5.1 class table line 150 ("N … `fetch`, `push` … may run alongside R and N operations"), line 154 (member-step lock), §15.2–15.3. Source: `push_member.rs` 58–64 → `mutation_guard.rs` 204–231 → 109 `WorkspaceMutatorLock::acquire_in` → `workspace_mutator_lock.rs` 13–23 (refuses `UnsupportedOperation` "workspace mutator lock is already held") → `platform_lock.rs` 7–25 (`flock(LOCK_EX|LOCK_NB)` on a fresh fd; separate open file descriptions in one process conflict). Fetch takes no guard (`handle_fetch.rs` 5–7, 77).
- **Violated invariant:** admission is the host's decision (proposals §5); an operation the host admits must not fail on a lock the host could have serialized; §15.2 "eight overlapping fetch and push operations … complete independently".
- **Sequence:** push P1 (N) on workspace W runs and holds `.gwz/locks/workspace-mutator.lock`. Client submits push P2 (N, same W); the class table admits it concurrently; P2's handler hits `acquire_in` → `EWOULDBLOCK` → `Failed(UnsupportedOperation)` with a workspace path hint, worded as if a foreign process held the lock. No effect, no queueing, no retry.
- **Impact:** the class table is unimplementable as written for push; §15.2/15.3 fail; users get spurious lock-held failures; the added per-member lock is redundant with the stronger lock push already takes.
- **Remedy:** classify push as W for its workspace (it already needs workspace-wide exclusivity across processes), or have N admission on a workspace acquire/await the mutator lease in the host before starting the worker; keep fetch as N with the member lock; document that the cross-process lock is a try-lock so only foreign processes can produce "already held".
- **Closure test:** two pushes on one workspace in one session complete without `UnsupportedOperation`; fetch∥push and fetch∥fetch stay concurrent.
- **Classification:** bounded correction.

### [P2-4] Retention (64 terminals) is smaller than admission (8 running + 64 queued = 72), so the outcomes of a client's own accepted, unreleased operations are evicted silently
- **Location:** §1 table lines 31–38; §5.1 lines 158–159; §5.4 line 185 ("when another operation's record becomes terminal beyond that, the oldest terminal record is evicted"); §4.2 line 112 ("Accepted … means that core owns the operation").
- **Violated invariant:** ownership "from admission until release, eviction or session end" must not lose the outcome of an accepted operation the client has not yet been able to read; refusals happen before effects, eviction here happens after them.
- **Sequence:** client submits 72 `submit`-mode operations — all admitted within the contract's own limits. They complete; at the 65th terminal the oldest terminal record is evicted. `operation.result` on the first returns `OperationExpired` (wire `io_error`, P2-1). For a push that succeeded the client cannot learn whether refs moved: a completed operation with "possibly had an effect" status.
- **Impact:** silent outcome loss reachable without exceeding any documented bound; the defaults are incoherent (attacked as coherence, per the deferral rule).
- **Remedy:** make retained ≥ running + queued, or count live records against the retained limit and refuse admission with `TransportSessionFull` before effect when the table is full; or evict only records whose result has been delivered once. State which. Keep "live records are never evicted".
- **Closure test:** submit running+queued operations, let all complete, read every result — none expired; admission against a full table is refused before effect.
- **Classification:** bounded correction.

### [P2-5] A reused outstanding `call_id` is refused with a `SessionError` carrying that same `call_id`, so the legitimate outstanding call receives a second reply
- **Location:** §4.1 line 99 (refused with `InvalidRequest`); §4.1 line 94 (`SessionError.call_id` required); §15.1; §3 line 74 (protocol errors end the session — reuse is not classified as one).
- **Violated invariant:** O2 — one reply per call, attributable to exactly one call.
- **Sequence (wire path; any non-bridge client, or a bridge bug):** call 7 (`push`, unary) is outstanding. A frame with `call_id = 7` arrives; the host answers `SessionError{call_id: 7, InvalidRequest}`. The client's demux completes call 7's waiter with `InvalidRequest` — the caller believes the push was refused before effect. The push completes; `SessionReply{call_id: 7}` arrives with no waiter (or a new one that reused 7) and is dropped or misattributed. Today's bridge treats `InvalidRequest` on its cancel path as benign, so a cancel-and-join proceeds as if nothing ran.
- **Impact:** one call, two replies; "refused" reported for work that ran to completion with remote effects; misattribution to later calls. The bridge's monotonic ids protect the in-process path only; the wire proof exists precisely for other clients.
- **Remedy:** define reuse of an outstanding `call_id` as a protocol error that ends the session (§3), or make `SessionError.call_id` optional for unattributable refusals (these are new messages, so that is a definition, not a change).
- **Closure test:** stream-bridge test sends a duplicate outstanding id; asserts the session ends (or an unattributed error) and that the original waiter never sees `InvalidRequest`.
- **Classification:** bounded correction.

### [P2-6] Per-operation environment capture on core threads lets trust/identity configuration drift between operations of one session, and races host-process `setenv`
- **Location:** §5.2 line 167 (each worker "runs `with_local_transport(meta, operation_id, handler)`. That builds the operation's own runtime"); §4.2 line 106 (transport settings framed as session-wide); §16 line 362. Source: `local_command.rs` 21, 33–46 (`std::env::vars_os()` per call; `HOME`/`SSH_AUTH_SOCK` in `mod.rs` 47–54; `GIT_SSL_CAINFO`/`SSL_CERT_FILE`, proxies, the `gh` environment); `TransportPlacement.md` 182 (capture of "startup timeout/pool policy"); today's extension captures once per session (`transport_session.rs` 373–378, cached `state.runtime`).
- **Violated invariant:** endpoint trust and identity are session-level policy the client can check first (`remote_identity`, `transport_capabilities`; contract §14 keeps the capability rule); lesson 4/O6 — core work must not depend on client-thread state at unpredictable times.
- **Sequence:** (1) client calls `remote_identity` under environment E1; (2) submits `fetch`, which queues; (3) another thread/task changes `SSH_AUTH_SOCK` or `GIT_SSL_CAINFO` (E2); (4) the fetch starts; its worker captures E2 and authenticates with an agent, CA or proxy the client never checked. Concurrently, `vars_os()` iterating `environ` on a core thread while CPython's `putenv` reallocates it on another is the concurrent read/modify Rust's `std::env` documents as unsound; today that window is once per session, the contract makes it once per operation, up to eight at a time.
- **Impact:** unobservable per-operation drift of trust roots, identity and credential-helper environment within one session; a probabilistic crash in the in-process library the contract targets.
- **Remedy:** capture `SshEndpointConfig`/`HttpsEndpointConfig` once at `open(options)` on the calling thread, keep them in session state, and build each per-operation runtime with `TransportRuntime::with_https(ssh.clone(), https.clone())`; give `with_local_transport` a variant taking captured configs; define `configure_transport_runtime` against that state.
- **Closure test:** after `open`, mutate `HOME`/`SSH_AUTH_SOCK`/`GIT_SSL_CAINFO`; a later operation's endpoint config equals the one captured at open (fixture-observable via known_hosts path and `remote_identity`).
- **Classification:** bounded correction.

### [P2-7] The client pump has no failure rule other than `recv() → None`; a pump that raises leaves every outstanding call pending forever while `send()` keeps succeeding
- **Location:** §10 lines 272–274; §3 line 74 (host-side protocol errors end the session; no client-side counterpart); §9 line 243. Proposals §8.3 place decoding in the pump.
- **Violated invariant:** O2's stand-in ("the channel's closure stands in for the reply") requires the client to observe closure; every outstanding call must get exactly one completion.
- **Sequence:** three calls outstanding. The pump receives a reply whose body fails Taut decoding for the expected response type, or `call_soon_threadsafe` raises for a loop that closed between the check and the call, or any other exception escapes the loop. The daemon thread exits; `recv()` is never called again, so the session never reports closure to the bridge; the three futures hang; new calls `send()` fine and hang too; `close()` sends `session.close` and hangs awaiting its reply. At interpreter exit the shielded cancel-and-join (§10) waits forever.
- **Impact:** a stuck client with no error, reachable from one unexpected frame; today's direct-call bridge always returns or raises.
- **Remedy:** specify that any exception in the pump closes the channel (extension `close()`), marks the bridge closed and fails every outstanding future with the typed closed-session error; a decode error for one call's payload fails only that call with a protocol error; the pump never exits without doing this.
- **Closure test:** inject an undecodable reply via a test host; assert every outstanding call fails with the closed-session error and subsequent `send` fails.
- **Classification:** bounded correction.

### [P3-1] Queue capacities and permit accounting for control calls are unspecified; "send never blocks" has no defined full-queue outcome
- **Location:** §3 lines 76–78 ("two bounded queues"; "send(frame) never blocks"); §9 line 242 (fails only "once the session has ended"); §10 line 274 (single async semaphore "so send() never waits"); §10 lines 276–279 (cancel frames sent from the cancellation path); §8 (`session.close` frame); §15.8 (calls from several loops — an `asyncio.Semaphore` is loop-bound).
- **Consequence:** if cancel/close frames bypass the semaphore, up to 2×1024 frames can be queued and the host's 1024-outstanding rule refuses the cancel (`TransportSessionFull`) — the requested cancel is lost and the task waits for natural completion; if they take a permit, the shielded cancel waits for a permit while holding one; per-loop semaphores (needed for §15.8) do not bound the host total, so "send never waits" degrades to refusals; the host→client bound is 1024 replies of up to 2 MiB each (event log) plus `diff.output` reads with no default byte limit — stated as bounded, size unstated. Proposals lesson 5 requires control traffic not to wait behind data.
- **Remedy:** state capacities ≥ outstanding-call limit plus reserved control capacity; define `send` on a full queue as a refusal error; exempt or reserve capacity for `operation.cancel`/`session.close`; make the bridge bound per-loop and say so; give default read byte limits.
- **Closure test:** 1024 outstanding reads, cancel all their tasks — every cancel is delivered and answered; `send` on a full queue raises rather than blocks or drops.
- **Classification:** bounded correction.

### [P3-2] `with_local_transport` finishes the transport from `Command::drop` during a panic unwind; a second panic aborts the host process — today's extension guards this, the contract drops the guard
- **Location:** §5.2 line 173 ("A panic is caught at the worker boundary … The session carries on"); §5.2 line 167 (uses `with_local_transport` as is). Source: `local_command.rs` 70–74 (`Drop for Command` → `finish()` → `executor.block_on`); today's `transport_session.rs` 721–743 (`finish_after_dispatch` runs finish under `catch_unwind`, reports "transport finish panicked", cleanup unconfirmed).
- **Consequence:** handler panics → unwinding → `finish()` runs `request.finish()`/`runtime.shutdown()`; any panic there (poisoned `expect`, a runtime already faulted) is a panic during unwinding → process abort; the whole Python process dies and "the session carries on" is false on that path.
- **Remedy:** catch the handler panic first, then run finish under its own `catch_unwind` (as today), reporting `Failed(InternalError)` with `peer_cleanup_confirmed = false`.
- **Closure test:** fault-injected panic in finish after a handler panic → operation `Failed`, next call succeeds, process alive (extends §15.5).
- **Classification:** bounded correction.

### [P3-3] Ordinary (non-candidate) builds have no cancellation lever; cancel and close wait for uncancellable libgit2 transfers, and §8's promptness claim does not hold there
- **Location:** §8 line 231 ("Network work fails promptly once cancelled"); §5.3 line 178; §16 line 363 ("Ordinary builds run handlers with the default backend"); §5.2 line 168. Source: `transport_binding.rs` 263–286 (non-candidate `Runtime` is empty, `configure` a no-op, libgit2 built-in transports); `lib.rs` 13–17 (`TransportSession` candidate-only); today's `bridge.py` 278–280 (close returns at once when there is no session).
- **Consequence:** in the default wheel `operation.cancel` of a running fetch has nothing to signal; its reply, `session.close()` and `Client.__aexit__` wait for the transfer's natural end, bounded only by libgit2's 9 s per-I/O stall timeout (a slow-but-alive transfer runs to completion). Today `close()` returns immediately in that build. The contract does not say this.
- **Remedy:** state the degraded semantics for ordinary builds (cancel = wait; close = wait; deadlines = libgit2 globals) and have `transport_capabilities` advertise cancellation support so the bridge does not promise promptness.
- **Closure test:** ordinary-build test: cancel of a running fetch returns after completion with `Completed`; capabilities report no cancellation.
- **Classification:** bounded correction.

### [P3-4] `diff.output` / `log.output` logs are not session-owned; session end neither releases them nor bounds them
- **Location:** §4.2 lines 114–118 ("with the semantics the bridge has today"); §2 (host owns operation records; direct-method logs unlisted); §8 (close report sums operations' cleanup only); §9 lines 248–251. Source: `native/src/dispatch/diff.rs` 1–10 and `diff_logs.rs` 1–33 (process-global `OnceLock` registry; the producer runs to completion before the reply; patch bytes stay in memory until `end_stream`); `lib.rs` 177–181 (`log_output_release` frees a temporary spool).
- **Consequence:** a session ending by channel closure leaves every unreleased diff log (whole patches in memory) and log spool alive for the process lifetime; another session in the same process can read them by `log_id` (status quo, but the contract now routes these as session calls without assigning ownership); the §5.4 memory bound does not cover them.
- **Remedy:** make direct-method logs session-owned (released at session end, bounded, included in the close report) and state the cross-session visibility rule.
- **Closure test:** open a byte-output diff, drop the channel without `end_stream`; the registry entry is released and a second session cannot read the id.
- **Classification:** bounded correction.

### [P3-5] Pump-thread lifetime at interpreter exit is unspecified; the daemon pump plus "dropping the object closes the channel" makes the forgot-to-close path re-enter CPython during finalization
- **Location:** §10 line 272 ("One daemon thread per session calls recv()"); §9 lines 243–244. `gwz-py/pyproject.toml` 6: `requires-python = ">=3.10"`. Today there is no pump; `asyncio.to_thread` executor threads are non-daemon and joined before finalization; `TransportSession::drop` closes on a spawned thread (`transport_session.rs` 136–157).
- **Sequence:** client never closes; interpreter exits; module teardown drops the session object → channel closes → host performs §8 steps 2–4 → `recv()` returns `None` → the daemon pump re-acquires the GIL during finalization. CPython before 3.14 terminates such a thread from inside `PyEval_RestoreThread` via `pthread_exit`, which on glibc force-unwinds through the extension's Rust frames and its `extern "C"` trampoline — an abort rather than a clean exit; 3.14 hangs the thread instead, which is benign. A non-daemon pump instead deadlocks exit (joined before the object is dropped). Not reproduced here (no execution permitted); upgrade to P2 on reproduction.
- **Remedy:** specify a bridge-level `atexit`/weakref finalizer that closes the channel and joins the pump before finalization, and that `close()` joins the pump; state the expected exit behaviour with an open session.
- **Closure test:** a script opens a Client, runs one operation and exits without close, on CPython 3.10–3.13 and Linux/macOS: exit code 0, no abort.
- **Classification:** bounded correction.

## 2. Invariant analysis

- **O1–O3 (one reply, one terminal).** Held for the in-process path: worker-spawn failure and queued-cancel terminals are written by the host before any effect (§5.2, §5.3); running terminals are written by the worker once; "success racing a cancel stays Completed" is consistent with `TransportRequest::finish` cancelling only after the handler returned (`request.rs` 328–334). The queued→running transition must be atomic with cancel settlement (text implies it, implementation must hold it). O2 fails on the wire for a reused id (P2-5) and on pump failure (P2-7). O5 fails across sessions (P2-2).
- **Admission (R/N/W, FIFO).** No deadlock found: the member lock is one resource per step with no nesting, held only inside running fetch/push workers; `par_map_per_host` permits are per operation, so a worker blocked on another operation's member lock never blocks that operation's permits; queued operations hold nothing; FIFO prevents W starvation; R bypass only competes for slots. Head-of-line blocking of an N behind a queued W is deliberate. Defaulting unclassified methods to W is safe. The cross-process `flock` conflicts inside one process (two sessions per process are serialized by refusal, as today) — complementary to W exclusivity, but it breaks the N class for push (P2-3). Refusals for a full queue and outstanding-call limit precede effects; resolution is read-only.
- **Cancellation.** Cooperative cancel is real in candidate builds: `TransportCancellation::cancel` → `Session::cancel` completes every open wait with `Cancelled` and cancels streams (`session.rs` 726–766); open waits carry a 150 s + io deadline (`driver.rs` 174–175) unless timeouts are disabled; `finish` is bounded by `CLEANUP = 5 s` (`driver.rs` 499–516) and `shutdown` by `cleanup()` (`session.rs` 851–864), so O5's "existing transport deadlines" hold per operation. Local handlers and direct methods have no cancellation point, as stated; a cancel of one waits for its terminal and the bridge's shielded cancel-and-join is today's behaviour. Close with a handler that never returns leaves the session closing, the pump blocked in `recv()`, and the interpreter able to exit because core threads are native (today's `to_thread` threads are joined at exit, so a local write mid-flight can now be torn by process exit — see §3). Ordinary builds have no lever at all (P3-3).
- **Retention and memory.** Live records are never evicted; no read races a unary discard (the client cannot know a unary's `operation_id` before its reply); the event-buffer reset rule exists (`push_event.rs` 628–655). Bounds: 64 × 2 MiB logs plus 1024 outstanding replies per session; per running operation one worker, two 5 ms-polling supervisors, one 2 ms link thread, endpoint workers, and up to `jobs` (default 100) member threads — bounded by the running limit of 8, same order as today's native session. Eviction of unread outcomes is the hole (P2-4).
- **Channel and pump.** "Nothing but frames crosses" holds; the host only sends replies so its volume is bounded by outstanding calls. Full-queue and control-call accounting are unspecified (P3-1); pump death is unhandled (P2-7); cross-loop delivery via `call_soon_threadsafe` must catch the closed-loop `RuntimeError` the text says is a drop.
- **Transport and workspace.** Several runtimes per process coexist safely: libgit2 transports are installed per remote (`transport_binding.rs` 216, `https_remote.rs` 128–135), never registered globally; `Runtime` and its host context are per `Git2Backend` (`backend.rs` 41–48), so no cross-operation identity bleed; the 256 registration cap and pool capacity are per `Session`, which per-operation runtimes reset. The only shared state is the timeout global (P2-2) and the environment (P2-6). The 8×32 connection cost matches `resolve_per_host` (32).
- **Status quo.** The CLI is untouched until a later phase; custom `CoreBridge` implementations are unaffected; the legacy `NativeModule` functions and `NativeCoreBridge(native=…)` become an "implementation choice" (§9), which silently strands anyone passing a custom native module. Worse-than-today paths found: ordinary-build close (P3-3), exit with an open session (P3-5), process exit no longer joining a local handler's thread (§3).
- **Wire proof.** Running the suite through both bridges proves behavioural parity under the suite's coverage, not the absence of hidden coupling. It cannot catch: process-global state the in-process path shares (timeout global, environment, libgit2 opts, the diff/log registries) because the stream run has one session per host process; in-process queue-full and pump-death paths (never reached); frame-size bounds (no maximum frame size is stated; `SessionReply` for a `diff.output` read with no byte limit is unbounded); duplicate-id and other non-bridge client behaviour; cwd divergence (mitigated: the Python client always sends `invocation.caller_cwd`, `client.py` 271). G3 is supported for the bridge's own traffic only.

## 3. Risks and next action

Residual risks below the finding bar:
- A `Session` supervisor thread lives until `closed && pending == 0` (`session.rs` 317–331); a stuck endpoint leaks a 5 ms-polling thread per affected operation in a long-lived process (bounded only by operations run).
- If the contract's member lock reuses `MemberLockManager`, its `.expect` on poison (`membermutationguard.rs` 13, 33) turns one panic into failure of every later fetch/push in the session; specify `into_inner` handling.
- Process exit no longer joins a running local handler (core threads are native; today's `to_thread` threads are joined), so a merge mid-write can be torn by a normal exit without `close()`; the same exposure the CLI has under Ctrl-C.
- A handler that fails for an unrelated reason after a cancel signal is reported `Cancelled` (§5.2), masking the real cause.
- `remote_identity`/`transport_capabilities` (R) wait for a running slot behind eight long operations; the client precheck before every network call (`client.py` 375) adds that latency.

Next action: revise the contract text and schema together — append the two error codes and fix the mapping (P2-1); move timeout and endpoint configuration into session state captured at `open` (P2-2, P2-6); reclassify push or serialize same-workspace pushes in the host (P2-3); make retention coherent with admission (P2-4); classify `call_id` reuse as a protocol error (P2-5); add the pump failure rule (P2-7); then address the P3 items in the same revision and re-review as a new revision of the same object.
