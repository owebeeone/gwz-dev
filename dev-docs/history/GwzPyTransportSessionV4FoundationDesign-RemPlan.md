# Python transport session v4 foundation — first design remediation

Date: 2026-09-24. The first committed V4 design tuple is **NO-GO** at root `fbee49ce45e0ee906ea0de45b6ac5c3db990e766`, gwz-core `a1f2102dd6da1bf96538b4972de7995255a53b48`, gwz-py `0ca424f36a2872a0896abaea89641513352fdf47` ([verdict](GwzPyTransportSessionV4FoundationDesign-Verdict.md)). The [Consistency](GwzPyTransportSessionV4FoundationDesign-ReviewConsistency.md), [Safety](GwzPyTransportSessionV4FoundationDesign-ReviewSafety.md) and [Surface](GwzPyTransportSessionV4FoundationDesign-ReviewSurface.md) reports are filed verbatim. This plan is one consolidated correction across the V4 design, the paired core paragraphs, the caller guide and one precedence pointer. It is not a series of per-finding patches. No implementation starts before the corrected tuple reaches GO.

None of the dispositions changes an ownership rule, a transfer or the single-arbiter rule. They calibrate the owner clocks, give one more entry a construction owner, move one reservation earlier, add one ownership value for construction and one fault transition, and correct text.

## Blocking findings

| Finding | Disposition | Closure evidence required |
| --- | --- | --- |
| **B1** — Consistency P2-1, Safety P2-2 | State one sizing rule in §3.5: each owner clock is the sum of the core deadlines that run in sequence inside the awaited future, plus a 1-second margin. §7.5 tabulates each wait against the source that bounds it. Capacity is 6 s (one 5 s arrival deadline). Bootstrap Ready is 6 s (the 5 s mux bootstrap deadline). Bootstrap-registration finish, request finish and `RegisteredCleanup::finish` are 11 s each, because the driver and endpoint registrations run two 5 s cleanup windows in sequence (`request.rs:328-339`). Local runtime shutdown is 11 s (endpoint then driver `cleanup()`). Legacy `TransportRequest::finish` is unchanged. §14's claim that the clocks matter only when the supervisor is dead then holds by construction. | With a live supervisor, hold each of the two sequential registration cleanups for about 4 s. Finish returns before the owner clock with core's report, `faulted` stays clear, a successful handler publishes `Completed`, and the next admission succeeds. Separately, stall the supervisor (see Consistency P3-3 below): the backstop fires within 11 s. |
| **B2** — Consistency P2-2, Safety P2-1 | Add a §7.2 subsection, "Entries without an issued operation ID", with three rules. (1) `transport_capabilities` never installs a runtime that has not bootstrapped. If no runtime is installed, the caller becomes the constructing owner under §3.6 while holding no record: the `constructing` flag, its clocks, bootstrap, the failure rule, the B6 unwind rule and close's join all apply. It then answers from the installed generation, which dispatch uses (GwzPyTransportDesign §4's same-generation rule). (2) ID-less local unary commands bypass the ledger. `faulted` does not refuse them, because they use no transport generation; they refuse once Closing starts (v2 §6). (3) Local submitted operations (`merge`, `clone_local_workspace`) are minted natively at submit entry under the session nonce, so they have no pre-entry interval. Their native worker owns them from mint to settle through the §7.3 gate. They are recorded in the session store, as v2 §6 already requires for merge responses, count toward the 64-record limit, and take no network slot, capacity or registration. Close neither cancels nor joins them. The high-level merge helpers release the record after reading its final response, as the implicit helpers do (Surface P3-6 below). No lookup through a native-session bridge reaches the process-global store (I10). I8 is narrowed: `faulted` refuses network issuance and admission only. | On a fresh Client, an identity-option fetch runs the capability preflight and is then admitted on the same generation, with the driver mux Ready before the first admission. A preflight construction failure leaves the session `Open`, and a later claim constructs. A preflight racing a claim's construction, and a close during preflight construction, both terminate. `status` and `commit` work before and after network work and while `faulted`. A submitted `merge` result is read by ID through the native bridge and never touches the process-global store. |
| **B3** — Consistency P2-3 | Move the ledger upgrade (4 KiB to the 8 MiB allowance, including the primary reader cursor and the 4 KiB recovery-metadata reserve) from `Claim::accept` to T2 `claim`, taken atomically with the top-level slot and before any core work. A refusal there settles `TransportSessionFull` with `NotRegistered` provenance. `accept` binds only the already-reserved cursor and stays infallible. Update §5.2, the §7.1 attach points and §12. | Specified now and executed in the ledger stage: with the ledger within 8 MiB of full, admission refuses `TransportSessionFull` with `request_id_consumed=false` and no core registration; after records are released, the same ID is admitted. |
| **B4** — Consistency P2-4, Safety P3-5 | Restate the GWZRequirements v4 paragraph to match GWZDesign. Core gains no new timer, callback or thread with authority over native records. The existing supervisor-driven mux bootstrap and route deadlines and the cleanup-expiry close remain; they fire before owner clocks and reach owners as faults. The owner-clock rule applies to futures awaited by the Python-session candidate path. V4 §3.5 and §3.6 list those closes among core faults, and §12 gains a row for a generation closed under an accepted operation by a sibling's cleanup expiry. | A documentation check that the requirement names each retained deadline at its source site. A native test in which a sibling's cleanup expiry closes the generation under accepted operation B: B settles exactly once through its owner (`Failed`, possible effect), there is no second terminal, and the session becomes `faulted` (B7). |
| **B5** — Consistency P2-5, Safety P3-1 | The reserved bootstrap registration ID carries a per-generation 128-bit random token inside the identifier grammar (`bootstrap-<32 hex digits>`). It is generated at construction and exposed nowhere; in particular it is not the session nonce, which appears in operation IDs. §11 item 6 states that the reservation is invisible to callers, so no caller-visible reservation is added to v2. The one-extra-registration limit applies only to runtimes that bootstrap, so legacy runtimes keep 256 (Consistency §3 residual). | `bootstrap-1` and the other deterministic forms are admitted as caller request IDs in the first generation. The bootstrap ID never appears in results, events, descriptors, errors or close reports. A legacy runtime that never bootstraps keeps the 256 limit. |
| **B6** — Safety P2-3 | Construction becomes one ownership value, `Construction`. It is created when `constructing` is set and held by the constructing owner across `from_environment()`, `bootstrap()` and the failure-path `shutdown()`. Its `Drop` on unwind clears `constructing`, sets `faulted`, closes the partial runtime's sessions synchronously and notifies the session condvar, so waiting claims refuse with `NotRegistered` provenance and close proceeds. Update §3.2, §5.3, I4 and §12's construction-panic row. | Inject a panic inside `bootstrap()` after Bind, with a second claim waiting and a concurrent `close()`. The waiter refuses `NotRegistered`, `faulted` is set, and close returns a conservative report within its bound. Repeat for a panic in the failure-path `shutdown()`. |
| **B7** — Safety P2-4, Consistency P3-9 | Any owner that causes or observes the close of the installed generation sets `faulted` under the session mutex before settling its own record. That covers the `CapacityMutation` guard, the internal retirement and authority closes, a phase-1 refusal because the endpoint session is closed or the driver mux is not Ready, and a mux-deadline or cleanup-expiry close that surfaces as an error. After that, network `reserve`, `begin_attempt` and `claim` refuse with typed `TransportGenerationBusy` and `request_id_consumed=false`. v2 §5 and §7 already name that code for a generation that cannot admit; the foundation introduces the model code now rather than at rollover. The caller guide and §12's retry column state the action: close and recreate the Client, which the rollover stage will later make unnecessary. | Hold retirement past the deadline: `faulted` is set, and the next network attempt refuses `TransportGenerationBusy` rather than `IoError`. Repeat after a post-mutation cancel, a driver-mux close and a sibling cleanup-expiry close. Local commands keep working (B2 rule 2). |

## Nonblocking findings folded into the same patch

| Finding | Disposition |
| --- | --- |
| Consistency P3-1, Safety P3-4, Surface P3-1 (prior Surface P3-2) — the retry example leaks handles on cancellation | Rewrite the example with one scope per handle covering `accepted()` and `result()`. Each handle is released exactly once on every exit; a still-live operation is cancelled and joined before release on an abnormal exit; cancellation is re-raised and never followed by a retry. State the hierarchy once: `GwzOperationCancelled` subclasses `asyncio.CancelledError` and is not a `GwzBridgeError`. Correct V4 §11 item 2's "including" wording to match. Line 79 lists only the paths the code covers. Closure: a walkthrough of cancellation at each await, including both admission race outcomes. |
| Surface P3-4 — `result()` cancellation rule is undocumented | The handle contract states that cancelling a task awaiting `result()` or iterating `events()` stops only that wait. The operation continues, stays cancellable through `cancel()`, and its record becomes terminal only then. This follows V4's ownership model: an accepted operation is owned natively, and a Python waiter only observes it. V4 §11 lists it as a clarification of behavior v2 leaves unstated. |
| Consistency P3-8, Surface P3-2 — a duplicate refusal reports `request_id_consumed=false` | Define the field as "this request ID is registered in this generation, or that cannot be ruled out". Phase 1 returns a typed refusal that distinguishes "already registered in this generation", so a duplicate refusal carries `True` from core provenance rather than from the error code. |
| Surface P3-3 — the field's presence on `GwzOperationCancelled` | Add `.request_id_consumed: bool` to the `GwzOperationCancelled` attribute list. It is present on every `GwzBridgeError` and `GwzOperationCancelled`, and is `True` once registration has occurred, including after acceptance. Define cancellation during admission after registration. |
| Surface P3-5 — the retry precondition is unobservable | Add a per-code table of when a pre-effect refusal can clear. `TransportSessionFull`: after releasing records found by `recent_operations()`, or after their expiry. `TransportCapacityConflict`: after the conflicting operation is terminal, with bounded backoff while cleanup lags. `TransportGenerationBusy`, `UnsupportedOperation`, and malformed or duplicate IDs: never within this Client and generation. The example calls an explicit caller-supplied wait before its single retry. |
| Surface P3-6 — records left by refused implicit calls | Implicit unary and stream forms release their internal record once the typed refusal is detached onto the raised exception, extending v2 §2's detached-record rule for cancelled helpers to pre-effect refusals. Explicit handles keep theirs until release. This also makes V4 §13 test 1's "no record-limit growth" hold (Safety §3 residual). |
| Consistency P3-2 — `Issued` and `Attempting` marked close-owed | Remove "mark close-owed" from that column of §3.4. |
| Consistency P3-3 — §13 test 4 cannot reach the owner clock | Test 4 stalls the supervisor-driven mux clock (a hang, not an exit) to reach the owner-clock branch. A separate test covers the exit hardening, which completes pending registration results rather than only closing and signalling. |
| Consistency P3-4 — the transition table, fault matrix and §11 item 5 disagree | Regenerate §12 from §5.2 with disjoint guards and one explicit precedence: a signalled cancellation with no `Completed` output settles `Cancelled` (code 73). Drop Closing and Closed from the T1 and T2 refusal rows. Use one drop-path kind across §5.2, §5.3 and §11 item 5: `Failed`, or `Cancelled` when cancellation was signalled. Add rows for `install_capacity_pair` and authority failures after pool mutation, and the missing effects on the spawn-to-accept panic row. Each §12 row cites the §5.2 row it instantiates. |
| Consistency P3-5 — refused transfers settle outside the ownership rules | Define a refused T1 or T2 as one atomic decision that settles on the sender's behalf, and list it in R2, §3.2 and I3. `abandon_attempt` returns that retained disposition, so the attempt never re-types it. |
| Consistency P3-6 — expiry acts on an owned `Attempting` record | Expiry does not apply to `Attempting`. |
| Consistency P3-7, Safety P3-2 — the §6 API sketches | Replace `progress()` with a shared progress handle obtained before phase 2 and written inside `register_and_open` on the owner's thread. Correct §1, which calls the witness withdrawn, to say it is kept as a same-thread progress handle. Split bootstrap into a Ready step and a finish step, each with its own owner clock (B1 values). |
| Consistency P3-10, Safety P3-3 — cross-loop `accepted()` | Serialize concurrent `accepted()` calls with a loop-agnostic in-flight future (a `threading.Lock` and a `concurrent.futures.Future`, awaited through `asyncio.wrap_future`). |
| Consistency P3-11 — unnamed supersession | Name in V4 §1 the frozen text of `gwz-py/dev-docs/GwzPyTransportDesign.md` §§2–3 that V4 supersedes for the Python session: the per-call `request()` flow and the "no extra registration" core additions. Add a matching pointer to that document's candidate-correction paragraph. |
| Safety §3 residuals adopted | Narrow §3.5's "dead or hung" to a dead supervisor. `_admit` takes the abandon path for `Exception` and re-raises any other `BaseException` unchanged after abandoning. Phase-1 entry checks `cancel_requested` as a level after any construction wait. The bridge feature-detects `begin_attempt` before using the V4 admission path. |
| Consistency §3 residuals adopted | Describe supervisor hardening's legacy effect accurately: waiters now wake instead of hanging. The V3 status line keeps its current form, which follows program precedent. |
