## 1. Findings (severity-ordered)

### P3-4 — `--shrink-from` keys by path, so a movement-only split or rename of a file holding listed occurrences fails the boundary job

- **Root cause.** `shrink()` (`check_cfg_boundaries.py:450-454`) looks each current `(repo, path, attrs, item)` up in the base by the full key; a listed occurrence whose file was renamed or split presents as a key "not in the base allowlist" → `ADDED` → exit 1, while its old key's disappearance passes as a removal.
- **Location.** `scripts/checks/check_cfg_boundaries.py:450-454`; `.github/workflows/checked-artifact-boundary.yml:71-86`.
- **Violated invariant.** The plan's standing rule (`GwzCoreSessionPlan.md` HEAD line 100): "A step that would take an existing file past about 1,000 lines splits it first in a movement-only commit (L1-11, L1-23), using the rust-split tool." The RemPlan's S-P3-3 intent is to stop *new* placements from being listed ("a change may drop entries … never add or raise them"); a moved debt entry is neither new nor raised.
- **Reproduction.** Replaying `shrink()`'s rule on the real allowlist with `src/git/gitbackend.rs`'s entries re-pathed to `src/git/gitbackend/delegates.rs` (what a split does): 30 `ADDED`, 0 removal errors. The re-keying already in this revision shows the mechanism live: the 14 `delegate!` lines in the round-1 comparison are `ADDED` although no occurrence was added. The file the plan schedules for a split first (`src/git/endpoint/https_auth.rs`, 934 lines, CS step at plan line 317) holds 0 keys today, so the collision is foreseeable, not scheduled; eight files hold 12–30 keys each.
- **Impact.** On `pull_request` and `push`, a movement-only commit that touches any of those files fails the boundary job with no sanctioned way through except migrating the moved debt in the same commit, which makes it not movement-only.
- **Required correction.** Compare totals per `(repo, attrs, item)` across paths: an `ADDED` key is an error only when that triple's summed count exceeds the base's summed count (a raised count likewise on the sum). Say so in the docstring `:53-56`.
- **Regression test.** Base `{src/a.rs: use x::Y, count 1}`; current `{src/b.rs: use x::Y, count 1}` → exit 0; current with both → exit 1; current `{src/b.rs: use x::Y, count 2}` alone → exit 1.

### P3-5 — The first statement after an inner attribute at the top of a block is not scanned

- **Root cause.** `target()` (`check_cfg_boundaries.py:304`) accepts a statement only when the token before its first attribute is `;`, `{` or `}`; after `#![…]` that token is `]`.
- **Location.** `scripts/checks/check_cfg_boundaries.py:303-305`.
- **Violated invariant.** Docstring `:18-21`: an unbraced statement in a block is flagged "wherever it sits".
- **Reproduction.** `fn f() { #![allow(unused)] #[cfg(unix)] let a = 1; #[cfg(unix)] g(a); }` → `[('#[cfg(unix)]', 'g(a)')]`; `let a` is missed. The same two statements without the inner attribute → both flagged.
- **Impact.** Bounded: the trees hold two inner attributes inside bodies (`crates/refcopy/src/native/windows.rs:39`, `crates/repo-inspect/src/paths.rs:212`), neither followed by a conditional attribute; only the statement directly after an inner attribute is affected.
- **Required correction.** In the guard, also accept a `]` whose matching `[` is preceded by `#` `!` (an inner attribute), or skip inner attributes when looking back.
- **Regression test.** The snippet yields `let a` and `g(a)`; `mod m { #![cfg(windows)] use a::I; }` still yields nothing (the inner attribute itself is not a target).
