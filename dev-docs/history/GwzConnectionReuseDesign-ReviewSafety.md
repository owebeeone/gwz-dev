## 1. Findings

### [P2-1] The instance-fault scope rule promises that live exchanges survive a worker-thread death or a caught panic, which the worker structure cannot deliver and which A3 forbids

**Location.** §8 "Instance faults" (lines 170) and "Panics" (171); §16.1 decision 9 (336); §17 "Instance faults" (359); C12 (277); §15 item 6 (298).

**Violated invariant.** A design's recovery claim must be reachable from the structure it names, and must not contradict an accepted authority it does not amend. A3:24–31 (accepted): "Worker panics are caught while the host remains owned; recover by shutdown and retained cleanup." Contract §5.2 stops a panicked handler's work rather than continuing it.

**State sequence.** §8 groups four faults — sticky cleanup, key-admission failure, "the SSH worker or HTTPS thread ending", and "a panic caught at an instance entry point (EP/ssh_shutdown.rs:59)" — and says of all of them: "Exchanges already active on other connections run to their own terminal, and the instance is disposed when its last binding detaches." §8 "Panics" adds "The instance is not shut down." At `ssh_shutdown.rs:59` the worker's `run` loop is wrapped in `catch_unwind`; a panic unwinds out of `run`, dropping its locals `pending` and `active` (ssh_worker.rs:855–856), whose `Active` entries own the leases and pumps of every live exchange, and `manage` then calls `pool.shutdown()`. After a caught panic or a thread exit there is no thread to advance those exchanges, and their state has already been dropped. The only faults for which C12's "admission closes and active exchanges drain" is achievable are the two that leave the loop running (`take_failure` at 879 and `take_disposal_error` at 907, which today set `stop` and clear `active`). Following the text as written for the panic case means re-entering the worker loop after a caught panic in instance code (pool machine, `transfer`, the host step), on state whose invariants have just been violated (the `expect("live lease")`/`expect("idle entry")` class in `pool/allocation.rs`), while it drives other clients' pushes.

**Impact.** In a server, a panic or thread death in one instance fails every active exchange of every client bound to it — a cross-client blast radius the design says does not exist, and one the Phase 6 exit row "cancelling or failing one operation leaves another's lease … intact" and §15 item 6 would not test on the thread-ending path (an injected fault that leaves the loop alive would pass). Under the literal reading, an implementer is instructed to keep pumping foreign pushes on a poisoned worker; an in-flight push "may already have been accepted" (RETRY §4), so a wrong terminal there is an uncertain remote effect. §17's "Instance faults still stop admission" understates the scope.

**Required correction (non-architectural; text).** In §8: split the fault set. (a) Faults that leave the worker running — sticky cleanup, key-admission failure — close admission and drain active exchanges (C12). (b) Thread-ending faults — the SSH worker or HTTPS thread ending, and a panic caught at an instance entry point — stop the instance as A3 requires: admission closes, every active exchange on it fails with its typed failure as today's stop does, leases are discarded, and the instance is disposed under the cleanup owner. Replace "The instance is not shut down" in "Panics" with: a panic inside instance code stops the instance; a panic inside binding code faults only the binding. Amend §17 to state that a worker panic fails every active exchange of every binding on that instance, cross-client in a server. Amend decision 9 to the same split, or record that A3's rule stands for thread-ending faults. Update C12 and §15 item 6 accordingly.

**Closure test.** §15 item 6 gains: with B holding a live exchange on an instance, an injected panic in the SSH worker loop (and separately a forced HTTPS thread exit) fails B's exchange with a typed failure, no further frame is delivered on that connection, the host context stays usable, and a later operation of B builds a fresh instance and completes; the existing injected non-panic fault (sticky cleanup) still lets B's exchange complete.

### [P3-1] Cross-scheme eviction names one victim and waits for its disposal, so a victim leased in the meantime leaves the waiter stuck until its allocation deadline

**Location.** §5 "Shared authority and eviction" (128–130); T4 (262); T5 (263).

**Violated invariant.** A waiter that can be served by evicting an idle entry must not fail while such an entry exists (REQ C4's bounded wait presumes progress; DES §7.2 step 3 "retire an idle entry first").

**State sequence.** Instance at `C_total` (256). Idle SSH entry E is the oldest idle of either scheme. An HTTPS request R asks the authority for a reservation; the authority "asks the pool that holds the oldest idle entry … to retire it" and R "proceeds when disposal frees the reservation." The SSH pool runs on its own worker thread; between the authority's choice and `retire_idle(E)` reaching that machine, an SSH request R′ leases E (allocation.rs:16–45 leases idle entries first). `retire_idle` must not close a leased entry (T4 says "closes a named idle entry"; closing a leased one would kill R′'s exchange). Nothing in the text re-selects a victim for R, and no disposal follows from E. R waits until its allocation deadline (30 s) and fails; RETRY §4 makes an allocation timeout non-retriable, so the member fails.

**Impact.** Spurious member failures under cross-scheme pressure at the ceiling, in a server only; bounded by the allocation deadline.

**Required correction.** In §5 and T4: `retire_idle` on an entry that is no longer idle is a reported no-op; the authority re-selects the oldest idle entry of the constrained group on that report and on every transition of an entry to idle or to disposed, until the waiter is served or its deadline passes. Closure test: an injected lease of the chosen victim between selection and retirement; the waiter is served by the next idle entry within its deadline.

### [P3-2] Idle expiry and the maximum-age bound run on a clock that does not advance during system sleep, so a surviving server serves dead idle connections on wake; the "60 s idle keeps this unlikely" claim does not hold across suspend

**Location.** §7 "Idle expiry" (148) and "Stale idle replacement" (150–153); §16.1 decision 5 (332); §17 "Silent idle death" (358).

**Violated invariant.** A bound on how long a pooled connection is trusted must be a bound in elapsed real time.

**State sequence.** The pool's `now` is fed from the host's `Instant` (`ssh_worker.rs` `move || elapsed(origin)`; `pool/clock.rs:50–55`). `Instant` excludes suspend on both release platforms (macOS `CLOCK_UPTIME_RAW`, Linux `CLOCK_MONOTONIC`). A `gwz server` (auto-started, `--idle-exit` 10 min) holds 32 idle connections after a fetch; the laptop sleeps for an hour within the 60 s window; on wake the entries read as seconds old, so neither idle expiry nor decision 5's age closes them, while the NAT and the peer have dropped them. The next SSH operation pays one 9 s stall per dead entry before replacement; the next HTTPS operation on each dead entry sends its request and fails without replacement (§7, §17) — one member failure per dead HTTPS connection, non-retriable (RETRY §4, after the first byte). The in-process CLI never starts a command with dead idle connections, so this exposure is new to reuse across commands.

**Impact.** Bounded (one stall or one failed member per dead entry, then the entry is discarded), but certain rather than "unlikely" on any host that sleeps, and it makes decision 5's 10-minute bound false in real time.

**Required correction.** State the clock rule: the pool's clock for idle expiry and the age bound includes suspended time (a boot-time clock, or a wall-clock cross-check that discards every idle entry when the monotonic and wall clocks disagree by more than the idle timeout). Reword §17 to say when silent death is expected. Closure test: with the injected clock, a discontinuity larger than the idle timeout expires every idle entry before the next lease.

### [P3-3] The instance-bound refusal reuses `transport_session_full` for a host-context condition, with no wait and no cause in the text

**Location.** §7 "Bound: 16 instances" (146); C3 (268); §15 item 11 (303).

**Violated invariant.** An error code must name the resource that is full so the caller can act on it (contract §4.2 defines `transport_session_full` for the session's queue, table, outstanding calls and logs); a refusal must not be issued while a short wait would serve the request (interface shape is a finding under L1-18's amendment).

**State sequence.** A server under `auto` with HOME equal; 17 concurrent clients whose snapshots name distinct `SSH_AUTH_SOCK` values (a CI host with per-job forwarded agents) or distinct `--ssh-timeout` values. Every instance has a binding; the 17th operation is "refused before any effect with `transport_session_full`." The client "never falls back to in-process" (SRV §7); the job fails. The client's own session limits are nowhere near full, so the code misdirects the operator; reducing that session's concurrency cannot help. Selection already runs under the 5 s admission deadline (§7), but the text refuses at once instead of waiting within it for an instance to unbind.

**Impact.** A new, opt-in-only failure class through a server whose diagnosis points at the wrong limit; bounded to concurrent distinct configurations above the bound.

**Required correction.** In §7: an operation that finds every instance bound waits within its admission deadline for an unbound instance, then is refused; the refusal's message names the endpoint-instance bound and its value, and the design records whether a distinct code is warranted (append-only under CS §13) or `transport_session_full` is kept with that message. Closure test (item 11): with 16 bound, the 17th is refused only after the deadline, with a message naming the instance bound; if one instance unbinds inside the deadline, it proceeds.

### [P3-4] The shared possession-proof job's clock and ownership are ambiguous when concurrent leases share it

**Location.** §4 third sub-bullet (94) and "Per-binding proofs" (99); §16.1 decision 6 (333).

**Violated invariant.** A shared bootstrap must not fail every waiter when its first requester's clock expires or its request is cancelled — the rule the design itself applies to bindings (§2 rejected alternatives; PLD:189–205).

**State sequence.** §4 says the proof "runs … under the request's stall clock and absolute deadline"; §4 also says "Concurrent leases that need one proof share one job." Thirty-two members of one operation lease idle connections of key K at once; the job is created for the first request. The user answers a confirm prompt at 12 s. Under the first request's 9 s stall the job is cancelled at 9 s; the text does not say whether the other 31 waiters fail ("returned to idle | fails Timeout"), start a job of their own, or wait for the answered prompt. Today each connection setup has its own job (AGENT §3), so this sharing is new.

**Impact.** Either 32 spurious proof timeouts after an answered confirmation, or 32 confirm prompts, depending on the implementer's reading; bounded by the operation.

**Required correction.** State that the shared job runs under the latest waiter's deadline (or the binding's), that a waiter whose own deadline passes fails alone and leaves the job running for the others, that the job's cancellation follows the operation's token only, and that a passed proof is recorded for the binding even if the first requester has already failed. Closure test (item 2b): with the fixture answering after the first requester's stall but within the others', exactly one prompt is shown and the remaining leases proceed.

## 2. Invariant analysis

The attacks below were made against the text and the cited code; each held.

- **Configuration ownership (§3), the core claim.** Every value an SSH or HTTPS connection is built from today (`local_command.rs:33–130`, `mod.rs:47–64`, `session.rs:388–404`, `https_connection.rs:205–225`) appears in the §3 table or is moved per request (`gh` environment, §6) or per Open (identity, HTTPS policy, limits). With byte-equal encodings, any value an instance uses equals the requester's own, so no request runs under another session's snapshot or the server's environment. Differing `HOME`, agent address, CA bytes, proxy, no-proxy semantics or timeouts partition instances. Lexical path equality only lowers reuse. No secret enters the configuration: the proxy parser refuses userinfo (`local_command.rs:106–116`) and never sets authorization (:128); the CA file is reduced to `CERTIFICATE` blocks; the agent address is redacted evidence under TRP §2.
- **`GH_TOKEN`, proxies and CA files differing between sessions.** Proxies and CA content are in the key. `GH_TOKEN` is not, and need not be: the helper is spawned per request with `env_clear()` plus the requesting session's snapshot (`https_auth.rs:317–333`), credentials are looked up afresh per request and redirect hop (`https_worker.rs:425–452`), and a reused TLS connection inherits neither credentials nor `authenticated` (HTTPS:259–260; GHA:55–59). No cookie jar exists. §15 item 1 tests both cases.
- **Swapped agent behind one address; keys removed, added, expired; confirmation keys.** All decided by the possession proof (§4). Adding a key changes nothing; removing the connection's key, its `-t` expiry, a swapped agent lacking it, or a denied `-c` prompt fails the proof, retires the connection and every idle connection of that key, and continues fresh. A swapped agent holding the key is authorized after one sign request — correct, since it could open its own connection with that key. Presence keys and certificates never reach a transport connection (OD11/TR2.8).
- **The departure from TR1.2 question 3.** Possession of the connection's key, proven now by the agent the requester's own snapshot names, is a sound and stronger primitive than "the agent's own identity", which has no stable form (a socket path repoints; peer credentials name a process, not its keys). The design records the departure and amends the question and the Phase 6 exit row (§13).
- **Proof domain separation and replay.** The signed blob is the OpenSSH SSHSIG form with a gwz `name@domain` namespace over SHA-512 of a fresh 32-byte nonce. SSH user-authentication data begins with `string session_id` (`agent_auth.rs:265–293`); the SSHSIG magic's first four bytes read as a length larger than any message, so neither blob parses as the other. Git's SSHSIG namespace differs, and the hashed message is random, so a proof cannot stand in for a commit signature. The signature is verified locally and never leaves the process. A malicious or relaying agent that cannot produce the signature gains nothing; one that can already holds the key's authority. The agent's reply method must equal the request (`agent_client.rs:60–94`), so an RSA SHA-1 downgrade is refused. ECDSA sign flags already exist (:63–66); verification is a new dependency (C9), correctly named.
- **Explicit identities.** The N2 re-read before every lookup, reuse included (`ssh_admission.rs:50–65`; `ssh_key_snapshot.rs:87–137`), keeps a changed or missing file from selecting a connection authenticated from other bytes; token equality names exact bytes inside one instance; a different explicit key never shares (`local_endpoint.rs:286–345` as cited).
- **known_hosts changes.** Re-read per cross-operation lease through the same loader and check as setup (`ssh_network.rs:39–64`, 235–284); a changed or removed entry retires the connection and its host-key siblings, and the fresh setup then fails host trust as today. A transiently unreadable file fails closed.
- **A sandboxed peer through a server; a forwarded agent.** The sandbox refusal is at accept (SRV §4; the amendment adds the listener side) before any frame; it composes with reuse because a session that cannot open cannot bind. A forwarded agent is just an agent at an address; when the forwarding ends the proof fails and the connection retires.
- **Capacity (§5).** The max rule keeps a lone operation's limits exactly as today (RETRY:39–41); idle reuse precedes creation (`allocation.rs:16–45`) and is gated only by the requester's own per-owner limits, so a small-limit operation is served by another's idle connections rather than starved of them; a lower limit evicts nothing of another operation; `TransportCapacityConflict` cannot arise. No deadlock: every wait is under the allocation deadline (P3-1 is a lost eviction, not a hang).
- **Lifetime (§7).** Instance construction does no trust, key, agent or network I/O (`ssh_local.rs:1–2`) and takes a cleanup permit (`ssh_worker.rs:332`); 16 instances leave 48 of the 64 permits (`agent_job.rs:578–602`) for stuck disposals, so turnover cannot starve construction and recreation cannot evade the bound (A3:33–40). Fork: forgetting rather than dropping is right — `Shared::drop` joins a thread that does not exist in the child (`ssh_worker.rs:74–86`) and `SshConnection::drop` shuts down a socket shared with the parent (`ssh_connection.rs:37–51`); pooled sockets are close-on-exec, so `gh` children do not inherit them.
- **Failure isolation (§8, §9).** `cancel_session` acts on the owner's session only and leaves idle entries (`lifecycle.rs:80–107`); Q6's `mux_retired` record is per registration (`session.rs:123–129`, `driver.rs:470–517`); a Cold key admits idle leases and serialises only new setups, and revalidation and replacement consume no attempt. The exception is P2-1.
- **Observations (§10).** Rows are built from the current operation's selection and suppressed per operation (`transport_observations.rs:41–88`); pool keys carry no path; gwz-cli renders no connection field today (`response_meta_json.rs:16–69`). The opaque `endpoint_id`/`connection_id` reveal only that same-user sessions share an instance.
- **Retained state (§12).** No snapshot in an instance; the `gh` helper child holds its own copy of the environment only until it is killed and reaped; the one retained secret — explicit key text pinned by an idle connection (`ssh_key_snapshot.rs:39–45`; `ssh_setup.rs:154–161`) — is named honestly and decision 10 removes it.
- **Irreversible steps.** Replacement happens only before the exec request (SSH) or before Hyper takes the request (HTTPS); no POST is replayed; retirement of idle connections costs only handshakes.

## 3. Risks and next action

**Residual risks below the finding bar.**
- **Contention through a server.** Under the max rule, an operation whose limits exceed the ceilings can hold an instance, and demand above 256 to one host from many clients turns into non-retriable allocation timeouts (member failures) that the in-process path never produces. This is the documented consequence of decision 8 and S5.4's ceiling choice; S5.4 should measure allocation-timeout rates, not only throughput. The provisional 256 ceiling also equals macOS's common default open-file soft limit, which the design notes gwz never raises.
- **Decision 10's alternative.** If the exception is kept, session A's private key text stays in a server's memory for up to a connection's life (10 min plus idle) after A ends; same user, in-memory only, but a longer window for any memory-disclosure defect.
- **Same-user exhaustion.** An instance's 64 key slots, the 64 setup jobs (now shared with proofs), the 8 helper slots and the instance ceilings are all exhaustible by another client of the same user; every case fails closed and is bounded, and §17 names most of them.
- **Registry atomicity.** Selection and "disposed when it has no binding and no connection" must be decided under one lock, or a binding can attach to a disposing instance at the 60 s boundary and fail spuriously; C3 should say so.
- **T3's comparison** must be by `Owner.session` (the binding), not the full `Owner` whose serial differs per request; the per-binding proof cache makes a wrong reading cheap rather than wrong, but the text should fix it. It should also say that a binding's own setup counts as its proof for that key.
- **Prompts.** An `ssh-add -c` prompt for a proof is indistinguishable from a login prompt, and a denial is followed by a second prompt for the fresh connection; TR2.8's route check adds a second agent round trip per remote per operation. Cost and UX, not safety.
- **Two-round cap.** No finding here is architectural: P2-1 and the P3s are text rules on fault scope, eviction, clocks, refusal and job ownership, and change no ownership, sharing or trust model.
