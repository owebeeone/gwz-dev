## 1. Findings

### [P2-1] The frozen anonymous-fetch port contract states a durable receiver-state guarantee that the landed implementation contradicts, and no test pins the real behaviour

**Location.** gwz-core `src/git/gitbackend/contract.rs:742–748` (the `GitBackend::fetch_anonymous` doc contract: "…persists no remote name, **does not update `FETCH_HEAD`** and follows no tags"), against `src/local_clone/tests/transport.rs:39–42` ("`update_fetchhead(false)` is requested, but the bundled libgit2 **still wrote the file** for this local transfer (observed here)") and `src/git/gitbackend/transport.rs:190` (`options.update_fetchhead(false);`).

**Violated invariant.** Boundaries §3 makes the compiled signatures plus their stated behaviour the interface checkpoint the consumer lanes branch on ("Lane C lands the actual compiling public signatures … before the consumer lanes branch"), and boundaries §3's closing paragraph requires the real declarations to specify error mapping and allowed call order — i.e. the doc on a port is normative, not decorative. A normative statement about durable state in the receiving repository must be true.

**State sequence.** `fetch_anonymous(receiver, source, ["+refs/heads/main:refs/gwz/local-imports/t1"])` on a receiver that a user has previously `git fetch`ed. The port requests `update_fetchhead(false)`; the bundled libgit2 writes `<receiver>/.git/FETCH_HEAD` for the local transfer anyway, wholesale-replacing the user's pending fetch record. `FETCH_HEAD` is durable, user-visible state consumed by `git merge FETCH_HEAD` and `git pull`. The two statements in the object cannot both be true; whichever is false, a lane reading the port contract to decide what a family import leaves in a receiver is misinformed.

**Impact.** Lane X (`gwz-local-import`) and lane T build their receiver-side assertions on this port. Design §6.2 permits "retained import refs" and forbids only persisted remotes and origin tracking-ref updates, so `FETCH_HEAD` is *permitted* — the defect is that the contract denies it while the implementation performs it, and nothing detects a change of that behaviour on a libgit2 bump. Direction: a fetch silently discards a user's prior fetch record (a loss of progress, small but real), and a lane asserting "the receiver holds nothing but the import ref" will write a test that is either wrong today or silently platform-dependent tomorrow.

**Required correction.** Make the contract state what the port actually guarantees — no persisted remote, no tag following, no `origin` tracking-ref update, explicit refspecs only — and say plainly that `FETCH_HEAD` is written by the underlying local transport despite `update_fetchhead(false)` and is not part of the port's promise. Drop the false clause from `contract.rs:746–747`.

**Closure test.** In `local_clone::tests::transport::fetch_anonymous_imports_an_explicit_refspec_without_persisting_a_remote`, replace the prose comment with an assertion that pins the observed state of `<receiver>/.git/FETCH_HEAD` after the fetch, so a libgit2 change that flips it fails the Tier B slice instead of quietly invalidating the contract.

### [P2-2] The frozen `FamilySession` call-order clause licenses removing a row before its pointer, and the interface then has no operation that can remove the orphan

**Location.** gwz-core `crates/family-store-contract/src/lib.rs:252–254` ("One held family lock. **Call order:** `reread`/`found`/`apply`/pointer operations **in any order** while held…") against `crates/family-store-contract/src/lib.rs:283–285` (`remove_pointer(&mut self, name: &MemberName)` — "Remove the pointer and marker **at the row's recorded path**"), with the behaviour pinned by the reference fake at `crates/family-store-contract/src/contract_tests.rs:561–564` (`view.members.get(name).ok_or(Refusal::NotFound)`).

**Violated invariant.** Boundaries §3: "The real declarations must specify ownership/lifetimes, per-call resource bounds, **allowed call order** and error mapping." Design §3.1's recovery row: "interrupted pointer-only detach/disband | an explicit repeat may remove remaining matching pointers/rows; never directory contents." Recovery states must be a closed grammar: every reachable state must have a named operation that leaves it.

**State sequence.** Under one held session on the family root, with member `A` recorded at `../ws-A` and its pointer + marker installed at that workspace:
1. `apply(&FamilyChange::RemoveRow { name: A, reason: Keep })` — permitted by `validate_transition` (`crates/family-model/src/transition.rs:209–218`: only `RemovalReason::Disposed` carries a state check) and permitted by the call-order clause. The index is written without `A`.
2. `remove_pointer(&A)` — the row is gone, so the store refuses `Refused(Refusal::NotFound)`. `../ws-A/.gwz/family-root` and `../ws-A/.gwz/local-clone-allocation` remain.
3. There is now no operation that can remove them. `remove_pointer` is keyed by member name and needs the row. `disband` (`FamilyChange::Disband`) clears the member map, so an orchestration that removes pointers row-by-row never visits the orphan. From the orphaned workspace itself, `read_view` and `try_lock` both resolve through the pointer to a root that no longer lists it — `StoreError::PointerTargetInvalid` once the index is disbanded — mapping to `manifest_invalid` (`src/local_clone/errors.rs:56–59`), so the clone cannot even disband itself.
4. Terminal state: a workspace whose every `gwz local …` and family merge/pull/push refuses `manifest_invalid` naming a root that holds no matching index, with no gwz command able to clear it and no refusal message naming a recovery.

The safe order is crash-recoverable and the unsafe one is not, which is exactly why the order must be stated rather than declared free: with pointer-removal first, a crash before the row write leaves the row present and an explicit repeat succeeds (`remove_pointer` is documented repeatable, absent files are not errors). The disposal library's own effect vocabulary already implies the safe order (`crates/local-disposal/src/lib.rs:188–194`: `PointerRemoved` before `RowDetached`), but enum declaration order binds nothing, and lanes N and D branch on the *contract*, not on lane D's eventual code.

**Impact.** The one sentence in the checkpoint that exists to stop two independently-developed orchestrations (install, disposal, disband) from disagreeing about write order instead licenses the one order that produces an unrecoverable orphan. Direction of the defect is fail-open: the family index loses a member it still owns files for, and the design's own stated repeat-recovery cannot be expressed.

**Required correction.** Replace "in any order" with the ordering the design requires and the fake already enforces: pointer/marker installation only after the `creating` row exists (already enforced — `contract_tests.rs:490–498` refuses a non-`Creating` row), and pointer/marker removal strictly before the row is removed or the family disbanded; state that a pointer whose row is gone is not reachable through this interface and must not be produced. (Alternatively widen `remove_pointer` to accept a recorded path so the orphan is addressable — a larger change; the ordering clause is the bounded fix.)

**Closure test.** A new case in `contract_tests::run_all`, e.g. `removing_the_row_before_the_pointer_is_refused_and_leaves_no_orphan`: found a family, allocate and install a pointer, `apply(RemoveRow{Keep})`, then assert `remove_pointer` refuses and that the fixture still observes the pointer — pinning that the store never silently accepts the orphaning order, and forcing lane S's real store to answer for it.

### [P3-1] The store conformance suite exercises neither pointer/marker operation, so the real store is never measured on the only cross-workspace writes or on `StoreError::Partial`

**Location.** gwz-core `crates/family-store-contract/src/contract_tests.rs:41–48` (`run_all`: six cases, all index/lock only). `install_pointer` and `remove_pointer` are exercised only in the crate's own `#[cfg(test)] mod tests` against `InMemoryFamilyStore` (`contract_tests.rs:625–698`), which no implementation is bound to.

**Violated invariant.** Boundaries §3: "Integration packages' small contract suites exercise a fake and the real core adapter on the applicable invariants; **fake-only tests do not establish adapter correctness**." Boundaries §6 makes the checkpoint ready only when "the ownership/dependency inventory, compiled interfaces, contract/fake tests, skeleton … agree".

**Consequence.** `install_pointer`/`remove_pointer` are the family's only multi-file, cross-workspace durable effects and the sole reason `StoreError::Partial { completed }` and `MetadataEffect::{MarkerWritten, PointerWritten, MarkerRemoved, PointerRemoved}` exist. Lane S's `YamlFamilyStore` can pass `run_all` in full while leaving both operations `Unimplemented`, or while writing the pointer before the marker, or while reporting `Io` where `Partial` is required — and lanes N and D will have been developed against `InMemoryFamilyStore`, whose marker-then-pointer ordering and partial-effect reporting nothing binds the real store to. `gwz-family-store`'s manifest already carries the `contract-tests` dev-dependency but its single test (`crates/family-store/src/lib.rs:108–132`) does not call `run_all` at all.

**Required correction.** Extend `run_all` with the pointer half: marker-before-pointer ordering on success, `Partial { completed: [MarkerWritten] }` when the pointer write fails after the marker write, repeatable `remove_pointer` whose second call reports no effects, and the two refusals (`ConflictingMetadata` for a destination holding an index, `PointerTargetInvalid` for one pointing at another family). The `StoreFixture` trait needs one added hook to script a write failure, mirroring `InMemoryFamilyStore::fail_next`.

**Closure test.** The added `run_all` cases themselves, plus a `gwz-family-store` test that runs `run_all` through a real temp-directory fixture (expected red at this checkpoint and turned green by lane S), so the suite is the lane's actual gate rather than a document.

### [P3-2] Both compile-probe harnesses copy `crates/` with no ignore filter, so the git-ignored per-crate `target/` the documented standalone Tier A command creates is copied into every probe

**Location.** gwz-core `scripts/checks/test_v1_lifecycle_privacy_probe.py:114–115` and `scripts/checks/test_check_checked_artifact_boundaries.py:32–33` (`shutil.copytree(ROOT / name, target / name)` over a tuple now ending in `"crates"`), against `.gitignore:34–35` (`/crates/*/Cargo.lock`, `/crates/*/target/`) and record §5.3, which documents `cargo test --manifest-path crates/<dir>/Cargo.toml --lib` as the standalone Tier A form — the command that creates those directories.

**Violated invariant.** A probe harness's copy set must be the source tree it means to compile; ignored build output is not source. `crates/` is the first entry in either copy tuple that can contain build output (`/target` sits at the repository root and was never in the set).

**Consequence.** A developer who runs the documented standalone Tier A command leaves up to thirteen `crates/*/target/` trees. The privacy harness performs one full copy per probe (8 probes; record §3 measures it at 96.7 s) and the checked-artifact harness one per compiler probe (record §3: 701 s over 74 tests). Each of those copies now also copies every per-crate build tree — unbounded disk and time growth on exactly the machine that followed the documented workflow, and a source of confusing local-only failures (disk exhaustion) in gates that are otherwise deterministic. CI is unaffected (fresh checkout), which is precisely why this will only ever bite locally and will look like flakiness.

**Required correction.** Give the `crates` copy an ignore filter, e.g. `shutil.copytree(ROOT / name, target / name, ignore=shutil.ignore_patterns("target", "Cargo.lock"))`, in both harnesses.

**Closure test.** A unit test over the copy helper that creates `crates/<x>/target/marker` in a scratch source tree and asserts the copied tree omits it.

### [P3-3] CI's Tier A step resolves each library without a lock, so an allowlisted third-party dependency will silently diverge between the standalone and product builds

**Location.** gwz-core `.github/workflows/checked-artifact-boundary.yml:71–85` (`cargo test --manifest-path "crates/$directory/Cargo.toml" --lib`, deliberately without `--locked`, comment at lines 77–78), with `.gitignore:34` excluding the generated per-crate `Cargo.lock`, and `scripts/checks/local_clone_inventory.json` already allowlisting `third_party: ["git2"]` for `gwz-repo-inspect` and `["git2","tempfile"]` for `gwz-local-testrepo`.

**Violated invariant.** A gate must not report green on a composition the product does not build. Boundaries §5 makes Tier A the per-library evidence command; boundaries §6 makes the CI job the enforcement.

**Consequence.** Today every crate is third-party-free, so nothing resolves and the form is exact. The moment lane I adds `git2` — already authorized by the inventory — the CI Tier A step resolves it fresh with no lock and may select a different version from the one `gwz-dev/Cargo.lock` and `gwz-core/Cargo.lock` pin for the product. A behavioural difference that the newer version tolerates produces a green Tier A over a composition that never ships; a developer's persistent, git-ignored per-crate lock diverges from CI in the other direction. Nothing in the gate set compares the two resolutions. Direction: false green, not false red.

**Required correction.** Either commit the per-crate `Cargo.lock` files and restore `--locked` on the CI step once any crate declares a third-party dependency, or run each library's Tier A command from the outer workspace in the same job so the product's resolution is the one measured. Record §7.6's Option A (nested workspace root) also closes it; whichever route is taken, name the retirement condition rather than leaving the bare `--manifest-path` form standing.

**Closure test.** Extend `check_local_clone_boundaries.py` with a rule that refuses a non-empty `third_party`/`dev_third_party` allowlist entry while the CI Tier A step runs unlocked — i.e. make the gate itself refuse the combination that produces the drift.

**The disposal/creation state grammar is closed and crash-recoverable under the design's own orderings — HELD.** I walked every crash point of `crates/family-model/src/transition.rs`. Nothing is lost and nothing is invented, so it is not a finding; but the record's "no lock file" claim is true only of the three family dispatch slots, which is where it is scoped.

**No new lock is taken by the skeleton — HELD.** The family wrapper never calls `try_lock`; the family lock has no writer; `WorkspaceMutationGuard`/`V1MutationLease` acquisition sites are unchanged.

**Transport partial effects — HELD except for P2-1.** `admitted_local_peer` (`src/git/gitbackend/transport.rs:151–170`) refuses `://` schemes, `git@`/`ssh@` scp syntax, and any path that is not an existing directory, all before `open_repo`; a peer such as `bob@host:repo.git` falls through the prefix check but is caught by `is_dir()`, i.e. fail-closed. ## 3. Risks and next action

Residual risks below the finding bar, recorded so a later auditor need not rediscover them:

- **`expected: "pending"` is self-declared.** A lane can drop a crate from `check_local_clone_boundaries.py` entirely by deleting its directory and flipping one JSON field; the only trace is the honest note line and the "N classified package(s) inspected" count. Flipping it is a visible diff in a lane-C-owned file, so this is discipline, not a hole — but the gate has no retirement condition for a `pending` entry (LBT-012 asks for one for exceptions).
- **`.gwz/family-root` records `root_path` as an absolute host path** (`docs/WorkspaceArtifacts.md`, format-1 sample) while index member paths are root-relative. Moving the root alone makes every clone's family operation refuse `manifest_invalid`. Recovery exists from the root side (`root.join(row.path)` still resolves the members), and design §3 does not require a relative pointer, so this is a documented same-user limitation — but it is the same orphan shape as P2-2 reached without any ordering mistake, and lane D's `DisposeError::PathMismatch` is what must stop it.
- **`TrackingBackend`'s anonymous ports are permissive where the real ports refuse.** `record_anonymous` (`src/workspace_ops/tests/g01/tracking_backend.rs:57–63`) records the transfer and only then consults the injected failure — the right direction for modelling a failure that may have left effects — but it applies neither the local-peer admission nor the empty-refspec rule. A lane-X test asserting "the wrapper refuses a non-local peer" against the double would pass without exercising the refusal. Admission is covered against the real backend in the Tier B slice, so this is a fidelity note for whoever writes the lane-X orchestration tests.
- **Bazel is unverified** (record §6), as the prompt scopes out; nothing in my axis depends on it.
