## 2. Findings (new in revision 2, severity-ordered)

### [P3-14] The lock record is presented as fact, though on Linux and macOS any same-user process, a sandboxed one included, can write or hold the lock file

- **Location:** §4 "The record" and "A held lock" (lines 291–292: "naming the holder's process ID and log path from the record"); §3 "The handshake's bound" (176: "the log path that the lock file records"); §6 "Listing" (591–594); §17 `start --foreground`, "the address taken" (1354: `already running at <address> (pid <pid>); its log is <log path>`) and `server_unavailable` at the bound (1376).
- **Root cause:** the record lives in a 0600 file of the user, which the design's own model (§4 "Files the host opens", §14 996) says a same-user sandboxed process may write; the file rule stops the host from following a link there, but not a sandboxed writer from filling a regular file the host or a client then reads, nor from taking the `flock` itself.
- **Sequence:** after an idle exit a sandboxed process writes `server-<key>.lock` with a pid of its choosing and holds the lock. The user's next `--server auto` finds no listener, starts a copy, and the copy exits saying "already running at `<address>` (pid `<forged>`); its log is `<forged path>`" — while `server status` says "not running". `list` says "not answering (pid `<forged>`, from its lock file)", which is honest; the start message is not. The outcome is the denial §14 already discloses for a squatted socket, but the message misdirects the user to a process that is not the holder.
- **Impact:** a misleading diagnostic on an adversarial path the design models; recovery by `--no-server` or an explicit address still works. Not ARCHITECTURAL: the lock and its record are unchanged in mechanism.
- **Required correction:** (1) every message that quotes the record says "from its lock file", as `list` does; (2) when the lock is held but nothing answers at the recorded address within the 5 s bound, `start` and the copy say so and name the lock file, rather than "already running"; (3) state in "Listing" and in "The handshake's bound" that the recorded address is parsed and walked as any address before any connect, so a forged address cannot reach a network file system or an automount (already implied by §3 "One type"); (4) state that every *reader* of the record (a starter, `list`, a client at the bound) opens it under §4's file rule, so a planted FIFO cannot block a reader.
- **Closure/regression test:** a lock file forged with a pid of a living unrelated process and a foreign address, and the lock held by a test process: `server start` reports the held lock as unverified from its file, `list` marks it not answering, no connect leaves the walk's rule, and a FIFO at the lock path blocks neither `list` nor a client at the bound.

### [P3-15] The handshake bound starts at connect, and a blocking `connect()` against a full accept queue precedes it on Linux

- **Location:** §3 "The handshake's bound" (176: "from its connect"); §4 "A stale socket" (293: "is connected to"); §6 "Probing first" (531) and "Listing" (591).
- **Root cause:** on Linux a blocking `connect(2)` to a Unix stream socket whose accept queue is full waits without limit (macOS returns `ECONNREFUSED` instead); a server whose accept thread has died leaves each timed-out client's pending connection in the queue, so after `backlog` attempts (128 in Rust's standard library) every later connect blocks before the bound's clock starts.
- **Sequence:** the P2-2 counterexample, repeated: a server's accept thread dies; with `GWZ_SERVER=auto` in a prompt hook or an agent loop, 128 commands each fail at the 30 s bound naming the pid; the 129th, from a fresh shell an hour later, hangs in `connect` with no message. The same applies to `server start`'s probe and to `list`. The stale-socket check under the lock cannot hit it (a gwz holder would hold the lock), but an explicit address at a busy foreign socket can.
- **Impact:** a bounded recurrence of the P2-2 hang for late arrivals only; the pid was named by the earlier failures, so recovery information has been emitted. Not ARCHITECTURAL.
- **Required correction:** every client-side connect (a command, the `server` subcommands' probes, `list`, and the host's stale-socket check) is non-blocking or carries a send timeout, and counts against the same bound (30 s for a command, 5 s for the subcommands); a connect that does not complete in time is reported exactly as a silent listener is, naming the pid where the kernel gives one.
- **Closure/regression test:** a listener double that never accepts, with its queue pre-filled: a client command fails within 30 s and `server status` within 5 s, each with `server_unavailable`, on Linux; the macOS row asserts the `ECONNREFUSED` path gives the same message.

### [P3-16] The Windows pipe name's randomness source and the collision path are unstated

- **Location:** §4 "On Windows" (229: "32 random hexadecimal digits"); §11 (769, 772).
- **Root cause:** the design's protection against squatting now rests on the name being unguessable, but the text names neither the generator nor what the host does if `CreateNamedPipe` with `FILE_FLAG_FIRST_PIPE_INSTANCE` fails because the name exists.
- **Consequence:** an implementation drawing from a seeded or time-based generator would restore the squat P3-7 closed; and a collision, however unlikely with 128 bits, would fail the start instead of redrawing.
- **Required correction:** the name is drawn from the operating system's cryptographic generator (`BCryptGenRandom` or `ProcessPrng`); a creation that fails because the name exists redraws, at most a few times, before failing with `server_unavailable`; the record is written only after the pipe exists, so a client never reads a name that has not been created.
- **Closure/regression test:** a Windows unit row asserting the generator used and that a pre-created pipe under the first drawn name makes the host draw another and succeed.

## 3. Invariant analysis (attacks that held, with evidence)

- **The three plan choices under the round-1 counterexamples.** The absolute Linux rule refuses both sibling sandboxes on both sides and lets neither host (P2-1 closed; §12 865, 874). The host-first `SessionHello` puts the secret-free frame before the snapshot on every byte stream, bounds the wait to `SessionOpened`, and refuses a foreign core before the snapshot crosses (P2-2, P3-1, P3-5 closed). The subcommand form is surface, with no safety consequence; the address rule is scoped to `start`, `stop` and `status` and `stdio` reads nothing.
- **The pre-session control plane.** `ServerControl` needs no session and skips the environment check, but it is reachable only by a peer that passed the host's peer check and only after the client's own listener verification; it can do what a same-user unsandboxed process can already do with a signal, and nothing more; a stdio host refuses it. The host accepts exactly one client frame after its Hello and closes after `ServerState`, so nothing else is reachable pre-session.
- **Disclosure order, revision 2.** parse → walk → self-check → connect → kernel-answered listener checks → `SessionHello` (≤ 4 KiB, tag 6, versions and core accepted) → `SessionOpen`. Every new message was checked for values: the bound message, the first-bytes message, `permission_denied`, the 79 templates and `list` print paths, pids, bytes the listener sent, or variable names — never an environment value, a known_hosts body, a token or an agent path.
- **The file rule.** A link, FIFO, foreign-owned or group-accessible entry at the lock, the log, `<log>.1` or `--log PATH` is refused and never followed, truncated or written; rotation replaces an entry through the directory descriptor and never writes through a plant; the starter opens the copy's log under the same rule so a crash before the copy's own open is kept. The OpenSSL scan's different rule is right for the system files it only reads.
- **Descriptors.** Only the standard streams reach a copy or a stdio child on all three platforms; a caller's `flock` and pipes end with the caller.
- **Stale sockets and probes.** A start creates nothing before its checks and probe; only `ECONNREFUSED` makes a socket stale; a foreign live socket survives and receives no byte.
- **Shutdown.** The listener stays open so a client learns it is stopping; the address is released last for a stated, correct reason (a second server's fetch would take only the member lock that lives in the draining host context); `force` shortens the drain at a warned cost; the record is cleared before the lock is released.
- **Idle and files read once.** `ServerControl` opens no session, so a `status` loop cannot keep a server alive; a server that has refused for a changed file exits at its next idle point whatever `--idle-exit`.
- **Departures with safety weight, judged:** the scan's link-following and root-owned files — correct, and not worse than in-process; the bound running to `SessionOpened` — a superset that closes my own "hung in `open`" case; the control frames — acceptable, above; the per-start pipe name — correct reasoning about the pipe listing, with P3-16's gap; the core-version check over every socket — a safe superset; sandboxed callers refused for the stdio form while the SSH form stays open — both fail safe, since the SSH form's `ssh` runs inside the sandbox and gains nothing; `permission_denied` — correct code for a rule that applies in-process too; step 1 keeping the listener — safe, and better diagnosed; Linux CI rows outside containers — a correct consequence, with the first-step assertion.
- **Not changed and still holding:** the must-match enumeration (my round-1 source checks stand at the same HEADs), the walk-versus-connect residual, PID pinning, reuse's revalidation as restated, redaction of logs, the SSH form's option-injection and no-terminal bounds.

## 4. Risks and next action

- **Container users.** No server inside a seccomp-profiled or user-namespaced container, devcontainers included; the design says so and fails closed with a message naming `--no-server`. If the operator wants servers there later, it is a new design decision, not a text fix.
- **`/proc` absent.** The Linux self-check needs `/proc`; without it a caller is refused as "a check that could not be made". Fail closed; worth one sentence in §14.
- **Rotation churn.** A same-user process planting a directory at `<log>.1` makes each auto-started server shut down at its next idle point; functionality persists between idles. Residual.
- **Inferred items that decide behaviour:** `PROC_USER_INIT_INO` for the initial user namespace (consistent with my recollection of the kernel's fixed inode numbers, and tested in §12), `GetNamedPipeServerProcessId` on a client handle and its `GetSecurityInfo` fallback, `POSIX_SPAWN_CLOEXEC_DEFAULT` with the launcher's other attributes, and Windows byte-range locking leaving the record readable.
