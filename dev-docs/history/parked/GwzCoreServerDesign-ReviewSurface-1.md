## 1. Findings (one subsection per finding, severity-ordered)

### P3-14 — The frozen strings name `gwz` literally, and §17 says gwz-py uses "the same strings"; on a gwz-py-only machine the messages point at a program that is not installed (not ARCHITECTURAL)

- **Location:** §17 intro ("gwz-py's forms are the same with `gwz-py` in place of `gwz`") versus the Help block ("gwz-py uses the same strings, in argparse's layout"), and the literal `gwz` inside frozen strings: the gwz-py summary `Run gwz commands in a long-lived server of your own`; the `stdio` refusal `… use gwz --server stdio <command>`; `run gwz server stop first`; `run gwz server stop --server <address>`; `run gwz server stop again … or gwz server stop --force`; `list`'s closing line; the `gwz: ` error prefix; the `gwz: server …` verbose lines; `gwz server: …` output prefixes.
- **Root cause:** the program name is a literal in the frozen strings and the two sentences about gwz-py disagree on whether it is substituted.
- **Violated invariant:** parity between the two CLIs where the object says they match; each message's next step must be executable. §17 itself states that gwz-py's server is its own interpreter on `gwz.cli`, "never the `gwz` executable", and each CLI's core build has its own `<key>`, so `gwz server stop` would not stop gwz-py's server even where both are installed.
- **Reproduction:** on a machine with only the gwz-py wheel, `gwz-py server stdio` at a terminal prints `… use gwz --server stdio <command>`; `gwz-py server start --idle-exit 1h` against a running server prints `… run gwz server stop first`. Neither command exists there.
- **Impact:** every recovery instruction the gwz-py CLI prints is wrong by one word, and the frozen text cannot be snapshot-tested for gwz-py as written.
- **Required correction:** one sentence in the Help paragraph: "`gwz` in every frozen string, prefix and instruction is the invoking CLI's program name (`gwz-py` for gwz-py); nothing else differs" — and apply it to the gwz-py summary line.
- **Closure test:** gwz-py help-snapshot and error-text rows asserting `gwz-py` in the summary, the `stdio` refusal, the different-options refusal, the stop-bound message and the error prefix.

### P3-15 [SSH form] — Commands refused under the SSH remote form have no error code or template, and "the commands that read local files" is not enumerated (not ARCHITECTURAL)

- **Location:** §17 "The SSH remote form", last bullet: "`hook`, `forall` and the commands that read local files are refused (§16)"; the error list has no entry for a command refused under the form.

### P3-16 — `permission_denied` for `SSH_AUTH_SOCK`: the `<rule>` values are not on the surface, no next step is given, and whether it applies without a server is unstated (not ARCHITECTURAL)

- **Location:** §17 "Existing codes on these paths": "`permission_denied`, when `SSH_AUTH_SOCK` fails the local-pipe rule (§5): `SSH_AUTH_SOCK does not name a local pipe (<rule>), so the agent was not opened`". Departure 16 states the rule "applies in-process too".

- **Impact:** a behaviour change to the in-process path — the released tool opened such agents — surfaced with an unreadable message.
- **Required correction:** enumerate `<rule>` as 81 does for `<what>`, state that the rule applies in-process and through a server alike, and end the template with the next step.
- **Closure test:** an error-text row per rule value, in-process and through a server.

## 3. Risks and next action

- **`start` with no options at a running auto server** (idle-exit 10 m) is idempotent by disposition; the user who meant a persistent server learns the truth only from `status`. A cheap improvement: append the running `--idle-exit` to the `already running` line.
- **`--force` on `start`, `status`, `list`** is a usage error under "refuses another's options"; because `--force` is an existing global, gwz-py needs a post-parse check to match. The `stop --force` row's "exits once its sessions are closed" should read "after closing its sessions" (the RemPlan's meaning).
- **`/tmp/gwz-<uid>/` pre-created by another user** makes `auto` unusable on that host; the directory refusal's next step ("choose another address") could add "or set XDG_RUNTIME_DIR or TMPDIR". The squatting itself is the Safety axis's question.
- **`gwz help COMMAND SUBCOMMAND` does not resolve in released gwz** (`unknown help topic 'local clone'`); Su-P3-1's closure test cites `gwz help server start`, so either the help verb is fixed in this release or the test and §17 should use `gwz server start --help`. Pre-existing; not charged to the object.
- **Python session limits** above a socket host's maxima are refused with `invalid_request` and no template; the Python paragraph's ten maxima are correct to state but heavy for a user-facing section — a table would read better. Neither is a defect.
- **Windows `auto` pipe name changes at every start**; the `start` message correctly tells the user to use `auto`, not the pipe name, so nothing copied from it goes stale.
- **Next action:** the four P3s are text edits to §17 (one sentence for P3-14, one template and a command list for P3-15, an enumeration and next step for P3-16, one token for P3-17). None blocks; they can land with the lane owner's acceptance edit. Verdict for revision 2 on this axis: **GO**.
