## 1. New findings

### [S2-P3-1] `install_pointer` takes a free destination while `remove_pointer` and the new orphan guard both key on the row's recorded path, and the conformance suite pins the permissive shape

**Root cause.** The equivalence `destination ≡ resolve(root, row.path)` is what makes the new S-P2-2 guard sound, and it is neither stated in the contract nor checked by any implementation or conformance case.

**Location.** gwz-core `crates/family-store-contract/src/lib.rs:305–312` (`install_pointer(&mut self, name, destination: &Path)` — "Write the allocation marker, then the pointer, into `destination`'s `.gwz/`… Refuses if the destination holds an index or a pointer to another family"; no path-equality requirement) against `:315–316` (`remove_pointer` — "the pointer and marker **at the row's recorded path**"), `crates/family-store-contract/src/contract_tests.rs:855` (`remove_pointer`: `let workspace = self.root.join(&row.path);`) and the new guard at `:713` (`RemoveRow`: `let workspace = self.root.join(&row.path);`). The over-claim it invalidates is `lib.rs:275–280`: "a pointer whose row is already gone is **not reachable through this interface** and **must never be produced**… so the safe order is the only order it accepts."

**Violated invariant.** Boundaries §3 requires the real declarations to specify allowed call order *and* error mapping; a contract sentence asserting unreachability must be true of the interface as declared. Design §3.1 additionally requires canonical paths and pointer equality for exactly this class of mistake.

**State sequence.** Under one held session, member `A` recorded at `../ws-A`:
1. `install_pointer(&A, D)` where `D` is any path other than the store's own resolution of `root.join("../ws-A")` — most realistically `D` = the *canonicalised* absolute destination the installing orchestration already holds, while the guard and `remove_pointer` join the relative row path un-canonicalised. On macOS a `TempDir`-rooted family makes these differ as a matter of course (`/var/...` vs `/private/var/...`). Accepted: the fake uses `destination` verbatim as the pointer key and reads `row` only for `state` and `allocation_id`.
2. `remove_pointer(&A)` → looks at `root.join(row.path)`, finds nothing, returns `Ok` with **empty effects** — indistinguishable from the documented repeatable no-op.
3. `apply(RemoveRow{Keep})` → the new guard looks at the same wrong key, sees no pointer, permits the removal.
4. Terminal state, and now strictly worse than before rem1: the pointer at `D` is unreachable (`remove_pointer` is row-keyed and the row is gone), **and** `Disband` is permanently refused, because the `Disband` guard (`contract_tests.rs:731–748`) scans *all* pointers by `family_id` + `root` rather than by row and will keep finding `D`. Before rem1 the family could at least be disbanded around an orphan; after rem1 the family index itself has no operation that removes it.

**The conformance suite pins the permissive shape rather than closing it.** `installing_a_pointer_over_another_familys_pointer_is_pointer_target_invalid` (`contract_tests.rs:130–172`) founds family two at `root_one/../root-two` with member `B` recorded at `../ws-A`, then calls `second.install_pointer(&b, &shared)` where `shared = root_one/../ws-A` — a destination that is *not* `B`'s recorded path — and requires the store to proceed to the `PointerTargetInvalid` check. A real store that hardened `install_pointer` by refusing a destination which is not the row's resolved path would **fail this conformance case**. So the suite actively obstructs the natural fix.

**Impact.** Lanes S, N and D branch on this contract. Lane S implements `YamlFamilyStore` against a suite that requires accepting a divergent destination; lanes N and D orchestrate install and disposal against a sentence promising the orphan cannot be produced. A single canonicalisation asymmetry — already carried as a residual risk in the remediation plan ("the store must canonicalise paths before `validate_transition`") — reintroduces the exact terminal state S-P2-2 was filed to close, now with `Disband` blocked as well. Direction: fail-open, and undetectable by the current suite.

**Required correction.** State the equivalence in `install_pointer`'s declaration — the destination must be the store's own resolution of the member row's recorded path, and a store must refuse a destination that is not (a typed refusal; `Refusal::PathCollision`/a `PathMismatch`-shaped arm, not `ConflictingMetadata`) — and say that `remove_pointer` and the `RemoveRow`/`Disband` guard resolve the same way, canonically, so the three agree by construction. Then repair the one case that contradicts it: give family two its own destination (`destination_of(&root_two, "../ws-A")`) and pre-plant family one's pointer there, so `PointerTargetInvalid` is still exercised without requiring a divergent install.

**Closure test.** A `run_all` case that installs a pointer through a *non-canonical spelling* of the row's destination (e.g. `root.join("./../ws-A")`, or via a symlinked parent on unix) and then asserts both that `remove_pointer` reports `PointerRemoved` for it and that `apply(RemoveRow)` is refused while it stands — i.e. a store whose three path derivations disagree fails the suite instead of stranding a pointer.

### [S2-P3-2] The S-P3-3 guard's "is CI unlocked?" detection is fail-open on any change to the workflow line's shape, and that half has no test

**Root cause.** `tier_a_unlocked` decides a safety question by single-line substring matching in one hard-coded file, and every way that match can fail — including ways unrelated to the guard retiring — returns "locked", which disarms the guard.

**Location.** gwz-core `scripts/checks/check_local_clone_boundaries.py:276–298`: the missing-file arm returns `False`; the scan returns `"--locked" not in line` on the **first** line containing both `"cargo test"` and `"--manifest-path"`; falling off the loop returns `False`.

**Violated invariant.** A guard whose purpose is to refuse a combination must not silently disarm when it cannot establish the combination's second half; boundaries §6 makes the CI job the enforcement, so the gate's model of that job has to fail toward refusal.

**Reproduction.** Three shape changes, none of which retires the underlying hazard, each of which turns the guard off with no diagnostic: (i) wrap the Tier A command across lines with a `\` continuation — ordinary here, since the enclosing `for directory in … \` loop at `.github/workflows/checked-artifact-boundary.yml:79–83` is already wrapped that way — and no single line contains both substrings, so the loop falls through to `return False`; (ii) move the Tier A loop to another workflow file, and the hard-coded `checked-artifact-boundary.yml` read yields nothing; (iii) introduce any earlier `cargo test … --manifest-path … --locked` line in that file and the first-match return reports "locked" for the whole workflow. The self-declared `ci_tier_a_unlocked: false` flag is a fourth, deliberate route, of the same class as the `pending` inventory state. Today the guard *is* armed (I evaluated it: `True`), so this is latent, not live.

**Impact.** The guard is the entire remaining mitigation for S-P3-3 until record §7.6 is decided; if it disarms, the false-green it exists to prevent — a Tier A pass over a third-party resolution the product never builds — returns silently, and the note line that would otherwise appear (`"… declared third-party edge(s) with a locked Tier A step"`) will read as reassurance while nothing is enforced. Aggravating: the new negative fixture `test_declared_third_party_with_unlocked_tier_a_is_rejected` drives both arms through the **inventory flag**, so the workflow-parsing path has zero test coverage.

**Required correction.** Invert the unknown case: return `True` (assume unlocked) when the workflow exists but no Tier A command can be identified, and when the file is missing but a `crates_dir` is present — reserving `False` for an affirmative `--locked` match or the explicit flag. Match the command across the whole `run:` block rather than per line (normalise `\`-continuations before scanning), scan every `.github/workflows/*.yml` rather than one hard-coded name, and require *all* matches to carry `--locked` rather than returning on the first.

**Closure test.** Two fixtures over `tier_a_unlocked` with no `ci_tier_a_unlocked` flag set: a synthetic workflow whose Tier A command is split across a `\` continuation must still report unlocked (and the gate must still refuse a declared third-party edge), and a workflow carrying `--locked` on every `--manifest-path` command must report locked.
