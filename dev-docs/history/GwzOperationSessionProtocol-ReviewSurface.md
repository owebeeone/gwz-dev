# Python operation-session caller guide: Surface review

**Verdict: GO.** I found four documentation defects with concrete first-day consequences, all P3. None establishes a post-release compatibility break under this review’s severity contract.

I reviewed only `dev-docs/GwzOperationSessionCallerGuideDraft.md` and the committed `gwz-py/README.md`. CLI help is inapplicable to this Python API review. The root SHA was `852fd94a082f82b8d4e9d777edf7d20acdf12576` and the `gwz-py` SHA was `45bcd7b3ea102ca927935cee1b41b43934d68140` at both the start and end. The command whitelist did not permit independent checks of the supplied `gwz-core` and `gwz-transport` SHAs. I made no changes or test runs.

### Findings

**P3-1 — Admission inputs and defaults are undiscoverable.** The guide shows `client.start_fetch()` without arguments, then refers to a caller-supplied `request_id`, explicit endpoint placement, a physical connection ceiling, and finite work and retained-result budgets. It gives no call signatures, option names, defaults, or retained-result-capacity error and recovery path. A caller trying to correlate the two example operations or recover from an admission failure must guess what to pass and when retrying can work. The guide should state the relevant signatures and defaults and map every admission limit to its error and recovery action. **Closure check:** a reader can configure or deliberately accept each default, then identify the response to each exhausted budget using the guide alone.

**P3-2 — The event-reading contract is incomplete.** At “You may iterate `first.events()`,” the guide does not show the iteration form, event fields, starting position, completion behavior, or how to recover after its stated cursor-gap error. In the requested two-operation walkthrough, I must guess how to read events from `second`, whether earlier events are replayed, and when reading is complete. Add a minimal event-reading example and specify replay, ordering, termination, and gap recovery. **Closure check:** the documented example reads the second operation from its first available event through completion and handles a lagging reader.

**P3-3 — Result and cancellation reports have no caller-visible outcome contract.** The guide says `cancel()` returns “its report” and a later Git or transport failure is reported through `result()`, but supplies no result/report shape or rule for whether failure is returned or raised. After cancelling the first operation before any event, I cannot tell how to distinguish cancellation from success or failure; after reading the second result, I cannot tell what to inspect. Document the returned types or fields and the exception behavior for success, cancellation, and operation failure. **Closure check:** examples classify all three outcomes without relying on source code.

**P3-4 — The example omits the release half of its lifecycle.** The opening example cancels one handle and reads the other result, but releases neither. Later text says `release()` frees records under a finite retained-result budget; it does not say when records otherwise expire or whether closing the client frees them. Repeating the example leaves the caller unable to predict retained-capacity use. Show release of both handles after their reports, results, and events have been consumed, and state its behavior on repeated calls and during client close. **Closure check:** the complete first-day example can be repeated without accumulating retained records.

### First-day walkthrough

The guide lets me start two fetches and obtain both IDs before the first event. It also tells me that `await first.cancel()` joins cleanup and leaves the second operation running. I must then guess the event-iteration syntax and event contents for `second`, the meaning of the cancellation report and `second.result()`, and when to release both handles. Leaving `async with Client(...)` documents endpoint cleanup, but does not resolve the retained-record question. These are documentation corrections to the proposed surface; the reviewed text does not establish a blocking interface defect.
