## 2. Invariant analysis (attacks that held, with evidence)

**2.1 The bound against adversarial jobs** (`context.rs:164-177`, `182-229`).
- *A job whose `poll` never reports finished.* `dispose` sets `closed`, then `wait_timeout_while(state, wait, |s| s.active() > 0)` with `wait = deadline − now`. The predicate stays true, the wait times out at the deadline, `remaining` is computed fresh under the lock, `released` is set, and the call returns. Test `shutdown_returns_at_its_bound…` shows `took >= BOUND` and `< BOUND + SLACK` with `ONE_PENDING`; the job is then polled to its end and dropped once (`drops() == 1`). The deadline is absolute (`Instant::now() + bound` at `context.rs:301`), so time spent acquiring the supervisor lock counts against it, not on top of it.
- *A job whose `poll` blocks, so the supervisor thread is stuck.* `polling` was set to the batch size before the lock was dropped (`:186-187`), and stays there while the thread is inside `poll`. `active()` is therefore ≥ 1, `dispose` times out at the bound and reports every job of that batch as pending. True: none of them can be polled again. The stuck thread is CS1.4's accepted consequence of a job that violates the trait's "without blocking"; `shutdown` never joins it, so its bound holds.
- *A job whose `poll` panics during shutdown.* `catch_unwind` at `:190` quarantines it; on re-lock `settled` is true (the batch shrank), `notify_all` wakes `dispose`, which counts it in `quarantined.len()`. Test `a_quarantined_job_appears_in_the_pending_report`: `ONE_PENDING`, returned without waiting the bound.
- *A job whose `Drop` blocks or panics.* Finished jobs are dropped through `discard` (`:234-236`) outside the lock and before the thread re-locks, so `polling` stays > 0 until the drop completes; a blocked `Drop` is therefore counted as pending at the bound, and a panicking one is contained. Quarantined jobs are dropped after `drop(state)` at `:222`, so neither case can hold the supervisor lock that `dispose` needs.
- *Is the report then true?* `remaining = active() + quarantined.len()` (`:172`) is taken under the lock after the wait. `remaining == 0` implies every finished job's `Drop` has already run (drops precede the re-lock that zeroes `polling`), no job is waiting, and nothing is quarantined. Over-counting is possible only for a job whose `poll` is returning `true` at the instant of the deadline, which is conservative.

**2.2 Re-entrancy and races.**
- *Lock order.* `HostShared::shutdown` takes `report` then, inside `dispose`, the supervisor mutex; `release`, `supervise` and the thread take only the supervisor mutex; `open` takes neither. One order, no inversion. The `report` guard is held across a wait on the supervisor's condvar, which releases the supervisor mutex, and nothing but `shutdown` ever wants `report`.
- *No condvar wait without a predicate.* `dispose` uses `wait_timeout_while`. The thread's `wait` (`:214-217`) and `wait_timeout` (`:206-210`) sit inside `loop`, whose body re-derives every decision from state under the lock, so a spurious wakeup is harmless.
- *No lost wakeup.* Every state change is made under the lock and followed by `notify_all` (never `notify_one`): `settled` at `:201-204`, `release` at `:157`, `dispose` at `:175`, `supervise` at `:285`, thread exit at `:225`. `dispose` re-checks its predicate under the lock before each wait, and the thread checks `released` under the lock before its untimed `wait`, so neither can miss the other's notification.
- *`shutdown` from a supervised job's `poll` (the supervisor thread).* `poll` runs outside the supervisor lock, so `dispose` acquires it, sets `closed`, and waits: the calling job is in `polling`, so the predicate stays true and the wait runs to the bound; the report counts the caller. No deadlock, a full-bound stall, a true report. From a job's `Drop` during the exit path (`:223`) the report is already stored, so the call returns at once.
- *From two handles at once.* The first holds `report` while it disposes; the others block on the mutex and receive the stored clone. Test `concurrent_shutdowns_wait_for_the_first_and_return_its_report`: six callers behind a `Barrier`, each `ONE_PENDING`, each within `BOUND + SLACK`. A later caller's wait ends when the first's bound does, which is before the later caller's own bound.
- *Racing `supervise`.* `closed` is the first write of `dispose` under the lock (`:166`). A `supervise` that took the lock earlier pushed its job before `dispose` could run, so it is counted and waited for; one that takes it later is refused (`:274-276`) and drops its job unpolled. There is no gap. The refused job drops on the caller's thread after the guard: `state` is a body local and `job` a parameter, so the guard is released first (function parameters drop after the body's locals).
- *Racing `open`.* `open` reads `shut_down` with `Acquire` (`:399`) and never blocks behind a running shutdown. An `open` whose load precedes the `Release` store (`:297`) still opens; that is the disclosed window, examined in 2.4.
- *Racing the drop of the last other handle.* `HostShared::drop` can run only when no handle exists, and `shutdown` holds `&self`, so the two cannot overlap. After `shutdown`, `release()` from the drop sets flags already set and notifies; nothing is disposed twice. Test `a_drop_after_shutdown_disposes_nothing_more`: the finished job's `drops()` stays 1 and `polls()` 1 across the drop, and the drop returns at once.
- *From a gate crossing or a cancel callback.* `shutdown` takes no gate lock and no session lock, and the supervisor never crosses a gate, so there is no deadlock; the consequence is a closure that holds its gate for up to the bound, which CS1.4's rule ("a crossing's closure … must be short and must not block", `gate.rs:18-21`) already forbids. `forbid_nesting` does not detect it. No planned caller does this: `shutdown`'s callers are drivers at their end (CS6.6, CS8.10). Recorded in §3.

**2.3 The report's truth and its reuse.** A job admitted during shutdown is impossible after `closed`; a quarantine during shutdown moves the job from `active()` to `quarantined.len()`, and both terms are summed; no finish is assumed, since only `Ok(true)` from `poll` ends a job. `peer_cleanup_confirmed` is the literal `false` at `:304`, so it can never read true while anything is pending. The stored report is returned to later calls even after jobs finished in between (test: `ONE_PENDING` after `drops() == 1`); this mirrors §8's repeated close, and no later step relies on a second call being current: CS6.6 and CS8.10 call once, CS4.5 drops without a report.

**2.4 After `shutdown`: fail-closed direction.** `supervise` refuses with `io::Error::other` and drops the job unpolled; the doc at `:266-269` binds the caller to register before starting work, so nothing starts that nothing cleans up. Test `after_shutdown_no_job_is_supervised_and_no_session_opens`: `(polls, drops) == (0, 1)`, no thread starts, `open` fails with `InvalidRequest`, and a further `shutdown` returns `NOTHING_PENDING`. A refused `open` drops its `SessionOptions`, so the snapshot it carried is wiped on refusal, a good property. In the disclosed race window a session may open on a shut-down host context; in CS1.9 it can do nothing (no `send`/`recv`), and in later steps its supervised work meets `closed` and its network work meets a disposed registry, while local work needs neither. That is a driver ordering error whose worst case is a session that runs locally and is refused for network work: not fail-open.

**2.5 Drop without and after `shutdown`; quarantined jobs.** Without `shutdown`, `release()` (`:152-158`) sets `closed` and `released` and returns without waiting, exactly CS1.4's behaviour plus a flag that no remaining handle can observe. After `shutdown`, the supervisor is already released and the drop adds nothing. Nothing drops on a wrong thread: finished and quarantined jobs drop on the supervisor thread as before, refused jobs on the caller's thread as CS1.4's spawn-failure path already did. Quarantined jobs now end at the supervisor's stop, which after `shutdown` comes as soon as the active jobs finish, possibly while the host context still lives. This is safe: the host context is closed to new work at that point, a quarantined job's `Drop` runs the same code it would run at the host context's drop (only earlier), and it is reported pending before it drops. It is also what makes "a drop after `shutdown` disposes nothing more" literally true. The plan's CS1.9 wording ("for the host context's lifetime") now describes the drop path only; see §3.

**2.6 `transport_off`.** It enters only through `SessionOptions.transport_off` (`:378`), false from `new` (`:388`), is moved by `open` (`:405-416`) and read by `SessionContext::transport_off` (`:354-356`). No code path reads the snapshot for it, `EnvironmentSnapshot` has no accessor the context calls at `open`, there is no `Default` for `SessionOptions`, no configuration file is read, and the process-globals checker reports no new environment read. Test `a_session_reads_transport_off_from_its_options_and_never_from_its_snapshot`: 10 switch-like names × 9 on/off values, two sessions of one host context, each reading its own option. A derivation ORed or ANDed with a snapshot value would fail one of the two sessions.

**2.7 Zeroization "when its session ends".**
- *Copies that escape.* POSIX `from_byte_pairs`: none, `OsString::from_vec` keeps the allocation. Windows `from_bytes` (`environment.rs:252-274`): the input `bytes` and the `units` vector are wiped; each lone-surrogate temporary is wiped (its `from_wide` starts at capacity 1 with length 0, so its one growth frees nothing secret); `text` is built at `bytes.len()`, which bounds canonical WTF-8 output (1↔1, 2↔2, 3↔3, 4↔4 bytes, and a pair written as two 3-byte surrogates shrinks 6→4), so it never grows. `push_wtf8`'s join branch, the one path that reallocates, is unreachable: `char::decode_utf16` emits an unpaired lead only when the next unit is not a trail, so a lone trail never follows a lone lead. The stack buffer of `encode_utf8` is the disclosed residual. `from_os_pairs` copies nothing. `insert`'s duplicate drops through `Wiped`. The `entries` vector's growth copies only `(ptr, cap, len)` triples, never bytes. `apply_to`'s copies in `Command` are documented as outside.
- *Who can hold the session context after the end.* In CS1.9 the `ClientChannel` is the only strong owner; gates hold a `Weak` (`gate.rs:243`) and upgrade it only inside `cross` for the closure's duration, and §8's step 5 revokes every gate before the session ends, after which no crossing is in flight. `nothing_can_copy_the_snapshot_past_its_session` pins at compile time that neither `EnvironmentSnapshot` nor `Wiped` is `Clone`, so the context's drop is the snapshot's only drop. `a_session_drops_its_snapshot_when_it_ends` shows the weak reference no longer upgrades once the channel drops.
- *Test soundness.* `a_name_or_value_overwrites_the_allocation_that_held_it` reads only the live allocation returned by `overwritten()` (same pointer asserted), sets its length to its capacity only after `overwrite` initialised every element, and checks zeros across the spare capacity that `secret_buffer` had filled with `#`. The writes are `write_volatile` followed by a `compiler_fence`, which the compiler cannot elide. No test touches freed memory.

**2.8 Secrets in new paths.** `ShutdownReport`'s `Debug` prints two scalars. The `io::Error` and `ModelError` messages are static strings. `SessionOptions`'s derived `Debug` prints the bool, `HostContext { .. }` and the snapshot's entry count (`formatted_output_carries_no_value_and_no_name`). No new panic message or log line carries a name or value.

**2.9 Threads and time.** `shutdown` spawns no thread; if the supervisor thread never started, `dispose` returns at once. The bound is `Instant` through `Condvar::wait_timeout_while`, so a wall-clock jump has no effect. A machine suspended mid-wait extends the bound in wall-clock terms by the suspend, as with every std timed wait; no instance clock is involved here (reuse §7's clock rule is CS7.13's).

**2.10 Accepted CS1.4/CS1.5 behaviour this step touches.** `release()` gains `closed`, unobservable after the last handle drops; `run()` gains `polling` and a `notify_all` on `settled`, which only adds wakeups that every waiter re-checks; `Wiped::drop` is the same overwrite through `overwritten()`; the Windows decoder is tested equal to `from_wide`; `open` gains one refusal; `SessionOptions` gains a field behind `non_exhaustive`. CS1.4's tests all still pass unchanged.

## 3. Risks and next action

None blocks. For the lane owner and the named steps:

1. **CS6.6 and CS6.7 — composing `peer_cleanup_confirmed`.** The shutdown report's `false` means "no peer took part" (§8's `(0, false)`), and after CS3.7 the same `false` will also mean "a peer did not confirm". A blind `&&` with the session's close report, as `local_command.rs:64-65` combines today, would turn a confirmed session into an unconfirmed command. The implementer flagged this; CS6.6 must combine so that a host context with no peer leaves the session's confirmation alone, and CS6.7's notice must not fire on this `false` alone.
2. **CS3.7 — the one deadline and counting.** The registry's disposal precedes the supervisor's inside the same `dispose(deadline)`; between the `shut_down` store and the supervisor's `closed`, `supervise` still admits the registry's leftover work, which is intended, and `remaining` then counts it. CS3.7 must not also count that work in its own remainder, or the report double-counts.
3. **CS3.5 and CS3.10 — the refusal contract.** Fail-closed after `shutdown` rests on the rule at `context.rs:266-269`: register the job, then start the work it owns. A caller that starts first leaks what the refused job would have cleaned up.
4. **The `open`/`shutdown` window (disclosed).** A session opened just before the flag is stored runs local work and is refused network work. Drivers order `shutdown` after their last `open`; CS4.5's exit finalizer and CS8.10's draining server already do.
5. **`shutdown` inside a crossing or cancel callback** is not detected by the gate's nesting rule and would hold the gate for up to the bound. No planned caller; the rule already forbids blocking in a closure. If a later step gives workers a reason to call it, add the check then.
6. **Windows in-process capture (CS6.6).** `from_os_pairs(std::env::vars_os())` receives strings that std's `from_wide` built by growing for non-ASCII values, freeing outgrown buffers unwiped before core ever sees them. This is the class of residue CS1.9 removed from `from_bytes`, but it lies in std at the driver's edge, outside the snapshot's claim. The byte-stream path (the server, where accumulation matters) uses `from_byte_pairs` and is covered. Worth a sentence in gwz-cli's capture at CS6.6.
7. **Plan text.** CS1.9's bullet says quarantined jobs hold their resources "for the host context's lifetime"; the object drops them when the supervisor stops, which after `shutdown` precedes the host context's drop. Safe (§2.5), and required by "a drop after `shutdown` disposes nothing more"; the plan's wording should follow the object.
8. **Clock and suspend.** The 5 s bound is process-visible monotonic time; a suspend mid-shutdown lengthens the wall-clock wait. No action; recorded so CS7.13's clock work does not assume `shutdown` reads an instance clock.
