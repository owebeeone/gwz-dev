## Findings

### S-1 (P2) — The fallback's safety net is gone, but the corrected libgit2 is not pinned into the build

- **Location:** `gwz-core/Cargo.toml:83` (`git2 = { package = "gwz-git2", … features = ["https", "ssh", "unstable-sha256"] }`, no `vendored-libgit2`); `git2-rs/libgit2-sys/build.rs:12` (`range_version = "1.9.7".."1.10.0"`) and `:113-116` (`try_to_use_system_libgit2 = !vendored && !zlib_ng_compat` → pkg-config system libgit2 is preferred when found); `gwz-core/src/git/gitbackend/transport.rs:327-335` (`fetch_anonymous` runs `remote_handle.fetch(...).map_err(git_error)?` alone); `gwz-core/dev-docs/GwzNoFallbackPlan.md:231-279` (removal record). Contrast `gwz-core/tests/transport_backend/prepare.py:87-88`, which *does* force `vendored-libgit2` for the candidate.
- **Root cause:** the removal rests on "the fork's Rust candidate `4c1caab` pins the native local-fetch correction" (Plan §4, line 238-246). That is true of the fork's *vendored C*. The fork's `build.rs` still prefers a system libgit2 in `[1.9.7, 1.10.0)` found via pkg-config, with no fix-presence probe, and gwz-core's dependency does not turn on `vendored-libgit2`. No production code asserts `cfg(libgit2_vendored)` (grep of gwz-core, gwz-cli, gwz-py: none). Every qualified consumer row in `GwzGitLibraryNativeConsumers.md:94-98` is "Vendored 1.9.7", and `GwzNoFallbackNativeFix.md:100,202` says the fixture "forces vendored libgit2" — the qualification pinned the property, the manifest does not.
- **Violated invariant:** the removal record's "the import runs on libgit2 alone" presumed the *corrected* libgit2. Before the object, an unpatched libgit2 fell through to `git fetch` and the import succeeded; after it, the same build fails the import.
- **Reproduction:** on a host with pkg-config and an upstream libgit2 1.9.7 development package (Homebrew or `libgit2-dev`), `cargo build` in gwz-core links the system library (the fork's build output then lacks `cargo:rustc-cfg=libgit2_vendored`), and `GWZ_TEST_GIT=real cargo test --lib -- local_clone::tests::transport_noncommit::native_same_tree_receiver_ref_does_not_block_the_fetch` fails at the native fetch with `object is not a committish`. Equivalent forcing: `LIBGIT2_NO_VENDOR=1`. **Not executed here:** this machine has neither pkg-config nor a system libgit2, so its four `gwz-libgit2-sys-*` build outputs all show `libgit2_vendored` and the tests pass; the selection is environmental, which is the point.
- **Impact:** bounded to builds that link a system libgit2 in that range (source builds, `cargo install`, downstream users of the published crate with Homebrew/apt libgit2). On such a build, `gwz merge --remote <lane>` and every family import into a receiver holding a tree-checkpoint ref (the motivating Codex case) fails with `GitCommandFailed: object is not a committish`, where 1.0.17 succeeded. No data loss: libgit2 fails before updating refs (the documented `FETCH_HEAD` truncation still applies). No secret exposure. The failure is loud but opaque, and the version guard at `transport_noncommit.rs:275,432` (`libgit2_version() == (1, 9, 7)`) cannot tell the fork from upstream — `gwz-git2 0.21.0` and upstream `git2 0.21.0` report identical numbers.
- **Required correction (one of):** (a) add `"vendored-libgit2"` to gwz-core's `git2` features, as `prepare.py` already does for the candidate; or (b) state and bound the risk where the removal is recorded (`GwzNoFallbackPlan.md` §4 "Not claimed") and in the user-facing install/merge docs: a system libgit2 loses the correction and the import then fails with that message. (a) is the safe one; (b) is the minimum.
- **Closure test:** with (a), every gwz-core build output under `target/*/build/gwz-libgit2-sys-*/output` contains `cargo:rustc-cfg=libgit2_vendored`, and `LIBGIT2_NO_VENDOR=1 cargo build` (the explicit opt-out) is the only way to link a system library; with (b), the two documents name the failure text and the build condition.

### S-3 (P3) — The `TESTS` rule can be waived through an `include` allowlist entry and evaded by a `cfg_attr`-carried path

- **Location:** `gwz-core/scripts/checks/check_process_globals.py:56-57` (docstring: "no allowlist entry waives it"), `:434` (`_path_attribute` reads only `#[path = …]`), `:468` (a non-literal `include!` in production becomes an `include` occurrence), `:725` (`TESTS` errors come only from files the scan reached).
- **Root cause:** two gaps in the reach, not in the rule. (a) A non-literal `include!` of a `tests/` file is an `<unparsed include>` occurrence; `include` is not in `GLOBAL_STATE_KINDS`, so a `permanent` entry without `imposed_by` is accepted, and the included file — and every global in it — is never scanned. (b) `#[cfg_attr(not(test), path = "../tests/x.rs")] mod x;` is not recognised as a path attribute; `mod x;` resolves to `src/x.rs`, is not found, and `tests/x.rs` is neither reached nor swept (the unreached sweep covers only the roots' directories).
- **Violated invariant:** "a file there that production code reaches … fails as `TESTS`, and no allowlist entry waives it".
- **Reproduction:** `…/scratchpad/review-cleanup/safety/tests_rule_evasion_probe.py` (fixtures in scratch): fixture A (`include!(concat!(env!("CARGO_MANIFEST_DIR"), "/tests/spliced.rs"))` plus an `include`/`<unparsed include>`/`permanent` entry) and fixture B (`cfg_attr` path) both return `errors: []`, `in_tests: []`, `unreached: []`, while the literal control C returns the `TESTS` error. The spliced file's `AtomicUsize` static is invisible in both.
- **Impact:** bounded. (a) needs a deliberate allowlist entry that a reviewer sees. (b) is a spelling the standing conditional-compilation rule already forbids, and `check_cfg_boundaries.py` ratchets `cfg_attr` occurrences (437 listed, "nothing new"), so a new one is flagged there — by the other gate, not this one.
- **Required correction:** fail closed in the checker: refuse an `include` occurrence in production whose literal fragments mention `tests/`, or refuse `permanent` for `<unparsed include>` outright; and parse `cfg_attr(<pred>, path = "…")` as a path attribute (conditional on `<pred>`, production unless it implies test). Add both fixtures to `test_check_process_globals.py::TestsDirectory`.
- **Closure test:** fixtures A and B each produce a `TESTS` error.
