## 2. Invariant analysis (attacks that held, with evidence)

- **The `thread_local CROSSING` entry and its disposition.** `CROSSING` is a `Cell<bool>` meaning "this thread is inside a crossing's closure or a cancel callback" (`gate.rs:39–43`), set by `CrossingMark::enter` and restored on drop, unwinding included (`:45–63`). It holds no session content, no operation identity and nothing that outlives a call, so two sessions cannot interfere through it; it is imposed by the remediation plan's accepted choice ("no crossing inside a crossing, on any gate"), which no per-gate record could detect. It therefore meets O9/§5.7's definition of `permanent` ("carry no session-relevant state"), the allowlist's own rule text, and GWZRequirements' "inventoried with a disposition". `debt` would be wrong: §5.7 closes O9 "when no allowlist holds a `debt` entry on the session path", and the gate is the session path, so a `debt` entry with no removing step would make O9 unclosable. The plan's §3.0 sentence "A step that adds state lists it as `debt` and names the step that removes it" is read purposively here: its purpose, as the plan's own Safety attack list states, is "gaming the ratchet by flipping `debt` to `permanent`" for state that carries session content, which this does not. The letter of that sentence and §5.4's inventory count are a plan-text impact, listed in §3. Held.
- **§1 and "`open` validates the limits it is given": the two new bounds.** `read_bytes ≤ 32 MiB` (`limits.rs:123–127`) derives from §3's fixed 64 MiB frame and §1's meaning of `read_bytes` as bytes returned by one read: the reply must fit a frame, and the contract states no envelope size, so a documented half-frame split is a validation rule the contract's sentence admits, and the server design's socket-host maximum (the 1 MiB default) sits far below it. `close_wait ≤ 1 h` (`:137–139`) caps a limit §8 calls a bound ("Close waits for workers, within a bound"); no accepted design asks for a longer wait (the server's maximum is the 60 s default; the reuse design's `shutdown` runs "within the close bound"), `Duration::MAX` is refused with `invalid_request` naming `close_wait`, and zero's meaning is documented (`:58–61`, `RustApi.md:174–175`). Both refusals are before any effect (`context.rs:251`). `MAX_CLOSE_WAIT` is private, so no new public item. Tests `a_read_leaves_half_the_frame_for_its_reply_envelope` and `close_wait_is_at_most_one_hour` pass. The pre-existing `Case` list still refuses `read_bytes = MAX_FRAME_BYTES` naming `read_bytes` (`:210`). Held.
- **`from_os_pairs` against §5.6 and §9.** §5.6 puts the capture at the driver's edge and says core never reads the environment; §9's byte-string form serves the extension boundary. `from_os_pairs` takes `(OsString, OsString)`, the platform's lossless native form for a Rust driver (raw bytes on POSIX, WTF-8 on Windows), and `from_byte_pairs` keeps serving the extension and the server design's `EnvironmentEntry { name: bytes, value: bytes }`. Both share one collector (`environment.rs:94–114`) and one check (`checked`, `:182–194`), refuse with `invalid_request` naming only the index, keep the first value per name, and wipe the remainder on refusal (`:105`). The RustApi.md text (`:148–161`) states the two constructors, their refusals with the Windows qualifier, first-wins, the platform name rules and the qualified zeroization accurately. Held.
- **The gate's states after the restructuring.** `cross` (`gate.rs:323–341`) takes the crossing lock, then checks `revoked`, upgrades the weak session, and for `effect`/`append` checks the token; `report` maps cancelled to "lands" and revoked to `None` (`:305–310`); `refusable` maps to the two `Cancelled` errors (`:312–318`). `revoke` cancels first, then takes the lock and sets `revoked` (`:211–216`), so once it returns no crossing is in flight and none can start. `state()` reads the atomic, the weak count and the token without the lock (`:277–286`). The eight round-1 gate tests are unchanged apart from location and pass, including `revocation_waits_for_a_crossing_in_flight_and_nothing_lands_after_it` and `a_gate_does_not_keep_its_session_alive`. O8, §5.3 and §5.6's two further states hold as in round 1.
- **"Nothing but the token cancels."** Unchanged: the only paths to `TokenInner::cancel` are `CallControls::cancel` and `revoke` (`:201–216`); `nothing_but_the_token_cancels` passes. Held.
- **§5.6's supervisor after quarantine.** A job whose poll panics is kept and never polled again (`context.rs:110–119`); with only quarantined jobs the thread waits without a timeout (`:126–132`); once released and with nothing left to poll it drops the quarantined jobs, containing a `Drop` panic (`:133–141, 149–151`), then reports it has ended. This is the SSH reaper's existing semantics (`agent_job.rs` `Retained::reap`: poisoned entries are kept and never claim disposal), so `SupervisedJob`'s unchanged signature still admits CS3.5's move, and the reuse design §7's "unfinished work stays under the supervisor" holds while the host context lives. "Dropping it stops its supervisor thread once its jobs have finished" (§5.6) holds for jobs that can finish, and a quarantined job no longer keeps the thread alive after release; `RustApi.md:146–147` says so. Tests `a_job_that_panics_is_quarantined_and_never_polled_again` (polled exactly once; no wake over 200 ms; ends within 1 s of the drop; `Drop` ran) and `a_quarantined_job_does_not_stop_the_others` pass. Held.
