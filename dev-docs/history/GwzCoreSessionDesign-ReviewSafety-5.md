## 1. Findings

### P3-1 — `cancellation` (8, bool, optional) is not absence-tolerant under Taut, so the degraded reading §5.8 relies on is unreachable against any writer lacking the field

*Carried from revision 4 (the same word at field 3); not a regression of revision 5, but the changed line is its carrier and the review areas ask for it. Not architectural.*

- **Root cause.** §13 L530 declares the appended field "optional". In the production DSL (`F(..., optional=True)`, `dsl.py` L134–151) that yields `missing_ok=False`, which every projection reads as present-but-nullable: the default Rust codec panics on a missing key, the fail-closed codec returns `MissingKey`, and gwz-py's strict Python decode raises. Only `missing_ok=True` tolerates absence, and the projection's own appended siblings 3–7 in the same message all carry it.
- **Location.** `dev-docs/GwzCoreSessionDesign.md` §13 L530; the meaning of false/null/absent is stated nowhere (§5.8 L359 says only "reports whether cancellation is supported").
- **Violated invariant.** G8 / Protocol.md: an appended field must keep older peers readable when crossing versions; §5.8: the bridge learns from this field that promptness is unavailable and "promises no promptness it cannot deliver". A reader following the text literally cannot learn that from a host that predates the field; the call fails instead.
- **Reproduction (by inspection).** Generate a reader from a schema with `cancellation=F(8, BOOL, optional=True)`; decode the v1.0.17 encoding `{1: true, 2: false}`: `generated.rs`-style `try_get(8)?` → `Err(MissingKey(8))`; gwz-py `decode_message("TransportCapabilitiesResponse", …)` → `GwzProtocolError("failed to decode …")`. With `missing_ok=True` the same input decodes with `cancellation = None`.
- **Impact.** In-scope pairs are same-build and always emit key 8, so no in-scope wire breaks; that is why this is P3, not P2. The concrete consequences are: (a) in the in-tree candidate build, if CS1.1 regenerates the production schema and gwz-py's IR before the candidate projection (which is stale at HEAD and ungated in CI), every `transport_capabilities` reply lacks key 8 and every identity-bearing Python operation fails with a raw `GwzProtocolError` rather than `_require_transport_capability`'s intended `UnsupportedOperation` message; the plan's CS1.1 lexical test and dual-cfg corpus run would catch this before merge, but only because those tests exist, not because the text is safe; (b) in the cross-version deployments Protocol.md is written for and the placement lane this revision now shares the message's number space with, a newer client cannot negotiate with an older host at all, and `cancellation` would be the only present-required field in a capabilities message otherwise built for absence.
- **Correction.** In §13 L530 write: "`cancellation` (8, bool, optional and may be absent — Taut `missing_ok`); absent or null means cancellation is not supported, the same as false." Mirror the one clause in §5.8 L359 ("absent or null reads as unsupported").
- **Closure test.** Add to §15.2: "A `TransportCapabilitiesResponse` encoded without key 8, and one with key 8 null, decode in both language projections with `cancellation` unset, and the bridge reports no cancellation support." CS1.1's lexical test then shows field 8 with `missing_ok` in both protocol files.

## 2. Invariant analysis

- **Mixed-version misread (production vs candidate).** Cannot occur. A production reader (`try_get(1)`, `try_get(2)`, later `8`) ignores the candidate writer's keys 3–7; a candidate reader tolerates a production writer's absent 3–7 via `try_get_opt` and `missing_ok`. Revision 5 removes the one collision that could have produced a decode failure: had a bool been read at 3 against a candidate writer's integer list, the fail-closed `try_bool` would have failed the call (a refusal, never a silent misread). No reader ever implemented field 3 as `cancellation` (sweep, §0). Holds.
- **Older released readers.** v1.0.17 gwz-core and gwz-py carry fields 1–2 only and ignore key 8 (Rust: no unknown-key check; Python: `__unknown__` captured, then dropped by `_from_wire_message`). The current candidate build already exercises this direction daily: gwz-py's production Python reader against a Rust writer emitting 1–7. Holds.
- **Newer reader, older writer.** Fails the call unless `missing_ok` (P3-1). Blast radius is one call: §10 fails only the call whose payload does not decode. No in-scope pair produces it.
- **Absent-as-false promise (§5.8).** With the text as written the field cannot be read as absent; against a same-build host it is always a bool, and null is undefined. No path promises promptness it cannot deliver on the strength of this field; the ordinary build writes false (§15.15). The separate, recorded C1 question (true in a transport build while native-path remotes cannot cancel promptly) is unchanged by revision 5 and stays with its named owners.
- **Stuck states from reserving 3–7.** None. Taut's validator permits the 1, 2, 8 gap; all encoders sort keys, so the candidate's 1, 2, 8, 3–7 declaration order is wire-invisible and the frames stay deterministic CBOR (§3). Before Phase 9, 3–7 live only in the projection, whose `_add_fields` refuses a production use of those tags at regeneration and whose CS1.1 lexical test refuses it at merge; at Phase 9 the projection and cfg are removed everywhere (release plan L410–411), so the "release that ships them" inherits the numbers with nothing left to collide. A production `reserved=(3,…,7)` would be the wrong tool — `compat.py` L108 makes un-reserving a breaking change — and the text does not suggest it. Holds.
- **One current authority while pending (§7.2, L1-08).** The status bullet names the pending state, the decision, its date and the plan item, and says revision 4 stands; §13's body says 8; the accepted text (root HEAD `4bf52e0`) says 3. An implementer cannot build 3 from the working tree, has no authorization to build anything ("authorizes no implementation"), and CS1.1 "does not merge until C8 settles" — through an accepted amendment, per L1-08's "same class of review … before work resumes". Holds. The trail would be tighter if the bullet named the root commit that holds revision 4 (`4bf52e0`), as the history paragraph does for revisions 1–3; not a finding.
