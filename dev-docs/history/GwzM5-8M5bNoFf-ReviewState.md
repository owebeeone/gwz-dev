## 1. Authority rule (§5) — VERIFIED, with one unpinned window (see P2-1)

Traced every consumer of `PendingMergeAction` in the committed tree. The rule "after the durable action write, the persisted action is the sole mode authority; live analysis only verifies" holds:

- **Preparation is the only live-analysis site** and runs only when no action exists (participant `Planned`/`Failed`/`Unattempted`/`Conflicted`, `observe/forward.rs:155-216`); mode enters exclusively from `record.mode` (`forward.rs:188-189`, `prepared_mode` :230-236); recorded inputs must equal the analysis before freezing (:179-187). The design's §5.1 nuance (freeze point = the durable write) is stated and correct.
- **Execution consumes only durable bytes**: `execute.rs:14` re-proves row-match + NotStarted via `verify_participant_action` (`forward.rs:39-83`), then passes `row.target_branch/before_commit/source_commit/commit_message` + the decoded frozen spec to the backend (`execute.rs:54-61`). No live derivation anywhere on that path.
- **Revalidation is a closed verifier, not a chooser**: the `(FastForward, Commit)` arm (`merge_support.rs:101-112`) accepts only frozen-tree == source-tree; every class flip is typed `MergeRecoveryRequired` (:142-150). Critically, `classify_merge` (:4-30) between the two *pinned OIDs* is a pure function of immutable ancestry — the frozen pair's classification cannot drift, ever; only object loss can intervene, and that fails typed. The ff-able no-ff arm is additionally immune to merge-algorithm version skew (tree equality by OID, no recomputation), unlike the clean-true-merge arm, which recomputes and fails closed on skew. This is a genuinely strong property worth stating in the design.
- **Completion maps from durable kind**: `forward.rs:356-362` — `TrueMerge → Merged`; `FastForwarded` is reachable only from a durable `FastForward` kind. A no-ff result cannot be relabeled.
- **Zero journal deltas: confirmed.** The journal wire (`GwzM5-8I2ActionJournalContract.md:44-117`) carries no mode anywhere; rollback anchors on the recorded result commit (:222-230), preservation on the participant result (:175-177), and abandonment is the record-contract §7 mechanism (:354-363), not a journal variant. Every reverse consumer is mode-blind by construction. The no-ff two-parent commit enters the reverse lane purely as "the recorded result commit."

**Adversarial interleaving (the brief's crash probe): can abandonment and execution both be legal after a crash between the durable write and first mutation?** Yes — deliberately, and it is resolved deterministically. At the exact `before_commit`, clean, spec-valid state, reconciliation returns NotStarted, which authorizes *either* continue (execute) *or* abort/preserve entry (bound exact-NotStarted abandonment). The chooser is the operator command; per command the route is unique; the race is serialized by the atomic record rewrite plus digest-bound proofs (`BoundExactObservation`/`PreparedReverseEntryView` bind `source_digest`; a stale proof cannot consume). The dangerous shapes are structurally excluded: NotStarted and Completed are mutually exclusive for `TrueMergeCommit` (a commit cannot be its own parent — `pending.rs:117-151`); an executed-but-unrecorded commit reconciles Completed, after which abandonment is unconstructible (reverse entry demands a `VerifiedParticipantNotStarted` proof that can no longer be issued; post-preservation abandonment separately refused, `reverse_entry.rs:83-88`); an external reset of the branch back to `before_commit` after execution re-yields NotStarted whose re-execution is OID-idempotent (frozen timestamps) — the state machine converges, never forks. An external fast-forward of the target branch to `source_commit` is classified Ambiguous, never adopted as completion (`commit_matches_prepared_merge` fails on parent shape) — the §7 "do not reclassify as fast-forward" sentence holds mechanically.

**The one window the design does not name** (basis of P2-1): execution order is commit-object write (`merge_prepared.rs:304-313`) → self-verify (:314-327) → `checkout_tree` (:328-329) → ref transaction commit (:330-333). A crash between :329 and :333 leaves worktree/index at the frozen tree with the ref at `before_commit` → dirty → Ambiguous → continue refused (`RecoveryEvidenceMismatch` at `forward.rs:497-501`) *and* abandonment refused (not NotStarted). Typed, fail-closed, operator-recoverable (restore worktree to before-state → NotStarted → idempotent re-execution to the same OID) — but it is not the "restart completes with the spec-determined commit" story, and no named suite pins it.

## 2. Determinism semantics (§4) — VERIFIED; Q4 position sound

- **Reconstruction, not re-stamping, verified at every cited site**: the only `Signature::now`/`SystemTime::now` sites in the backend are prepare-time (`merge_support.rs:275, :361, :366`). Execution reconstructs from frozen values (`signature_from_prepared` :319-344), self-verify and adoption compare epoch-seconds + offset (:346-354, :388-393; `merge_prepared.rs:314-327, :39-69`). `PendingGitSignature` carries `time_seconds`/`timezone_offset_minutes` on the wire (`model/v0.rs:131-139`) — the timestamp is already frozen wire, so amendment M5b-W1's first clause pins existing truth.
- **The §4.1 table is complete**: parents, tree, message, both signatures all from the action; libgit2 `commit()` sets no encoding/extra headers; message NUL-rejected at execution; production-frozen specs are post-libgit2-normalization so they round-trip byte-exact. A forged spec fails closed pre-mutation (`validate_prepared_commit` + `GitObjectIdentity.validate` + wire bounds `action.rs:103-109`) — and, importantly for the state model, a pre-mutation-unexecutable forged action *remains abandonable* (NotStarted still provable), so no new permanent wedge.
- **Restart-across-hosts: pinned.** After the durable write, no configuration is ever re-read on any execute/adopt path — a restart on a host with different repo/global git config produces the identical commit. Before the durable write, re-preparation legally re-resolves identity and re-stamps — nothing was frozen; the design states the freeze point explicitly (§5.1) and Q4 confirms from-freeze as the meaning. **Q4 position: sound — affirm.** Cross-operation reproducibility would change frozen wire meaning (`time_seconds`) and decouple commit timestamps from reality for no stated requirement.
- One wording nit (P3-3): `repo.signature()` resolves the *effective* git identity (repo-local → global → system); §4.2's "the repository's configured identity" under-describes it.
