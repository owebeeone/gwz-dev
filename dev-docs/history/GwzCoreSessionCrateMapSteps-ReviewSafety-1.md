## 3. Changed-range analysis

- **The `Body` guard.** Panic path: `recv`'s locals drop in reverse order, so the wipe runs before the poisoned `reader` guard drops, and the next call ends the session with `Closed::Stream(Other)` as before. The new test that closes the end from inside `Read::read` while `recv` holds the reader mutex shows the `try_lock` design holds under a re-entrant close (the writer is dropped, the reader left to the call in flight). Nothing new is copied: `write_frame` still borrows the caller's body. `black_box` is documented as best-effort; the invariant claimed is the same as core's, the barrier weaker, and the doc says so.
- **The `Mutex` in `ClientChannel`.** Lock order: `close()` takes the channel's state lock inside `end.close()` and releases it before taking `held`; `drop(held)` runs after the `held` guard has gone (the guard is a temporary of the `let` statement), so the host end's own `close()` and the context's drop take no lock while `held` is held. Nothing is nested. Poisoning: under `held` only `take()`, `Arc::clone` and a test closure run, none of which can half-change the `Option`, so `into_inner` recovery is sound. `close()` against a concurrent `send`/`recv`: neither touches `held`; a waiting `recv` wakes with `Closed::Local`; a `send` that lands before the close is discarded when the host end drops, as a dropped handle discarded it before. Two concurrent `close()`s: idempotent on the end, one takes `Held`. Field drop order without `close()` is unchanged (end, host end, session). One test-only residual: `close()` called from inside a `with_host_end` closure would relock `held` on the same thread; no production path can do this.
- **The checker's `include!` following.** Termination: each file is keyed by its resolved path and reaches `production` at most once, after which it is skipped, so self-inclusion and mutual inclusion terminate (probed: `lib.rs` including itself, `a.rs` and `b.rs` including each other, both statics listed). Outside the tree: a literal path outside the repository is read and scanned as production, keyed by its absolute path, so a static there fails the gate (probed). A non-UTF-8 include crashes with a `UnicodeDecodeError` traceback and exit 1: fail-closed, though as a crash rather than a finding; rustc refuses the same file, so no production tree can carry one. Non-literal includes become `<unparsed include>` occurrences; gwz-core's only `include!` sits in a test module and is exempt. The broader `<unparsed static>` rule also lists `static` inside a `macro_rules!` matcher or invocation (probed): fail-closed false positives, none present in the three trees.
- **Tier A `--doc`.** The new CI step passes for all eighteen crates locally (seventeen with no doctests, gwz-session-host 1 + 4); the boundaries unit test pins the two commands (27/27). Release, publish and crate-version test modules pass (20, OK, 29).
