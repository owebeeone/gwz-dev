# Python transport concurrency — round-1 verdict merge and remediation

Date: 2026-09-23. Status: **NO-GO**. The first draft at root `c1cb20c98c803500fe7c4ad4d0451e6c5905df28` and Python `45bcd7b3ea102ca927935cee1b41b43934d68140` received independent [Consistency](GwzPyTransportConcurrency-ReviewConsistency.md) and [Safety](GwzPyTransportConcurrency-ReviewSafety.md) NO-GO reports. The [Surface report](GwzPyTransportConcurrency-ReviewSurface.md) also says NO-GO, but disclosed that its reviewer opened source despite a docs-only mandate. File it as useful feedback, not as qualifying docs-blind Surface acceptance evidence. A fresh docs-only Surface review is required on the corrected interface.

This is a **design** verdict. It does not claim that a released Python build contains the candidate restriction or the discovered result-store exposure. It keeps `gwz-py` Phase 6 completion, Phase 7 activation and v1.1.0 publication blocked. The previous design GO reports remain unedited historical evidence for their reviewed object.

The two authoritative axes found more than a missing concurrency guard. In particular, Safety P0-1 shows that parallel clients can collide in a process-global operation store. Correction 1 must redesign the full session/request/result boundary; a same-capacity admission change alone is insufficient. No implementation patch should proceed against the first draft as authority.

| Finding | One disposition in the corrected design | Required closure evidence |
| --- | --- | --- |
| Safety P0-1 | Make event/result/merge records session-owned, enforce owner on every lookup and reject duplicate live IDs within that session before `Accepted`. Keep module-level compatibility calls isolated. | Two clients submit the same explicit request ID with opposite completion orders; each reads only its own events/result; foreign lookups refuse. |
| Consistency P2-1 | Explicitly supersede retry plan §6 and S1.4 blanket non-idle refusal for *unchanged compatible capacity* only. Retain refusal of incompatible capacity before remote work. | Contract cross-check and held-lease equal/different-capacity core cases. |
| Consistency P2-2 | Decide and name the exact Phase 2 differing-limit overlap exit-row amendment. The accepted retry rule currently makes different limits different physical capacities; do not claim that test still passes. | Read Phase 2, retry and Python clauses together; execute the final agreed different-limit case. |
| Consistency P2-3, Safety P2-3 | Distinguish live-operation admission from the mux's 256 *lifetime* request tombstones. Specify a quiescent generation rollover or another bounded stale-ID-safe scheme while preserving the captured endpoint trust/credential context. | More than 256 sequential operations, failed registrations, delayed stale messages and rollover/close races; no permanent loss of service or stale attachment. |
| Consistency P2-4, Safety P2-5 | Bound aggregate Python-client workers and accepted submissions independently of pool checkout `max_requests` and caller-controlled per-operation `jobs`. Use a bounded/fallible worker launch path; every spawn failure and panic terminalizes the reserved operation and wakes close. | Many concurrent multi-member operations, oversized explicit `jobs`, injected spawn failure/unwind and close; asserted finite workers/queued work and one terminal result per accepted ID. |
| Consistency P2-5, Safety P2-2 | Name the physical policy owner and pre-Open admission handshake for Python's explicit `cli` placement, or amend the Python 1.1.0 surface to refuse that placement before credential access. Do not claim an unimplemented route is covered by the local guard. | Bound-CLI equal/different-capacity case if supported; otherwise a typed early-refusal case and accurate capabilities/docs. |
| Consistency P3-1, Safety P2-1 | Serialize **every** initial or later capacity transition with a leader, target and cancellable waiters; publish its completed value atomically before compatible admission. | Barrier at pool/authority transition, concurrent same-target requests, different-target refusal, failed install, cancellation and close wakeups. |
| Safety P2-4 | Move submitted event/result storage into the owned session and give both active event backlog and completed record retention explicit finite limits with a typed, observable overflow/expiry path; never silently lose a successful operation's result. | Many completed and abandoned streams, slow readers, expiry lookup and bounded memory while live readers still get their promised outcome. |
| Surface P2-1 | Document a public operation handle or stable caller-provided identity available before first event/final response; do not rely on undocumented `op_` string construction. | From a high-level stream, obtain identity immediately and cancel it from another task while a peer continues. |
| Surface P2-2 | Freeze where each capacity refusal surfaces for unary, submit and stream forms, with stable typed reasons and a stated safe retry condition. `Accepted` must have one precise meaning. | Exercise conflicting policy and live-operation exhaustion through all three forms; assert type, attribution, timing and recovery. |
| Surface P2-3 | Replace the one-slot completed-cancellation cache with bounded per-ID retention or expressly narrow repeat semantics, without making foreign IDs indistinguishable from retained IDs. | Cancel A/B in both orders, repeat A, test expiry and foreign-ID refusal. |
| Surface P2-4 | Make Python close a shared completion that survives waiter cancellation; context exit and repeated close must join it and preserve the final report. | Repeatedly cancel close waiters with two active operations, then await close again and compare the retained result. |
| Surface P3-1 | Add a caller-facing concurrent-client example and capacity/cancellation/close guidance to the Python guide before activation. | Docs-only first-day walkthrough succeeds without reading source or the design plan. |

Correction 1 should be **one revised design patch** with explicit supersessions, a finite resource model and exact caller semantics, followed by a new settled tuple. Consistency and Safety re-verdict the counterexamples above; because the correction changes ownership and the public API, use fresh independent full-axis reviewers rather than relying only on the old changed-range proofs. Obtain a docs-only Surface verdict. Any implementation review comes later and cannot self-close these design findings.
