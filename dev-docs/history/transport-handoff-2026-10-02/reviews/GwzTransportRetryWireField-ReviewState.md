## 1. Findings

### [P3-1] On the Cli placement the driver records the policy's R while the endpoint beyond the port runs the default 3: two retry counts for one operation, a false `attempt N of M`, and a backstop sized for the wrong count

- **Root cause (one):** the field is "carried on the in-process operation policy" (retry plan §5) and reaches an endpoint only through `open_request`'s Local arm: `mod.rs:278` reads it, `mod.rs:295` installs it on `local_endpoint` after `admit_client_request`. The Cli arm (`request::is_cli`, `mod.rs:258-271`) has no endpoint in this process, so only the driver's record is set (`request.rs:25`). The far endpoint registers through `CliEndpoint::register_request` → `ClientRequest::new` → `session.register(request, None)` (`request.rs:353`) with no policy, so its `Operations` entry is made at the default (`operations.rs:58`, `DEFAULT_MAX_RETRIES = 3`, baked into each machine at `operations.rs:40`). The driver then infers from its own record: `spent_budget(&failure, self.max_retries(request))` (`driver.rs:48`) and `open_backstop_ms(io, max_retries)` (`driver.rs:212`, `669`).
- **Violated invariant:** §5 "Let `R` be the resolved `--max-retries`. The number of attempts is `R + 1`" — one R per operation; and S3.3's claim that `Session::set_max_retries` "installs it in the driver's registration and the endpoint's machines at admission", true of the Local route only.
- **State sequence:** `TransportRuntime::install_cli()`; `CliEndpoint::new(config)` on the far side of the port; `RequestMeta { transport.placement: Cli, policy.max_retries: Some(0) }` → `open_request`: driver record R=0, each open's backstop 159 s at stall 9 s; endpoint machines R=3. Open to a host that stalls: the endpoint runs 4 attempts (about 44 s at stall 9 s; up to 627 s if every attempt uses the aggregate and the interaction allowance). Driver: (a) the final stall is a `Timeout`/`Stall`, so `spent_budget` returns `(1, 1)` and the member reads "ssh setup timeout: stall (attempt 1 of 1)" after four connections; (b) if the endpoint's attempts outlast 159 s, `driver.rs:528-534` completes the open with a bare `Timeout` (no origin: "ssh setup timeout: unknown"), `owner.cancel(&entry.request)` cancels the whole request and disconnects the peer, mid-retry. With R=10 the display is "(attempt 11 of 11)" after four.
- **Impact:** bounded today. No product consumer installs the Cli placement: gwz-cli enters through `with_local_transport` (`dispatch.rs:8`), gwz-py through `with_cancellable_local_transport` (`transport.rs:107`), gwz-cli sets no `placement` (`invocation.rs:72`), and `CliEndpoint`/`install_cli`/`require_cli_ssh` have no non-test caller in gwz-core, gwz-cli or gwz-py. The placement is public API and the 1.2.0 session host's cross-process shape; the only test of the budget's reach, `retry_tests.rs:40`, drives `TransportPlacement::Local`. The moment a consumer installs the Cli placement under the candidate switch this is P2 (parity and diagnosability on a shipped path).
- **Required correction:** until the session protocol carries the budget with the per-request limits (reuse design §9's next revision / CS7.x — gwz-transport's schema has no such field), fail closed on the Cli arm: `open_request` refuses a Cli-placed request whose `policy.max_retries` is `Some(_)` (`unsupported`, naming the placement), and the driver's record on that route stays at the default; or the checkpoint records the gap and the 1.2.0 plumbing step names `max_retries` beside `concurrency` and `max_connections_per_host`, which the Cli arm also never carries (`mod.rs:279-293` is Local-only).
- **Closure test:** a Cli-placement pair (as `driver_tests` builds one) with `max_retries: Some(0)` against a silent listener: either the request is refused at `request()`, or exactly one connection is accepted and the display ends "(attempt 1 of 1)".

### [P3-2] A wire value above `u32::MAX` is accepted and silently saturated to `u32::MAX`, where a negative one is refused

- **Root cause (one):** `request.rs:406` `u32::try_from(value).unwrap_or(u32::MAX)`; `validate_meta` (`request.rs:381-386`) refuses only `< 0`; gwz-cli's parser (`retry.rs:28-36`) accepts any `i64 >= 0`.
- **Violated invariant:** fail-closed direction for an out-of-domain value — the negative branch refuses, the overflow branch clamps; and §1 "does not clamp a requested value down".
- **Sequence:** `--max-retries 4294967296` → `policy.max_retries = Some(4294967296)` → host R = 4294967295. `spent_budget`'s `M = R.saturating_add(1)` = 4294967295, so a spent-budget display names a count the user did not give. No illegal machine state: `machine.rs` counts with `saturating_add`, `backoff.rs:12-16` caps the shift at 14 doublings (30 s), `wait_bound_ms` and `open_backstop_ms` are saturating `u64` (about 6.8×10^14 ms; `Instant::checked_add` still returns `Some`), so the backstop is merely proportional to the request. Diagnosability only.
- **Impact:** a typo is neither refused nor honoured as given; the display can name a count the request never carried.
- **Required correction:** refuse `> u32::MAX` in `validate_meta` beside the negative check ("max_retries exceeds the supported range"), and in gwz-cli's parser; or state the ceiling in §8 and the help.
- **Closure test:** `Some(i64::from(u32::MAX) + 1)` refused with `InvalidRequest` before registration (as `a_negative_max_retries_is_refused_before_the_request_registers` pins the negative); `Some(i64::from(u32::MAX))` accepted.

### [P3-3] `gwz merge` accepts `--max-retries` silently where the merge validator refuses every other policy field it does not act on

- **Root cause (one):** `src/workspace_ops/merge/validate.rs:176-187` enumerates `sync`, `remote`, `concurrency`, `progress_min_interval_ms` and `max_connections_per_host` through `reject_policy_field`; `max_retries` is not enumerated (the validator is both-build code, the field candidate-only). gwz-cli attaches the global policy to every command (`invocation.rs:65`) and `RetryArgs::apply` sets the field for every command (`invocation.rs:129`); `merge_meta` (`invocation.rs:301-308`) clears only `progress_min_interval_ms`.
- **Violated invariant:** the validator's closed grammar — a policy field merge does not act on is refused at the request boundary, not ignored.
- **Sequence:** candidate build, `gwz merge --max-retries 0 <source>` → `policy.max_retries = Some(0)` → `validate_common_meta` → `Ok`; nothing reads the field. `gwz merge --jobs 1 <source>` → refused.
- **Impact:** bounded — a no-op flag accepted silently on one command in the candidate build; no state effect. Possibly outside TR2.1's scope as a code change; the lane owner may route it.
- **Required correction:** a `cfg_if` candidate arm in `validate_common_meta`: `reject_policy_field("policy.max_retries (--max-retries)", policy.max_retries.is_some())?`.
- **Closure test:** a candidate-build row with `max_retries: Some(0)` on a merge request refused `InvalidRequest`; the ordinary build's rows unchanged.

## 2. Invariant analysis

- **Read once per operation, immutable after.** `open_request` reads `meta.policy.max_retries` from one immutable `RequestMeta`, twice in one call (`mod.rs:278` for the endpoint, `request.rs:25` for the driver), after `validate_meta` (`mod.rs:257`). The driver's record is written once at registration (`requests.rs:15-25`; `session.rs:429` creates it at 3, `register` precedes); the endpoint's `Operations` entry is written once at admission (`placement_endpoint.rs:174`, `https_endpoint.rs:145`) and every key's machine is made from it at the key's first use (`operations.rs:33-44`), which cannot precede the install on the Local route (admission → install → `RequestContext::new` → `begin`/`ready` → opens). Later reads are from the record (`driver.rs:48`, `205-209`; `request.rs:247`), never from the wire again. A changed meta is refused by `validate` (`request.rs:37-46`, always called with `self.meta`). Per key: all keys of one operation share one R (§5's "Let R…"). Holds.
- **Absent, null → 3 on both sides.** `try_get_opt(9)` → `None`; explicit null → `None` (`candidate_generated.rs:2493`); `request::max_retries` → `DEFAULT_MAX_RETRIES` (`request.rs:400-408`); the driver record and the endpoint entry default to the same constant. Production's encoder writes keys 1-8 (`generated.rs:2442` is the last), gwz-py's package has no field, and the unit test `operation_policy_carries_max_retries_and_an_older_writer_leaves_it_absent` (`tests.rs:41-58`) pins `Some(0)` round-trip and an 8-key map → `None`. Holds; "not a protocol version bump" holds since production files are untouched and the field is `MISSING_OK` like every other candidate addition (`candidate.taut.py:80-121`), with `_add_fields` refusing a later production field at tag 9 or the name (regeneration fails closed).
- **Malformed → refusal, never a silent default.** Non-map → `WrongType`; non-int at key 9 → `WrongType`; unsigned above `i64::MAX` → `IntOverflow`; duplicate key → `DuplicateMapKey` (`cbor.rs:254-290`, `614-631`, `673-680`). Negative → `InvalidRequest` before any read or registration (`request.rs:381-386`, pinned by `retry_tests.rs:169`). Only absent and null are the default. A candidate writer always emits key 9 (null when absent, `lib.rs:97-99`); a production decoder ignores it, and that build has no retry machine, so no divergence there. Holds; the one asymmetry is P3-2.
- **Zero → exactly one attempt.** `machine.rs:181`: attempt 1 > 0 → `close`; pinned at three levels (`machine_tests.rs:95`, `placement_endpoint/retry_tests.rs:302`, `retry_tests.rs:40` with (0, 1) and (1, 2) connections and the "(attempt 1 of 1)" display). Holds.
- **No illegal state from any admissible `u32`.** `attempts`/`attempt` use `saturating_add`; `wait_ms` caps at 30 s from the 15th doubling (`backoff.rs:12-16`), jitter `< 250 ms` (`backoff.rs:35-43`); `wait_bound_ms` is exact for every R (1+2+4+8+16 s then 30 s each) and saturating; `open_backstop_ms` saturating `u64`. Published bound (§5): `(R+1)×aggregate + Σwaits + R×250 ms` — the machine's waits match; the driver's backstop `(R+1)×(150 s + stall) + wait bound` is above §5's full bound (`(R+1)×155 s + waits`) at the default stall 9 s (643.75 s ≥ 627.75 s at R=3) and never cuts the machine's own sequence short there. `--ssh-timeout 0` → no backstop, as §5 says ("no network-clock bound"). Holds; see §3 risk 1 for stall below 5 s.
- **Closed grammar of per-operation retry state; no new stuck state.** Install → machines → `remove` on cancel/finish (`cancel.rs:28` after every open of the request is marked abandoned and its queued opens dropped; `https_endpoint.rs:529` after entries are retired). A late result for an abandoned SSH open is finished before `attempt_failed` (`completion.rs:132-146`), `attempt_failed` returns for an unknown request (`completion.rs:191`), HTTPS `settle` is guarded by `retired`/`is_cancelled`, and HTTPS `admit` needs `held` — no path re-creates a removed entry at the default. A request id cannot be re-registered (`session.rs:400-403`). An admission that fails after the endpoint install drops the `ClientRequest`, whose `Drop` cancels and removes. Holds. `1afea66d` re-keys the SSH machines by `(pool key, identity)`; `Operations` is generic in that key and still keyed by the request id first (`completion.rs:115`, `198`), so this analysis stands at that SHA.
- **Corpus.** 33 request vectors, each policy map `a8` → `a9`, as claimed. The appended sample is −7 (`09 26`), a value the host refuses, so the candidate corpus pins codec parity only; the admissible domain is pinned by the unit tests above. Observation, not a finding.
