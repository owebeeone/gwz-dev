## 1. Findings

### F1 — P3 — The schema-level additive-tag contract test silently excludes the new field

- **Root cause.** `tests/transport_consumer/candidate/test_candidate.py::test_overlay_has_exact_additive_tags_and_missing_ok_contract` (lines 64–90 at the object) holds an explicit `expected` dict of every candidate overlay addition — `TransportOptions`, `RequestMeta`, `ResponseMeta`, `TransportCapabilitiesResponse`, `TransportObservation` — asserting each field's tag and `optional == MISSING_OK`. The commit adds `OperationPolicy.max_retries` (tag 9, MISSING_OK) to the overlay in `candidate.taut.py` but does not add `"OperationPolicy": {"max_retries": 9}` to `expected`. The test still passes only because it checks the listed fields and is not exhaustive, so the commit's "35 passed" is true but no longer means what the test's name says.
- **Exact location.** `tests/transport_consumer/candidate/test_candidate.py` lines 65–83 (the `expected` literal); `protocol/candidate/candidate.taut.py` lines 91–99 (the addition).
- **Violated invariant.** The retry plan's S3.4 and §5 ("optional policy field … Absence means 3, so an older writer keeps this default. That is not a protocol version bump") rest on the field being MISSING_OK at tag 9. The repository's one schema-level assertion of that contract for the overlay is this test; after the commit the new field is outside it, while every other overlay addition is inside.
- **Reproduction.** `git show 9a235acb:tests/transport_consumer/candidate/test_candidate.py | sed -n 64,90p` — no `OperationPolicy` key. Thought experiment the test must catch and now does not: change line 97 of `candidate.taut.py` from `optional` to a required presence, or tag 9 to 7; `test_candidate.py` passes unchanged. (The Rust test `operation_policy_carries_max_retries_and_an_older_writer_leaves_it_absent` would catch the presence flip, but only in the unix candidate test build — see §3.)
- **Impact.** Bounded: the wire behaviour at the object is correct and proven by the platform-independent corpus parity (tag 9 present, value −7) and the Rust older-writer test (tag 9 absent → `None`). The defect is that a later edit can regress the field's tag or presence — the case that would make every older writer's policy fail with `MissingKey(9)` — without the schema contract test objecting.
- **Required correction.** Add `"OperationPolicy": {"max_retries": 9}` to `expected`; and make the test exact, as its name claims: assert that the set of `(message, field)` pairs present in `NEW` and absent in `OLD` equals the set `expected` enumerates, so a future overlay addition cannot bypass the contract either.
- **Closure test.** The corrected test fails when `max_retries`'s tag, presence, or existence changes in `candidate.taut.py`, and when an overlay field is added without a matching `expected` entry; it passes at the corrected revision. CI's "Candidate Python tests" step already runs this file.

No P0, P1 or P2 found. Specifically refuted attacks: a production decoder refusing tag 9 (it ignores it; evidence 4); an exhaustive struct literal breaking the candidate build (none; evidence 8); a hand edit in a generated file (the diffs are exactly the generator's output set and shape; evidence 5–6); a production surface change (none; evidence 2, 9); a silent drop of the field through `convert.rs` (no wire→model→wire path exists; evidence 7); a missing inventory line (the reason string is not a site by the checker's definition; evidence 9); a divergent `try_get_opt` in the candidate's actual CBOR runtime (identical; evidence 4).

## 2. Invariant analysis

**Wire compatibility, both directions.**
- *Older writer without tag 9 → candidate decoder.* Production `generated.rs::to_cbor` writes tags 1–8; gwz-py's Python writer writes the production schema's 1–8. The candidate `from_cbor` arm is `try_get_opt(9)` → `None`; the reader maps `None` → `DEFAULT_MAX_RETRIES = 3` (evidence 10). Proven at the object by the Rust test (strips tag 9 from an encoded map → `None`). The pair is real in 1.1.0: gwz-py's Python client against a candidate-built native extension (evidence 11).
- *Candidate writer with tag 9 → production decoder.* The candidate encoder always emits tag 9 (`Null` when `None`), consistent with every other candidate field and with the `src/lib.rs` 97–99 note that candidate vectors cannot round-trip through production types. The production decoder, the retained old Rust reader and the retained Python decoder all ignore an unknown tag (evidence 4). In 1.1.0 no such pair exists: the CLI is in-process (a struct, never bytes), gwz-py decodes requests with the same build's decoder and never decodes an `OperationPolicy` (request-side only; evidence 3), and every cross-process placement is 1.2.0 under `gwz_session_candidate`. The tolerance is nevertheless established for the mechanism by `candidate_compat.rs::candidate_writer_is_readable_by_retained_old_rust_decoder` and `test_candidate.py::test_new_writer_old_schema_reader_ignores_new_tags` (tags 4/5 of `TransportOptions`); it is not asserted for `OperationPolicy` specifically (see §3).
- *No protocol version bump.* `schema_version` stays `"gwz.protocol/v0"` (`validate_meta`), no error code is added, and the production schema digest is unchanged, as S3.4 requires.

**Value domain.** The wire admits any `i64` (the corpus's own sample is −7). At the object commit nothing reads the field; the commit says so and defers to S3.3, which is accurate. From 766b2953: negative → refused by `validate_meta` before registration and before any read (call order verified); `0` → `Some(0)` → one attempt (plan §8 "0 = do not retry"); absent/`Null` → 3; values above `u32::MAX` saturate to `u32::MAX` — technically a clamp the plan's §1 does not describe, of no practical consequence (the backoff and bound arithmetic are saturating). The CLI flag refuses negatives at parse time and accepts any `i64 ≥ 0`.

**Generated code and corpus.** Exactly the regenerator's four outputs changed; the Rust and Python deltas are the minimal emitter output for one optional int field; the corpus delta is the single-pair insertion in precisely the 33 vectors that embed the message; vectors.rs and golden.json agree entry-for-entry at both revisions; all three pinned digests match the trees; the pinned generator is taut-proto 0.10.0 as the commit states. Regeneration not re-executed here (read-only); CI's `--check` is the mechanical gate.

**`convert.rs`.** Correct in both builds: production needs the allowance (the `..Default::default()` is needless there), the candidate build fills `max_retries: None`. No silent drop: the model carries no such field, nothing converts a wire policy to the model and back, and the host reads the field directly from the wire policy, exactly as `progress_min_interval_ms` and `max_connections_per_host` are read (the updated comment says so). Observation, not a finding: the impl has no caller inside gwz-core, its crates, its tests, or gwz-cli; it is public API of the published crate, so its retention is a semver matter outside this commit's scope.

**Rule (a).** Holds: the field is reachable only through `candidate_generated.rs` under `cfg(gwz_transport_candidate)`; no ordinary-build surface, file or digest changes; the inventory is correct as is.

**Claims in the commit message vs. the diff.** Every verifiable claim checks out: keys 1–8 in production's encoder; gwz-py generated from the production schema; the four regenerated files; the 8→9 growth of each request vector's policy map; the retained precedent for the allowance; the field's gating.
