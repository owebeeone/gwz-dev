## 1. Findings

### [P2-8] `remote_identity` is classified R and run on the direct pool, but its `set`/`unset` ops write repository configuration and all three ops acquire the try-lock workspace mutator lock
- **Location:** contract §4.2 line 135 (`remote_identity` among the direct methods), §5.1 lines 188–192 (R: "anything; they run on direct workers"), §5.2 line 209, §15.4 ("R calls run alongside it"). Source: `handle_remote_identity.rs` 16–27 (`acquire_workspace_mutation_guard_for_request_in(…, OpenMergeCommand::RemoteIdentity, dry || op == Get)`), lines 37–52 (`set` writes the key path; `unset` clears it); `mutation_guard.rs` 109 (the `flock` is taken before the `dry_run` branch, so `get` holds it too, briefly); `workspace_mutator_lock.rs` 13–23 (try-lock, refuses `UnsupportedOperation` "workspace mutator lock is already held"); `gwz.taut.py` 1051.
- **Violated invariant:** "Every method belongs to exactly one class" with a correct class; a writer must not be admitted alongside W (§16 names this hazard); an admitted call must not fail on a lock the host could have serialized (the B6 rule the revision adopted for push). §15.4 requires R calls to run alongside a W operation.
- **Sequence:** (1) `materialize` M (W) runs and holds the workspace's `flock` for its duration (minutes). (2) The client calls `remote_identity get` (R): a direct worker takes it at once, `acquire_in` gets `EWOULDBLOCK`, the read fails "already held". (3) Reverse order: `remote_identity set` (R by the table, a write in fact) is running on a direct worker; W operation P starts; P's `flock` attempt loses the race and P fails `UnsupportedOperation` — a mutator failed by a "read". Today the same race exists between concurrent Python calls (`remote_identity` is not a network method, so nothing serializes it); the contract turns it into a promise it cannot keep.
- **Impact:** §15.4 is unmet for `remote_identity`; a misclassified writer sits on the pool the contract created to bypass W exclusivity; spurious "already held" failures of W operations and of `remote_identity` itself. The `flock` prevents actual overlap, so the consequence is refusal, not corruption.
- **Remedy:** classify `remote_identity set|unset` as W (queued, exclusive per workspace) and `get` as R implemented without the mutator lock (a gated manifest/config read), or classify all three as W; state that direct methods take no mutator lock (verified true for the other seven).
- **Closure test:** `remote_identity get` answers while a materialize runs on the same workspace; `remote_identity set` queues behind a running W; no W operation ever fails with "already held" because of a `remote_identity` call in the same session.
- **Classification:** bounded correction.

### [P3-6] After a bounded close, a detached W worker keeps the workspace `flock`; the client's own retry is refused with a message attributing the lock to another process, and nothing lets it wait or identify the worker
- **Location:** §8 lines 359, 367 (detached workers), §5.1 line 196 ("already held" can come only from another process or another session), §5.6 lines 291–293, §16 line 571. Source: every W handler acquires the mutator lock for real runs (`materialize.rs` 31, `pull_head … handle.rs` 65, `handle_repo_lifecycle.rs` 57/225/306, `push_member.rs` 58); today's close never returns while a worker runs (`transport_session.rs` 920–927), so the state "my worker is still writing after close returned" is new.
- **Consequence:** (1) client closes during a materialize stuck in a long local checkout; close returns after `close_wait` with `pending_local_work = 1`; the client opens a new session (or runs the CLI) and retries the materialize; the retry is refused "workspace mutator lock is already held" — safe, but the text's attribution is wrong and there is no API to wait for the detached worker. (2) For fetch (N, no mutator lock) the session-scoped member lock manager gives no exclusion against a detached fetch from a closed session; git's own ref locking bounds the damage to a failed ref update or a torn `FETCH_HEAD`.
- **Remedy:** move the member lock manager and a registry of detached workers into the host context; let a later session's admission on that workspace wait on (or refuse with a distinct code naming) the detached worker; have gwz-py create one host context per process by default (driver-owned, created before any session, consistent with O7/O9); correct §5.1's attribution sentence.
- **Closure test:** close with a latched W worker, reopen, submit a W on the same workspace: it queues until the latch is released, or fails with a code that names a detached worker, never "another process".
- **Classification:** bounded correction.

### [P3-7] Control frames are handled in order behind admission, and admission resolves workspace roots on the admission thread; a slow or hung resolution stalls every later cancel and close, and the close bound cannot start
- **Location:** §5.1 lines 179–182 ("Resolution first"; roots resolved on the admission thread; refused "before it becomes an operation"), line 184 (records created at admission), §7 line 348 ("The host handles frames in order, so the cancel finds the admitted operation"), O5 line 72 (the host's only timers are the read wait and the close bound), §3 line 103 (control reserve exists for queues only).
- **Sequence:** a submit whose root lies on a slow or hung network filesystem enters resolution (`resolve_workspace_paths_in`, manifest reads, repository revalidation); every later frame, including `operation.cancel` for unrelated operations and `session.close`, waits behind it; no host timer bounds resolution; the client's exit finalizer times out on its own bound and exits with the session unshut. Today each call runs on its own thread, so a hung resolution blocks only itself. The O7 property "a cancel before `accepted` finds the record" is what forces the in-order rule, and the text creates the record only after resolution, so the two rules conflict.
- **Remedy:** create the pending record (keyed by `call_id`, with token and gate) at receipt, before resolution, so a cancel can settle it; resolve per operation on the admission thread or a small pool; dispatch control frames on the channel thread without waiting for earlier admissions; or bound resolution by a host timer and refuse.
- **Closure test:** with resolution latched for one submit, a cancel of another operation and a close both complete within their own bounds.
- **Classification:** bounded correction.

### [P3-8] "Delivered once" is marked by the host when a reply is sent, but the Client consumes results in several steps and can drop a reply, so a delivered mark and actual possession diverge
- **Location:** §5.4 lines 243–245, §5.1 line 203, §10 line 432 (reply of a stopped wait is dropped), §10 table (`merge_operation_response` → `operation.response`). Source: `client.py` 1333–1346 (`operation_result` then `merge_operation_response`), 380–398 (`_stream_call` reads the result only after the event loop completes).
- **Sequences:** (a) under a full table, `MergeOperationHandle.result()` delivers the result (record now evictable), a concurrent admission evicts it, and `merge_operation_response` gets `operation_expired` for a merge that succeeded; (b) a task awaiting `operation.result` is cancelled while the reply is in flight — the host has marked delivered, the bridge dropped the reply, a retry gets `operation_expired` (today the result stays retained); (c) a stream consumer that breaks out of `fetch_stream()` never reaches `operation_result`, so unread terminals accumulate until admission refuses `transport_session_full`, with no visible cause in the Client API. Eviction is oldest-delivered-first, so (a) and (b) need a table full of live and unread records; (c) is routine.
- **Remedy:** mark delivered only when every view the method declares has been delivered (result and, for merge, response) or after release; have the bridge retain the last delivered result per operation in its own view until release, so a dropped reply is not lost; have the Client's stream helpers deliver or release in `finally`.
- **Closure test:** merge handle result under a full table returns the response; a cancelled result wait followed by a retry returns the result; 200 early-exited streams do not exhaust admission.
- **Classification:** bounded correction.

### [P3-9] A detached operation's host-written `Cancelled` terminal is indistinguishable at operation level from a cancel before effect, though the detached worker may still complete
- **Location:** O3 line 66, §6 line 329, §8 steps 5–6 and line 367. `cancelled` (73) is documented as "cancelled after remote effects became possible" (`gwz.taut.py` 831–833), so the code itself does not say "outcome unknown".
- **Sequence:** close during a long merge; at the bound the merge is detached and its record settled `Cancelled`; step 6 answers the client's held `operation.result` with `errors[0].code == cancelled`; the merge then finalizes on disk. The client reads a definite `Cancelled`, later runs `merge start` again and is refused by the durable lifecycle (REQ-089F/J), which protects the workspace but leaves the client with a wrong belief; the only hint is the session-level `pending_local_work`.
- **Remedy:** mark detachment in the operation's result: a second `errors` entry (`internal_error`, "detached at the close bound; outcome unknown") or an appended optional field; keep the session-level count.
- **Closure test:** the §15.9 latch test reads the detached operation's result and finds the detachment marker.
- **Classification:** bounded correction.

### [P3-10] The environment snapshot's confidentiality and lifetime are unspecified
- **Location:** §5.6 lines 270–275, §9 line 377 (`options` carry the snapshot), §5.7 rows 2 and 7, §11, §12. Today the environment is captured per call and dropped (`local_command.rs` 21, 33–46); under the revision the whole `os.environ` (tokens, cloud credentials, anything the host application exports) lives in the session context for the session's lifetime, reachable through every gate, and is passed whole to `gh` per operation (as today, `https_auth.rs` 324–325).
- **Consequence:** nothing forbids echoing snapshot values in `SessionError.message`, events, `TransportObservation`s or diagnostics; nothing says the snapshot is dropped at session end; the Python capture from `os.environ` is `str`-decoded, so a non-UTF-8 `HOME` or CA path can be mangled unless captured as bytes.
- **Remedy:** state that the snapshot is secret-bearing: never serialized into a frame, event, result, error message or log; passed only to the endpoint helpers that need it (`gh`, with `env_clear`); dropped when the session ends; captured as bytes (`os.environb`).
- **Closure test:** an error raised for an invalid proxy or CA setting contains no environment value; the snapshot is unreachable after close.
- **Classification:** bounded correction.

## 2. Invariant analysis

- **O1–O3, O7.** Records, tokens and gates at admission before `accepted`; the client's `call_id` before send; the waiter registered before send: the fast-reply race is closed. One terminal per operation holds with the detached case host-written. The gap is the interval between receipt and admission (P3-7), where a record does not yet exist although the client already holds the handle.
- **Admission.** Still no deadlock: member locks are single-resource with no nesting, the lock manager blocks and recovers from poisoning, per-host permits are per operation, one push per workspace removes the push-vs-push refusal, FIFO prevents W starvation, direct calls have their own pool. Verified that none of `status`, `ls`, `list_snapshots`, `diff`, `log`, `transport_capabilities`, `configure_transport_runtime` touches the mutator lock; `remote_identity` does (P2-8).
- **Control reserve.** At most 8 operations and 8 direct calls run, so at most 16 cancels are held long; cancels of queued or terminal targets answer at once; one close; 64 suffices. Queue capacity 1024 + 64 on both sides equals the maximum of held calls plus waiting replies, so the host never blocks on its reply queue, and close's step 6 (≤ 1088 replies) fits.
- **Cancellation and close.** The token attaches at request registration, so a cancel before the runtime exists settles the operation without effect; network I/O fails promptly in transport builds; `finish` and runtime `shutdown` stay bounded (5 s each); `close_wait` 60 s is coherent for network work and a policy for local work. Gate revocation makes a detached worker inert toward session state; it cannot make it inert toward the workspace (§8 says so) or release its `flock` (P3-6).
- **Retention and memory.** Live and undelivered records are never evicted; refusal before effect otherwise; event rings of 4096; 64 open logs; 1 MiB reads; 64 MiB frames. Bounded, with the delivery-mark race (P3-8) and unbounded per-log bytes (status quo) as residuals.
- **Environment and context.** Core's own environment reads are all `debt` in the allowlist and the check reproduces the inventory exactly (24 items). The check catches statics with interior mutability, `thread_local!`/`lazy_static!`, `std::env` and libc env calls, `home_dir`, `git2::opts`, `git2::transport::register` and global hooks; it does not catch `Command` inheritance (P3-11), libgit2's own internal environment reads (HOME/XDG config search), or crates outside its roots (P3-12).
- **Process exit.** The finalizer closes and joins the pump within the close bound; detached workers are then killed by exit, disclosed in §16. Today's `close_inner` never returns while a worker runs, so exit today joins local work; the revision trades that for a bound and says so.
- **Status quo.** Nothing found that is worse than today beyond what §16 discloses and P3-6/P3-8 name; the `remote_identity` race exists today between concurrent Python calls, and becomes a contract defect only because the class table now promises otherwise.
- **Wire proof.** §12 now states its blind spot (process-global state). Remaining differences between the adapters that the two runs would not show: the environment source (client snapshot in-process, host's own over the wire), non-bridge client behaviour (P3-13), and the queue-full path.

## 3. Risks and next action

Residual risks below the finding bar:
- `cancelled` (73)'s schema comment ("after remote effects became possible") no longer matches its use for queued cancels; update the comment and the ErrorCatalog so clients do not reconcile remotes after a no-effect cancel.
- §6's "member rows are the planned rows, marked skipped" presumes a handler that errors after cancellation had no member effects; handlers that can error late must report rows from their own state.
- In transport builds, `git://`, `http://` and `file://` remotes still use libgit2's native transports with the frozen process-wide timeout, which the session's `configure_transport_runtime` no longer sets.
- Per-session host contexts each own a parked reaper thread and helper budgets; the host context's drop must stop the reaper, or short-lived sessions leak a thread each.
- `GIT_SSL_CAINFO` file contents are re-read at each operation's derivation; the snapshot fixes the path, not the file.
- Interpreter exit waits at most the close bound, then detached local writes can be torn (disclosed in §16).

Next action: a revision that reclassifies `remote_identity` (P2-8) and folds in the eight P3 corrections, then a re-verdict on that tuple (remediation round 2 of 2).
