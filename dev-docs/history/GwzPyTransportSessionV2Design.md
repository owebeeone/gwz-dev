# Python concurrent transport session v2 — identity, outcomes and close

Date: 2026-09-24. Status: **accepted design at root `78a46ef58bdfc3fac0c5a6600597465c9436c20d`, core `7a8b8efb7f9a08d9d0055cb860071a36b26c3d9d`, Python `cddb38204fbbd11808cc3c414807aa66a5910ce0`, after [Consistency](GwzPyTransportSessionV2-ReviewConsistency-4.md) and [Safety](GwzPyTransportSessionV2-ReviewSafety-4.md) reported GO; this accepts the contract only, not implementation or activation**. The operator requested a bounded redesign after the [previous NO-GO verdict](GwzPyTransportConcurrencyDesign-Verdict-2.md). This is a new, complete Python-session contract, not a third patch to the rejected concurrency design. The stream sequencing and ordering contract in `gwz-transport` is unchanged; the accepted sequenced-stream host proof remains a separate activation gate.

## 1. Boundary and precedence

A Python `Client` using `NativeCoreBridge` owns one lazily constructed native transport host, its SSH/HTTPS endpoint pools, and a **session-owned outcome ledger**. Several network operations may overlap on that host; one leased physical connection still serves one exchange at a time. Local-only operations do not construct the network host. The ledger has a lifetime separate from the physical host: closing the Client stops work and shuts the host, but retained operation outcomes remain readable without reopening it. Existing custom bridges remain supported through their existing call/stream surface; the new handle and ledger APIs require native session hooks and otherwise refuse `UnsupportedOperation` before effects.

This document replaces the Python one-active-operation, network-lock, one-completed-cancellation and blanket post-Closing lookup rules in `gwz-py/dev-docs/GwzPyTransportDesign.md` §§2–4. It also supersedes that design's §2 statement that the installed **runtime host** stays stable until close and its §4 cancellation rationale that the session never reuses a caller request ID. The captured endpoint configuration stays stable, but runtime generations may roll over; cancellation is pinned to public operation ID **and its original core generation**, never a bare caller request ID. This document **withdraws** `GwzPyTransportConcurrencyDesign-1.md` as implementation authority and incorporates its compatible-capacity, bounded-work and generation rules as restated here. For a shared Python endpoint, it replaces `gwz-core/dev-docs/GwzRemoteTransportRetryPlan.md` §3 item 7, §6 and S1.4's non-idle refusal **and** its no-non-idle-lease installation condition with §4 here. It replaces the different-physical-limit overlap exit row in `GwzRemoteTransportPlan.md` Phase 2 with the exact case in §4. It narrows `GwzV110Plan.md` S6.3's Python placement claim as in §3. The reviewed replacements are authoritative for the Python session once core requirements and design are updated before behavior changes. Existing Git command semantics, `gwz-transport` envelopes, and the GWZ request/response methods stay the same; §7 appends two terminal error enum values to the GWZ Taut schema.

## 2. Identity is visible before effects

`Client.start_fetch(...)`, `start_push(...)` and the other mapped `start_<network-method>(...)` methods are **synchronous factories** returning an `OperationHandle` immediately on a native Client. Construction validates Python arguments, including a nonempty caller `RequestMeta.request_id` of at most **128 UTF-8 bytes** with no Unicode control characters, matching core `identifier` exactly (generated IDs obey the same grammar), allocates a session nonce plus next contiguous 64-bit serial as `operation_id`, stores the caller's request ID (generated if omitted), and creates a small session-owned ledger record. An over-limit, empty or control-containing ID raises `GwzBridgeError(code="InvalidRequest")` synchronously with no issued record, endpoint construction or credential work. A custom bridge without native session hooks refuses `UnsupportedOperation` before issuing a handle. Every allocated serial is an *issued* ID, including one whose admission later refuses. An issued ID whose record has expired returns `OperationExpired`; a serial above the high-water mark, malformed ID or foreign nonce returns `InvalidRequest`. The high-water mark is fixed-size; no lifetime tombstone table is kept. An unpredictable 128-bit nonce separates Clients. A handle keeps a reference to its own ledger, so it remains usable after Client close or drop until its stated expiry. It cannot access another Client's records.

`await handle.accepted()` is the **one-shot** admission step. It either returns the same handle after all admission prerequisites in §5, or terminalizes that handle with a typed pre-effect refusal. `result()` and `events()` require `accepted()` to have been called; on an unstarted handle they raise `InvalidRequest` rather than silently beginning network work. After a pre-effect refusal, `result()` raises that same retained `GwzBridgeError` and `events()` ends with no Git events. `cancel()` on an unstarted handle terminalizes it with `Cancelled` and effect `none`; `release()` can discard an unstarted or terminal record. Repeating `accepted()` on an accepted handle returns the same handle; repeating it after a refusal raises the retained refusal, so a new handle is required to retry. Python cancellation while awaiting `accepted()` leaves the already-returned handle reachable; it cancels and joins only that operation, then raises `GwzOperationCancelled` (a `CancelledError` subclass) carrying that handle and its terminal evidence. It cannot create an accepted operation whose ID the caller was never given.

The existing unary and stream helpers keep their operation arguments. A stream helper returns an `OperationStream` implementing `AsyncIterator`, with public `operation_id`, `request_id`, `result()` and `aclose() -> OperationOutcome`; its identity is available synchronously before first iteration. Internally unary and stream forms create a handle before first await or iteration and use the same admission path. If the caller **cancels the Python task** running a unary or stream helper after admission, cleanup completes before `GwzOperationCancelled` is raised. That exception has stable `.operation_id`, `.request_id`, `.response: OperationResult | None` and `.effect` attributes. For admitted cancellation, `.response` is the detached terminal result and `.effect` is conservatively `"possible"`; the internal ledger record is then released. For pre-admission cancellation, `.response is None` and `.effect == "none"`. Handle-admission cancellation carries the same attributes **plus `.handle`**, which the caller already received. The same exception object is delivered after repeated task-cancellation requests; a cancellation never strands a charged record. The exception is not swallowed by `async with` exit. **Early iterator abandonment** (break, explicit `aclose()` or drop) follows the separately retained-stream rule in §6, rather than silently releasing the last result. For an operation still live when close is called, the close report additionally lists its attributed outcome (§6), including when its Python task is detached.

The caller's request ID remains the ID passed to core registration and the correlation key in events/results. It may match a request ID in another Client. A request ID already used in the **current core generation** of the same Client is refused before acceptance, even after its earlier operation completed; the core's lifetime-used set is authoritative. A pre-registration capacity/session/placement refusal does **not** consume that request ID, so a new handle may retry it after the conflict clears. A successful registration consumes it even if worker launch then fails. A later runtime generation may accept it again, but public operation IDs remain distinct. Every cancellation handle and native cancellation lookup binds the issued public operation ID to its original core generation, so an old handle cannot cancel a new-generation request with the same caller ID. No `op_` concatenation is used as a public identity.

## 3. Placement and endpoint ownership

The Python 1.1 session has a local endpoint only. Its capabilities advertise local placement; if a typed internal request asks for explicit CLI placement, it receives `UnsupportedOperation` **before** runtime construction, credential access or mutation. The current high-level Python `TransportOptions` has no placement keyword. A future CLI placement handshake requires a separate design. SSH agent, known-host, explicit key and `gh` HTTPS secrets remain endpoint-local and are absent from Python errors/events.

## 4. Compatible physical capacity

`Client(..., max_connections_per_host=32)` establishes the default shared physical per-host policy for that Client; each network method's omitted `max_connections_per_host=` **inherits** it. An explicit per-operation override is still allowed and may conflict with live work under the rule below. Each request resolves the four physical `pool::Capacity` fields using the accepted retry rules: both per-host fields from the inherited/overridden value, `total=max(256, jobs)`, and pool `max_requests=max(1024, jobs)`. Python's per-operation argument is `concurrency=` (default 100), corresponding to `jobs`; retry policy and member selection remain per-operation. Pool `max_requests` counts checkout requests, **not** top-level operations, workers, events or results.

A single leader serializes **every** initial or later capacity installation. Equal-target waiters have a cancellable five-second bound without holding the state mutex or host message pump. Successful installation atomically publishes the paired SSH/HTTPS pool configuration, shared reservation authority and installed capacity. Failure wakes waiters; if partial physical rollback cannot be proved, that endpoint generation fails closed and drains. If the installed four-field capacity is already equal, admission never reinstalls, resizes, resets idle timers or evicts a peer, including under a held lease. A **different** physical capacity can be installed only with zero live operations, zero non-idle leases and completed physical cleanup. A differing request while any remains gets pre-effect `TransportCapacityConflict`, even when a live operation is momentarily between leases. It can retry with a new handle after the conflicting operations and cleanup retire.

The corrected Phase 2 exit case is: operations with different **per-operation fan-out** can overlap only if their resolved four physical fields are identical, and combined leases obey those fields. Lower fan-out does not evict another operation's connection. Operations requiring different physical capacities do not overlap. A held-lease equal-capacity request joins; a held-lease or between-leases different-capacity request refuses before effects. The candidate CLI's single-operation capacity behavior is unchanged.

## 5. Admission, workers and generations

One session has at most **8** reserved/admitting/running/finishing top-level operations, **8** top-level native workers, **128** member workers and **256** queued member work items, independent of caller `concurrency=` and pool `max_requests`. An explicit `concurrency` above 128 remains represented in the request and can change physical capacity under §4, but it does not raise the session's worker ceiling. Queue producers wait without a second unbounded queue or a host-pump lock. Thread launch is fallible and worker unwind has a completion guard. A top-level slot or result-budget refusal is `TransportSessionFull` before acceptance and effects.

`Accepted` means: the ledger owns its already-public operation ID; the full per-operation result allowance **including one primary event-reader cursor** in §6 is reserved; placement and physical capacity passed; one bounded worker slot was reserved; core registered the caller request ID; and a fallible native worker spawn succeeded. A stream helper claims its primary cursor before this state commits. The worker waits at a gate until this state is committed, so no Git work precedes `Accepted`. A failed spawn releases reservations and terminalizes the handle with a typed pre-effect error; a successful core registration still consumes a generation ID. Worker panic after `Accepted` publishes exactly one attributed terminal result **after** `TransportRequest.finish()` and wakes result, event, cancel and close waiters. `call()`, `submit()` and high-level stream first iteration use the same admission checks; a `submit()` `Accepted` response means this exact state, not Git success. Pre-effect capacity/session failures surface before that response in all forms.

The core mux retains at most **256 lifetime registered request IDs per generation**. Before a 257th registration, a quiescent session waits for operations, delivery tickets, endpoint work and physical cleanup to retire; it shuts the old runtime and creates a fresh runtime and Port from the **captured first-construction endpoint configuration**, not a fresh environment read. Healthy idle connections are closed. Public operation IDs and retained ledger records do not reset. Old frames cannot attach to the new Port. A finite cleanup failure returns `TransportGenerationBusy` and leaves the old generation closing; close racing rollover wins. Failed pre-registration attempts consume no core ID; successful registration consumes one even if worker spawn later fails.

## 6. Outcome ledger, close and resource bounds

The native session, not process-global `operations::STORE`, owns all session event, result, merge-response and cancellation records. Every session lookup first verifies nonce and issued serial, then reads **that session's** record. Module-level compatibility calls keep an isolated legacy store. Two Clients using the same explicit caller request ID cannot read or overwrite one another's records. Each accepted operation publishes one terminal result only after transport finish; a terminal event precedes iterator end. `cancel()` joins cleanup and publication, returns the same `TransportCleanup` on repeat while retained, and never cancels a peer. If normal completion won the race, `result()` returns it; otherwise it raises `GwzOperationError` with the retained failed `OperationResult` and conservative effect `possible` for an admitted operation. The error contains no credentials. An unaccepted handle's cancellation has effect `none`. `OperationStream.aclose()` explicitly cancels and joins its operation and returns a small `OperationOutcome` containing both IDs, terminal status/code and effect; the retained full result is still available by ID. Dropping a stream object requests cancellation through its existing native token without spawning an unbounded cleanup worker; the session's normal finish path and close still join it. A `break` from iteration does not implicitly discard or release the operation record.

On a native Client, `Client.close()` atomically stops new admission, cancels live operations, joins their finish paths and shuts the host once. The host and pools are gone after close; **the ledger remains**. A handle and `Client.operation_result(id)`, `operation_events(id)`, `cancel_operation(id)`, `release_operation(id)` and `recent_operations()` may read or release an already-issued record after close, without any endpoint or credential work. `recent_operations()` returns up to 64 caller-owned compact descriptors (public/caller IDs, state, terminal code and conservative effect), including early-abandoned streams; it never looks into another Client. New network and local Git commands refuse `InvalidRequest`; repeat close returns the same report. Event iterators created before or after close read only the retained ledger. An iterator waiting at close is woken by its terminal event; a later read can drain it. A reader that reaches expiry before draining gets typed `OperationExpired`. The native `Client.close()` returns `TransportCleanup` with the existing physical facts plus bounded `operations` summaries for every operation live when close began (at most 8): public and caller IDs, terminal status/code, and conservative effect. `__aexit__` retains this report as `Client.close_report` even though it discards the method return. The public return type remains `TransportCleanup | None`: a custom bridge without `close` returns `None` and sets `close_report=None`, preserving the accepted custom-bridge contract without invented physical facts. A custom bridge with `close` returns and retains exactly its bridge-provided report; native-only ledger APIs refuse `UnsupportedOperation` if the bridge has no corresponding session hook. The report contains no payload or secrets. Repeatedly cancelling a Python close waiter does not cancel native close; the waiter joins cleanup before propagating `CancelledError`, and a later close reads the same report. A handle keeps the ledger alive after Client drop; no host is reconstructed by reading it.

The native session admits at most **64** issued-but-unreleased records (including unstarted handles and early-abandoned streams) and **64 MiB** of charged event/result/reader-metadata data. Each retained caller request ID is at most 128 UTF-8 bytes. An issued unstarted record reserves **4 KiB** inside the 64 MiB ledger for its identity, one required discovery descriptor and any small failure state; 64 such records reserve at most 256 KiB. On admission, that 4 KiB is upgraded atomically to the operation's **8 MiB total allowance**, not added to it. The 8 MiB includes a fixed **4 KiB required-recovery metadata reserve** for identity, one `recent_operations()` descriptor and a possible close summary, as well as its event/result/failure and primary-reader budgets. Thus eight full admissions consume exactly 64 MiB including all required recovery metadata. A required descriptor reads its pre-reserved value without a new allocation charged to the ledger; optional extra retained copies may refuse before creation. At close, a summary charge transfers from its operation reservation into the retained Client close report and stays counted against the 64 MiB ledger until Client drop, even if its operation record is later released or expires. Completion exchanges the remaining per-operation reservation for actual charged bytes while preserving required metadata charges until their respective lifetimes end. Creating a 65th unstarted handle refuses `TransportSessionFull` synchronously before effects; the error directs the caller to `recent_operations()` and release/expiry. An unstarted handle charges that fixed 4 KiB record reservation; it reserves no 8 MiB operation allowance. Before `Accepted`, an operation reserves its full **8 MiB** allowance from the 64 MiB ledger, covering required events, result, a small failure slot, **one primary event-reader cursor and the 4 KiB required-recovery metadata reserve**. Its events use at most **2 MiB** of that allowance. A stream helper claims that reserved cursor before the worker gate opens; a handle's first `events()` iterator claims it later without another aggregate charge. Completion exchanges the reservation for actual charged bytes **plus required recovery metadata and the retained primary-cursor allowance**, releasing the rest. Readers share immutable retained event/result buffers rather than copying payloads; at most **8 readers per operation** may exist. An additional optional reader charges its cursor to free aggregate capacity and may refuse `TransportSessionFull` without changing the operation outcome; required primary-stream access never does. A stream reader failure after acceptance for a reason other than optional-reader exhaustion cancels and joins the operation, then raises `GwzOperationError` with its attributed terminal result and `effect="possible"`; it cannot return a bare capacity error after effects. Aggregate pressure refuses operations before acceptance; unrelated retained data cannot turn a within-limit success into a post-effect failure. Only that operation's own overflow yields a retained `TransportRecordLimit` terminal with possible effect; the unary error carries its full detached result before auto-release. Progress may be coalesced only where the published event schema permits; required start/error/terminal events are not silently dropped. No success is reported after record overflow.

Completed, refused and unstarted records expire **15 minutes** after terminalization or handle creation, respectively, or on explicit release. A bounded process-wide expiry timer holds only weak ledger references and evicts charged payloads on time even if nobody calls the Client again; it never reads results across Clients. A live iterator has at most the same 15-minute deadline and cannot pin payload indefinitely. `release()` discards a completed, refused or unstarted record; releasing a live accepted operation refuses `OpenOperation` until cancellation or completion has joined. A repeat release reports `OperationExpired`; foreign or never-issued IDs return `InvalidRequest`. Drop of an unstarted handle releases its slot. Drop of a started handle or stream does **not** release an accepted record: the Client ledger retains it through terminal publication and the advertised deadline even when no handle or reader remains. An ID string does not extend that deadline. A completed result is discoverable through `recent_operations()` and inspectable by ID through its deadline, including after close. The maximum 64 retained records makes abandonment finite; if they fill the ledger, the caller lists and explicitly releases completed records or waits for expiry before new work. The close report's compact summaries are bounded by eight entries and retained with the Client; they do not include full operation results.

## 7. Typed terminal representation

Append `cancelled=73` and `transport_record_limit=74` to `GwzErrorCode` in `gwz-core/protocol/gwz.taut.py`, regenerating the Rust and Python projections from Taut. Do not encode these outcomes as display strings or unrelated generic codes. `OperationResult.errors` carries one of those typed codes, both IDs and available nonsecret transport facts; the Python `GwzOperationError` exposes that `OperationResult` as `.response`, plus a Python-only `.effect` of `"possible"` for admitted cancellation or self-overflow. `GwzOperationCancelled.response` has the stable optional type in §2. The effect field is not a new Taut field; it is conservatively derived from the terminal code, never inferred from human text. The Taut request/response **method set** and `gwz-transport` stream envelope remain unchanged. The new enum members are append-only within the existing GWZ outer protocol compatibility rule; the operator's transport-envelope compatibility waiver does not waive that outer rule. No separate-client compatibility translation is needed for the current Python-session path.

Pre-acceptance `TransportCapacityConflict`, `TransportSessionFull`, `TransportGenerationBusy`, duplicate request-ID and unsupported-placement refusals use typed bridge errors with effect `none`. A cancellation or overflow after acceptance is a retained `OperationResult` failure, never a second admission refusal. A caller must inspect a possible-effect push's remote ref against its intended target before replay; neither cleanup completion nor a virtual-stream close proves Git push success or failure.
