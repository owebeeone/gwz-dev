## 1. Findings

### [P3-1] The byte-stream adapter frees a discarded body without wiping it

- **Location:** `gwz-core/crates/session-channel/src/byte_stream.rs:186–190` (`read_frame`: `let mut body = vec![0; size - 1]; if fill(stream, &mut body)? != body.len() { return Err(truncated()); }`) and `:147–151` (`recv` discards a frame read while the session was ending: `(Ok(_), Some(closed)) => Err(closed)`).
- **Violated invariant:** server design §4 "Secrets": the host "keeps the snapshot only for its session, then zeroizes it, since a long-lived server would otherwise accumulate every client's secrets"; contract §5.6 as amended (the snapshot crosses once, in `SessionOpen`, and is zeroized). The program's own bar is CS1.9's accepted object, which fixed exactly this class in core ("a Windows decoding fix that stops freeing unwiped partial values").
- **Reproduction:** a `SessionOpen` (tag 4) whose stream ends or fails after the tag byte: `read_frame` allocates the body at the prefixed size, `fill` returns short or `Err`, and `body` is dropped as `Vec<u8>` with no wipe. Three exits do this: a short `fill` (client killed mid-handshake), a stream error other than `Interrupted`, and a panic inside `stream.read` (unwinding drops `body`). A fourth is `:149`: the host's handshake bound (server §3, 30 s) calls `close()` while the reading thread is inside `read_frame`; the frame completes and is discarded whole. The existing tests `end_of_stream_between_frames_is_the_peers_closure_and_inside_one_a_truncation` and `a_stream_that_panics_mid_frame…` exercise the paths; nothing wipes.
- **Impact:** fragments of a client's environment (tokens, agent-socket paths) remain in the serving process's freed heap after a failed handshake. Bounded: same process, no other principal, no logging; a long-lived socket host accumulates them across failed clients. The known residual in the checkpoint names only the partly read case; the discarded-whole case at `:149` is the same root cause.
- **Required correction:** keep the body behind a small guard, `struct Body(Vec<u8>)` with `Drop { self.0.fill(0); std::hint::black_box(&self.0); }` and an `into_inner` via `mem::take` on the success path, so every exit of `read_frame`, unwinding included, wipes; wipe the frame discarded at `:149` the same way. Safe code only, so `#![forbid(unsafe_code)]` stands; `black_box` is std's best-effort barrier, weaker than core's `write_volatile` plus fence, and the module doc should say so. The successful body is handed to core as today; core's decoder owns its wipe (CS1.10, CS8.x).
- **Closure test:** a unit test that the guard's drop leaves a live buffer all zero with its capacity unchanged (fill the spare capacity first, as CS1.9's `a_name_or_value_overwrites_the_allocation_that_held_it` does), and a reading test that a truncated frame, a failing stream and a panicking stream each reach `read_frame`'s exit through the guard (structurally, by making the guard the only owner of the buffer).

### [P3-2] `ClientChannel::close()` ends the session but keeps its snapshot alive until the handle drops

- **Location:** `gwz-core/src/session_host/context.rs:330–332` (`close(&self)` delegates to `self.end.close()` only) with the fields at `:295–304`; `gwz-core/docs/RustApi.md:207` ("Dropping the `ClientChannel` ends the session and drops its context") and `:216` ("`close()` ends the session as dropping the `ClientChannel` does").
- **Violated invariant:** contract §5.6: the snapshot "is dropped when the session ends", and as amended "zeroized when the session ends"; RustApi's own equivalence between `close()` and drop.
- **Reproduction:** `let channel = open(options)?; channel.close();` then `channel.recv()` is `Err(Closed::Local)` and the host end sees `Closed::Peer` (the session has ended at both ends, per `closing_the_client_channel_ends_the_session_at_both_ends`), yet `Arc::downgrade(channel.session()).upgrade()` still succeeds: the `SessionContext` and its `EnvironmentSnapshot` live until the `ClientChannel` is dropped. At HEAD there was no `close()`, so the equivalence is new text over new behaviour.
- **Impact:** bounded: the snapshot outlives the session's end for as long as a driver keeps a closed handle (a gwz-py bridge object between `close()` and its collection; a Rust driver's scope). The zeroization itself is unchanged at drop (`a_session_drops_its_snapshot_when_it_ends` passes). CS2.2 removes the condition by construction when `open` hands the session to `serve`.
- **Required correction:** either hold `session` (and `host_end`) in a `Mutex<Option<…>>` and `take()` them in `close()`, so the context drops and the snapshot is wiped at the close; or change RustApi's two sentences to say that the context and its snapshot drop with the handle, not at `close()`. The first is about ten lines and keeps the documented equivalence.
- **Closure test:** `closing_the_client_channel_drops_its_snapshot`: the weak reference taken from `channel.session()` no longer upgrades after `channel.close()`, with the handle still alive.

### [P3-3] The process-globals checker is blind to a static that a `macro_rules!` declares

- **Location:** `gwz-core/scripts/checks/check_process_globals.py:497–507` (`_static`: when the token after `static`, or after `mut`/`ref`, is not an identifier, the declaration is listed as `<unparsed static>` only inside a `thread_local!` or `lazy_static!` body, and otherwise dropped silently).
- **Violated invariant:** the map's §1 "No globals" as the checker enforces it, with the operator's ruling that no counter, flag or thread-local is ever `permanent`; the file's docstring (`:31–34`) and the allowlist's rule text claim that an unreadable static "fails closed"; the standing rule that lint checks are syntax-aware and inspect every branch.
- **Reproduction:** the scratch crate `scratchpad/review1-safety/probe_globals/`: `macro_rules! counter { ($name:ident) => { static $name: AtomicU64 = AtomicU64::new(0); }; } counter!(D_MACRO);` compiles to an ordinary process-wide counter (the rustc probe mutates it), and `check_process_globals.py --repo … --allowlist …` lists nine other candidates but never `D_MACRO`. The same probe shows the checker is otherwise fail-closed where the brief asked: a type alias (`static A: Counter`) is listed as "state behind Counter"; `OnceLock<Holder>`, `LazyLock<Mutex<u8>>`, `[AtomicU64; 2]`, the path form `std::sync::atomic::AtomicU64`, `static mut` and a `#[cfg(windows)]` static are all listed; a static under `#[cfg(any(test, feature = "test-support"))]` is scanned as production; `static K: &str` and `static L: &Plain` are the only skips, and rustc itself refuses a `&`-static to interior-mutable data (E0492), so the `&` skip cannot hide state.
- **Impact:** a counter or flag can enter production code in gwz-core, gwz-transport or gwz-py without an allowlist entry, and the "list only shrinks" ratchet does not see it. No such macro exists in the tree today; the consequence is a gate that can be passed by a pattern its rule text says it refuses.
- **Required correction:** in `_static`, list `<unparsed static>` whenever the token after `static` (past `mut`/`ref`) is not an identifier, whatever the enclosing macro. A `static` identifier token occurs in Rust only in declarations, `extern` blocks and nightly `static ||` closures (the lexer already turns `'static` into a lifetime token), so the rule has no false positive in stable code. A second, pre-existing gap the probe also shows: `include!("../extra/included.rs")` of a file outside the root's directory is not followed and its static is not listed; there is no production `include!` in gwz-core or the crates today (the one in the tree is `transport_host/tests.rs`), so this is a hardening note, not a finding: follow `include!` with a literal path, or fail closed on one.
- **Closure test:** in `test_check_process_globals.py`, a source with the macro above yields one `static <unparsed static>` occurrence for the file; and, if the include rule is taken, a source with `include!("x.rs")` yields either the included file's occurrences or an `<unparsed include>` occurrence.

## 2. Invariant analysis

**Area 1, the channel crates (step 3).**
- *Framing order and allocation.* `read_frame` (`byte_stream.rs:172–191`) reads the 4-byte prefix, checks `Frame::check_size` (zero → `Empty`, over 64 MiB → `TooLarge`) before reading on, then the tag byte through `Carrier::ByteStream.tag` before allocating, then allocates once at the prefixed size. Held: `a_length_prefix_over_64_mib_ends_the_session_before_anything_is_allocated` uses a reader that fails the test if read past the prefix, and `a_tag_outside_the_registry_ends_the_session_before_its_body_is_read` likewise for the body. The cap counts the tag byte and the body, which is what the prefix states (`frame.rs:8–10`, `:45–49`), and `a_length_prefix_of_exactly_64_mib_is_read_whole` pins the boundary.
- *Hostile input.* Every `recv` allocation is bounded by the cap and released before the next read; a peer that stalls mid-body holds one buffer per end. A reader returning more than asked is caught by the `filled < len` loop and reported as truncation. No `unwrap` on peer data; `u32::from_le_bytes … as usize` cannot overflow on any supported target. Held.
- *EOF and errors.* EOF between frames is `Closed::Peer`, inside a frame `Closed::Stream(UnexpectedEof)`, checked at every cut of an 8-byte frame; `Interrupted` is retried; any other error ends the session with its kind. A stream that panics inside a half poisons that half's mutex, and the next call ends the session with `Closed::Stream(Other)` and drops the half (`lock_half`, `:80–91`), so the lost framing is never resumed. Held.
- *Write atomicity.* `send` holds the writer for both `write_all`s and the flush (`:110–130`); the frame is checked before a byte is written; a failure ends the session and drops the writer, so the peer sees EOF mid-frame and fails closed. `concurrent_senders_keep_each_frame_whole` (4 senders × 50 frames of 4 KiB over an OS pipe) holds.
- *In-process queues.* Bounded by per-lane counters over one `VecDeque` that starts empty (`in_process.rs:64–81`); `send` takes the state lock, never waits on a condvar, refuses `Full` with the frame and drops nothing; the control reserve is its own count, so a full call lane never refuses a control frame and a full reserve leaves the call lane alone; one deque keeps cross-lane order. `stop` records the first `Ending` for both ends (`get_or_insert`), clears only the stopping side's inbox, and wakes both condvars. The state lock is never held across a panic (no fallible operation under it), so `into_inner` recovery is sound. Held: the eight-case conformance suite passes on both adapters, and the in-process tests cover each refusal and closure reason.
- *Secrets.* `Frame`'s `Debug` prints tag and length only, and every derived `Debug` (`SendError`, `Result<Frame, Closed>`) goes through it; no `Display` on `Frame`; test assertions on bodies use plain `assert!`. Tags 4–8 are refused in-process (`ByteStreamOnly`), so no `SessionOpen` ever sits in an in-process queue. The only unwiped drops are the adapter's own discards, P3-1.

**Area 2, the gate's capability design (step 4).**
- *No closure, callback or clone can cross or revoke.* A crossing takes `&mut OperationGate` (`gate.rs:302–356`) and hands its closure a `GateScope` with `session()` alone; the three `compile_fail` doctests pin E0499, E0599 (both `scope.effect` and `scope.revoke`) and E0373; `CallControls`, `OperationGate`, `HandlerContext` and `GateScope` are proven not `Clone` by the `NotClone` ambiguity trick; `GateView` and `CancellationToken` carry only `state()`, `token()` and `is_cancelled`. Held.
- *The thread record.* `Crosser::enter` runs after the lock and the state checks, and clears on drop, unwinding included, before `_held` releases (declaration order `_held`, `session`, `_crosser`). `ThreadId`s are never reused. So the only false positive would be a same-thread, same-gate re-entry, which is precisely the deadlock the record exists to turn into a panic; `a_revoke_inside_a_crossing_panics` shows the panic comes before `cancel`, so the gate is still `Live` afterwards and a later revoke returns. `a_crossing_records_its_thread_only_while_its_closure_runs` shows no stale record after a panicking closure. Held.
- *False negatives.* Beyond the plan's three (another operation's gate in a closure; a worker's gate moved into a callback; a closure blocking on another thread's crossing), one more interleaving is worth naming for later steps: a callback that revokes a *different* gate from the host's reading thread now proceeds and waits for that gate's crossing, where CS1.4's thread-local would have panicked. If the reading thread runs callbacks under the table lock (§5.3) and the other closure wants that lock, that is a deadlock the object cannot detect. No such path exists: nothing in gwz-core calls the gate, and the residual is the map's stated one. Carried in §3.
- *Races and locks.* `revoke` cancels, then takes `crossing`, then stores `revoked` under it (`:170–175`); `cross` checks `revoked` and upgrades the session under the same lock; so a crossing in flight blocks `revoke` and none starts after it, as `revocation_waits_for_a_crossing_in_flight_and_nothing_lands_after_it` shows (100 ms negative wait). Lock order is `crosser` briefly, or `crossing` then `crosser` briefly; `forbid_reentry` holds nothing else; the token's `callbacks` lock is never held while a callback runs or while `crossing` is taken. No cycle. `state()` reads the atomic and the weak count without a lock, and a closure holding the upgraded `Arc` can never observe `Revoked` from inside. `CancelRegistration::drop` upgrades, removes under the lock and drops the callback outside it; during `cancel` the list is already taken, so a drop from a callback finds nothing. Held.
- *Panics compared with CS1.4.* Same-gate re-entry: panic before the lock in both designs, now also refused at compile time. A panic in a closure poisons `crossing`, which guards `()`, and `lock` recovers it. A revoke from a destructor during unwinding still aborts, as CS1.4's did; the carried obligation (guards outside closures, CS2.4/CS2.5/CS2.9) is unchanged. No path is worse; the difference is detection scope, disclosed in the plan's §7 and §11.

**Area 3, the supervisor move (B3).** `Supervisor::shutdown(bound)` (`supervisor.rs:164–176`) holds its own `report` mutex across `dispose`, whose `wait_timeout_while` releases only the state lock, so a concurrent caller waits for the first and gets the same count; the deadline is absolute; `dispose`, `run`, `release` and `discard` are the CS1.9 bodies moved verbatim, with `SUPERVISOR_POLL` renamed `POLL_INTERVAL`. `HostShared` keeps its own report cache and `shut_down` flag; its former `Drop` is now `Supervisor::drop`, which runs first in field order and releases the thread without waiting. The thread holds `Arc<Shared>` and exits only when released and idle, as before; a job whose `poll` blocks keeps it alive, which CS1.9 accepted. The nine supervisor tests keep CS1.9's 300 ms bound and 700 ms slack and pass. *`test-support`:* it is enabled only by gwz-core's `[dev-dependencies]` line (`Cargo.toml:114`); the workspace uses resolver 2, so a non-test build never unifies it, and a dependant never builds gwz-core's dev-dependencies at all; the Bazel target lists no `crate_features`; the checker scans the `test_support` module as production and finds no static. Held.

**Area 4, the `ClientChannel` wiring (B5).** `open` validates limits, refuses a shut-down host, then allocates the context and `pair(channel_limits)` (`context.rs:243–269`): no effect before refusal. No driver, and nothing in gwz-core outside `session_host`, calls `open`, `send` or `recv`, so the parked host end's forever-`recv` is reachable only by tests, which never wait on it. `host_end` lives in `ClientChannel` only; `SessionContext` holds host, snapshot, limits and the flag (`:173–179`), so no `GateScope` can reach a channel end (O6). Drop order `end`, `host_end`, `session` closes both ends then wipes the snapshot; `a_session_drops_its_snapshot_when_it_ends` passes unchanged. `close()` is P3-2.

**Area 5, `gwz-ids` (step 2).** `next` is a `fetch_update` with `checked_add`, so its panic needs 2^64 draws: unreachable. `new_id_source` (`operation_context.rs`) draws the prefix from `getrandom::u64()` (present in the locked 0.3.4) and falls back to `RandomState::new().hash_one(pid)`, whose per-thread keys are already seeded by any earlier `HashMap` on that thread. *Sites:* `verified_write.rs` and `rewrite.rs` keep their `create_file … AlreadyExists → continue` loops; `durable_write.rs`'s `stage_durably_with` creates once; all three go through `FileSystem::create_file`, whose native implementation is `OpenOptions … create_new(true)` (`filesystem/native/filesystem_impl.rs:250–262`) and whose fake is a tree `create` that refuses an existing name; family-store's `publish.rs:108–127` now uses `create_new(true)` where HEAD used `File::create`, which truncated. So a collision, which now needs two equal 64-bit random draws where HEAD needed pid reuse against a stale temp, costs a refused create or a retry, never a clobber; `a_taken_temporary_name_is_never_clobbered_and_the_next_one_is_used` and `a_taken_temporary_name_is_skipped_and_left_as_it_was` pin it. The 64-attempt cap returns the last `AlreadyExists` before any write, so the target is untouched. Write, flush, `sync_all`, rename and directory flush are the same statements in the same order in both `stage_durably_with`/`publish_staged` and `write_then_rename`; the checked-artifact seam is re-pinned with `write_atomic_verified: 1` and the gate names no in-scope path. Family-store's litter test (`.local-family.yml.tmp.4242.0`) shows nothing parses temp names, so the new `{prefix}-{seq}` shape breaks no cleanup. Held.
