### [P3-28] "Release to make room" can delete the spool of a log whose reader is about to open, unlike the operation-table rule it cites, which evicts only delivered records
- **Location:** §5.4 line 265 ("the oldest log that its producer has sealed and that has no reader stream open is released first, as the operation table evicts delivered records") against line 255 ("A record is delivered once every view its method declares has been delivered"); line 268; §15.7 line 601.
- **Violated invariant:** an irreversible step (spool deletion, line 262) needs a precondition that the holder of the handle has had its chance; the operation table's precondition is delivery, and the log rule substitutes "never read", which is the state of every freshly completed diff.
- **Sequence:** one session; a client runs many byte-format diffs concurrently (`asyncio.gather` of 100 `Client.diff` calls, each followed by `diff_output`). Diffs are direct calls on 8 direct workers; each mints its log at start (line 262, "open from its creation"). The first eight complete and seal; their tasks have not yet resumed because the event loop is busy (a CPU-bound section, or each task does work between `diff` and `diff_output`). Fifty-six more complete and seal. The 65th log's open finds 64 open logs, 56 of them sealed with no reader, and releases the oldest: the first diff's log, whose task then sends its first read and gets `operation_expired`. Nothing told the client at `diff` time; the manifest reply it holds names a log that no longer exists, and the spool is gone. Revision 2 would have refused the 65th open before any effect instead.
- **Impact:** a spurious `operation_expired` on a valid handle under a burst of diffs, indistinguishable from client misuse; bounded (the client can re-run the diff) and reachable only at 64 concurrent unread sealed logs, but the failure lands on an earlier, innocent request rather than on the one that exceeded the bound.
- **Required correction:** make the room-making release eligible only for a sealed reader-less log whose seal is older than the fixed read wait (30 seconds, §1), so that a reader that is merely late keeps its handle; otherwise refuse the open as before. Alternatively, give `diff.output` an explicit release (an end stream with a fresh `stream_id` releases a sealed reader-less log) and have `Client.diff` release in `finally` when it never opened the output, which also closes the missing half of the mint/release pair that P3-25 exposed; that alternative touches the accepted §4.2 line 153 rule and is the operator's call.
- **Regression test:** 8 diffs' logs minted and sealed, then 64 more opened within a second; a first read of the first log within 30 seconds succeeds. The existing line 601 test keeps holding for logs older than the bound.
- **Classification:** bounded correction.

### [P3-29] "Core runs `git credential fill` itself, … never prompting" is not achievable by "`env_clear()` plus the snapshot" alone; the stated remedy, followed literally, prompts through askpass or the terminal, can block a worker, and creates a new plaintext-secret surface the secrecy rule does not cover
- **Location:** §5.8 line 356 ("spawned with `env_clear()` plus the snapshot and never prompting, as libgit2's lookup never does"); §5.6 line 295 and §5.7 line 343 (the same spawn rule); §5.6 line 292 (the secret-bearing rule covers the snapshot only); §15.8 line 606 (no no-prompt assertion).
- **Violated invariant:** the remedy for a `debt` entry must not be worse than the status quo it replaces. libgit2's lookup (git2 `CredentialHelper::execute`) runs the configured helpers with `get` and never prompts. `git credential fill` differs: when the helpers return no password it prompts, first through `GIT_ASKPASS`, then `core.askPass`, then `SSH_ASKPASS`, then the terminal; only `GIT_TERMINAL_PROMPT=0` (terminal) and `credential.interactive=false` (git 2.40 and later, all prompts) suppress it. The snapshot is the process environment at open; IDE terminals (VS Code, JetBrains) set `GIT_ASKPASS` in it.
- **Sequence:** ordinary build after the remedy; a Client opened from a VS Code terminal; an HTTPS fetch to a host with no configured helper; core spawns `git credential fill` with the snapshot; git runs the snapshot's `GIT_ASKPASS` program, which pops the IDE's credential prompt or blocks; the worker blocks in the child's `wait`; `operation.cancel` cancels the token but nothing kills the child, because the contract states no kill-on-cancel for this spawn (the `gh` helper has `kill_on_drop` and a deadline at `https_auth.rs` 300–331; this one has neither in the text); close detaches the worker at 60 seconds; the child keeps the prompt open past process exit. In a headless service without `GIT_TERMINAL_PROMPT=0`, git tries `/dev/tty` and fails, which is the harmless case, but a developer's terminal gets a password prompt from a library call that never prompted before. Separately, the password now arrives on a pipe into core's Rust code and is passed to `Cred::userpass_plaintext`; the §5.6 secrecy rule names only the snapshot, so nothing forbids it in an error message or log.
- **Impact:** a new stuck state and a new user-visible prompt introduced by the remedy; a plaintext credential handled by core outside any stated secrecy rule.
- **Required correction:** §5.8 states the mechanism: spawn with the snapshot plus `GIT_TERMINAL_PROMPT=0` and without `GIT_ASKPASS`/`SSH_ASKPASS` (a disclosed, named deviation from "the snapshot", as the `gh` spawn already makes), or `-c credential.interactive=false` with the git 2.40 caveat; `kill_on_drop` and a bounded wait, with the child killed when the token is cancelled or the gate is revoked; the helper's stdout is secret-bearing under §5.6's rule and only `username`/`password` are parsed (later gits also emit `password_expiry_utc`, `oauth_refresh_token` and `capability[]` lines, which must be tolerated and never logged); `approve`/`reject` are not called, matching libgit2 today. Add the `GIT_ASKPASS` case to §15.8.
- **Regression test:** with `GIT_ASKPASS` in the snapshot naming a program that records its invocation and no helper configured, an HTTPS fetch fails with an auth error, the recorder never runs, the worker returns within the bound, and the error carries no environment value; a helper that sleeps past the bound is killed when the operation is cancelled.
- **Classification:** bounded correction to a stated but unimplemented remedy.

### [P3-30] The bridge drops a result it holds when any call on that operation reports `operation_expired`, so a late cancel after host eviction discards the last copy
- **Location:** §10 line 456 ("An operation's entry also goes when the operation is released, or when a call on it reports `operation_expired`"); §4.2 line 166 (cancel on an evicted record gets `operation_expired`); §5.4 lines 255–257. This clause applies the Verdict-2 blind-convergence rule and Safety P3-26's own remedy, so it is the round-2 remedy that has the hole, not the operator's application of it.
- **Violated invariant:** delivery is not consumption (the Safety P3-8 closure): a result the host counted delivered by sending the reply must stay reachable to the client until it releases it or the bound expires, not be purged by an unrelated signal.
- **Sequence:** a lower-level bridge user's task awaiting `operation_result` is cancelled; the reply arrives and the bridge keeps it (line 455). The session is busy; the host's table fills and evicts the record, which is delivered. A late timeout handler calls `cancel_operation(operation_id)`; the host answers `operation_expired`; the bridge drops the view entry. The user then calls `operation_result`: the view misses, the host answers `operation_expired`. Revision 2 kept the entry until release and would have returned the result. The Client's stream helpers release in `finally`, so they are unaffected; the exposure is the bridge-level API §10 documents for exactly this retry.
- **Impact:** a result the process held a moment earlier becomes `operation_expired` through a cancel that was itself a no-op; narrow but a data-availability regression from revision 2 on the path the view exists to serve.
- **Required correction:** drop an entry on `operation_expired` only when the reporting call was `operation.release` (or when the client consumed the result through the view); a cancel or response call that reports `operation_expired` leaves the retained result in place; the size bound still applies.

## 2. Invariant analysis

Attacks that failed, with the evidence:

- **Registry waits versus the try-lock and the running limit.** A W or push on a recorded workspace waits in its own session's queue (§5.1 line 206), so it holds no running slot; "N and W operations of the same workspace start in queue order" (line 210) lets other workspaces' entries pass a registry-blocked head, so one session's long W does not stall another session's unrelated work. No two sessions can wait on each other: registry waits happen only before start; running operations wait only on member locks, which are single-resource, blocking, poison-recovering and cancellable (line 204); the mutator lock is a try-lock and never waited on. A running push in A holding member lock m and a running fetch in B waiting on m resolves when A's step ends. Starvation of one session's W by another's continuous stream is possible but bounded per request and cancellable; not a stuck state.
- **Detached workers.** A detached worker keeps its `flock` and its registry record until it ends; sharing sessions wait, cancellably; the wait is disclosed (§16 line 644). A detached worker cannot take new member locks (its next gated request fails), so it can only hold what it already had. Dropping a host context while a detached worker runs turns later refusals into correctly attributed "another host context" refusals. Not worse than revision 2.
- **Log release to make room.** A log with any reader stream open is never released (line 265; §15.7 line 601); a released log answers `operation_expired`, distinguishable from another session's `operation_not_found`. The gap is the slow-reader precondition (P3-28).
- **Retained replies.** Bounded by the table size, oldest first; the host's own bound is the same; a dropped view entry can still be served by a retained host record. The only loss path is P3-30.
- **Host-context creation.** One per process under a process-wide lock; an explicit context on `NativeCoreBridge` is an intentional second context, and its consequence (no shared member locks) is the disclosed "another host context" case. Across threads the race is closed. Across `fork` the "exactly once" flag is inherited with a dead supervisor thread and possibly a held creation lock; the text does not touch fork, and today's process-global supervisor has the same exposure, so it is a residual, not a finding.
- **Credential disposition while unimplemented.** The ordinary build still lets libgit2 spawn helpers with the live environment; §5.6 line 291, §5.8 lines 355–356, §16 lines 646 and 659 and the `debt` entry disclose it honestly. The §15.8 line 606 test is correctly an after-acceptance assertion. The remedy's unstated mechanism is P3-29; its ratchet blind spot is P3-31.
- **libgit2's own reads.** The SSH agent socket and home-directory discovery are named as outside the snapshot in ordinary builds and for natively handled remotes in transport builds (§5.8 line 355; GWZRequirements line 18). Honest and bounded.
- **Transport-check move.** The gwz-core-side allowlist and its rule text are correct when the check runs; the check's `--repo`/`--allowlist` path handles a foreign repository (checker 486–496); gwz-py's leg is real and fail-closed in CI. The gwz-transport leg runs in no CI (P2-9).
- **Mixed versions.** The gwz-transport allowlist is keyed to whatever sibling sits beside gwz-core, which is the checkout the candidate build links (`prepare.py` 33), so a stale or advanced sibling fails on gwz-core's side by design; that is the intended coupling once the gate runs.
- **Disclosure.** The snapshot's WTF-8 byte-pair capture removes the lossy-string path; no new frame, event or log field carries it. The one new secret surface is helper output (P3-29).
- **Status quo.** P3-23 to P3-27 each end in a state no worse than revision 2 for their original sequences. Two revision-3 mechanisms are worse than revision 2 in a narrower case each (P3-28's innocent handle, P3-30's late cancel), and one is worse than revision 2 outright (P2-9's absent gate).
